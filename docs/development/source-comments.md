# Исходники без комментариев

В собственных исходниках ZeDone запрещены обычные и документирующие комментарии,
включая Rust `///`/`//!`, JSDoc, HTML/XML и CSS. Обоснования решений и инструкции
размещаются в `docs/`. Строки, регулярные выражения, URL, содержимое heredoc,
shebang и исполняемая директива PowerShell `#Requires` комментариями не считаются.

Единый состав проверки задаёт [comment-policy.json](../../scripts/comment-policy.json).
Проверяются исходники продукта, прототипов, тестов, визуальных примеров и скриптов,
включая новые файлы, ещё не добавленные в Git. Конфигурационные JSON/YAML/TOML,
документация, lockfiles, зависимости и результаты сборки в область не входят.
Android XML, ProGuard и Gradle-скрипты входят как исходные ресурсы и сборочный код.

Сторонний код исключён: Gradle wrappers, патчи зависимостей и upstream
`PluginManager.kt` не входят в собственные корни; стандартные `buildSrc`-классы
Tauri и генерируемые Tauri/Wry Android-классы исключены явно. Их лицензионные
уведомления сохраняются. Собственный `PluginLifecycle.kt` проверяется; его MIT
уведомление находится в `android-patches/LICENSE-MIT`. Исключения для нового
стороннего кода добавляются по происхождению файла, а не по наличию комментариев.

## Команды и сборка

Перед любой сборкой установить закреплённые версии инструментов из
`scripts/environment-versions.json` и выполнить `bun install --frozen-lockfile`
в корне. Для прототипов дополнительно установить их зависимости в `prototypes/`.
Проверка использует Bun, закреплённые Babel/Vue/PostCSS и PowerShell (`pwsh`)
для токенизации `.ps1`. Эти инструменты нужны на машине сборки, а не в приложении.

- `bun run check:comments` — проверить весь собственный исходный код.
- `bun run test:comments` — проверить распознавание комментариев и исключений.
- [Impact-фикстура](../../tests/fixtures/source-comments-impact.yaml) показывает
  изменение сборочного поведения до/после PR. Её семь сценариев выполняются
  той же командой тестов; численные замеры в ней относятся к указанной базе PR.
- Cargo запускает общую проверку из `build.rs` продуктового и прототипного core
  и обеих оболочек. Ошибка останавливает `check`, `build`, `test` и `clippy`.
  Cargo следит за корнями политики, поэтому добавление нового файла или
  комментария блокирует и повторную сборку с кэшем. Пути наблюдения задаются
  относительно manifest, чтобы общий Cargo-кэш не привязывал проверку к другой
  копии проекта или worktree.
- Оба Vite-конфига проверяют исходники до сборки или запуска dev-сервера.
- Оба Android `settings.gradle` проверяют их до конфигурации и компиляции Gradle,
  включая прямой запуск wrapper. Для Android используется хостовый Bun.

Ошибка содержит путь и строку. Удаление комментария восстанавливает сборку;
флага отключения проверки нет. Прямой вызов стороннего компилятора вне штатной
сборки проекта не является поддерживаемой точкой входа этой политики.

## Генерация контрактов и тесты типов

Формы данных по-прежнему определяются Rust. Описания типов и операций заданы
метаданными `schema`/`utoipa::path`; описания полей хранятся по одному разу в
`schema-descriptions.json` рядом с соответствующим core. Общий modifier
`api/schema-descriptions.rs` применяет их к проверяемым путям OpenAPI и отвергает
пропавшие цели и повторные описания. Готовый `ApiDoc` остаётся источником
OpenAPI, TypeScript и валидаторов; ручное редактирование артефактов не требуется.

Генераторы удаляют комментарии из TypeScript, сохраняя описания в OpenAPI.
`--check-types` продолжает сравнивать результат генерации с сохранёнными файлами.
Отрицательные проверки TypeScript находятся в `tests/type-errors` и
`prototypes/type-errors`: `scripts/check-type-errors.mjs` сопоставляет реальные
диагностики компилятора с ожидаемыми строками и кодами. Поэтому служебные
`@ts-expect-error` не нужны. Положительные примеры проверяет обычная сборка типов.

Решение и ограничения: [ADR-0061](../architecture/decisions/0061-source-comment-policy.md).
