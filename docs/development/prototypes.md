# Прототипы P01

P01 проверяет техническую пригодность выбранного стека на синтетических данных.
Текущий каркас содержит Rust workspace, синтетический echo-контракт и генератор
OpenAPI через utoipa. HTTP-сервера, интерфейса, APK и хранилища пока нет. Объём следующих шагов задаёт
[очередь](../agent/work-queue.md#p01--ограниченные-прототипы-платформ), состояние
приёмки — [план-журнал](../agent/plan-journal.md).

## Подготовка и проверка

Используйте инструменты из [Quick Start](quick-start-windows.md). Версии Rust и Bun
берутся только из [environment-versions.json](../../scripts/environment-versions.json).
Node.js для P01.01–02 не нужен; совместимость генератора TypeScript проверяется в P01.03.

Из корня репозитория, в PowerShell 7 на Windows или Linux:

```powershell
$versions = Get-Content -Raw scripts/environment-versions.json | ConvertFrom-Json
rustup toolchain install $versions.rust --profile minimal --component rustfmt --component clippy
if ($LASTEXITCODE -ne 0) { throw 'Rust installation failed.' }
Push-Location prototypes
try {
    cargo "+$($versions.rust)" fetch --locked
    if ($LASTEXITCODE -ne 0) { throw 'Dependency fetch failed.' }
    bun run check
    if ($LASTEXITCODE -ne 0) { throw 'Prototype check failed.' }
} finally {
    Pop-Location
}
```

Установка toolchain нужна только при его отсутствии. Проверка сама инструменты
не устанавливает. `cargo fetch --locked` загружает зависимости по lock-файлу;
повтор нужен после его изменения или при отсутствии кеша. Затем достаточно
`bun run check` из `prototypes/`.
Команда проверяет точную версию Bun, запускает закреплённый Rust, rustfmt, Clippy
с запретом предупреждений, тесты и release-сборку. Ненулевой код любой команды
останавливает весь прогон. `Cargo.lock` отслеживается; проверки используют `--locked --offline`.
В конце генератор запускается заново, его вывод побайтно сравнивается с `openapi.json`;
отсутствующий или устаревший файл даёт ненулевой код без перезаписи.

Rust-зависимости закреплены в `core/Cargo.toml` и общем `Cargo.lock`.
JavaScript-зависимостей пока нет, поэтому `bun install` и `bun.lock` не нужны.
Повторение в новой копии исходников без `target/` должно проходить теми же командами.
Lock-файл интерфейса и его статическая проверка появятся в P01.03.

Workflow [Prototype foundation](../../.github/workflows/prototype-foundation.yml)
вызывает ту же команду на Windows и Linux. Наличие workflow не означает успешный
запуск Actions и не проверяет APK или Android WebView.

## Rust-контракт и OpenAPI

`core/src/lib.rs` — источник моделей `EchoRequest`/`EchoResponse` и описания
`POST /prototype/echo`. Операция возвращает поле `text` без изменений и хранения;
допустимы пустая строка, русский текст и Unicode. Отсутствующее поле, `null`
и значение другого типа отклоняются при десериализации. HTTP-обработка ошибок,
маршрут и клиент появятся в P01.03; сейчас сетевого вызова ещё нет.

`utoipa` формирует OpenAPI 3.1.0 из Rust. `core/src/bin/generate-openapi.rs`
выводит только JSON в stdout; Bun запускает закреплённый Cargo и управляет файлом.
Из `prototypes/`:

```sh
bun run generate:openapi
bun run check:openapi
bun run check
```

Первая команда явно обновляет отслеживаемый `openapi.json`; проверяйте diff после
изменения Rust. Вторая сверяет только схему, третья выполняет все проверки.
JSON не редактируется вручную; LF закреплён в `.gitattributes` для одинаковых
байтов на Windows/Linux. Генератор не добавляет время или пути машины.
Ошибка компиляции/генерации останавливает запись. Для отмены изменения правят Rust
и повторяют генерацию; удалённый файл восстанавливается той же командой.

Rust-тесты проверяют JSON-вход и результат echo, недопустимые значения, обязательные
строковые поля и ссылки запроса/ответа в схеме. Это проверки прототипного контракта,
а не прикладных операций ZeDone. Совместимость с TypeScript и Android ещё не проверена.

## Структура и изоляция

| Путь | Назначение |
| --- | --- |
| `prototypes/core/` | Непубликуемый Rust crate; общий код для последующих проверок |
| `prototypes/Cargo.lock` | Единственный lock-файл Rust workspace |
| `prototypes/openapi.json` | Генерируемый HTTP-контракт; сверяется с Rust |
| `prototypes/scripts/check.mjs` | Общая команда проверок для человека, агента и CI |
| `prototypes/target/` | Удаляемые результаты сборки, исключённые из Git |
| `temp/prototypes/<run-id>/` | Будущие синтетические БД, снимки и временные копии |
| `docs/reports/p01-02/` | Локальные доказательства текущего шага; не публикуются |

Текущий код не открывает БД, пользовательские каталоги приложения, сеть или камеру.
Проверка пишет только результаты сборки в `prototypes/target/`; runner задаёт этот путь
явно, независимо от `CARGO_TARGET_DIR` вызывающего процесса. Данные и отчёты не
переносятся автоматически в продукт. Только `generate:openapi` дополнительно
пишет производный `prototypes/openapi.json` после успешной генерации.

До первого хранилища в P01.05 требуется реализовать явную передачу изолированного
каталога запуска. Отсутствие этого параметра должно останавливать прототип без
перехода к штатной БД; запретить путь вне своего каталога, ссылки и повторное
использование чужого запуска. Это требование к будущему коду, сейчас БД не создаётся.
Общий доступ извне и реальные приглашения не включаются до соответствующих проверок
прав. В P01.10 допускаются только синтетические данные и ограниченный тестовый доступ.

Для отмены сборки используется прерывание команды. Из корня можно удалить только
вычисленный Cargo-каталог этого workspace:

```powershell
$versions = Get-Content -Raw scripts/environment-versions.json | ConvertFrom-Json
$prototypeTarget = Join-Path (Get-Location).Path 'prototypes/target'
cargo "+$($versions.rust)" clean --manifest-path prototypes/Cargo.toml --target-dir $prototypeTarget
if ($LASTEXITCODE -ne 0) { throw 'Prototype cleanup failed.' }
```

Исходники, `Cargo.lock`, OpenAPI и локальные отчёты сохраняются. Повторный `bun run check`
восстанавливает результат. Будущие БД и снимки очищаются только внутри собственного
проверенного абсолютного каталога запуска; очистка `temp/` не удаляет доказательства
из `docs/reports/`. Удалять или переустанавливать общие инструменты для этих проверок
не требуется.

## Контрольные сценарии

Каждая строка исполняется после появления соответствующего кода. В P01.01 сценарии
описаны, но ещё не запускались. Для каждого нужны успех, отказ и обратная операция
через общее ядро, где она применима; прямое изменение SQLite агентом недопустимо.

| Сценарий | Что фиксировать | Шаг |
| --- | --- | --- |
| Типизированный вызов | Один результат Rust через HTTP и клиент, регенерация после изменения контракта | P01.02–03 |
| Android | Тот же результат через IPC, русский ввод, клавиатура, «Назад», перезапуск | P01.04 |
| Хранение | Сохранение после перезапуска, Unicode-поиск, снимок и отказ записи | P01.05 |
| Доска | Открытие карточки, перемещение и возврат, выполнение и снятие отметки, отказ без дубликата | P01.06 |
| Markdown | Буквальный HTML, внешняя ссылка по нажатию, изображение без загрузки до нажатия | P01.07 |
| QR | Точные синтетические данные, сканирование, отмена, отказ разрешения и ручной ввод без модели/сети/GMS | P01.08–09 |
| HTTP в APK | Равенство HTTP/IPC, разрешённый и запрещённый запрос, закрытие/повторный запуск | P01.10 |
| Полный прототип | Все действия A62, версии и ограничения по платформам | P01.11 |

Матрица результатов ведётся отдельно для Chrome/Windows, Opera/Windows,
Android 13 AOSP-эмулятора и целевого Galaxy A32. Сборка Rust на Linux подтверждает
только host-проверки. Для интерфейса, HTTP и IPC указываются отдельные результаты
или причина неприменимости; отсутствие физического телефона отмечается как
непроверенный охват, а не как успешный результат эмулятора.

## Методика времени для P01

Основание — [ADR-0020](../architecture/decisions/0020-prototype-latency-targets.md)
и A62. Ниже выбран воспроизводимый начальный протокол эксперимента, а не новые
продуктовые ограничения или измеренная производительность.

Для первого сравнения выбран набор: одно пространство,
три колонки, 30 карточек с заголовками `Карточка 0001`–`Карточка 0030`; первые 24
описания по 5 строк, следующие 5 по 100, последнее — 200 строк. Каждая строка имеет
вид `Заметка NNNN: ёж, ЕЖ, café, 😀.` и соединяется LF без завершающего LF.
Номер — номер строки, дополненный нулями до четырёх знаков. Карточки идут по 10
на колонку в порядке номеров; история, корзина, конфликты и изображения изначально
пусты. Это фиксированный синтетический профиль для сравнения, не максимум нагрузки.
Генератор и проверка точного содержимого появятся вместе с моделью в P01.05.
Более крупные наборы, история и нагрузки Automerge определяются перед P02/P09.

До прогона записать ревизию и хеш данных, фактические байты UTF-8/число строк,
release-режим сборки, инструмент измерения, версии ОС/браузера/WebView, устройство
или эмулятор, открытые экраны и фоновые операции. Изменение профиля образует новую
серию; не объединять её с предыдущими результатами. Чувствительные сведения,
идентификаторы процессов и сырые отсчёты остаются в `docs/reports/`.

| Действие | Начало → конец | Стартовый ориентир |
| --- | --- | --- |
| Открытие карточки | Ввод команды → контент доступен для работы | 300 мс |
| Перемещение | Завершение жеста/ввод команды → подтверждение сохранения ядром и отображение результата | 300 мс |
| Выполнение/снятие отметки | Ввод команды → подтверждение сохранения ядром и отображение результата | 300 мс |
| Поиск | Запуск запроса → показ первых результатов, включая задержку debounce, если она есть | 1 с |
| Запуск | Запуск ZeDone → первый доступный для работы экран | 3 с |

На ПК отдельно измерять запуск браузера; не включать его молча в запуск ZeDone.
Внешний HTTP-вызов агента измерять отдельно до ответа о сохранении; он не заменяет
проверку отображения в UI. Внутренние интервалы Rust и UI служат диагностике,
их нельзя вычитать из полного времени. Не вычитать отметки разных часов устройств.

Для каждого интерактивного сценария выполнить 5 прогревочных и 30 измеряемых
повторов. После перемещения/выполнения возвращать исходное состояние обычной
обратной командой и дожидаться сохранения; обратную команду также измерять отдельно.
Все созданные при этом записи истории сохранять, фиксировать состояние перед
серией. Для повторения серии использовать новую копию исходного синтетического
набора, а не незаметную очистку истории посреди измерения.

Запуск проверять двумя отдельными сериями по 10 раз: после остановки всех процессов
ZeDone и повторное открытие в уже работающем процессе. Отдельно фиксировать первый
запуск после установки. Это не проверка холодного дискового кеша ОС; такую проверку
нельзя заявлять без отдельного протокола. На Android записать способ остановки APK;
запуск из эмулятора не подтверждает время целевого телефона.

Хранить все отсчёты в миллисекундах с монотонными часами одного наблюдателя.
Указать точность метода, минимум, медиану, p95 методом ближайшего ранга
(`ceil(0.95 × n)` в отсортированном ряду) и максимум. Отказы/тайм-ауты записывать
отдельно с количеством попыток, не исключать молча и не подменять нулём.
Сопоставлять с ориентиром всю серию, включая превышения; p95 сам по себе не
закрывает A62. Общий критерий остаётся открытым до полного набора действий и платформ.

Отдельные серии для фонового обмена, копирования и восстановления добавляются,
когда появятся эти операции. Учёт всей памяти, процессов и пиков следует
[ADR-0019](../architecture/decisions/0019-memory-budgets.md); счётчики и нагрузки
уточняются до соответствующих измерений. Время сборки и расход одного пустого
Rust crate не подтверждают цели задержек или бюджета памяти ZeDone.

Источники команд: [utoipa](https://docs.rs/utoipa/6.0.0/utoipa/),
[Cargo fetch](https://doc.rust-lang.org/cargo/commands/cargo-fetch.html),
[Cargo workspace](https://doc.rust-lang.org/cargo/reference/workspaces.html),
[Bun subprocess](https://bun.sh/docs/runtime/child-process).
