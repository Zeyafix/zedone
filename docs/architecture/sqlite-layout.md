# ZeDone: организация SQLite, снимки и миграции

Дата документальной проверки: 2026-10-25.

Продуктовые уточнения миграций и аварийного восстановления: 2026-10-26. Их авторитетный источник — раздел 1.1 [продуктовой спецификации](product-spec.md); техническая реализация ещё не проверена.

Статус: для первой версии выбраны одна SQLite-база на устройство и логические снимки и восстановление отдельных пространств через общее Rust-ядро. SQLite и rusqlite с `bundled` также выбраны. Схема данных, формат снимков и механизм миграций ещё не утверждены. Прототипы и измерения в рамках этой оценки не выполнялись. Подтверждённые требования находятся в [продуктовой спецификации](product-spec.md).

## 1. Выбранная основа первой версии

Подтверждено: одна SQLite-база на устройстве с явной принадлежностью пользовательских данных пространствам. Она содержит данные пространств и необходимые локальные служебные записи. Снимки и восстановление отдельных пространств выполняются логически через общее Rust-ядро, по согласованной политике хранения.

Основание выбора: приложению уже нужен полный экспорт пространства, а восстановление должно стать новым действием с сохранением независимых правок другого устройства. Поэтому механизм получения согласованного состояния пространства нужен при любом количестве файлов базы. Общая база позволяет выполнять связанные изменения пользовательских и служебных записей одной транзакцией; поиск по всем локальным пространствам и применение схемы требуют меньше координации нескольких файлов. Принятый компромисс — повреждение общего файла может затронуть несколько пространств; проверяемое восстановление обязательно.

Общая база также требует аккуратного ограничения каждой операции нужным пространством. Это проверяется в общем Rust-ядре и тестах доступа. Разделение на несколько файлов само по себе не реализует модель прав ZeDone.

## 2. Сравнение вариантов

### Одна база устройства

Все пространства используют общую схему. Связанные изменения данных, необходимых сведений синхронизации и локального состояния операции можно фиксировать одной транзакцией. Глобальный поиск обращается к одной базе, соблюдая выданные права. SQLite предоставляет транзакции для согласованной работы с базой. [SQLite: транзакции](https://www.sqlite.org/lang_transaction.html).

Цена этого варианта — логические снимки и восстановление выбранного пространства. Внутри снимка должны быть только данные выбранного пространства и необходимые для его восстановления сведения. Восстановление сохраняет остальные пространства и актуальные локальные права и настройки. Повреждение общего файла может затронуть несколько пространств, поэтому проверяемое восстановление остаётся обязательным.

### База каждого пространства и служебная база устройства

Данные пространства, его история, корзина, конфликты и необходимые сведения его обмена размещаются в отдельной базе. Локальные настройки, подключения и права устройства размещаются отдельно. Этот вариант хорошо совпадает с границей синхронизации и резервного копирования; Online Backup API может получить физический снимок базы одного пространства. [SQLite: Backup API](https://www.sqlite.org/backup.html).

Потребуется управлять несколькими файлами, соединениями и версиями схемы. Поиск по всем пространствам должен объединять результаты в Rust с соблюдением прав, порядка и пагинации. Число одновременно открытых баз и фоновых операций нужно ограничивать и измерять на Android.

Создание пространства, восстановление, окончательная очистка и изменение его регистрации могут затронуть базу пространства и служебную базу. В WAL-режиме SQLite гарантирует атомарность отдельного файла, но не общего набора файлов; внешние ключи также не пересекают границы схем. Для таких операций понадобится явный порядок шагов и восстановление после прерывания. [SQLite: ATTACH и атомарность](https://www.sqlite.org/lang_attach.html), [SQLite: внешние ключи](https://www.sqlite.org/foreignkeys.html).

В обеих схемах у объекта должен быть один авторитетный экземпляр на устройстве. Отображаемые имена, поисковые индексы и кэши не становятся независимо изменяемыми копиями данных. Каталог нескольких баз, если такой вариант будет выбран, должен явно отделять собственные локальные сведения от производных данных пространств.

## 3. Снимки и восстановление

Online Backup API копирует содержимое целой базы. В варианте общей базы он подходит для технической копии всей базы, а снимок одного пространства требует отдельного извлечения данных. Требование отдельных копий пространств сохраняется при обоих вариантах хранения. [SQLite: Backup API](https://www.sqlite.org/backup.html).

Подтверждено: автоматический снимок включает полное состояние выбранного пространства — текущие данные пространства и его объектов, корзину, всю пользовательскую историю версий, нерешённые конфликты и необходимые сведения восстановления. Формат и конкретный технический состав проектируются отдельно. Это правило одинаково для обеих платформ и всех адаптеров общего API.

Подтверждено: полное восстановление пространства возвращает теги и назначения, которые существовали в выбранном снимке, даже если их удалили после его создания. Это правило не добавляет отдельную операцию восстановления удалённого тега; исключение из обратимости относится к отдельному тегу. После восстановления применяется согласованный порядок паузы обмена и передачи восстановления как нового действия.

Подтверждено: по умолчанию автоматические копии хранятся в локальном каталоге данных приложения. На Windows и Android можно выбрать другую локальную папку, изменить выбор повторно или вернуться к каталогу по умолчанию. Настройка сохраняется локально на устройстве и доступна через общий API в пределах выданных прав. На Android файлы в каталоге приложения удаляются вместе с приложением. [Android: файлы приложения](https://developer.android.com/training/data-storage/app-specific).

При смене папки подтверждён перенос существующих автоматических копий ZeDone: сначала копирование и проверка всех переносимых снимков, затем сохранение нового расположения и удаление исходных копий. Правило включает ежедневные и страховочные снимки, в том числе копии удалённых пространств, и действует при возврате к каталогу по умолчанию. До переключения ошибка сохраняет прежнюю настройку и исходные копии. Ошибка удаления после переключения сохраняет новое расположение и проверенные копии; приложение сообщает об оставшихся дубликатах. Посторонние файлы не изменяются, ротация самим переносом не запускается. Механизм проверки, согласование с созданием снимков и восстановление после сбоя проектируются отдельно.

Подтверждено: при недоступности выбранной папки приложение сообщает об ошибке и повторяет попытки в ту же папку при работающем приложении. Работа с пространствами продолжается; другая папка автоматически не выбирается. Неуспешная попытка не обновляет сведения о последнем успешном снимке и не запускает ротацию. После возврата доступа применяются прежние правила частоты и изменений без восполнения пропущенных дней. Состояние ошибки и сведения о последней успешной копии доступны через интерфейс и общий API в пределах выданных прав на Windows и Android. Периодичность повторных попыток уточняется отдельно.

Подтверждено: миграция базы и восстановление существующего пространства не начинаются, пока в выбранной папке не создан и не проверен новый страховочный снимок текущего состояния. Ошибка записи или проверки, включая недоступность папки, оставляет исходное состояние неизменным этой операцией; прежний страховочный снимок сохраняется и не заменяет новый. Другая папка автоматически не используется. При восстановлении в новую установку после переустановки допускается отдельное исключение для подтверждённо отсутствующего состояния исходного пространства, описанное ниже; миграции оно не касается. Причина отказа доступна через интерфейс и общий API в пределах выданных прав на обеих платформах. Конкретный состав копий для согласованного восстановления общей базы и служебных данных проектируется отдельно.

Подтверждено 2026-10-27: после явного выбора папки ZeDone автоматически находит свои резервные копии и показывает пространства и даты, в том числе в чистой установке без прежней базы и настроек. Просмотр каталога через интерфейс и общий API одинаков на Windows/Android в пределах прав; восстановление запускается отдельно и явно. Обнаружение не меняет данные, файлы, настройку папки создания копий и состояние обмена, не запускает перенос или ротацию. Инженерное следствие: каталог должен восстанавливаться из доступных копий без прежнего локального индекса; формат метаданных, проверки и обработка повреждённых файлов ещё проектируются. Источник требований — спецификация §1/10, будущая проверка — сценарий 57/A57 в P07.

Для выбранной общей базы предлагаются следующие детали реализации:

Подтверждено 2026-10-27: восстановление копии пространства после переустановки сохраняет идентичность самого пространства, а новая установка подключается к другому устройству заново с подтверждением. Права агентов на новой установке выдаются заново; автоматического возврата прежних подключений и прав из копии пространства нет. Сохраняются пауза до явного возобновления, изоляция актуальных разрешений другого устройства и общие правила сохранения независимых правок; [ADR-0016](decisions/0016-reinstallation-pairing-and-access.md), сценарий 58/A58. Для новой установки при подтверждённом отсутствии текущего состояния исходного пространства разрешено восстановление без страховочного снимка отсутствующего состояния, после проверки совместимости/целостности копии и с сохранением исходного файла; сценарий 59/A59. Проверка отсутствия согласуется с применением; ошибка чтения не доказывает отсутствие. Если пространство существует, в том числе в корзине, новый страховочный снимок обязателен. Технические идентификаторы и полномочия ещё проектируются. Исключение не отменяет страховочные копии миграции; аварийное восстановление всей базы имеет отдельные правила.

1. Получать согласованное состояние выбранного пространства в транзакции чтения и записывать его в отдельный снимок. Формат архива и способ выполнения длительного чтения остаются техническими решениями; нужно проверить задержки автосохранения во время копирования.
2. Использовать общий механизм извлечения полного состояния пространства для экспорта и резервного снимка. Технические сведения и применение различаются: импорт создаёт независимое пространство, восстановление возвращает исходное и формирует новое действие. Нужные технические сведения для восстановления определяются при проектировании интеграции выбранного Automerge.
3. Сначала полностью создавать и проверять новый снимок, затем выполнять согласованную ротацию. Соблюдать 7 ежедневных копий и отдельные последние снимки перед миграцией и перед восстановлением. Дни без изменений пропускаются.
4. Перед восстановлением прочитать и проверить снимок, сохранив текущее состояние по согласованной политике страховочной копии. Применять восстановление через общее ядро с сохранением идентичности пространства и актуальных сведений, необходимых для обмена. Обмен восстанавливаемого пространства приостанавливается до явной команды; после неё восстановление передаётся как новое действие.
5. Сохранять достаточные сведения об окончательной очистке для распознавания повторно пришедших данных и независимых новых правок. Количество файлов базы не определяет, какие технические записи можно удалить.

Проверка SQLite-файла не покрывает все прикладные связи. Например, `integrity_check` не проверяет внешние ключи; для них предусмотрен `foreign_key_check`. Дополнительно нужны проверки принадлежности данных пространству, ссылок, формата и обязательных сведений восстановления. Конкретный набор проверок проектируется вместе с форматом снимка. [SQLite: проверка целостности](https://www.sqlite.org/pragma.html#pragma_integrity_check).

## 4. Миграции

Подтверждено: вся необходимая цепочка миграций общей базы, включая служебные данные, атомарна. При ошибке до фиксации восстанавливается исходное состояние, промежуточная версия схемы не остаётся результатом обновления. Новая версия напрямую обновляет любую ранее официально выпущенную схему без промежуточных установок; сохраняются миграции и проверки исторических схем.

Подтверждено: помимо согласованных снимков отдельных пространств перед каждой попыткой создаётся и проверяется полная согласованная копия SQLite-базы со служебными данными в выбранной папке. Дополнительный расход места принят. Одна постоянная полная копия перед последней успешной миграцией заменяется новым отдельно созданным снимком только после следующей успешной миграции и проверки результата. Ошибка и ежедневная ротация не удаляют прежние исправные копии; обработка снимков-кандидатов после сбоя уточняется технически.

Подтверждено: после ошибки текущая попытка останавливается с понятной причиной. В текущем запуске повтор выполняется только явно; при следующем запуске необходимая миграция снова начинается автоматически с обязательными проверками и новым проверенным страховочным снимком. Обычные операции новой версии ждут успешного завершения.

Подтверждено: исправные снимки пространств всех ранее официально выпущенных форматов остаются восстанавливаемыми. Необходимое преобразование выполняется на рабочей копии с сохранением исходного файла. Реализация преобразований и проверок исторических снимков входит в будущий план.

Подтверждено: после установки обновления необходимая миграция запускается автоматически при первом запуске новой версии, без отдельной команды или подтверждения через интерфейс либо API. До изменения схемы выполняются обязательные проверки и создаётся и проверяется новый страховочный снимок в выбранной папке. Невыполнение этих условий останавливает миграцию до изменения данных с понятной причиной отказа. При требуемой миграции обычные операции новой версии с этой базой доступны после её успешного завершения. Порядок одинаков для Windows и Android и всех адаптеров общего ядра; механизм миграций и конкретные проверки ещё проектируются.

Подтверждено: при обнаружении более новой схемы базы, которую старая версия приложения не поддерживает для записи, она отказывает в открытии и предлагает установить подходящую новую версию ZeDone. Проверка совместимости выполняется до миграции и обычных операций с базой. Схема, пользовательские данные и служебные записи сохраняются без изменений; режим чтения такой схемы и автоматический откат в первой версии не предусмотрены. Причина отказа доступна через интерфейс и общий API на Windows и Android. Конкретные версии и механизм проверки совместимости ещё проектируются.

Подтверждено: для синхронизации одинаковые версии ZeDone на ПК и телефоне не обязательны. Разные версии допускаются при явно поддержанной и проверенной совместимости протокола и формата данных с сохранением данных и согласованных правил конфликтов. Совместимость обмена проверяется отдельно от совместимости локальной схемы: она не разрешает старой версии открывать неподдерживаемую новую базу. Конкретные сочетания версий и механизм проверки проектируются отдельно.

Подтверждено: после устранения несовместимости протокола или формата данных обмен возобновляется автоматически после успешной проверки совместимости при доступном соединении. Локальная работа во время несовместимости продолжается, изменения сохраняются до обмена. Явная пауза пространства после восстановления сохраняется до отдельной команды возобновления; обновление приложения и успешная проверка совместимости её не снимают. Причина остановки и состояние явной паузы различимы через интерфейс и общий API на обеих платформах. Механизм и периодичность повторных проверок проектируются отдельно.

Предлагается хранить последовательность версионированных миграций в репозитории и фиксировать применённую версию в базе. Для номера прикладной версии SQLite предоставляет `user_version`; сама SQLite не определяет его смысл. Формат журнала миграций и выбор вспомогательной библиотеки остаются открытыми. [SQLite: user_version](https://www.sqlite.org/pragma.html#pragma_user_version).

Для выбранной общей базы предлагаются следующие детали реализации с соблюдением подтверждённых требований:

- До изменения схемы создавать и проверять согласованные снимки пространств и дополнительную полную копию базы в выбранной папке. Отдельные снимки сохраняют назначение для восстановления пространства, полная копия обеспечивает аварийное восстановление общей базы со служебными данными. Проверить согласованность их исходного состояния и порядок публикации файлов.
- Проверить транзакцию для всей цепочки изменений схемы, данных и отметки применённой версии. Для шагов, которые нельзя выполнить в такой транзакции, спроектировать механизм с той же гарантией атомарности всей цепочки и восстановлением после прерывания. Фиксация промежуточной схемы как результата неудачного обновления не допускается. SQLite описывает транзакционную процедуру изменения структуры таблиц. [SQLite: изменение схемы](https://www.sqlite.org/lang_altertable.html#otheralter).
- Считать миграцию успешной после проверки результата. Прежний страховочный снимок заменять только после успеха; ошибка сохраняет предыдущие исправные копии.
- Проверять совместимость до миграции и обычных операций с базой, соблюдая подтверждённый отказ в открытии неподдерживаемой новой схемы без изменения базы. Поддержать обновление всех выпущенных схем и восстановление исправных снимков всех выпущенных форматов. Для повреждённого снимка или неподдерживаемого будущего формата возвращать понятную ошибку; преобразование старого формата сохраняет исходный файл.
- Сохранять различие версий внутренней схемы, переносимого архива и протокола синхронизации. Изменение схемы одной реплики не означает автоматически совместимость протокола с другим устройством.

### Отдельное аварийное восстановление всей базы

Подтверждено: если после сбоя миграции целостность рабочей базы не подтверждена, обычная работа и обмен останавливаются, проблемное состояние сохраняется отдельно. Приложение переходит в служебный режим и показывает причину, выбранную проверенную полную предмиграционную копию и охват восстановления. Восстановление всей базы запускается только явной командой; автоматического восстановления нет. Повтор миграции в текущем запуске остаётся ручным.

Аварийное восстановление разрешено, даже если получить исправный новый снимок повреждённого текущего состояния невозможно: проблемное состояние предварительно сохраняется отдельно, предмиграционная копия проверяется. Сохранённая повреждённая база не считается исправным снимком. Обычное восстановление пространства по-прежнему требует нового проверенного снимка текущего состояния. Правила общие для Windows, Android и адаптеров ядра; полномочия на полную копию, восстановление и проверку доступа при повреждении базы остаются открытыми и не расширяют административный доступ автоматически.

## 5. Критерии будущего прототипа

Это критерии будущих проверок, а не результаты выполненного прототипа. Подтверждённые правила раздела 1.1 продуктовой спецификации обязательны для выбранного механизма.

1. Снимок пространства A содержит полное состояние A: текущие данные, корзину, всю пользовательскую историю, нерешённые конфликты и необходимые сведения восстановления. Пользовательские данные пространства B в снимок не попадают. Состояние снимка согласовано при параллельном редактировании.
2. Восстановление A сохраняет данные B и актуальные локальные права, возвращает теги и назначения из снимка A, включая удалённые позднее, создаёт новое действие восстановления и оставляет обмен A на паузе до явного возобновления. Отдельное восстановление удалённого тега остаётся недоступным.
3. Прерывание создания снимка, применения восстановления или миграции сохраняет возможность получить целостное состояние; предыдущие исправные копии остаются доступны по выбранной политике.
4. Изменение карточки и необходимые сведения её синхронизации фиксируются согласованно; повтор операции не создаёт дубликатов.
5. Поиск по всем доступным пространствам соблюдает выданные права и показывает карточку с конфликтом один раз, учитывая все конфликтующие варианты текста.
6. На Windows и Android измеряются задержки сохранения и поиска, время копирования и миграции, память и дисковый объём. Режим журнала, число соединений и размеры контрольного набора задаются в плане; показатели ещё не подтверждены.
7. Выбор другой локальной папки и возврат к каталогу по умолчанию доступны на обеих платформах через общий API в пределах выданных прав. На Android проверяются выбор папки и повторный доступ после перезапуска; недоступное расположение возвращает понятную ошибку. Перенос существующих ежедневных и страховочных снимков, включая копии удалённых пространств, проверяется в порядке «копирование и проверка → сохранение нового расположения → удаление исходных копий». Проверяются сбои между этапами и перезапуск без потери исправных копий, сохранение прежней настройки при ошибке до переключения и сообщение об оставшихся дубликатах при ошибке удаления после него. Посторонние файлы не изменяются.
8. При отключении накопителя или отзыве доступа к папке ошибка видна в интерфейсе и общем API, а обычная работа с пространствами продолжается. Повторные попытки при работающем приложении используют ту же папку; ротации, обновления последнего успешного снимка и автоматического переключения папки при ошибке нет. После восстановления доступа соблюдаются согласованные частота и условия создания снимков без восполнения пропущенных дней.
9. Миграция базы и восстановление существующего пространства не начинаются без нового проверенного страховочного снимка текущего состояния в выбранной папке. Проверяются недоступность папки, ошибка записи и ошибка проверки: операция не изменяет исходное состояние, прежний страховочный снимок сохраняется, другая папка автоматически не используется. Причина отказа доступна через интерфейс и общий API на Windows и Android. Исключение восстановления в новую установку при подтверждённом отсутствии исходного пространства проверяется отдельно в сценарии 59/A59; страховочные копии миграции сохраняются.
10. Первый запуск новой версии после установки обновления автоматически выполняет необходимую миграцию после обязательных проверок и нового проверенного страховочного снимка, без отдельной команды или подтверждения. До успешного завершения требуемой миграции обычные операции новой версии с этой базой не выполняются. Проверяется одинаковое поведение интерфейса и общего API на Windows и Android, включая отказ при невыполненных условиях начала миграции.
11. Старая версия приложения отказывает в открытии более новой схемы, которую не поддерживает для записи, и предлагает установить подходящую новую версию. Проверяются сохранность схемы, пользовательских данных и служебных записей, отсутствие режима чтения такой схемы и автоматического отката, одинаковая причина отказа через интерфейс и общий API на Windows и Android.
12. Для явно поддержанных сочетаний разных версий ZeDone на Windows и Android проверяется синхронизация совместимых протокола и формата данных с сохранением данных и правил конфликтов. Различие номеров версий приложения само по себе не блокирует обмен. Совместимость обмена проверяется отдельно от совместимости локальной схемы базы и одинаково определяется для интерфейса и общего API; поддержанные сочетания и результаты фиксируются в документации.
13. После остановки обмена из-за несовместимости протокола или формата данных успешная проверка совместимости при доступном соединении автоматически возобновляет обмен без отдельной команды. Локальные изменения, сделанные до этого, сохраняются. Для пространства с явной паузой после восстановления обмен в обе стороны остаётся на паузе до отдельной команды, в том числе после обновления и перезапуска приложения. Состояния различимы через интерфейс и общий API на Windows и Android.

14. Ошибка второго шага цепочки 1 → 2 → 3 возвращает всю базу, включая служебные данные, к исходной схеме 1. Для прерывания на каждом этапе проверяется целостное исходное состояние либо успешно зафиксированное целевое состояние схемы 3. Промежуточная схема 2 не становится результатом неудачного обновления. Проверки результата предшествуют признанию миграции успешной.
15. Ошибка останавливает текущую попытку с причиной. В текущем запуске повтор только явный; следующий запуск автоматически начинает необходимую миграцию с обязательными проверками и новым проверенным страховочным снимком. Обычная работа новой версии до успеха недоступна.
16. Полная предмиграционная копия включает пользовательские и служебные данные общей базы и создаётся дополнительно к снимкам пространств в выбранной папке. Прежняя постоянная полная копия сохраняется до успеха следующей миграции и проверки результата; ошибка и ежедневная ротация её не удаляют. Проверяется прерывание записи и замены копий без потери прежних исправных файлов.
17. При неподтверждённой целостности после сбоя обычная работа и обмен остановлены. Проверяются отдельное сохранение проблемного состояния, явная команда аварийного восстановления, проверка полной предмиграционной копии и показ охвата всей базы. Невозможность создать исправный новый снимок повреждённого состояния не запрещает эту отдельную операцию. Обычное восстановление пространства сохраняет обязательный новый проверенный снимок; полномочия служебного режима проверяются после их отдельного проектирования.
18. Набор исторических схем напрямую обновляется текущей версией без промежуточных установок, всей атомарной цепочкой. Исправные снимки каждого ранее официально выпущенного формата восстанавливаются; преобразование рабочей копии не меняет исходный файл. Наборы проверок сохраняются и дополняются при выпуске новых схем и форматов.

Оценка сохраняет требования обратимости с согласованными исключениями, общего API, паритета платформ и единого источника истины. Выбраны одна база устройства, логические снимки пространств и дополнительная полная предмиграционная копия. Поведение миграций, аварийного восстановления и совместимости исторических схем и снимков согласовано; детали схемы, режим журнала, формат снимка, механизм миграций и интеграция выбранного Automerge ещё требуют технического проектирования и проверки. Документ не является ADR.
