Требования к миграциям и восстановлению уточнены в разделе 1.1 [продуктовой спецификации](product-spec.md) и [организации SQLite](sqlite-layout.md). Новые прототипы и измерения ещё не выполнялись.

Статус: для сложных компонентов интерфейса выбран Reka UI, для простых кнопок и полей — стандартный HTML с собственным оформлением ZeDone. Для перетаскивания выбраны SortableJS через VueDraggablePlus с обязательной технической проверкой. Для синтаксиса Markdown первой версии выбран базовый CommonMark с буквальным показом пользовательского HTML; для просмотра — markdown-it + DOMPurify с обязательной технической проверкой. Для синхронизации выбран Automerge для Rust с обязательной технической проверкой. SQLite и rusqlite с `bundled` выбраны как основа хранения с обязательной технической проверкой на Windows и Android. Axum и Tokio выбраны для HTTP API на обеих платформах как адаптер к общему Rust-ядру; работа сервера в APK требует обязательной технической проверки. Для управления JavaScript-зависимостями и запуска инструментов интерфейса и CI выбран Bun с обязательной проверкой всей цепочки Vue/TypeScript/Vite/Tauri и генерации API. Выбраны utoipa + OpenAPI + openapi-typescript + openapi-fetch; совместимость новых инструментов с Bun ещё не подтверждена, см. [ADR-0003](decisions/0003-api-contract-toolchain.md). Сборки и прототипы ZeDone в рамках этой проверки не выполнялись. Подтверждённые продуктовые требования находятся в [спецификации](product-spec.md); документация технологий не является доказательством достигнутой производительности приложения.

## 1. Выбранная основа и предложения

Подтверждено 2026-10-27: для создания Windows-установщика выбран Inno Setup; установка и установка обновлений выполняются только для текущей учётной записи без запроса прав администратора; [ADR-0017](decisions/0017-windows-per-user-installation.md). Версия Inno Setup и сценарий сборки ещё определяются, проверки упаковки и обновления ZeDone не выполнялись.

Для локального хранения выбраны SQLite и rusqlite с `bundled`; техническая проверка на Windows и Android обязательна. Для HTTP выбраны Axum и Tokio как адаптер к общему Rust-ядру с обязательной проверкой сервера в APK. Для Android-оболочки выбран Tauri 2; резерв — Kotlin + Android WebView с подключением Rust. Пригодность выбранной оболочки проверяется ограниченным прототипом. Версии фиксируются при реализации после проверки совместимости.

Подтверждено: в прототипе Tauri 2 первым проверяется IPC через команды Tauri как транспорт между Vue-интерфейсом APK и Rust. HTTP на Windows и внешний HTTP-доступ к APK используют те же прикладные операции Rust. Бизнес-правила, права доступа и работа с хранилищем остаются общими. Окончательный выбор внутреннего транспорта Android подтверждается по результатам прототипа.

### Компоненты интерфейса: Reka UI и стандартный HTML

Подтверждено: для сложных компонентов выбран Reka UI, для простых кнопок и полей — стандартные семантические HTML-элементы; [ADR-0004](decisions/0004-ui-components.md). Подключаются только необходимые компоненты. Собственное оформление ZeDone задаётся общим компонентам и используется на обеих платформах.

Обоснование выбора — сокращение собственного кода клавиатурной навигации, фокуса и доступности, который должен поддерживать AI-агент. Это инженерная оценка; частота ошибок агента и пригодность интеграции ZeDone ещё не измерены. В P01/P05 обязательны проверка совместимости с Bun/Vue/TypeScript/Vite/Tauri, собственное оформление, фокус, клавиатурное и сенсорное управление, экранная клавиатура и системная кнопка «Назад» Android. Наличие готовых механизмов доступности не заменяет проверки приложения. Перетаскивание выбрано отдельно в [ADR-0005](decisions/0005-drag-and-drop.md): SortableJS через VueDraggablePlus. Синтаксис первой версии — базовый CommonMark; [ADR-0006](decisions/0006-markdown-syntax.md). Для просмотра Markdown выбраны markdown-it + DOMPurify с обязательной технической проверкой.

### Перетаскивание: SortableJS через VueDraggablePlus

Подтверждено: для перетаскивания карточек между колонками одного пространства и изменения порядка карточек и колонок выбраны SortableJS через VueDraggablePlus; [ADR-0005](decisions/0005-drag-and-drop.md). SortableJS отвечает за механику переноса, VueDraggablePlus — за интеграцию с Vue и TypeScript. Ожидаемое сокращение связующего кода является инженерной оценкой, а не измеренным снижением ошибок AI-агента.

Завершение жеста вызывает ту же прикладную операцию Rust-ядра, что явные команды интерфейса, HTTP и CLI. До подтверждения ядром перенос не считается сохранённым; при ошибке показывается причина и представление согласуется с авторитетным состоянием. Явные команды для клавиатуры и управления без перетаскивания сохраняются, как и правила идентичности, блокировок и конфликтов порядка.

В P01/P05 обязательны проверка с Bun/Vue/TypeScript/Vite/Tauri, перенос и изменение порядка, мышь и сенсорный ввод, прокрутка, отказ ядра и ошибки сохранения, отсутствие потери или дублирования карточек и равнозначность явных команд. Работа проверяется в целевых браузерах Windows и Android APK; пригодность жестов и производительность ZeDone ещё не подтверждены.

### Синтаксис Markdown: базовый CommonMark

Подтверждено: для первой версии выбран базовый CommonMark без расширений таблиц и текстовых чекбоксов; [ADR-0006](decisions/0006-markdown-syntax.md). Поддерживаются заголовки, выделение, списки, ссылки, цитаты и блоки кода. Исходный текст с разделителями таблиц и маркерами «- [ ]» сохраняется и отображается по базовым правилам; отдельные таблицы или интерактивные чекбоксы из него не создаются, отметка выполнения карточки не меняется.

Для парсинга и безопасного просмотра выбраны markdown-it + DOMPurify: markdown-it преобразует Markdown в HTML, DOMPurify очищает результат перед отображением. Используется один модуль общего клиентского интерфейса с одинаковой конфигурацией на обеих платформах; непроверенная разметка после очистки не добавляется. HTML-разметка пользователя показывается как обычный текст вместе с тегами, исходный текст сохраняется; обычное форматирование Markdown работает. Это явно ограниченный профиль отображения поверх базового CommonMark. В выбранном markdown-it требуется явное отключение HTML (`html: false`), поскольку стандартный пресет CommonMark включает HTML. Для DOMPurify используется HTML-профиль; активные адреса изображений до нажатия подавляются также до этапа очистки, сама очистка не является запретом сетевой загрузки. HTTP/HTTPS-ссылки открываются по нажатию вне ZeDone: в отдельной вкладке браузера на Windows и во внешнем браузере на Android, без замены экрана карточки сайтом и без автоматического перехода при просмотре. Механизм открытия на Android проверяется в прототипе; библиотека интеграции этим решением не выбирается. Удалённые изображения из Markdown загружаются внутри карточки только по отдельному нажатию; до этого показываются описание или заглушка с действием загрузки. До нажатия не должно быть сетевых запросов на изображения, включая этапы парсинга и очистки HTML; загрузка относится к выбранному изображению. Ошибка сети даёт понятное сообщение и повтор, не изменяя исходный текст и не останавливая работу с карточкой. Интеграция проверяется в прототипе на обеих платформах. В P01/P05 фиксируются поддерживаемая версия спецификации, настройки парсера и одинаковое поведение на Windows/Android; сценарий 50 и A50 ещё не проверены. В P01 обязательны установка/импорт библиотек и сборка с Bun/Vite, проверка TypeScript и фактический просмотр в браузерах Windows и Android APK. DOMPurify использует DOM целевого браузера/WebView; успешная сборка не заменяет проверки очистки и отсутствия запросов на изображения до нажатия.

## 2. SQLite и rusqlite

SQLite предназначена в том числе для локального хранения приложений и устройств. Она допускает несколько читателей, но одновременно выполняется одна запись в конкретную базу. Для ZeDone это выглядит подходящим ограничением: один локальный процесс обслуживает человека, агента и обмен. Достаточность очереди записи и задержки при автосохранении предстоит измерить. [SQLite: подходящие применения](https://www.sqlite.org/whentouse.html).

rusqlite предоставляет Rust-интерфейс к SQLite. Выбранный флаг `bundled` собирает поставляемый с зависимостью исходный код SQLite, позволяя приложению контролировать её версию. Этот вариант выбран для обеих платформ с обязательной технической проверкой Windows и Android. SQLite написана на C; запрет собственного unsafe в ядре, хранении и синхронизации сохраняется в уже согласованных границах. [rusqlite: сборка и возможности](https://github.com/rusqlite/rusqlite).

Интерфейс rusqlite синхронный; `Connection` поддерживает `Send`, но не `Sync`. Предлагается выполнять работу с базой вне потока интерфейса и потоков выполнения асинхронных сетевых задач, через управляемый рабочий поток и ограниченную очередь. Длительные копирования нужно организовать так, чтобы они не задерживали короткие операции редактирования. Конкретная организация потоков и соединений проверяется прототипом. [rusqlite: Connection](https://docs.rs/rusqlite/latest/rusqlite/struct.Connection.html), [Tokio: блокирующие задачи и отдельные потоки](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html).

При документальном сравнении рассмотрена SQLx: её SQLite-драйвер использует фоновый поток и каналы для неблокирующего обращения. Выбор rusqlite связан с прямым API необходимых функций SQLite, включая резервное копирование; преимущества по скорости или памяти перед SQLx не измерены. [SQLx: SqliteConnection](https://docs.rs/sqlx/latest/sqlx/struct.SqliteConnection.html), [rusqlite: backup](https://docs.rs/rusqlite/latest/rusqlite/backup/index.html).

Два ограничения нужно учесть до реализации:

- Стандартный SQLite `LIKE` игнорирует регистр только для ASCII. Подтверждённый поиск «работа» → «РАБОТА» требует подходящей обработки Unicode. Конкретный алгоритм сравнения и поисковый индекс ещё не выбраны. [SQLite: LIKE](https://www.sqlite.org/lang_expr.html#like).
- Online Backup API создаёт согласованный снимок целой базы. Для первой версии выбрана одна база устройства с согласованными логическими снимками отдельных пространств через общее Rust-ядро. Восстановление одного пространства сохраняет остальные пространства и сведения, необходимые для синхронизации. [SQLite: Backup API](https://www.sqlite.org/backup.html).

Выбор одной базы устройства и логических снимков и восстановления отдельных пространств, сравнение альтернатив и предложения по миграциям описаны в [оценке организации SQLite](sqlite-layout.md). Схема данных, формат снимков и механизм миграций ещё уточняются.

Подтверждено: автоматический снимок сохраняет полное состояние пространства — текущие данные, корзину, всю пользовательскую историю версий, нерешённые конфликты и необходимые сведения восстановления. Формат снимка и конкретные технические записи определяются при проектировании.

Для автоматических копий подтверждены каталог данных приложения по умолчанию и выбор другой локальной папки на Windows и Android. Доступны повторная смена папки и возврат к каталогу по умолчанию через общий API в пределах выданных прав. Существующие автоматические копии ZeDone, включая ежедневные и страховочные снимки и копии удалённых пространств, переносятся: копирование и проверка, сохранение нового расположения, удаление исходных копий. Ошибка до переключения сохраняет прежнюю настройку и исходные копии; ошибка удаления после переключения оставляет новое расположение действующим и явно показывается. Проверка переноса, сбоев и повторного запуска входит в будущую проверку работы с файлами.

При недоступности выбранной папки подтверждены сообщение об ошибке и повторные попытки в ту же папку при работающем приложении; работа с пространствами продолжается, автоматического выбора другой папки нет. Ошибка не обновляет последний успешный снимок и не запускает ротацию; после возврата доступа пропущенные дни не восполняются. Статус доступен через интерфейс и общий API на обеих платформах. Периодичность повторных попыток уточняется отдельно.

Миграция базы и восстановление существующего пространства не начинаются без создания и проверки нового страховочного снимка текущего состояния в выбранной папке. При недоступности папки или ошибке записи либо проверки операция не изменяет исходное состояние и не использует другую папку автоматически. Прежний страховочный снимок сохраняется и не подменяет новый; причина отказа доступна через интерфейс и общий API на Windows и Android. Для восстановления после переустановки в новую установку при подтверждённом отсутствии текущего состояния исходного пространства принято отдельное исключение: проверить копию и сохранить её исходный файл, не требуя снимка отсутствующего состояния; [ADR-0016](decisions/0016-reinstallation-pairing-and-access.md), A59. Исключение не отменяет страховочные копии миграции. Состав копий для согласованного восстановления общей базы и служебных данных проектируется отдельно.

Необходимая миграция базы после установки обновления автоматически запускается при первом запуске новой версии после обязательных проверок и создания проверенного страховочного снимка. Отдельная команда или подтверждение не требуются. Обычные операции новой версии с этой базой доступны после успешного завершения требуемой миграции одинаково через интерфейс и общий API на Windows и Android. Механизм миграций и конкретные проверки остаются техническими решениями.

Для старой версии приложения с более новой схемой, которую она не поддерживает для записи, подтверждён отказ в открытии с предложением установить подходящую новую версию ZeDone. База сохраняется без изменений; режим чтения такой схемы и автоматический откат в первой версии не предусмотрены. Проверка совместимости предшествует миграции и обычным операциям с базой; причина отказа доступна через интерфейс и общий API на обеих платформах. Механизм проверки и конкретные версии определяются отдельно.

Полное восстановление пространства возвращает теги и назначения из снимка, в том числе удалённые после его создания. Согласованное отсутствие восстановления удалённого тега относится к отдельному тегу; отдельная операция для него не добавляется.

Выбор SQLite не определяет алгоритм обмена. Изменения пространств и конфликты передаются протоколом ZeDone; структура локального хранилища проектируется под его требования.

Для синхронизации подтверждена возможность использовать разные версии ZeDone на Windows и Android при явно поддержанной и проверенной совместимости протокола и формата данных. Совпадение номера версии приложения не требуется. Проверка должна сохранять данные и согласованные правила конфликтов и выполняться общим ядром для интерфейса и API. Совместимость обмена рассматривается отдельно от совместимости локальной схемы базы; конкретные поддерживаемые сочетания версий и механизм проверки ещё проектируются.

После устранения несовместимости протокола или формата данных подтверждено автоматическое возобновление обмена после успешной проверки совместимости при доступном соединении. Локальная работа продолжается, изменения сохраняются до обмена. Явная пауза пространства после восстановления сохраняется до отдельной команды возобновления, включая обновление и перезапуск приложения. Причина остановки и состояние явной паузы различимы через интерфейс и общий API на обеих платформах. Механизм и периодичность повторных проверок проектируются отдельно.

## 3. Axum и Tokio

Axum предоставляет обработку HTTP-запросов, извлечение и проверку параметров и интеграцию с Tower. Он рассчитан на Tokio и Hyper. Axum и Tokio выбраны для роли HTTP-адаптера вокруг общего ядра Rust на Windows и Android. [Axum: возможности и совместимость](https://docs.rs/axum/latest/axum/).

Выбранный HTTP-адаптер предназначен для браузерного интерфейса Windows и разрешённых внешних обращений к работающему приложению, включая APK. Прикладные правила, права ZeDone и доступ к данным остаются в общем Rust-ядре. Работа HTTP-сервера в составе APK требует обязательной технической проверки. Адреса прослушивания задаются явно по требованиям спецификации — loopback для обычного интерфейса и отдельно разрешённый доступ через Tailscale.

Проверка должна показать одинаковые результаты одной команды через HTTP и локальный адаптер, отказ вне выданных прав, действие отзыва доступа и отзывчивость API во время операций хранения. Для Android отдельно проверяется совместная работа сервера и оболочки с одним ядром и авторитетным хранилищем.

## 4. Android: выбран Tauri 2, резерв Kotlin + WebView

Tauri поддерживает интерфейсы из HTML, JavaScript и CSS, вызовы Rust из интерфейса через команды и мобильные плагины на Kotlin. Tauri 2 выбран Android-оболочкой с общим Vue-интерфейсом и Rust-ядром по решению разработчика; см. [ADR-0001](decisions/0001-android-shell.md). Ожидаемое уменьшение собственного кода оболочки — проектная оценка, а не результат сравнения прототипов. [Tauri: назначение](https://v2.tauri.app/start/), [команды и IPC](https://v2.tauri.app/concept/inter-process-communication/), [мобильные плагины](https://v2.tauri.app/develop/plugins/develop-mobile/).

Запасной вариант — собственная оболочка Kotlin + Android WebView с подключением Rust. Android предоставляет `WebViewAssetLoader` для загрузки локальных ресурсов. При этом потребуется самостоятельно сопровождать связь с Rust и платформенные интеграции. Обе схемы используют WebView; переход на Kotlin сам по себе не доказывает улучшения расхода памяти или скорости Vue-интерфейса. [Android: локальные ресурсы WebView](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content).

Документация Tauri предусматривает Android SDK/NDK и настройку мобильной сборки на Windows. Это подтверждает предусмотренный путь сборки, но не успешную сборку ZeDone. [Tauri: требования Android](https://v2.tauri.app/start/prerequisites/#android).

Подтверждено: Tauri 2 выбран до технической проверки. Резерв Kotlin + Android WebView рассматривается при выявленных ограничениях, мешающих выполнить обязательные требования ZeDone; основания перехода фиксируются отдельным архитектурным решением. Для проверки Tauri 2 в эмуляторе Android 13 на Windows 11 предлагается следующий набор сценариев:

1. APK содержит интерфейс и данные и работает без ПК и интернета.
2. Русский ввод, клавиатура, системная кнопка «Назад», перетаскивание, импорт и экспорт работают по выбранным сценариям.
3. Разрешённый HTTP-запрос с ПК через Tailscale читает и изменяет локальные данные открытого APK до обмена с ПК; проверяются ограничения прав и отзыв доступа. Первым проверяется IPC через команды Tauri для интерфейса APK; при одинаковых исходных данных и правах одна команда через IPC и HTTP даёт одинаковый прикладной результат.
4. Автосохранение, остановка и повторный запуск, создание снимка и восстановление сохраняют уже записанные данные.
5. Сборка сохраняет запрет собственного unsafe в ядре, хранении и синхронизации; необходимые платформенные исключения имеют отдельное обоснование.
6. Измеряются запуск, отклик и память. Измерения эмулятора не подтверждают показатели Galaxy A32; перед выпуском рекомендована проверка на нём.

Ограничения Android на фоновую сеть и выполнение сохраняются при любой оболочке. Постоянный сервер при закрытом APK не входит в подтверждённые обещания продукта. [Android: Doze и App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby).

### Подключение устройств: QR-код и ручной ввод

Подтверждено: при уже настроенном Tailscale ПК показывает QR-код, который считывает телефон; запасной способ — ручной ввод адреса ПК в Tailscale и одноразового кода. Оба способа требуют дополнительного явного подтверждения запроса на ПК; до него телефон ожидает без подключения и обмена пространствами. Пространства для синхронизации выбираются явно; [ADR-0009](decisions/0009-device-pairing-qr-and-code.md). Состав QR и протокол подключения ещё проектируются; способ ввода использует общие прикладные операции и правила доступа.

Для чтения QR камерой Android выбран [официальный Tauri Barcode Scanner](https://v2.tauri.app/plugin/barcode-scanner/) с обязательной технической проверкой; [ADR-0022](decisions/0022-android-qr-scanner.md). Для генерации QR в Rust выбран qrcodegen без сторонних зависимостей, с единым модулем отображения в SVG и обязательной проверкой чтения; [ADR-0023](decisions/0023-qr-generation.md). В P01 проверить минимальный срез на синтетических данных: совместимость с Bun/Vue/TypeScript/Vite/Tauri, камеру и разрешения, отмену/повторный вход, недоступную камеру и ручной ввод. В просмотренном Android-коде ветки `v2` используется `play-services-mlkit-barcode-scanning`, то есть отдельно загружаемая модель. Первая загрузка принята разработчиком: до готовности используется ручной ввод, после готовности сканирование можно повторить; неготовность не выдаётся за неверное приглашение. Проверить первый запуск APK без сети/модели и недоступные Google Play Services; готовность QR сразу после установки без загрузки не требуется. Текущая документация указывает Rust не ниже 1.90; точные совместимые версии фиксируются при подготовке прототипа. Проверка сканера не подтверждает безопасность протокола и выдачи прав; полный контракт определяется в P03 и проверяется в P06 по A51.

## 5. Инструменты разработки интерфейса

Документальная проверка: 2026-10-25. Подтверждено: для управления JavaScript-зависимостями и запуска инструментов интерфейса и CI выбран Bun. Вся выбранная цепочка Vue/TypeScript/Vite/Tauri проходит обязательную проверку совместимости на Windows и в CI. Node.js/npm и pnpm рассмотрены как альтернативы.

Среда выполнения инструментов и менеджер пакетов выполняют разные роли. Node.js можно сочетать с npm или pnpm. Bun предоставляет и среду выполнения, и менеджер пакетов; эти роли также можно оценивать отдельно. Готовому ZeDone по подтверждённым требованиям достаточно Rust-компонентов и собранного веб-интерфейса; средства сборки нужны разработчику и CI.

### Сравнение вариантов

1. **Node.js LTS + pnpm — рассмотренная альтернатива.** Документация Vue и Tauri предусматривает Node.js для разработки веб-интерфейса; конкретная LTS-версия должна удовлетворять требованиям выбранных Vue/Vite и остальных инструментов. pnpm по умолчанию использует изолированную структуру зависимостей, которая помогает обнаруживать обращения к пакетам, явно не объявленным проектом. Его общее хранилище повторно использует файлы пакетов. Аргумент в пользу этого варианта — явное управление зависимостями; преимущества по времени и месту на диске для ZeDone не измерены. Дополнительная обязанность — устанавливать и закреплять версию менеджера пакетов. [Node.js: выпуски и LTS](https://nodejs.org/en/about/previous-releases), [Vue: начало работы](https://vuejs.org/guide/quick-start.html), [Tauri: Node.js](https://v2.tauri.app/start/prerequisites/#nodejs), [pnpm: структура зависимостей](https://pnpm.io/symlinked-node-modules-structure), [pnpm: общее хранилище](https://pnpm.io/motivation).
2. **Node.js LTS + npm — полноценная альтернатива.** npm обычно поставляется с Node.js. Команда `npm ci` устанавливает зависимости по существующему lock-файлу, прекращает установку при несовпадении зависимостей и не обновляет lock-файл. Изоляция зависимостей доступна и в npm через настройку `install-strategy=linked`; по умолчанию используется `hoisted`. Этот вариант сокращает число отдельно устанавливаемых инструментов. [npm: npm ci и стратегии установки](https://docs.npmjs.com/cli/v11/commands/npm-ci/).
3. **Bun — выбранные менеджер пакетов и среда запуска.** Он поддерживает Windows и установку по lock-файлу через `bun install --frozen-lockfile`. Документация Bun перечисляет отличия от Node.js API; выбор принят с обязательной проверкой всей цепочки Vue/Vite, проверки типов и Tauri CLI. Принятый риск — совместимость этой цепочки ещё не подтверждена прототипом. Производительность на ZeDone также не измерялась. [Bun: установка](https://bun.sh/docs/installation), [Bun: установка пакетов](https://bun.sh/docs/pm/cli/install), [Bun: совместимость с Node.js](https://bun.sh/docs/runtime/nodejs-compat).

### Выбранная цепочка API и совместимость с Bun

Подтверждено: выбрана цепочка utoipa + OpenAPI + openapi-typescript + openapi-fetch; [ADR-0003](decisions/0003-api-contract-toolchain.md). Rust-описания данных и операций служат источником HTTP-контракта; utoipa создаёт OpenAPI, openapi-typescript — типы TypeScript, openapi-fetch использует эти типы для HTTP-запросов. Генерируемые представления не редактируются вручную; CI проверяет их согласованность с Rust и выполняет проверку типов.

Совместимость выбранной цепочки с Bun пока не подтверждена. В P01 обязательны чистая установка пакетов по lock-файлу Bun, генерация OpenAPI из Rust, запуск openapi-typescript под Bun, импорт и сборка openapi-fetch через Vite, проверка типов и работа HTTP-клиента в целевых браузерах Windows и Android WebView. Фиксируются версии, команды и фактическая среда выполнения каждого шага.

Документация openapi-typescript описывает Node.js. Установка пакета через Bun не доказывает выполнение генератора под Bun; неучтённый запуск Node.js через строку запуска CLI не считается успешной проверкой Bun. При обязательной потребности в Node.js фиксируются конкретный шаг, причина и версия как дополнительное требование разработки/CI. Bun остаётся менеджером пакетов; Node.js не добавляется в зависимости готового ZeDone. [openapi-typescript: требования и запуск](https://openapi-ts.dev/introduction), [openapi-fetch](https://openapi-ts.dev/openapi-fetch/).

OpenAPI описывает HTTP и само по себе не создаёт адаптер команд Tauri IPC. Для Android используются те же сгенерированные типы данных и прикладные операции Rust; связь имён команд, параметров, результатов и ошибок с контрактом и окончательный внутренний транспорт ещё требуют проверки P01/P03. Проверка типов не заменяет проверку входных данных и прав в ядре.

### Предлагаемые правила для будущей реализации

- Закрепить совместимую версию Bun; локальная разработка и CI используют её. Способ установки определяется для закреплённой версии инструмента.
- Хранить один авторитетный lock-файл JavaScript-зависимостей `bun.lock` в репозитории. В CI проверять его наличие и явно выполнять `bun install --frozen-lockfile` либо `bun ci`; установка не должна переписывать граф зависимостей. [Bun: lock-файл](https://bun.sh/docs/pm/lockfile), [Bun: установка](https://bun.sh/docs/pm/cli/install).
- Объявлять команды разработки, сборки и проверки в `package.json`; человек и агент запускают одинаковые команды. Проверить их на Windows и на Linux-машинах CI для Android.
- Явно проверять Bun как среду выполнения JavaScript-инструментов. Обычный `bun run` может учитывать строку запуска CLI с `node`; для запуска под Bun предусмотрены, например, `bun --bun run <script>` и настройка `run.bun` в `bunfig.toml`. Конкретные команды и фактическая среда запуска каждого шага проверяются прототипом. Обнаруженные требования отдельных инструментов к Node.js отражаются в результатах проверки совместимости. [Bun: запуск](https://bun.sh/docs/runtime), [Bun: настройки запуска](https://bun.sh/docs/runtime/bunfig).
- Включить отдельную проверку типов Vue/TypeScript. Vite выполняет преобразование и сборку без проверки типов; Vue рекомендует `vue-tsc` для Vue-компонентов. Для этого в будущем плане предлагается отдельная команда проверки. [Vue: TypeScript](https://vuejs.org/guide/typescript/overview.html).
- На прототипе проверить чистую установку зависимостей через Bun, генерацию OpenAPI через utoipa, запуск openapi-typescript под Bun, импорт и сборку openapi-fetch через Vite, проверку согласованности генерируемых артефактов, проверку типов, сборку общего интерфейса и вызов Tauri CLI для Android на выбранной среде Bun. Поддержка установщика пакетов сама по себе не подтверждает пригодность всей цепочки сборки.

Новые package-файлы и lock-файлы в рамках этого обсуждения не создавались. Установка зависимостей, сборки и сравнительные измерения npm/pnpm/Bun ещё не выполнялись. Bun выбран; конкретная версия, способ установки и совместимость всей цепочки определяются и проверяются при подготовке будущего прототипа.

## 6. Выбранная основа синхронизации: Automerge для Rust

Подтверждено 2026-10-26: разработчик выбрал Automerge для Rust; основание и ограничения оформлены в [ADR-0002](decisions/0002-automerge-sync.md). Обязательное сравнение двух реализаций заменено ограниченным прототипом выбранной библиотеки в P02. Реализация всего приложения для технической проверки не требуется.

Automerge предоставляет модель документов, протокол обмена и доступ ко всем конкурирующим значениям через `ReadDoc::get_all()`. Прототип должен явно сохранять и показывать варианты по правилам ZeDone: автоматически выбранное библиотекой значение само по себе не является разрешением пользовательского конфликта. Markdown проверяется как одно поле с ручным разрешением независимых текстов. [Automerge: модель, конфликты и обмен](https://docs.rs/automerge/latest/automerge/).

Разработкой занимается AI-агент. Приоритет выбора — уменьшение объёма собственной сложной логики, понятная документация и возможность автоматической проверки. Ожидаемое снижение риска ошибок агента является инженерной оценкой, а не результатом сравнительных измерений. Использование Automerge сосредотачивается в одном внутреннем модуле Rust-ядра; агент сверяется с документацией закреплённой Rust-версии. [Automerge: материалы для LLM](https://automerge.org/docs/guides/using-automerge-with-llms/).

Модель причинных версий отдельных полей на готовых компонентах, например `crdts::MVReg`, рассмотрена как альтернатива и не входит в выбранную основу. Отдельный сравнительный прототип этой модели больше не обязателен. [MVReg: документация Rust](https://docs.rs/crdts/latest/crdts/mvreg/struct.MVReg.html).

Прототип сохраняет одно авторитетное локальное состояние на основе Rust и SQLite, общие прикладные операции и запрет собственного unsafe в ядре, хранении и синхронизации. Формат размещения документов и изменений Automerge, согласованная фиксация и поисковые представления уточняются при техническом проектировании. Прикладные правила контейнеров, уникальности тегов, удаления и восстановления проверяются независимо от наличия готовых структур библиотеки.

Обязательный набор критериев:

- Правила раздела 1.2 и относящиеся к синхронизации сценарии раздела 11 продуктовой спецификации: объединение разных полей, сохранение конфликтующих значений, перестановки, названия контейнеров, назначения тегов и конкурирующие решения конфликтов. Независимо созданные одноимённые теги одного пространства автоматически объединяются с сохранением всех назначений; сценарий 49 проверяется в прототипе Automerge. Сценарий 52 проверяет явный конфликт при независимом переименовании двух существующих тегов в одно имя с сохранением тегов/идентификаторов/назначений и выбором разных имён, доступностью изменения заголовка/текста/статуса выполнения/колонки карточки при спорном только имени тега и временным запретом назначения/снятия спорных тегов до выбора разных имён. Сценарий 53 проверяет те же правила при переименовании существующего тега против независимого создания нового тега с тем же именем; [ADR-0012](decisions/0012-tag-rename-conflicts.md). При автообъединении сохраняется одно из исходных написаний с общим итогом на устройствах независимо от порядка/повторов доставки и возможностью последующего переименования; это также проверяется в сценарии 49. Согласование идентификаторов, конкретный алгоритм выбора исходного написания и остальные коллизии имён уточняются отдельно; запрет переименования в занятое имя сохраняется.
- Повторы, обрывы и разный порядок доставки дают одинаковые данные и набор конфликтов. Пользовательские изменения и необходимые сведения обмена фиксируются согласованно с SQLite; успех не объявляется до фиксации. Повторный запуск сохраняет уже записанные изменения и сведения обмена.
- Удаление, окончательная очистка, группы удаления и очистка истории сохраняют независимые новые правки. Долго отключённое устройство возвращается без автоматической отвязки; сокращение технических сведений не возвращает очищенные данные и не теряет новые изменения.
- Снимки и восстановление соблюдают согласованные идентификаторы, причинные границы и паузу пространства до явного возобновления. Восстановление поздних правок очищенного контейнера сохраняет минимальный согласованный охват.
- На контрольном наборе измеряются загрузка, обмен, память, дисковый объём и его рост при повторном автосохранении и очистке пользовательской истории. Измерения Windows и Android фиксируются отдельно; эмулятор не подтверждает показатели целевого Galaxy A32. Приняты верхние границы ОЗУ всего ZeDone с интерфейсом и пиками: 4 ГБ на ПК и 2 ГБ на Android; ADR-0019/A61. Изолированное измерение Rust-прототипа не закрывает совокупный бюджет. Итоговые бюджеты времени выпуска и точная методика памяти ещё определяются; стартовые ориентиры прототипа приняты в ADR-0020.
- Оцениваются объём собственного кода, сложность сопровождения AI-агентом, необходимые платформенные обходы, зависимости и их пригодность для выбранного стека. Небольшой объём кода не заменяет проверку сохранности данных и обязательного поведения.

Порядок практических запусков, версия библиотеки, модель данных, контрольный набор и точные команды определяются при подготовке прототипа. Результаты должны явно разделять подтверждённые возможности, измерения и оставшиеся ограничения. Выбор Automerge уже принят; техническая пригодность для всех требований ZeDone пока не подтверждена. При необходимости пересмотра выбора основания фиксируются отдельным архитектурным решением.

## 7. Состояние проверки и требования проекта

Выполнена документальная оценка компонентов; SQLite и rusqlite с `bundled` выбраны с обязательной технической проверкой обеих платформ, Axum и Tokio — с обязательной проверкой HTTP-сервера в APK. Для первой версии выбрана одна база устройства с логическими снимками и восстановлением отдельных пространств через общее Rust-ядро. Tauri 2 выбран Android-оболочкой с резервом Kotlin + Android WebView; первым внутренним транспортом проверяется IPC через команды Tauri. Пригодность выбранной оболочки и окончательный выбор внутреннего транспорта проверяются прототипом. Bun выбран для управления зависимостями и запуска инструментов интерфейса и CI с обязательной проверкой всей цепочки. Для API выбраны utoipa + OpenAPI + openapi-typescript + openapi-fetch; совместимость с Bun, фактическая потребность в Node.js и интеграция общих типов с Android IPC ещё проверяются. Сборка Windows, сборка APK, запуск в эмуляторе, сетевой сценарий Tailscale и измерения ещё не выполнялись. Поведение миграций, аварийного восстановления и совместимости исторических схем и снимков согласовано в продуктовой спецификации. Схема данных, форматы и механизм миграций ещё проектируются; для синхронизации выбран Automerge для Rust; обязательный прототип его интеграции и технической пригодности ещё не выполнен.

Рекомендации сохраняют требования обратимости с согласованными исключениями, общего API человека и агента, паритета Windows и Android и единого авторитетного локального состояния. Проверки снимков и восстановления входят в критерии пригодности. Выбор Tauri 2 и резерв Kotlin + Android WebView оформлены в [ADR-0001](decisions/0001-android-shell.md), выбор Automerge для Rust — в [ADR-0002](decisions/0002-automerge-sync.md), цепочка API — в [ADR-0003](decisions/0003-api-contract-toolchain.md), компоненты интерфейса — в [ADR-0004](decisions/0004-ui-components.md), перетаскивание — в [ADR-0005](decisions/0005-drag-and-drop.md), синтаксис Markdown — в [ADR-0006](decisions/0006-markdown-syntax.md); этот документ не является ADR.
