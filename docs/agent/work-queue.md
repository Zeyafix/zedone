# ZeDone: малые шаги выполнения

Этот файл предназначен исполняющему AI-агенту. Он задаёт объём, зависимости и состояние малых шагов. [План-журнал](plan-journal.md) хранит приёмку T/A/M/S, проблемы, доказательства EV и историю; его текущий статус — проекция выбранного шага. Требования читаются в [спецификации](../architecture/product-spec.md) и связанных ADR. Не копировать сюда требования или результаты приёмки.

## Как выбрать и выполнить шаг

1. Прочитать текущий статус журнала, строку `current_step`, относящиеся к ней DEC/BUG/GAP и полные требования по указанным критериям. Затем читать только нужный раздел очереди и документы. История чата не является обязательным входом.
2. Проверить рабочее дерево, исходную ревизию и доказательства зависимостей. Чужие изменения сохранить. Выбирать один разрешённый шаг, у которого зависимости `done` и доступны в используемой базе; порядок строк не заменяет зависимости. Если задача ограничена частью плана, не расширять её автоматически.
3. Развернуть только выбранный шаг в рабочую карточку по шаблону ниже. Указать одну проверяемую цель, точный охват PR и проверки. Если для неё нужны несколько независимых изменений, сначала разделить шаг, затем писать код. Будущие строки остаются планом результатов; неизвестные команды и структуру проекта заранее не выдумывать.
4. В строке шага установить `in_progress`, в журнале записать `current_step` и `active_work`. Реализовать изменение, необходимые проверки и документацию. После шага ядра приоритет отдавать готовому соответствующему шагу интерфейса: P05 разрешено чередовать с P04, не ожидая всего P04. Аналогично готовые шаги P06/P07/P08 могут выполняться до завершения всех предыдущих этапов.
5. Проверить полный diff относительно базы, затем выполнить подходящие проверки. Для функционала проверить отказ/ошибку, обратное действие, общий API человека и агента и обе платформы в применимом объёме. Собственное состояние UI, поисковый индекс и типы клиента не становятся независимыми источниками данных. Полный смысл и исключения читаются в критериях, а не только в краткой строке.
6. Сохранить результат и ограничения в EV, обновить затронутые критерии журнала и состояние шага. Подготовку/публикацию PR выполнять по [ze-pr](../../.agents/skills/ze-pr/SKILL.md) в рамках исходного поручения. Наличие очереди не разрешает публикацию, слияние или установку инструментов за пределами задачи и не вводит дополнительных согласований для уже разрешённой работы.
7. Обновить журнал и точку продолжения по шаблону. Если поручение охватывает несколько шагов, продолжать готовые шаги самостоятельно; каждый сохраняет собственную границу проверки/PR. Завершать этап только по его критериям, а не по числу закрытых строк.

Состояния шагов: `planned`, `in_progress`, `verified`, `blocked`, `done`. `verified` — локальные проверки выполнены, но нужные CI/интеграция ещё ожидаются; это не пройденная приёмка. `done` — согласованный охват проверен и доступен в указанной интегрированной ревизии. Если работа выполняется без PR по прямому поручению, указать локальную ревизию и отсутствие слияния явно. Одновременно вести один активный шаг; уже принятые шаги при регрессии возвращать в работу, их доказательства — в `stale`. Для `blocked` нужны ID проблемы, условие снятия и готовый независимый следующий шаг, если он есть.

## Локальная подготовка машины

Перед работой с окружением проверить `docs/reports/state.json` и связанные локальные отчёты, если они существуют. Результаты осмотра, установленные версии и пути, сведения о доступах, сохранённый вывод команд, локальные EV, снимки настроек и состояние подготовки конкретной машины хранить только в игнорируемой `docs/reports/`. Эти данные не включать в коммиты, PR, общую документацию и публикуемые артефакты.

Характеристики ПК и телефона в спецификации задают целевые средства проверки, а не личные устройства разработчика. Перед коммитом и отправкой выполнять [правила публикуемых данных](../development/repository-privacy.md): noreply, проверка состава и метаданных, отправка только веток и тегов. Служебные refs со снимками остаются локальными.

Инструменты устанавливаются в штатные каталоги; отдельная папка `environment/` не нужна. В `temp/` допустимы только удаляемые загрузки, распаковки и проверочные примеры. Очистка `temp/` не должна лишать состояния, доказательств проверок или данных для отмены настройки. Если сохранилась прежняя `temp/environment/`, перед очисткой перенести из неё в `docs/reports/` состояние, отчёты, доказательства проверок и снимки настроек; проверить ссылки в отчётах и состоянии, при совпадении имён сначала сверить содержимое без перезаписи.

Строки P00 описывают общий порядок подготовки. Их выполнение для конкретной машины и локальный вклад в T13–T17 отмечаются в `docs/reports/state.json`; они не меняют состояния общего реестра проекта и не подтверждают готовность другой машины. Общие зависимости брать из очереди, готовность локальной среды — из локального состояния. Если локального состояния нет, начать с P00.01: проверить фактическое окружение без предположения, что инструменты отсутствуют.

По решению разработчика от 2026-10-28 (LOG-098) проверка на совершенно чистой системе исключена из P00/T17 и не является ожидающим условием приёмки или перехода к прототипам. Проверки выполняются на существующей ОС; переустановка инструментов требует отдельного поручения. Решение само по себе не закрывает остальные критерии P00 и не подтверждает независимость от ранее установленных компонентов и настроек.

Для проверки или настройки только текущей машины отдельная ветка, коммит и PR не нужны. Локальный шаг получает `done` после проверки его результата; интеграция локального отчёта в Git не требуется. Изменения общих инструкций, конфигурации проекта и CI проходят обычный процесс в рамках поручения. В Git сохраняются воспроизводимые команды и требования к версиям; перед подготовкой проверяется актуальность стабильных выпусков, затем совместимые версии закрепляются в общих инструкциях.

## Граница PR

- Один PR отвечает на один вопрос проверки: одно поведение, один отказ или один результат подготовки. Примеры: восстановление карточки; отказ устаревшему перемещению; доступность Android-эмулятора в CI. PR не равен фазе P00–P09.
- Ориентир — до 300 изменённых вручную строк, включая проверки и документацию. Это сигнал пересмотреть объём, а не лимит, ради которого удаляются тесты или обрывается безопасная операция. Сгенерированные файлы и lock-файлы считать отдельно, проверяя происхождение и необходимый состав. Превышение объяснить одной неделимой причиной в карточке/PR.
- Не смешивать с шагом посторонний рефакторинг, обновление зависимостей и форматирование всего проекта. Обязательное сопутствующее исправление включать с объяснением; независимое — отдельным шагом. Пару действие/обратное действие и атомарность сохранения не разрывать ради размера PR.
- Крупную строку до реализации разделить на дочерние `Pxx.nn.1`, `Pxx.nn.2` с собственными зависимостями, проверками и состояниями. Сохранить ID родителя как итоговую проверку без отдельного большого PR; внешние шаги ждут его `done`. Не перенумеровывать существующие ID и не оставлять зависимость между частями только в чате.
- Не накапливать несколько зависимых непроверенных PR. Следующий зависимый PR готовить на интегрированном результате предыдущего; стек PR допустим при отдельном разрешении. Ожидающие CI/ревью записывать как ожидающие, без объявления успеха. Нужная инфраструктура CI развивается вместе с изменением.
- Ограниченный промежуточный срез обозначать явно. До появления полного сценария не открывать незавершённые операции пользователю/внешней сети. Нельзя временно обходить права, сохранять только часть транзакции, терять историю/данные обмена или разрешать прямую запись агента в SQLite. Прикладные правила безопасности действуют с первого изменяющего запроса.
- Прототипы P01/P02 используют синтетические данные и изолированное хранилище. В продукт переносится только явно проверенный код; временные обходы и тестовые полномочия не становятся настройками выпуска.

## Карточка текущего шага и передача

Развёрнутую карточку хранить в связанном отчёте EV, а в `active_work` — краткую цель и ссылку на неё; не заводить второй реестр состояний. До появления EV незавершённые сведения помещать в событие журнала. Использовать такой состав:

```yaml
step: P00.01
base_revision: "SHA и состав существующих незакоммиченных изменений"
goal: "Одно наблюдаемое изменение или результат подготовки"
requirements: [T17] # Полные критерии и нужные разделы спецификации/ADR
dependencies_evidence: [] # ID шагов, интегрированные ревизии/EV
scope: [] # Затронутые файлы/модули; вне scope нет попутных изменений
checks: [] # Реальные команды после осмотра проекта; ожидаемый результат/платформа
reverse_and_failure: "Обратное действие, отказ, сбой; либо обоснованная неприменимость"
result: "Выполнено, проверено, осталось; PR URL/head/CI, если PR есть"
evidence: [] # EV, артефакты и непроверенные ячейки матрицы
next: "Один следующий шаг или действие с условием готовности"
```

Начальный шаг подготовки каждой машины — **P00.01**: только инвентаризация существующего окружения и перечень недостающего. Результат — `docs/reports/environment-inventory.md` с версиями, доступностью, недостающими компонентами и ограничениями; карточка и доказательства тоже остаются в `docs/reports/`. Команды осмотра выбирать после проверки среды; не выводить учётные данные. Установка начинается последующими шагами в рамках поручения на их выполнение. Существующее локальное состояние определяет точку продолжения подготовки машины.

## Реестр шагов

Во всех таблицах «Критерии» означает вклад в доказательства, а не автоматическое полное закрытие. При создании очереди все 98 критериев сохранены с исходными ID, полным смыслом, этапом окончательной приёмки и `not_run`; текущее состояние всегда читать в журнале. Для каждого шага обязательны точные проверки из рабочей карточки; краткая проверка в таблице задаёт минимальный охват. Проверка только одной платформы даёт частичный результат, где требуется обе. Это начальная декомпозиция, а не обещание фиксированного числа PR: до начала каждого будущего шага заново оценить его размер и при необходимости разделить.

Открытые решения уточнять до затронутого кода. Если решение меняет продуктовый договор, запросить его у разработчика; техническое решение в полномочиях агента принять с доказательствами. Назначение шага не закрывает DEC:
