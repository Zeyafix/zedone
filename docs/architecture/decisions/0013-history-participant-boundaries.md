# ADR-0013: границы и состав видимых версий истории карточки

Дата: 2026-10-26.

Статус: принято разработчиком. Реализация и техническая проверка не выполнены.

## Контекст

Непрерывное редактирование объединяется в одну видимую версию истории; локальное автосохранение выполняется чаще. Требовалось уточнить границу серии, когда текст карточки последовательно меняют разные участники.

Разработчик выбрал отдельные версии при смене участника. Пример: человек меняет текст, затем агент, затем снова человек. Объединение близких по времени правок независимо от участника рассмотрено как альтернатива.

Для двух отдельных команд одного агента разработчик также выбрал отдельную видимую версию после каждой команды. Объединение близких по времени команд одного агента в одну версию рассмотрено как альтернатива.

Разработчик выбрал сохранять заголовок и описание вместе в каждой версии карточки. История только описания без заголовка рассмотрена как альтернатива.

Разработчик подтвердил восстановление старой версии новой правкой: прежние заголовок и описание становятся текущими, новая видимая версия добавляется в историю, а все прежние версии сохраняются.

Для неожиданной остановки и быстрого перезапуска разработчик выбрал завершение прежней сохранённой серии. Продолжение прежней серии после перезапуска рассмотрено как альтернатива.

Разработчик выбрал 30 секунд без новых правок как существенную паузу для завершения серии непрерывного ввода. Интервалы в одну и пять минут рассмотрены как альтернативы. Частота локального автосохранения — отдельный параметр.

## Решение

- Каждая видимая версия содержит заголовок и текст описания карточки из одного сохранённого состояния. Успешное изменение только заголовка участвует в истории по тем же правилам, что изменение описания; неизменившееся поле также входит в версию. Прежние значения обоих полей доступны для просмотра и восстановления по общим правилам.
- Успешное восстановление выбранной старой версии записывает её заголовок и описание как новую правку и сразу фиксирует новую видимую версию. Предшествующая история сохраняется, включая версии после выбранной. Например, после версий 1 → 2 → 3 восстановление первой даёт версию 4 с содержимым первой; восстановление третьей затем даёт версию 5 с содержимым третьей. Ручная очистка истории сохраняет отдельные согласованные правила.
- Смена участника при успешно сохранённом изменении заголовка или описания завершает предыдущую серию редактирования и начинает новую. Долгая пауза между участниками не требуется.
- Последовательность «человек → агент → человек» образует три раздельных этапа истории с доступом к тексту после каждого этапа. Возврат прежнего участника не объединяет его новую серию с предыдущей через промежуточную правку другого участника.
- Несколько локальных автосохранений внутри одной непрерывной серии одного участника по-прежнему группируются. Существенная пауза — 30 секунд без новых правок заголовка или описания в этой серии. По истечении паузы серия завершается видимой версией с успешно сохранёнными данными; дальнейший ввод начинает новую серию. Новая правка до истечения 30 секунд продолжает серию и начинает отсчёт паузы заново, если другая согласованная граница ещё не завершила серию. Чтение и повторное автосохранение неизменившихся данных не сдвигают эту границу. Завершение редактирования, смена участника и остальные согласованные границы могут завершить серию раньше.
- Если после успешного автосохранения приложение или клиент редактирования неожиданно завершился до фиксации видимой версии, после перезапуска прежняя серия завершается отдельной видимой версией с последними успешно сохранёнными заголовком и описанием этой серии. Дальнейший ввод начинает новую серию даже при быстром перезапуске тем же участником. Повторные перезапуски без новых правок не создают дубликатов или пустых версий; уже завершённая серия повторно не фиксируется.
- Каждая отдельная прикладная команда, успешно изменившая заголовок или описание карточки, фиксирует свою видимую версию при сохранении результата. Две отдельные команды одного агента подряд создают две версии с состоянием обоих полей после каждого шага, даже без существенной паузы. Одна команда, изменившая оба поля, создаёт одну версию. Запись заголовка, описания и соответствующей версии должна быть согласованной.
- Дискретная прикладная команда и автосохранение непрерывного ввода — разные логические действия. Несколько автосохранений внутри одной серии не превращаются в отдельные видимые версии из-за этого правила. Одна и та же дискретная команда имеет одинаковую границу истории для человека и агента через интерфейс, HTTP и CLI; тип клиента сам по себе не выбирает правила истории.
- Правило относится к сохранённым изменениям заголовка и описания. Чтение и отклонённый запрос сохранения сами не создают видимую версию и не меняют участника открытой серии. Временно пустой обязательный заголовок остаётся несохранённым вводом и не попадает в историю как успешно записанная версия. Все устаревшие команды изменения карточки, включая восстановление, отклоняются по единой проверке актуальности заголовка, описания, тегов, выполнения, положения и состояния активна/в корзине по ADR-0007. Состав видимой версии остаётся заголовком и описанием; дополнительные предусловия операций и условия команд других объектов проектируются в DEC-003.
- Границы и содержимое версий определяются общими прикладными операциями Rust-ядра по авторитетному локальному состоянию. Правило одинаково для интерфейса, HTTP и CLI на Windows/Android. Видимая история остаётся общей для пространства и синхронизируется по согласованным правилам.

## Границы и технические вопросы

Решение касается последовательно сохранённых правок. Независимые изменения на устройствах без связи сохраняются по правилам синхронизации и конфликтов; их порядок не выводится из времени прихода или часов устройства. Группировка не разрешает текстовые конфликты автоматически.

Способ определения участника и сессии, вкладок и устройств проектируется в общем ядре и контракте доступа. Сам выбор HTTP или CLI не определяет участника. Точные идентификаторы, доверенный контекст вызова и согласованная запись границы серии/истории с автосохранением проверяются в P03/P04. Смена участника не даёт дополнительных прав записи.

Логическая команда отличается от сетевой попытки её доставки. Создание и изменения существующей карточки, включая восстановление версии, имеют безопасные повторы по ADR-0008: один идентификатор с неизменными операцией, целью, параметрами и исходным условием актуальности обозначает повтор той же команды. Уже выполненная команда возвращает свой результат без новой версии или границы серии и без отмены позднейших правок. Чтение и отклонённая команда также не создают версий. Способ идентификации команды и серии, хранение результатов и техническое согласование записи проектируются в P03/P04.

Частота автосохранения остаётся открытой в DEC-004; интервал существенной паузы подтверждён — 30 секунд без новых правок. Состав версии подтверждён: заголовок и описание вместе. Поведение восстановления подтверждено: новая правка и новая видимая версия с сохранением прежней истории. После неожиданной остановки сохранённая незавершённая серия завершается, дальнейший ввод начинает новую. Формат хранения, идентификация завершившейся сессии и технический механизм согласованной фиксации после сбоя проектируются отдельно в P03/P04. Технический отсчёт паузы и обработка задержек автосохранения и фоновых ограничений Android проверяются при реализации; версии содержат успешно сохранённые данные по общим правилам ошибок записи.

Граница серии восстанавливается по её сохранённым данным через общее ядро; текущее авторитетное состояние и более новые правки других клиентов сохраняются по общим правилам. Завершение серии применяется также при закрытии или сбое вкладки Windows и остановке APK Android. Последние успешно сохранённые данные остаются надёжными; выбранный риск потери несохранённого ввода с пустым обязательным заголовком не расширяется. Обнаружение завершившейся сессии и повторный запуск после сбоя во время самой фиксации проверяются технически; отдельные технические шаги не должны создавать лишние пользовательские версии.

Восстановление выполняется через общие прикладные операции с теми же правами и применимыми проверками актуальности и конфликтов. Оно синхронизируется как новая сохранённая правка; независимые изменения на другом устройстве сохраняют согласованные правила конфликтов. Ошибка записи или отклонённая команда не меняют текущую карточку и не создают ложную версию. При неизвестном результате восстановления действуют ограниченные автоматические, затем ручной повтор той же команды по ADR-0008; одна логическая команда фиксирует одну версию независимо от числа доставок. Восстановление версии, как и остальные изменения существующей карточки, использует единую проверку актуальности её заголовка, описания, тегов, выполнения, положения и состояния активна/в корзине по ADR-0007; дополнительные предусловия операций и условия команд других объектов проектируются в DEC-003.

## Проверка и правила проекта

Уточнён сценарий 21 и A21: несколько автосохранений одного участника группируются; последовательные успешные правки «человек → агент → человек» без существенных пауз дают отдельную версию для каждого этапа с доступом к соответствующему тексту. Последний этап завершается обычной границей серии. Новая серия человека не поглощает его старую серию или этап агента. Чтение и отклонённый устаревший запрос не создают ложную границу. Проверить общий результат через интерфейс, HTTP и CLI, перезапуск после фиксации версий и передачу истории на другое устройство. P04/P05; все критерии сохраняют `not_run`.

Две отдельные команды одного агента, последовательно добавляющие абзац и меняющие формулировку, сохраняют две видимые версии с промежуточным и итоговым текстом сразу после успешных команд. Проверить тот же результат для дискретных команд человека, группировку автосохранений непрерывного ввода, перезапуск, передачу истории на другое устройство и отсутствие версии от отклонённой команды. При сочетании смены участника и отдельной команды границы не создают дополнительных пустых версий. Ошибка записи не оставляет новую версию без соответствующей сохранённой правки или успешный результат без его версии.

Проверить изменение только заголовка при неизменном описании, только описания при неизменном заголовке и обоих полей одной командой. Каждая версия содержит соответствующую пару из одного сохранённого состояния; одна команда не даёт две версии по числу полей. Две отдельные команды переименования дают две версии. После перезапуска и обмена прежние заголовок и описание доступны для просмотра и восстановления через общий API на обеих платформах. Временно пустой заголовок и ошибка записи не создают ложную версию; последняя успешно сохранённая пара и её история сохраняются. Группировка непрерывного ввода и граница при смене участника применяются также к переименованию.

Сценарий 54 и A54: создать три версии с различающимися заголовком и описанием, восстановить первую и получить четвёртую с её парой полей, сохранив все прежние версии. Затем восстановить третью и получить пятую, вернув состояние до первого восстановления. Проверить отсутствие группировки восстановления с соседним непрерывным вводом, сохранность карточки и истории при отказе или ошибке записи, результат после перезапуска и обмена. Интерфейс, HTTP и CLI на Windows/Android используют одну прикладную операцию; проверка общего API входит в P04, паритет в P05, обмен в P06. A54 сохраняет `not_run`.

Сценарий 21 и A21 дополнены остановкой после нескольких успешных автосохранений до завершения серии. После быстрого перезапуска доступна одна версия с последней сохранённой парой полей прежней серии. Дальнейший ввод тем же участником образует новую серию; её завершение не поглощает прежнюю версию. Проверить повторные перезапуски без ввода, уже завершённую серию, сбой во время её фиксации и сохранность более новых правок другого клиента. Охват: вкладка Windows, APK Android, общий API и передача истории. Риск несохранённого пустого заголовка проверяется отдельно по A33; A21 остаётся `not_run`.

Для интервала паузы в сценарии 21/A21 проверить на управляемом отсчёте: при 29 секундах без других границ серия остаётся открытой; новая правка до 30 секунд продолжает её и начинает новый отсчёт. При достижении 30 секунд серия завершается одной видимой версией, дальнейший ввод начинает новую. Длительное отсутствие правок не порождает дополнительных версий; чтение и повторные автосохранения неизменившегося содержимого не откладывают границу. Проверить оба поля, общий результат интерфейса/HTTP/CLI на Windows/Android и сохранение остальных границ. Интервал группировки не задаёт частоту автосохранения.

Документация отражает выбор. Сохранённые версии позволяют посмотреть и восстановить предыдущие заголовок и описание по общим правилам; единая отмена серии действий не добавляется. Общий API человека и агента, паритет платформ и единое авторитетное локальное состояние сохраняются как требования. Реализации и продуктовой приёмки пока нет.
