# Теги через общий API

Используйте тот же Service через HTTP `/v1/commands/<operation>`, CLI или Tauri IPC;
прямая запись в SQLite не является API. JSON-контракт и клиент выведены из Rust.
`tag.read/list` требуют Read, изменения — ReadWrite точного пространства.
Действующие права, срок и отзыв проверяются также перед replay.

| Команда | Параметры |
| --- | --- |
| `tag.create` | `space`, новый `tag`, `name` |
| `tag.read` | `space`, `tag` |
| `tag.list` | `space`, `include_deleted` |
| `tag.rename` | `space`, `tag`, `name`, `expected` из TagSnapshot |
| `tag.delete` | `space`, `tag`, `expected` из TagSnapshot |
| `card.set_tag` | `space`, `card`, `tag`, `present`, `expected` карточки, `expected_tag` тега |

TagSnapshot содержит `space`, `tag`, варианты `names`, `state`:
`active/deleted/conflicted`, причинную `version`. Список отсортирован общим ядром.
`include_deleted=true` и `tag.read` позволяют проверить техническую отметку
удаления; это не корзина и не возможность восстановления.

```ts
import { newTagId, prepare } from "../../client/commands";
const tag = newTagId();
const create = await prepare(subject, "tag.create", { space, tag, name: "Работа" }, store);
await client.deliver(create);
// Затем свежие card.read и tag.read с новыми ID, а не старые receipts.
const assign = await prepare(subject, "card.set_tag", {
  space, card, tag, present: true,
  expected: cardSnapshot.version, expected_tag: tagSnapshot.version,
}, store);
await client.deliver(assign);
```

Для снятия используйте новую команду с `present:false` и актуальными версиями.
Noop не меняет доменную версию, но проверяет исходные условия. Не заменяйте набор
тегов целиком. Сохраняйте исходные ID/версии/имя/флаг в намерении до доставки;
при неизвестном исходе повторяется точное намерение. `stale_state` требует
свежего чтения и нового решения, а не автоматической подмены expected.

Имена сравниваются Unicode White_Space trim + канонический full case folding
с NFC-ключом, независимо от локали. Исходное имя сохраняется. Занятое имя даёт
`conflict`, пустое — `invalid_request`. Переименование не объединяет теги.
Различие е/ё, внутренние пробелы и диакритика сохраняются.

`tag.delete` атомарно снимает назначения в активных карточках и корзине, сохраняя
карточки. Новые/снятые назначения делают подготовленное удаление устаревшим;
токены также консервативно учитывают корни имён пространства. Новый тег с прежним
именем получает новый ID; старый ID занят отметкой удаления. `tag.restore` нет.
Повтор старого успешного назначения возвращает старый receipt и не назначает тег
снова после снятия/удаления. Для текущего состояния нужны новые read-команды.

Собственные конфликты карточки блокируют обычные изменения. Конфликт только
имени тега блокирует его назначение/снятие, сохраняя правки карточки и работу
с другими тегами. Общий UI P05.06 вызывает эти же команды без отдельной модели
данных: список тегов пространства, назначения в карточке и подписи на доске
строятся из свежих TagSnapshot/CardSnapshot. Имя не нормализуется клиентом.
При stale новый запрос готовится только после нового явного решения; старый
receipt при повторе не становится текущим состоянием. Продуктовые решения/обмен — P06.

Независимые создания одноимённых тегов одного пространства объединяются
причинной проекцией (P06.07.1). `tag.read` по любому исходному ID возвращает
представляющий `tag`; используйте его из свежего snapshot. `tag.list`, содержимое
пространства и `CardSnapshot.tags` показывают группу один раз. Исходные ID также
принимаются `tag.rename/delete` и `card.set_tag`, с актуальными версиями группы
и карточки. Receipt остаётся исходным, даже если его ID позже стал alias.
Минимальный исходный ID представляет группу; третье независимое создание может
изменить этот ID, поэтому не считайте старый список актуальным после обмена.
Выбранное написание принадлежит исходным именам; последующее переименование
не отменяется доставкой уже учтённых созданий. Коллизии переименований и поздний
мост не объединяются. Решения позднего моста и назначения/снятия S05
описываются ниже вместе с коллизиями имён и удалением против назначения P06.08.

`card.inspect_tags {space, card}` возвращает `card` и `assignments` с `tag` и
`values` каждой сохранённой связи. `[false,true]` — спорное назначение.
`card.resolve_tag {space, card, tag, present, expected, expected_tag}` выбирает
один вариант этой связи с версиями свежей карточки и тега. Принимается alias;
другие связи, поля и конфликты не меняются. Обычная `card.set_tag` конфликт не
разрешает. Оба решения доступны, последующее назначение/снятие обратимо.
Группа удаления контейнера, спорные родители и конфликтующий тег блокируют
решение. Для отдельной карточки выбор назначения сохраняет её состояние корзины.

Для позднего моста `TagSnapshot.name_group` содержит полный набор исходных ID;
при отсутствии группы поле опущено. Прочитайте `tag.list` и передайте
`tag.resolve_names {space, tag, names:[{tag,name,expected}, ...]}` с каждым ID
группы, отдельной свежей версией и разными свободными именами. Все имена
проверяются и сохраняются атомарно. Включите уже переименованный тег группы.
Назначения и ID сохраняются; после решения доступны обычные переименования.
Команда также разрешает коллизии двух переименований и переименования против
создания. Используйте точный полный `name_group` из свежего snapshot; он может
включать прежних участников уже разрешавшегося конфликта. Для нескольких вариантов
одного имени группа содержит один представляющий ID. При aliases запись охватывает
все исходные объекты, назначения сохраняются.

При `TagSnapshot.deletion_conflict=true` используйте
`tag.resolve_deletion {space, tag, keep, expected}`. `keep:true` сохраняет тег со
старыми и независимыми назначениями, `keep:false` подтверждает удаление со снятием
всех назначений. Принимается alias, `expected` — свежая версия тега, учитывающая
его связи. Это явное решение существующего конфликта, не `restore` удалённого тега.
До решения затронутые карточки заблокированы; решение не снимает их собственные
конфликты текста/места/прочих связей. Спорные имена разрешите затем отдельно.
Права ReadWrite, активное пространство, срок/отзыв, stale и replay проверяет общий
Service. [ADR-0072](../architecture/decisions/0072-tag-name-and-deletion-collisions.md).

Read-команда требует Read, оба решения — ReadWrite пространства. Stale требует
перечитывания и нового явного выбора; не подставляйте версии автоматически.
При неизвестном исходе повторяйте точное сохранённое намерение. Receipt не
отменяет последующие правки. Разные независимые решения дают новый конфликт,
одинаковые сходятся. [ADR-0071](../architecture/decisions/0071-tag-conflict-resolution.md).

Запускайте базу штатным startup. Пока весь план не завершён, действует одна
стартовая схема v1 по ADR-0047; прежние базы разработки отклоняются без записи.
Не сбрасывайте базу ради запуска и не используйте старый writer.
