# ADR-0002: Automerge для Rust как основа синхронизации

Дата: 2026-10-26.

Статус: принято разработчиком. Техническая проверка ZeDone ещё не выполнена.

## Контекст

Разработкой ZeDone занимается AI-агент. При выборе основы синхронизации приоритетны уменьшение объёма собственной сложной логики, понятная документация, ограниченная область интеграции и возможность автоматической проверки.

Ранее планировалось сравнить два Rust-прототипа: композицию компонентов причинных версий отдельных полей и Automerge. После обсуждения разработчик явно выбрал Automerge.

## Решение

- Основа синхронизации — Automerge для Rust. Конкретная совместимая версия закрепляется при подготовке прототипа.
- Обязательное сравнение двух реализаций заменяется ограниченным прототипом выбранного Automerge в P02. Модель из отдельных компонентов, например MVReg из crdts, остаётся рассмотренной альтернативой и не входит в выбранный стек. При препятствующих обязательным требованиям ограничениях выбор пересматривается по результатам проверки с отдельной фиксацией основания.
- Использование Automerge сосредотачивается в одном внутреннем модуле общего Rust-ядра. Интерфейс, HTTP и CLI вызывают прикладные операции ядра, а не независимо реализуют работу с библиотекой.
- SQLite остаётся авторитетным локальным хранилищем. Формат размещения документов и изменений Automerge, поисковые представления и согласованная фиксация данных проектируются и проверяются в P02/P03; независимо изменяемые копии состояния не допускаются.

## Основание

Automerge предоставляет модель документов, учёт изменений и протокол обмена. Ожидается, что готовая основа уменьшит объём сложного кода, который агент должен правильно написать и сопровождать, по сравнению с собственной композицией отдельных компонентов. Это инженерная оценка; измерений частоты ошибок AI-агентов на ZeDone нет.

У проекта есть материалы для LLM и документация Rust API. При реализации агент использует документацию закреплённой Rust-версии; примеры JavaScript не считаются подтверждением наличия тех же методов и поведения в Rust.

## Сохранение правил ZeDone и проверка

- Разные независимые значения одного поля показываются как конфликт. Для таких полей нужны все конкурирующие значения через ReadDoc::get_all(); одиночное значение обычного чтения не считается пользовательским разрешением конфликта.
- Markdown остаётся одним полем с ручным разрешением независимых текстов. Автоматическое посимвольное объединение текста не добавляется.
- Прикладные правила порядка, перемещения, имён, удаления, корзины, восстановления и блокировок сохраняются. Наличие стандартных структур Automerge само по себе не подтверждает выполнение этих правил.
- Прототип проверяет повторы, перестановки и обрывы обмена, согласованную запись с SQLite и повторный запуск, возвращение долго отключённого устройства, снимки и восстановление, очистку пользовательской истории и безопасное сокращение технических данных. A49 проверяет автоматическое объединение независимо созданных одноимённых тегов со всеми назначениями. A52 проверяет явный конфликт при независимом переименовании двух существующих тегов в одно имя с сохранением идентификаторов и назначений и выбором разных имён, доступностью четырёх согласованных изменений карточки при спорном только имени тега и временным запретом назначения/снятия спорных тегов до выбора разных имён. A53 проверяет те же правила при переименовании существующего тега против независимого создания нового тега с тем же именем; [ADR-0012](0012-tag-rename-conflicts.md).
- Измеряются память, дисковый объём и его рост при автосохранении, загрузка и обмен на Windows и Android. Численные бюджеты и точная модель данных ещё определяются.

Выбор сделан до технической проверки приложения; пригодность для всех требований ZeDone и снижение ошибок агента пока не доказаны. P02, T05 и S10 остаются непройденными. Обратимость с согласованными исключениями, общий API человека и агента, паритет платформ, единое авторитетное локальное состояние и запрет собственного unsafe в ядре, хранении и синхронизации сохраняются.

## Начальная реализация

Начальный срез P02.01 использует Automerge 0.12.0: полный документ, локальный
actor ID и долговечный sync state сохраняются одной транзакцией в изолированной
SQLite. Это проверяемая временная модель; окончательная схема продукта,
пригодность конфликтов и общий вывод P02 остаются открытыми. Команды и границы —
[описание прототипа](../../development/automerge-prototype.md), результаты —
[EV-025](../../agent/verification/EV-025-automerge-persistence.md).

P02.02 уточняет временную модель поля: каждое присваивание — новый неизменяемый
Map с целым скалярным текстом в `value`. `get_all()` читает все присваивания с их
ID; разные строки требуют выбора, одинаковые строки сохраняют идентичности без
ложного конфликта. Решение проверяет актуальность прочитанного состояния и
создаёт новый Map, в том числе при выборе одного из прежних текстов.

Причина — штатная оптимизация scalar `put` в Automerge 0.12.0: выбор видимого
победителя может только удалить другие операции, сохранив прежнюю идентичность
выбранного значения. При конкурентном решении или последующей независимой правке
это не гарантирует сохранение обоих решений ZeDone. Новый `put_object` выражает
каждое решение отдельным присваиванием без изменения зависимости; объект
присваивания после создания не редактируется. Проверки обоих исходных вариантов,
конкурирующих решений, повторов, перестановок изменений и перезапусков —
[EV-026](../../agent/verification/EV-026-automerge-conflicts.md), BUG-003.

Это техническая модель прототипа, не новый продуктовый договор. Дополнительные
объекты и история требуют измерений P02.06; итоговая схема и DEC-002 не закрыты.
Перестановки проверяются на наборе изменений; `sync` Automerge требует надёжный
упорядоченный поток одной сессии, что учитывается при проектировании P06.

## Идентичность контейнеров

P02.03.1 расширяет пробник фиксированной иерархией пространства/колонок/карточки.
Объекты Map сохраняют Object ID независимо от названий; связи используют эти ID.
Конфликт названия блокирует обычную правку самого контейнера, сохраняя доступ
к содержимому с его собственными блокировками. Явный выбор проверяет состояние
выбранного объекта, а не heads всего документа: независимая правка содержимого
не меняет прочитанное название контейнера. Все варианты и конкурирующие решения
используют прежнюю модель присваиваний. Это ещё не продуктовая схема/генератор ID;
порядок, перемещения и сортировка пространств — P02.03.2, удаления — P02.05.
Результаты и ограничения — [EV-027](../../agent/verification/EV-027-automerge-containers.md).

## Порядок в прототипе P02.03.2

Пробник сохраняет колонку и ранг карточки одним неизменяемым присваиванием
`{parent, rank}`. Независимые положения читаются целиком через `get_all`;
разные значения требуют явного выбора, одинаковые не создают ложного конфликта.
При конфликте объект один раз попадает в группу конфликтов пространства вместо
спорных позиций; собственные конфликты не распространяются на содержимое.
Выбор одного поля сохраняет блокировки других конфликтующих полей объекта.

Лексикографический ранг из пар `(u32, Object ID)` выделяется между соседями,
при необходимости удлиняется. Object ID даёт устойчивый порядок разных объектов
в одном промежутке, не требуя ручного выбора или переиндексации соседей.
Сортировка пространств в пробнике: группа конфликтующих названий по ID,
затем точная строка Unicode и ID при равенстве. Это временные технические
выборы модели; продуктовые API/поиск и границы документов не определяются ими.
Рост путей/истории и память требуют P02.06, пригодность T05/DEC-002 не закрыта.
Команды, доказательства и ограничения —
[описание прототипа](../../development/automerge-prototype.md) и
[EV-029](../../agent/verification/EV-029-automerge-order.md).

## Назначения в прототипе P02.04.1

Для фиксированных тегов состояние каждой связи карточка–тег использует
тот же регистр неизменяемых присваиваний. Связь адресуется парой Object ID;
разные теги не заменяют весь набор назначений карточки. Снятие — явное значение
регистра, не физическое удаление ключа. Поэтому снятие против независимого
снятия и повторного назначения сохраняет оба варианта для явного решения S05.
Выбор проверяет состояние выбранной карточки и не снимает остальные её конфликты.

Это ограниченная проверка назначений, не решение об идентичности объединённых
тегов, Unicode, коллизиях имён или удалении самого тега. Эти части проверяются
в P02.04.2/.3; продуктовая схема и техническая пригодность DEC-002 остаются
открытыми. Проверки/ограничения — [EV-030](../../agent/verification/EV-030-tag-assignments.md).

## Идентичность в прототипе P02.04.2.1

Независимые одноимённые создания одного пространства сохраняют исходные Object ID
как адреса. Общая проекция объединяет только причинно независимые создания,
используя неизменяемое исходное имя и историческое чтение по heads до создания.
Причинно следующее создание освободившегося имени остаётся отдельным тегом;
совпадение текущих имён после переименования не является основанием для слияния.
Неоднозначный поздний «мост» к уже известным разным тегам сохраняется без
автослияния с охранным отказом обычным операциям; окончательное правило/решение
этого случая остаётся в DEC-005 и следующем срезе коллизий.

Регистры имён/назначений по разным исходным ID читаются совместно с причинным
приоритетом: присваивание содержит heads до записи, `get_at` определяет известные
ему прежние присваивания. Поздняя правка перекрывает их без удаления истории,
неизвестная независимая правка остаётся вариантом. Для равных ключей имени
первое строковое ID присваивания задаёт одно исходное написание; ID-представитель
группы тоже вычисляется, ссылки не переписываются. Все исходные ID сохраняются.

Это временная техническая проверка A20/A49, не итоговая модель продукта или
Unicode-договор. Рост причинных метаданных/стоимость исторических чтений требуют
P02.06. Явные решения коллизий и удаление тега остаются P02.04.2.2/P02.04.3;
результаты и ограничения — [EV-032](../../agent/verification/EV-032-tag-identities.md).
