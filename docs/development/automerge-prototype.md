# Прототип Automerge — хранение, поля, порядок, теги и корзина P02

Этот срез проверяет сохранение и конфликты на синтетических данных, без нового экрана или
сетевого API. Команды одинаковы для разработчика и агента. Требуются уже
подготовленные инструменты из Quick Start; установка не входит в проверку.

Из `prototypes/`:

```powershell
bun run check:automerge
# ANDROID_SERIAL указывает только на запущенный тестовый emulator-NNNN.
# ANDROID_HOME и NDK_HOME указывают на подготовленные SDK и закреплённый NDK.
bun run check:automerge --android
```

Первая команда собирает проверочный CLI и запускает `prepare`, `resume`,
`conflicts-prepare`, `conflicts-resolve`, `conflicts-resume`, `containers-prepare`,
`containers-resolve`, `containers-resume`, `order-prepare`, `order-resolve`,
`order-resume`, `tags-prepare`, `tags-resolve`, `tags-resume`, `identity-prepare`,
`identity-rename`, `identity-resume`, а также фазы имён, поздних созданий,
удаления тегов и корзины (см. соответствующие разделы ниже) отдельными процессами
во временном каталоге. Вторая собирает x86_64 и arm64,
запускает те же фазы и Rust-тесты пробника на x86_64 Android-эмуляторе. Физические
устройства драйвер отвергает. Временные каталоги удаляются в `finally`;
эмулятор запускает и останавливает вызывающая сторона.

`bun run check` включает проверку процессов хоста. Android CI использует
`scripts/check-android-ci.mjs` внутри существующего жизненного цикла тестового
AVD, затем проверяет прежний APK. Вывод проверок сохранять в игнорируемой
`docs/reports/`, без локальных путей и сведений устройств в общей документации.

## Проверяемая модель

Закреплён [Automerge для Rust 0.12.0](https://docs.rs/automerge/0.12.0/automerge/)
(MIT, MSRV 1.90). Библиотека используется только во внутреннем модуле
`core/src/automerge_probe.rs` и его дочерних модулях;
CLI вызывает его `run`, не редактирует SQLite напрямую. Собственный unsafe
запрещён на уровне общего ядра и CLI. Это временный внутренний прототип,
не продуктовые команды для HTTP/IPC/CLI.

Файл `automerge-probe.sqlite3` содержит строки A/B — две синтетические реплики
одного пространства, представленного одним документом с полями `title` и `text`.
Для сценария конфликтов используется отдельный `automerge-conflicts.sqlite3`.
P02.02 уточняет модель P02.01: каждое присваивание поля — новый неизменяемый Map
с единственным скалярным `value`. Markdown остаётся целым полем, не Text CRDT.
P02.03.1 добавляет отдельную фиксированную иерархию контейнеров, описанную ниже.
Каждая строка одной SQLite-транзакцией сохраняет полный документ `save()`,
локальный actor ID и `sync::State::encode()` для одного фиксированного соседа.
Обе реплики в одном файле — удобство драйвера; общей транзакции двух устройств
нет. Конкурентная запись несколькими процессами не является контрактом пробника.

`load()` восстанавливает документ, затем явно возвращается сохранённый actor ID.
Встроенный `State::encode()` сохраняет общие подтверждённые heads; временные
флаги соединения, включая `in_flight`, после загрузки сбрасываются библиотекой.
Сравнение после перезапуска проверяет actor, heads, число изменений, поля и
долговечные сведения соседа. `expected.json` — только контрольный результат,
не источник состояния и не резервная копия. Новая сессия должна доставить
правку после потери сообщения предыдущего процесса.

Обратное редактирование сохраняет историю. Удаление/возврат A из снимка в памяти
не затрагивает B; это проверка обратимости пробника, не продуктовая корзина или
алгоритм восстановления резервной копии. Проверяются отказ SQLite после UPDATE,
блокировка базы и повреждение документа/сведений обмена: прежнее состояние не
заменяется пустым, ошибочная запись не подтверждается.

## Конфликты и решения

`get_all()` возвращает все присваивания поля с ID операций. Сравнение текстов
точное, без введения новых правил Unicode/нормализации. Несколько присваиваний
одинаковой строки не требуют ручного выбора, но их ID сохраняются. Разные
строки создают конфликт; обычная правка любого поля такой карточки запрещена.

Выбор существующего варианта и ввод объединённого текста выполняются одним
методом `resolve`: он сравнивает прочитанные heads и варианты всей синтетической
карточки с текущими, затем создаёт новое присваивание. Новая известная версия
отклоняет устаревший выбор без изменения документа. Ещё не полученная независимая
версия остаётся конкурентной при последующем обмене. Два разных независимых
решения дают новый конфликт; после выбора обоих полей обычные правки доступны.
Прежние значения остаются в истории документа; это не пользовательская история P04.

Новая Map-идентичность необходима: в Automerge 0.12.0 `put` прежней скалярной
строки, совпадающей с видимым победителем, может лишь удалить конкурентов,
сохранив старое присваивание. Два независимых решения тогда могут не сохраниться
как два варианта. `put_object` всегда создаёт отдельное присваивание; его `value`
позже не редактируется. Это модель поверх штатных операций Automerge без патча
зависимости. Цена дополнительных объектов/роста истории измеряется в P02.06.

Три `conflicts-*` фазы проверяют независимые поля, спор заголовка/Markdown,
сохранение конфликта, перезапуск, два автономных решения, ещё один перезапуск,
новый конфликт решений и окончательный выбор с обратной правкой.
`conflicts-expected.json` сравнивает весь набор вариантов/ID, heads и историю
после перезапуска и не используется для восстановления данных.

Rust-тесты дополнительно проверяют оба выбора исходного текста, устаревший
выбор, позднюю независимую правку, отказ SQLite и совпадающие строки. Для полного
набора изменений с конкурирующими решениями проверяются все циклические сдвиги
прямого и обратного порядка с двукратной доставкой каждого изменения и сохранением
результата в SQLite. Это проверка `apply_changes`, не перестановка сообщений sync.
Штатный sync требует надёжный упорядоченный поток; после обрыва создаётся новая
сессия. Буферизация/дедупликация сетевых сообщений продуктового транспорта — P06.

Работа в APK/WebView, полномочия, запись несколькими процессами, аварийное
завершение в середине commit, физический arm64, рост/память и продуктовые форматы
этой проверкой не подтверждаются. Промежуточный формат пробника не является
выпущенным форматом продукта; миграция прежних временных баз не обещается.
Следующие границы — P02.04–P02.06 и P03.
Доказательства: [EV-025](../agent/verification/EV-025-automerge-persistence.md),
[EV-026](../agent/verification/EV-026-automerge-conflicts.md),
[EV-027](../agent/verification/EV-027-automerge-containers.md),
[EV-029](../agent/verification/EV-029-automerge-order.md).

## Идентичность и названия контейнеров

`automerge-containers.sqlite3` хранит другой синтетический документ A/B: одно
пространство, две одноимённые колонки и карточку в первой колонке. Фиксированные
ключи `space`/`left`/`right`/`card` адресуют подготовленные объекты Map, их
Automerge Object ID используются как идентичности и в связях `parent`.
Имена не используются для адресации или объединения объектов. Это ограниченный
пробник, без генератора продуктовых ID или операций создания/удаления; подготовка
всей иерархии атомарна. Генерация произвольных объектов и удаления — следующие шаги.

Названия и текст карточки используют те же неизменяемые присваивания, что и
P02.02. Конфликт названия сохраняет один объект со всеми вариантами, не скрывает
его содержимое и не заменяет родительские связи. Обычная правка спорного объекта
отклоняется; независимые правки дочерней колонки/карточки доступны, если у неё
нет собственных конфликтов. Совпадающие строки не создают ложного конфликта,
но идентичности присваиваний сохраняются.

Явный выбор сравнивает ID, связи и все поля самого выбранного объекта с ранее
прочитанными. Изменение содержимого не делает неизменившееся название устаревшим;
новое присваивание самого объекта делает. Выбор создаёт новое присваивание,
конкурирующие решения или поздняя независимая правка дают новый конфликт.
Обратная правка не удаляет прежнюю историю Automerge.

Три `containers-*` фазы сохраняют конфликт и автономные решения между отдельными
процессами. `containers-expected.json` проверяет actor, heads, историю, peer,
все варианты/ID и связи; он не восстанавливает данные. Rust-тесты также проверяют
собственный конфликт вложенной карточки, ошибочный/устаревший выбор, отказ SQLite
после UPDATE и дублированную/переставленную доставку полного набора изменений.

Порядок карточек/колонок, перемещения и порядок списка пространств с группой
«Конфликты названий» проверяет следующий изолированный сценарий. Продуктовые
список/поиск/UI/HTTP/IPC пока не добавлены; приёмка S03 остаётся частичной.

## Порядок и перемещения

`automerge-order.sqlite3` хранит фиксированную иерархию из четырёх пространств,
пяти колонок и четырёх карточек. Все они находятся в одном синтетическом
документе только для проверки порядка; это не решение о границах документов
продукта. Object ID, домашнее пространство, имена и текст сохраняются при
перемещении. Домашнее пространство неизменно: перенос между пространствами
отклоняется до изменения документа.

Положение — одно неизменяемое присваивание с канонической JSON-строкой
`{parent, rank}`. Поэтому независимые переносы в разные колонки сохраняют два
целых варианта, не смешивая колонку одного переноса с рангом другого. Разные
позиции одной карточки/колонки требуют выбора; совпадающие позиции сохраняют
ID присваиваний без ложного конфликта. Спорные объекты исключаются из обычного
порядка и один раз входят в группу конфликтов своего пространства. Содержимое
спорной колонки остаётся доступным. Обычная правка самого объекта блокируется
любым его конфликтом; выбор одного поля не снимает конфликт остальных.

Ранг — лексикографический путь пар `(u32, Object ID)`. Между соседними рангами
выбирается середина доступного числового промежутка; при исчерпании промежутка
путь удлиняется. ID задаёт одинаковый на устройствах порядок разных объектов,
поставленных между одними соседями. Можно затем вставить объект и между ними.
Плавающая точка, переиндексация соседей и зависимость от порядка доставки не
используются. Команда проверяет смежность соседей после исключения перемещаемого
объекта. Выбор конфликта дополнительно сравнивает все поля выбранного объекта
с прочитанным состоянием; правка его содержимого не меняет выбор колонки.
Продуктовые токены актуальности и повторы команд остаются в P03/P04.

Порядок пространств вычисляется из того же документа: сначала конфликтующие
названия по Object ID, затем остальные по точной строке Unicode с Object ID
при равных именах. Локаль ОС, регистр и нормализация не влияют на этот временный
порядок. После решения имя возвращает пространство в обычную часть списка.
Это технический выбор пробника; продуктовые сравнение/поиск и проекции API
проверяются отдельно в P03–P06.

Три `order-*` фазы сохраняют исходные конфликты, автономные решения и итоговый
выбор/обратное перемещение между отдельными процессами. `order-expected.json`
сравнивает actor, peer, heads, историю, все варианты/ID, принадлежность и
вычисленный порядок; не восстанавливает SQLite. Rust-тесты проверяют также
отказ после UPDATE, неверную колонку/соседей, устаревший выбор, сочетание
текстового/позиционного конфликтов, позднее перемещение и доставку изменений
с повторами/перестановками. Длина рангов, рост истории, память и масштаб ещё
не измерены; компактирование/удаления не добавлены. Они относятся к P02.05/06.

## Назначения и снятие тегов

P02.04.1 добавляет `automerge-tags.sqlite3`: фиксированные два пространства,
четыре тега и три карточки. Object ID карточки и тега задают связь; одинаковое
имя тега в другом пространстве не меняет её идентичность. Назначить тег чужого
пространства или неизвестный ID нельзя. Фиксированные ключи адресуют только
объекты пробника, не определяют продуктовый формат или генератор ID.

Состояние каждой связи хранится в отдельном регистре `tag:<Object ID>` внутри
карточки. Значения `present`/`absent` — целые неизменяемые Map-присваивания
из P02.02. До первого назначения регистр пуст; отсутствие присваивания не
подменяется операцией снятия. Снятие сохраняется явным значением, а не удалением
регистра: иначе нельзя сохранить конфликт с независимым повторным назначением.
Разные теги изменяют разные регистры и объединяются без диалога; одинаковые
значения не создают ложного конфликта. Повтор уже установленного состояния
ничего не пишет; это не продуктовая гарантия повторов команды из P03.

Разные значения одной связи требуют явного выбора. Карточка сохраняет ID,
заголовок, текст, пространство и все варианты связи. Её обычная правка и любые
назначения/снятия приостановлены; другие карточки продолжают работать. Выбор
сравнивает прочитанное состояние всей карточки с текущим, включая ID операций,
и создаёт новое присваивание. Другие карточки не делают этот выбор устаревшим.
Разные автономные решения снова дают конфликт; совпадающие решения сохраняют
операции без ложного конфликта. Выбор связи не снимает собственный конфликт
текста. Смена назначения обратима тем же методом; сам тег не удаляется.

Три `tags-*` фазы сохраняют конфликт, автономные решения и итоговый выбор между
отдельными процессами. `tags-expected.json` — контроль actor, peer, heads,
истории и всех полей/ID, а не источник данных. Rust-тесты также проверяют
сохранность старых назначений, оба решения, запреты без мутации, позднее решение,
доставку полного набора изменений с повторами/перестановками и отказ SQLite
после UPDATE. Временные каталоги удаляет общий драйвер.

Это изолированный пробник без UI/HTTP/IPC и продуктовых прав. Создание/
автообъединение и последующее переименование проверяет отдельный сценарий ниже;
разрешение коллизий, удаление тега, положение/выполнение карточки с назначениями
и рост/память остаются следующими срезами. A39/S05 остаются частичными до продукта/P06.
Доказательства и ограничения — [EV-030](../agent/verification/EV-030-tag-assignments.md).

## Идентичность независимо созданных тегов

P02.04.2.1 добавляет изолированный `automerge-tag-identity.sqlite3`: два пространства,
три карточки и список динамических созданий. Map каждого создания имеет Object ID,
неизменяемые домашнее пространство, исходное имя и heads до создания. Исходные
ID не удаляются и остаются допустимыми адресами после объединения. Для одного
набора изменений общая проекция выбирает минимальный строковый Object ID группы;
добавление позднего создания может изменить этот представитель, поэтому ссылки
не переписываются на него. Авторитетны исходные объекты/регистры в документе SQLite,
а не вычисленные группы или контрольный JSON.

Автообъединение использует исходное имя и причинную независимость созданий,
проверяемую историческим чтением `get_at` по сохранённым heads. Одноимённые
создания другого пространства и причинно последующее создание освободившегося
имени не объединяются. Простого сравнения текущих имён недостаточно: оно ошибочно
слило бы два существующих тега при переименовании. Поздний «мост» независимого
создания между двумя уже известными разными тегами также не даёт автоматического
слияния: все исходные теги/назначения сохраняются, обычные операции приостановлены.
Это охранный отказ ограниченного пробника; принятое разработчиком правило
сохранения трёх разных тегов с явным выбором имён ещё требует P02.04.2.2.2; ADR-0012.

Названия и назначения используют неизменяемые Map-присваивания с `value` и heads
до записи. При чтении объединённого тега собираются регистры всех исходных ID;
присваивания, известные более позднему присваиванию, исключаются из текущего
набора через `get_at`. История сохраняется. Несколько одинаковых значений не
создают ложного конфликта; разные назначения/имена сохраняются как варианты.
Таким образом, снятие после объединения перекрывает уже известные назначения
по другим ID, а повтор старых изменений не возвращает назначение или имя.
Имена с одинаковым ключом сравнения автоматически показывают написание первого
присваивания в строковом порядке ID. Результат принадлежит введённым вариантам,
не зависит от доставки и не принуждается к нижнему регистру. Последующее
переименование, включая смену регистра, перекрывает известные исходные имена.

Временное сравнение `trim().to_lowercase()` закреплено только в этом пробнике.
Проверяются кириллица/регистр/краевые пробелы и различие «е»/«ё», без Unicode
нормализации, транслитерации или полного case folding. Политика для продукта,
точный набор краевых пробелов и размеры полей остаются открытыми в DEC-005.
Пустое/занятое имя, чужое пространство и неизвестный ID отклоняются до записи.
Выявленная коллизия имён или смешанная причинность не объединяет теги молча;
назначения/снятия спорных тегов запрещены. Собственный конфликт назначения/текста
карточки блокирует изменения всех её назначений, другие карточки доступны.
Явные решения согласованных коллизий совместно с aliases описаны ниже;
неоднозначная идентичность позднего моста остаётся P02.04.2.2.2.

Три `identity-*` фазы работают отдельными нативными процессами: независимые
создания/назначения, обмен и правка через исходные ID, затем перезапуск, доставка
старого набора и обратные изменения. `identity-expected.json` проверяет actor,
peer, heads, историю, варианты и ID; он не восстанавливает документ. Тесты также
проверяют перестановки полного набора изменений с повторной доставкой, третье
независимое создание, повторное занятие освобождённого имени, защиту от коллизий
и SQLite AFTER UPDATE ABORT. Это ещё не продуктовые команды создания/удаления:
удаление тега и его конфликт с назначением — P02.04.3; продуктовые UI/API/права,
общая Unicode-политика, масштаб/память и физический arm64 не подтверждаются.
Доказательства — [EV-032](../agent/verification/EV-032-tag-identities.md).

## Явное разрешение имён тегов

P02.04.2.2.1 проверяет оба согласованных случая ADR-0012: два независимых
переименования в одно имя и переименование против независимого создания.
Коллизия не объединяет существующие теги, не добавляет суффиксов и не меняет
назначения. `blocked` — вычисленный запрет обычных действий; он отражает
пересечение вариантов имён разных тегов и незавершённое решение позднего
создания. `creation_conflict` содержит исходные ID всей такой группы.

Выбор получает наблюдавшийся каталог имён одного пространства: исходные ID,
все варианты с ID присваиваний и причинным контекстом. Любое изменение этого
каталога делает выбор устаревшим, включая новое присваивание того же имени;
правки карточек и другого пространства выбор не инвалидируют. Это ограниченная
модель актуальности пробника, не продуктовый протокол P03.

Операция требует по одному имени для каждого тега связной группы коллизии.
Любой исходный alias допустим как адрес; два aliases одного тега не заменяют
выбор для другого. Проверяются непустота, попарная уникальность и занятость
всеми вариантами имён вне группы по общему временному сравнению.
«Все»/«Всё» допустимы, «Всё»/« ВСЁ » — нет. Все проверки предшествуют
транзакции, затем все выбранные имена записываются одним изменением Automerge
с прежними ID. SQLite сохраняет весь документ, actor и состояние обмена вместе.

Конкурирующие одинаковые решения сохраняют присваивания без ложного конфликта;
разные решения сохраняются как варианты имён. Если после обмена варианты
одного тега больше не пересекаются с именами другого, его собственный конфликт
можно разрешить отдельно; остальные конфликты остаются. Позднее неизвестное
решение не теряется из-за локального разрешения или следующего переименования.
Повтор уже известных изменений не отменяет новую правку.

Пробник карточки дополнен заголовком, описанием, флагом выполнения и колонкой
из трёх фиксированных колонок двух пространств. Это независимые регистры,
а не продуктовая модель порядка. При спорном только имени тега все четыре
поля доступны, включая обратные изменения; чужая колонка отклоняется.
Назначение/снятие спорных тегов блокируется по любому исходному ID на всех
карточках пространства. Остальные теги доступны; собственный конфликт
любого поля или назначения карточки сохраняет её общую блокировку и после
разрешения имён. Выбор имён не переписывает ни поля карточки, ни назначения.

Три фазы `names-prepare`, `names-resolve`, `names-resume` запускаются общим
CLI/драйвером отдельными процессами Windows/Android. Два изолированных файла
`automerge-names-renames.sqlite3`/`automerge-names-creation.sqlite3` проверяют
каждый случай: нерешённую коллизию с четырьмя правками карточки, автономные
решения, затем обмен, новые конфликты и окончательный выбор с обратными
действиями. `names-*-expected.json` проверяет сохранённый документ/actor/peer/
heads/историю/все поля/ID, не восстанавливает базу. Общая команда:
`bun run check:automerge` или `bun run check:automerge --android`.

Удаление тега, продуктовые UI/HTTP/IPC/права, Unicode-политика, физический
arm64 и масштаб/память остаются вне среза.
Доказательства и фактическая матрица —
[EV-033](../agent/verification/EV-033-tag-name-resolution.md).

## Позднее создание между разными тегами

P02.04.2.2.2 реализует принятое исключение ADR-0012/LOG-215: ПК переименовал
«Работа» в «Личное» и создал новый «Работа», отключённый телефон независимо
создал «Работа». Общая проекция всегда сохраняет три исходных ID раздельно.
Связная группа выбора включает все три тега, даже первый с другим текущим
именем. До полного выбора назначение/снятие всех трёх заблокировано;
четыре поля карточки доступны при отсутствии её собственных конфликтов.

Для каждого причинно неоднородного компонента созданий проверяются контексты
текущих присваиваний имён. Пока хотя бы одно присваивание не наблюдало все
создания компонента, `creation_conflict` связывает все его ID. Явный выбор
проверяет имена и записывает их одной транзакцией с общим текущим контекстом.
После этого временная связь снимается, исходные ID остаются раздельными.
Конкурирующие решения проходят обычную проверку вариантов/коллизий имён;
равные значения не блокируют, разные сохраняются для нового выбора.
Формат сохраняемого документа не меняется; отдельного флага решения в SQLite нет.

Фазы `bridge-prepare`, `bridge-resolve`, `bridge-resume` общего CLI/драйвера
проверяют нерешённую группу, автономные решения и их разрешение после обмена
в отдельных процессах. `automerge-bridge.sqlite3` — синтетическая база,
`bridge-expected.json` — только проверочный отпечаток. Обратные действия,
старые/повторные/переставленные изменения и отказ SQLite проверяются вместе;
границы платформ и доказательства — [EV-034](../agent/verification/EV-034-late-tag-creation.md).

## Удаление тега и независимое назначение

P02.04.3 использует те же исходные ID и причинные регистры. Создание тега
записывает `life=alive`; обычное удаление и выбор удаления — `life=deleted`,
выбор сохранения при конфликте — `life=alive`. Контекст решения наблюдает
текущие исходные ID и назначения. Предельные по причинности записи `life`
и положительные назначения определяют состояние: удалён, существует либо
конфликт удаления. Конкурирующие одинаковые решения не создают ложного
конфликта; разные сохраняются вариантами для нового явного выбора.

Удаление скрывает все назначения сразу одной проекцией состояния тега,
не стирая доказательства из документа. Сохраняются карточки, их поля,
колонки, другие теги и одноимённый тег другого пространства. При спорном
удалении все карточки с назначениями спорного тега блокируют обычные правки;
в диагностическом снимке карточки есть вычисленное `conflicting`.
Оба решения доступны общему Rust/CLI-пути. Выбор сравнивает наблюдавшиеся
данные тега и все его назначения; изменение другого тега или пространства
его не обесценивает. Собственный конфликт карточки сохраняется после выбора.

Отдельного восстановления тега нет (§7 спецификации). Создание с прежним
именем получает новый ID и пустые назначения. Старые ID остаются технически;
их повторная доставка не возвращает назначения. Удалённые ID не занимают
имя и не участвуют в выборе имён существующих тегов при позднем создании;
причинная раздельность исходных ID сохраняется.

Фазы `deletion-prepare`, `deletion-resolve`, `deletion-resume` добавлены
в `bun run check:automerge` и `bun run check:automerge --android`. Две
синтетические базы `automerge-deletion-{keep,delete}.sqlite3` проверяют оба
решения отдельными процессами; `deletion-*-expected.json` — отпечатки,
которые не восстанавливают данные. `life` расширяет только изолированную
фикстуру пробника, продуктового формата и миграции нет. SQLite по-прежнему
сохраняет документ/actor/peer вместе; проверяется AFTER UPDATE ABORT.

Рост истории, сканирование каталога/назначений и исторические чтения требуют
оценки P02.06 перед переносом в продукт. Полное восстановление пространства
из снимка, продуктовые UI/HTTP/IPC/права, APK/WebView, физический arm64,
полный Unicode и масштаб не входят в этот срез. Фактические результаты —
[EV-035](../agent/verification/EV-035-tag-deletion.md).

## Корзина карточки против независимой правки

P02.05.1 проверяет две фиксированные карточки в активных контейнерах.
Заголовок, текст, выполнение, целая позиция (колонка и порядок) и одно
назначение тега записываются неизменяемыми Map-присваиваниями. Обычная
правка в той же транзакции записывает `life=active`; отправка в корзину —
`life=trash`. Независимая правка против удаления оставляет оба варианта
состояния, карточка показывается в проекции `conflicts`. Просмотр данных
и явный выбор доступны, обычные правки всех её полей заблокированы;
другая карточка остаётся доступной.

Выбор корзины сохраняет независимые правки внутри карточки. Выбор активности
возвращает ту же карточку с ними на доску. Обычное восстановление из корзины
и повторное удаление сохраняют ID, поля и назначения. Команды сравнивают
наблюдавшийся снимок всей карточки; правка другой карточки не делает его
устаревшим. Отказ не пишет новый документ или ложное решение.

Разрешение состояния не разрешает собственные конфликты полей. Разрешение
поля при спорном состоянии или в корзине не восстанавливает карточку
неявно. Равные решения состояния не конфликтуют, разные и поздние остаются
вариантами. Старые и повторные изменения не возвращают уже рассмотренную
карточку на доску; ранее не виденная независимая правка создаёт новый
явный конфликт. Часы и срок отключения не выбирают победителя.

Фазы `trash-prepare`, `trash-resolve`, `trash-resume` общего CLI/драйвера
запускаются отдельными процессами. Две базы `automerge-trash-{active,trash}.sqlite3`
и проверочные отпечатки `trash-*-expected.json` проверяют оба решения,
перезапуск, обмен и обратные операции. JSON не восстанавливает данные;
источник истины — документ/actor/peer в SQLite, как в прежних пробниках.

Это ограниченная фикстура, которая не заменяет проверенные модели полного
порядка и множества тегов. Группы удаления контейнеров, окончательная
очистка, пользовательская история, HTTP/IPC/права, APK/WebView и физический
arm64 остаются следующими шагами. Матрица и реальные результаты —
[EV-036](../agent/verification/EV-036-card-trash.md).

## Корзина колонки и группа удаления

P02.05.2.1 добавляет отдельную фикстуру: одно активное пространство, две
колонки, активные и ранее удалённая карточки, независимые новые карточки.
Поля и состояния используют прежние неизменяемые Map-присваивания. Обычная
правка/создание карточки в той же транзакции подтверждает активность колонки;
независимое удаление остаётся вариантом её регистра состояния. Колонка и
активное содержимое до решения проецируются в `conflicts`, обычные правки
и создание в ней заблокированы. Другая колонка остаётся доступной.

Каждое обычное удаление получает ID группы из операции Automerge (`cycles`),
а активные карточки — ссылку `group`. Их собственный регистр `life` не
перезаписывается: корзина группы вычисляется из состояния колонки. Поэтому
ранее или независимо удалённая отдельным действием карточка остаётся в
корзине при восстановлении колонки. Обычное удаление проверяет свежесть данных
колонки и активных карточек; ранее удалённые карточки не входят в его охват.
Явный выбор при конфликте сравнивает весь показанный состав и данные.

Выбор корзины включает независимые новые активные карточки в исходную группу.
Выбор восстановления возвращает контейнер с содержимым, сохраняя собственные
состояния и конфликты карточек. Равные решения не создают ложного конфликта;
разные/поздние решения требуют нового выбора. Конкурентные обычные удаления
сохраняют оба причинных ID группы. Последующее обычное удаление начинает
новую группу; ранее удалённые объекты не переоформляются. Часы не используются.

Отдельная карточка из колонки в корзине может быть восстановлена в другую
активную колонку того же пространства с сохранением ID/полей/назначения.
Ссылка на прежнюю группу снимается, исходная колонка не восстанавливается.
Её последующее восстановление или повторное удаление не затрагивает карточку
в новой колонке. Конфликты текста, названия/порядка колонки и состояния не
разрешаются неявно выбором другого конфликта.

Общий CLI/драйвер запускает `column-trash-prepare`, `column-trash-resolve`,
`column-trash-resume` отдельными процессами на Windows/Android. Две базы
`automerge-column-trash-{active,trash}.sqlite3` проверяют оба решения,
обратные действия и одиночное восстановление в другую колонку. JSON-файлы
`column-trash-*-expected.json` — проверочные отпечатки; данные/actor/peer
читаются из SQLite и сохраняются вместе. AFTER UPDATE ABORT проверяет
отсутствие частичной записи группы и состояний.

Полный порядок/перемещения и множество тегов остаются в прежних пробниках;
этот срез проверяет целую позицию внутри колонки и одно назначение.
Пространство в корзине, вложенные группы и его предварительное восстановление —
P02.05.2.2; очистка, история, масштаб/память и продуктовые UI/HTTP/IPC/права
проверяются позднее. Новый APK/WebView и физический arm64 не проверяются.
Матрица и результаты — [EV-037](../agent/verification/EV-037-column-trash.md).
