# ADR-0056: запрос устройства и постоянное ожидание без доступа

Дата: 2026-11-14. Техническое решение P06.01.2.3, EV-099.

## Доставка и область доверия

Host-компоненты предоставляют общий процесс для человека и агента. Новый
внешний listener, формы подключения и подтверждение пока не включаются.
PairingHost::serve принимает предоставленный host сокет, сам выполняет TLS
ADR-0055 и обслуживает только request/inspect/cancel. Его закрытый HTTP router
нельзя смонтировать на прежнем plaintext listener. Команды данных,
bootstrap, подтверждение и выдача прав здесь отсутствуют.

Адрес вводится отдельно. Составной код `zd1:<invitation>:<fingerprint>:<code>`
содержит 32/64/64 строчных hex-символа и связывает приглашение с SHA-256
сертификата. Это одно представление для ручного ввода и будущего QR. Доверие
получают от создающей стороны вне проверяемого соединения; сетевое получение
или автоматическая замена pin запрещены. Клиент проверяет pin до отправки
кода и ключа. Перенаправления, прокси из окружения и plaintext fallback отсутствуют.

Канал использует HTTP/1 через hyper/tokio-rustls. Один запрос на соединение,
4096 байт тела, ограниченные HTTP buffers, пять секунд TLS handshake и десять
секунд обмена; до восьми одновременных соединений на один PairingHost. Origin
запрещён, Authorization/Content-Type однозначны. Ответы no-store. Ошибка после
отправки означает outcome_unknown, повтор сохраняет исходный запрос и секрет.

## Запрос и повтор

Запрашивающий host до отправки сохраняет независимые случайные request ID,
ключ ожидания и будущий ключ доступа в OS-слоте pending-pairing-v1. Один namespace
одновременно содержит один незавершённый запрос. Слот не заменяется при ошибке,
потере ответа или повреждении. Windows Credential Manager и Android Keystore
используют правила ADR-0055; слоты изолированы именем ключа/файла и Android AAD.
До выдачи прав будущий ключ ничего не разрешает.

Сервер получает код, verifier будущего ключа и заявленное имя устройства.
Имя — лишь подпись (1–80 Unicode-символов, не пробельная, без control),
не удостоверение личности или криптографическое доказательство типа устройства.
Код проверяется в core по domain-separated SHA-256 ADR-0054; сравнение digest
в storage использует subtle. Ключ ожидания имеет отдельный домен pending-key/v1;
он и код не попадают в обычные команды, receipts или SQLite.

Один writer lock охватывает текущие приглашение, срок, попытки, запрос и receipt.
UNIQUE(invitation) сохраняет одноразовость также после отмены. Пять неверных
корректно оформленных кодов блокируют приглашение до новой явной выдачи;
перезапуск не сбрасывает счётчик. Неизвестные/истёкшие/отменённые/использованные/
заблокированные приглашения возвращают access_denied без раскрытия причины.
Ошибочный код фиксирует счётчик успешным исходом транзакции, затем adapter
возвращает отказ. SQL/receipt/сбой до commit откатывают весь изменяющий результат.
Успешный запрос регистрирует срок в TransactionClock для проверки перед commit.

Повтор доказывает тот же ключ ожидания и код, проверяет полный исходный запрос
и возвращает исходный receipt. Новый command ID после использования приглашения
не запускает создание заново. Receipt не является текущим статусом; новое чтение
требует нового ID. Успешное ожидание не истекает вместе с приглашением: код
ограничивает момент первого приёма, а не срок уже принятого ожидания.

## Чтение, отмена и источники данных

Секрет ожидания позволяет только читать/отменять собственный запрос через TLS;
он не является access key и не даёт права подтверждения. Администратор получает
pairing.inspect/cancel/list через Service/HTTP/CLI/IPC с ManageDevices.
Отмена проверяет expected. Отмена приглашения также завершает его ожидание.
Отмена не удаляет пространства и не освобождает использованный код; повторное
подключение требует нового приглашения. После подтверждённой отмены host может
явно удалить свой pending OS-слот. Жизненный цикл слота сериализует host.

pairing_requests и failures в pairing_invitations — локальные данные SQLite v1,
вне Automerge и снимков пространств. StateVersion приглашения учитывает попытки
и использование, версия запроса — собственную и родительскую отмену.
Новая изменяемая стартовая схема и синтетический эталон следуют ADR-0047:
старые базы отклоняются без записи/сброса. Rust — источник контракта;
OpenAPI/TS/валидатор производны. Полные T09/A51 и DEC-003 остаются открытыми:
подтверждение/отклонение/права — P06.01.2.4, полная приёмка — .5, UI — P06.01.3.
