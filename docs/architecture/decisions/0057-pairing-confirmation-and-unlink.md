# ADR-0057: подтверждение подключения и обычный реестр доступа

Дата: 2026-11-15. Техническое решение P06.01.2.4, EV-100.

## Решение и атомарность

Административный Service предоставляет pairing.confirm/reject/unlink. Ожидающий
секрет не даёт ни одного из этих полномочий. Confirm требует ManageDevices и
ManageAccess; reject — ManageDevices, административная unlink — оба. Каждая
команда повторно проверяет текущего администратора до чтения receipt/запроса.
Человек и агент используют один Service через HTTP/IPC/CLI.

Confirm принимает request, expected, явные scope и expires_at_unix_ms. Права
проходят те же валидаторы, что access.issue; неизвестные пространства, пустая
область, неверный срок или повторный verifier отклоняются. Нет неявной выдачи
записи/администрирования. Отдельных политик доступа или реестра устройств нет.

В одной writer-транзакции проверяются expected и pending, создаются обычный
access principal и ключ из сохранённого verifier, фиксируются решение/связь
и receipt. Subject равен случайному request ID; коллизия с любым прежним
principal отклоняется без замены. Подтверждающий не может быть этим subject.
Секретный будущий ключ уже сохранён получателем в OS pending session;
подтверждение его не передаёт, не генерирует заново и не помещает в JSON.
Заданный срок проверяется также перед commit. Любой отказ откатывает весь состав.

## Терминальные состояния и отзыв

Отмена относится к pending, reject сохраняет отдельное отклонение. Оба исхода
не выдаются за подтверждение и не допускают последующего confirm того же запроса.
Отмена приглашения завершает только ожидание; уже выданный доступ отзывается
отдельно. Повторы возвращают исходный receipt, не подтверждают заново и не
восстанавливают отозванные права. Свежий статус требует нового command ID.

Confirmed связан с первоначальным access verifier и subject. Обычные
access.revoke/replace меняют состояние подключения на unlinked, поскольку
исходный ключ больше не активен. Текущая версия запроса включает решение,
версию обычного grant и активность исходного ключа. Старый expected не может
отозвать новую выдачу. Истечение grant не является автоматической отвязкой:
каждое действие обычного API проверяет срок и отказывает на его границе.

Unlink отзывает обычный grant/ключ, сохраняя документы, историю, peers и receipts.
Проверка последнего бессрочного администратора остаётся общей. Получатель
может отвязать только собственное ещё подтверждённое подключение через
session.unlink и TLS /v1/pairing/unlink с pending secret и expected. Этот
маршрут не может выдавать права, подтверждать или отзывать чужой subject.
После access.replace старый pending secret не может отозвать новую выдачу.

Для повторного подключения нужны новое приглашение, request и ключ. Даже
административный replay прежнего confirm не оживляет старый ключ. Явная
access.replace сохраняет прежний subject по своим правилам и не оживляет
старую связь. OS pending slot пока хранит также ключ подтверждённого устройства;
его нельзя удалять после confirm. Host-only session.credential заимствует ключ
для прежнего общего API, который независимо проверяет действующие права.
Удаление слота допускается после подтверждённого терминального исхода, когда
его credential больше не нужен; неизвестный исход требует сохранения и повтора.

## Источники и границы

SQLite v1 содержит decision и FK subject в pairing_requests; check ограничивает
связь подтверждённого запроса. Семантическая валидация требует исходный verifier
у этого principal. Права/активность берутся из access_*; Automerge не меняется.
PairingSnapshot содержит nullable subject без ключей, verifier и копии прав.
Rust остаётся источником OpenAPI/TS/валидатора. Схема и синтетический эталон
развиваются по ADR-0047; прежние базы не записываются и не сбрасываются.

Проверка компонента выполняется Windows/native Android. Полный процесс
Rust→Kotlin→TLS, постоянный listener, формы, физические устройства, обмен
пространствами и полная приёмка T09/A51 остаются последующим шагам .2.5/.3/P06.03.
