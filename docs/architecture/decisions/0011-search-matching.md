# ADR-0011: поиск запроса как непрерывного фрагмента текста

Дата: 2026-10-26.

Статус: принято разработчиком. Реализация и техническая проверка не выполнены.

## Контекст

Для обычного поиска уже согласованы заголовки и текущий текст карточек, отсутствие учёта регистра, активное пространство по умолчанию, переключение на все локальные пространства и поиск по сохранённым конфликтующим вариантам с одним результатом на карточку. Требовалось уточнить правило совпадения текста.

Разработчик выбрал совпадение одиночного запроса с любой частью слова. Совпадение только с началом слова и только с целым словом рассмотрены как альтернативы.

Для запроса из нескольких слов разработчик выбрал один непрерывный фрагмент: слова рядом и в указанном порядке. Поиск всех слов в произвольном порядке и поиск хотя бы одного слова рассмотрены как альтернативы.

Дополнительно разработчик выбрал различать «е» и «ё» при текстовом поиске. Их уравнивание только для поиска рассмотрено как альтернатива.

Для пробелов разработчик выбрал обрезку только краёв запроса и точное совпадение внутри фразы, включая табуляцию и переносы строк. Замена серий пробелов, табуляции и переносов одним пробелом рассмотрена как альтернатива.

Для пустого после обрезки краёв запроса разработчик выбрал показ всех доступных карточек выбранной области поиска. Отсутствие результатов до ввода непустого запроса рассмотрено как альтернатива.

Для пунктуации и специальных символов разработчик выбрал буквальный поиск без поисковых операторов. Отдельный синтаксис, например маска «*» для любого окончания слова, рассмотрен как альтернатива.

Для порядка результатов разработчик выбрал порядок доски: порядок колонок, затем карточек внутри них. При поиске по всем локальным пространствам сначала используется порядок пространств по именам, затем порядок каждой доски. Сортировка с недавно изменёнными карточками в начале рассмотрена как альтернатива.

Для найденных карточек со спорным местом карточки или её колонки разработчик выбрал группу «Конфликты» в начале результатов своего пространства. Размещение этой группы в конце рассмотрено как альтернатива.

Для пространств с конфликтующим названием разработчик выбрал отдельную группу «Конфликты названий» в начале списка пространств и поиска по всем пространствам. Размещение в общем алфавитном списке по первому из спорных имён рассмотрено как альтернатива.

## Решение

- Одиночный поисковый запрос находит вхождение в любую часть слова в заголовке или текущем Markdown-тексте карточки.
- Запрос «план» находит «план», «планирование» и «перепланировка». Согласованное отсутствие учёта регистра сохраняется: «ПЛАНИРОВАНИЕ» также совпадает.
- «е» и «ё» различаются: запрос «елка» не совпадает с «ёлка» и наоборот. Регистр игнорируется отдельно: «ЁЛКА» совпадает с «ёлка», «ЕЛКА» — с «елка». Исходное написание текста сохраняется.
- Запрос из нескольких слов ищется как один непрерывный фрагмент в указанном порядке без учёта регистра. «купить молоко» находит «Нужно купить молоко сегодня», но не «Купить вечером молоко» и не «Молоко купить».
- Пробелы по краям запроса обрезаются. Внутри фразы пробелы, табуляция и переносы строк учитываются точно, без схлопывания и замены одного вида другим. Запрос «купить молоко» с одним пробелом не совпадает с двумя пробелами, табуляцией или переносом строки между этими словами.
- Если запрос после обрезки краёв пуст, текстовое условие снимается: возвращаются все доступные карточки выбранной области поиска. Это относится и к пустой строке, и к вводу одних краевых пробелов. Выбранная область поиска, права доступа и правило одного результата на карточку сохраняются; очистка строки не переключает область поиска.
- Пунктуация и специальные символы ищутся буквально и не удаляются из запроса или текста при сравнении. «C++» ищет фрагмент «C++», «план*» — фрагмент со звёздочкой. Кавычки входят в искомый текст, а не выделяют фразу специальным синтаксисом. «*», «?», «%», «_», скобки и обратная косая черта не становятся масками, регулярными выражениями или поисковыми операторами. Отдельного синтаксиса операторов нет; сохраняются обрезка краёв, отсутствие учёта регистра и остальные согласованные правила совпадения.
- Подготовка запроса и сравнение выполняются по общему правилу Rust-ядра для всех адаптеров. Исходный текст карточки не обрезается и не переписывается поиском.
- Фрагмент должен целиком совпасть в заголовке либо в текущем тексте. Он не составляется из конца заголовка и начала текста или из разных конфликтующих вариантов.
- Правило действует для всех сохранённых конфликтующих вариантов заголовка и текста. Карточка возвращается один раз с отметкой конфликта по общему правилу.
- Область поиска и проверки доступа сохраняются: поиск не предоставляет доступ к чужим пространствам. Интерфейс, HTTP и CLI на Windows и Android используют общее правило Rust-ядра.
- Результаты поиска с однозначным местом на доске следуют сохранённому порядку колонок и карточек. При поиске по всем локальным пространствам применяется общий порядок пространств: группа «Конфликты названий» перед пространствами с однозначными именами, которые идут по именам, затем порядок результатов внутри каждого пространства. Это правило применяется и к непустому, и к пустому после обрезки запросу.
- Пространство с нерешённым конфликтом названия показывается один раз в группе «Конфликты названий» в начале списка пространств и поиска по всем пространствам, с отметкой конфликта и доступом к сохранённым вариантам названия. В поиске группа содержит только доступные пространства с найденными текущим запросом карточками. После разрешения названия последующий список или поиск возвращает пространство в обычный порядок по выбранному имени. Общие прикладные операции предоставляют интерфейсу, HTTP и CLI тот же порядок и сведения о группе; сам показ группы не выбирает имя и не меняет согласованные блокировки контейнера и доступность работы с его содержимым.
- Найденные карточки с неопределённым местом из-за конфликта перемещения, порядка самой карточки или позиции её колонки показываются один раз в отдельной группе «Конфликты» в начале результатов своего пространства. После неё идут остальные результаты в порядке доски. Группа содержит только карточки, найденные текущим запросом в пределах выбранной области и прав; при поиске везде она располагается внутри результатов соответствующего пространства. Общий API предоставляет тот же порядок и сведения о принадлежности к группе.
- После разрешения конфликтов, определяющих место карточки и её колонки, при последующем поиске подходящая запросу карточка возвращается в обычный порядок. Если место остаётся спорным, карточка остаётся в группе. Группировка сама не разрешает конфликт, не меняет сохранённые позиции и не вводит новых блокировок редактирования: действуют согласованные правила собственных конфликтов карточки и её контейнеров.
- Порядок результатов определяется общими прикладными операциями по тому же авторитетному локальному состоянию, что и порядок доски и списка пространств. Интерфейс, HTTP и CLI на Windows/Android возвращают согласованный порядок; изменение сохранённого порядка доски учитывается в последующих результатах поиска.

## Границы и технические вопросы

Правила одиночного запроса, непрерывного фрагмента из нескольких слов, различия «е»/«ё», внутренних пробелов, пустого после обрезки запроса, буквальной пунктуации/специальных символов и общего порядка результатов выбраны. Точный набор краевых пробельных символов Unicode, остальная политика Unicode-сравнения/нормализации и ограничения полей уточняются отдельно в DEC-005. Различие «е»/«ё» здесь относится к текстовому поиску карточек; правила равенства имён тегов и сравнения имён пространств этим решением не определяются.

Конкретное сравнение имён пространств, устойчивый порядок при одинаковых именах и внутри группы «Конфликты названий» уточняются при техническом проектировании. Устойчивый порядок внутри группы карточек «Конфликты» также уточняется при проектировании; это решение задаёт положение двух групп. Группировка не выбирает произвольное имя или позицию из нерешённого конфликта. Карточка с конфликтующим текстом и однозначным местом на доске возвращается один раз на этом месте с отметкой конфликта по согласованным правилам.

Новые зависимости и поисковый индекс не выбраны. Реализация должна выполнять согласованные совпадения, включая кириллицу без учёта регистра, и пройти проверку производительности. Выбор SQL-предикатов и индекса выполняется по результатам прототипа; наличие SQLite само по себе не подтверждает нужное поведение Unicode-поиска.

Выбранный впоследствии алгоритм или индекс должен сохранять буквальность запроса. Служебный синтаксис конкретного механизма поиска не становится частью пользовательского запроса; применение внутреннего механизма не должно превращать символы в маски или требовать экранирования символов как поисковых операторов.

## Проверка и правила проекта

Уточнены сценарий 19 спецификации и A19: проверить совпадения в начале, середине и конце слова, непрерывный фрагмент из нескольких слов, отказ совпадения при другом порядке или вставленном слове, отсутствие составного совпадения из разных полей/конфликтующих вариантов. Проверить обрезку краёв запроса, точные совпадения внутренних пробелов/табуляции/переносов и отсутствие их взаимной подмены или схлопывания. Пустая строка, строка из обычных пробелов и очистка ранее непустого запроса должны возвращать все доступные карточки выбранной области без её переключения. Проверить активное пространство, все локальные пространства, ограниченные права, отсутствие карточек в доступной области и один результат на карточку с конфликтующими текстами. Охват включает заголовок и текущий текст, разный регистр кириллицы при обязательном различии «е»/«ё» в обоих направлениях, сохранение исходного написания, конфликтующие варианты, один результат на карточку, область поиска и права. Все критерии сохраняют `not_run`.

Для буквального поиска дополнительно проверить «C++» против «C++» и «C», «план*» против «план*» и «планирование», фразу с кавычками против фразы без них, одиночную кавычку, «%», «_», «?», скобки и обратную косую черту. Специальные символы не требуют экранирования в поисковом синтаксисе и не создают ошибку поискового синтаксиса. Проверки выполняются для заголовка, текущего текста и сохранённых конфликтующих вариантов через интерфейс и общий API на обеих платформах; исходный текст не меняется.

Для порядка результатов проверить несколько колонок с ручным порядком карточек, несколько пространств с разными именами, непустой и пустой запросы, учёт сохранённой перестановки колонок/карточек при последующем поиске и одинаковый порядок через интерфейс, HTTP и CLI. Набор для проверки должен различать ручной порядок доски, алфавитный порядок заголовков и время изменения карточек. При конфликтующем тексте и однозначной позиции сохраняются один результат, его место и отметка конфликта. Проверки устойчивого порядка при одинаковых именах и внутри групп дополняются при техническом проектировании.

Для группы «Конфликты» проверить конфликт перемещения карточки, её порядка в одной колонке и позиции колонки с найденными карточками. Группа находится перед обычными результатами внутри каждого пространства, соблюдает запрос, область и права, не дублирует карточки по спорным позициям. После полного разрешения места карточки и колонки она переходит в обычный порядок; при оставшемся конфликте места остаётся в группе. При конфликте только текста с однозначным местом карточка остаётся в обычном порядке. Проверить непустой и пустой запросы, несколько пространств и общий результат через интерфейс, HTTP и CLI на обеих платформах. Группировка не добавляет запрета работы с карточками колонки, у которых нет собственных конфликтов.

Для группы «Конфликты названий» проверить список пространств и поиск везде при непустом и пустом запросах: спорные пространства идут первыми, каждое показывается один раз с доступом к вариантам названия; остальные пространства идут по именам. Поиск соблюдает запрос и права, включая отсутствие совпадений в спорном пространстве. При одновременном конфликте места карточки её группа «Конфликты» остаётся внутри своего пространства. После разрешения названия пространство возвращается в обычный порядок, а ещё нерешённые конфликты карточек сохраняются. Проверить общий порядок и сведения о группах через интерфейс, HTTP и CLI на Windows/Android, сохранение данных и правил блокировки контейнера/работы с его содержимым; A19 и S03.

Поиск не изменяет данные; запрос можно изменить или очистить. Общий API человека и агента, паритет Windows/Android и одно авторитетное локальное состояние сохраняются как требования. Документация отражает выбор; реализации и приёмки пока нет.
