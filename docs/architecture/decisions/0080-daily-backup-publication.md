# ADR-0080: публиковать ежедневную копию по свидетельству SQLite

Дата: 2026-11-26. Статус: реализовано и проверено локально в P07.04/EV-157; CI/интеграция отдельно.

## Решение

Политика [ADR-0079](0079-daily-backup-policy.md) подключается к прежнему
полному `capture_export`. Ревизия зависит от упорядоченных хешей всех scoped
изменений, включая ожидающие зависимости, и незавершённого текста; время
захвата и служебные receipts в неё не входят. Снимок включает тот же полный
граф, историю, корзину, конфликты и pending-текст, что экспорт P07.02.

Допуск, захват, проверка и свидетельство успеха сериализуются прежним SQLite
writer lock. Права и receipt явного действия находятся в той же транзакции;
финальная проверка срока сохраняется. Новые правки ждут завершения захвата
и остаются изменениями относительно сохранённой ревизии. Другой процесс
не создаёт второй успешный снимок за ту же дату. Запрос, ожидавший writer,
получает согласованное актуальное состояние после предыдущей попытки.

Служебные записи используют отдельный NUL namespace в `command_results`,
как страховочные копии P07.03. Ключи внешних receipts канонизированы иначе
и не пересекаются. Схема базы не меняется. Состояние политики, порядок
последних семи файлов и очередь удаления сохраняются атомарно; полная копия
SQLite включает их, scoped архив пространства не переносит лимиты устройства.

Идентификатор установки сначала сохраняется отдельной транзакцией, до
любого файлового эффекта. Кандидат имеет отдельный каталог с именем,
связанным с установкой и пространством; пользовательские пути не принимаются.
Файл записывается `create_new`, синхронизируется, ограниченно перечитывается
и проверяется по длине, SHA-256 и метаданным. Успех учитывается по локальной
дате завершения проверки/формирования свидетельства, а не начала записи.
Свидетельство и результат явного запроса коммитятся вместе. Неизвестный исход
транзакции требует чтения/replay, а не нового пользовательского намерения.

Только после commit обслуживание создаёт проверяемый `commit.json` и удаляет
уже зафиксированные устаревшие/явно удалённые копии. Новая копия проверяется
до удаления старых; ошибка не ротирует прежние исправные файлы. Незавершённый
маркер восстанавливается по авторитетному SQLite-свидетельству. При старте
обслуживание удаляет только непризнанные незавершённые кандидаты собственной
установки; чужие namespaces, ручные экспорты, страховочные копии и каталоги
с маркером без текущей ссылки сохраняются. Последние нужны после отката базы
или переустановки; их полный каталог относится к P07.05. Символические ссылки
и неожиданные файлы не обходят проверку пути и не удаляются рекурсивно.

Явное удаление убирает ссылку и ставит файл в очередь очистки в одной
транзакции с receipt; лимит успешного дня и последняя успешная ревизия
сохраняются. Ошибку физического удаления показывает `cleanup_pending`.
Обслуживание после операций, при старте и раз в пять минут повторяет такую
очистку. Очередь ограничена 64 ссылками; при её заполнении новые попытки
отказывают с сохранением прежних файлов до устранения проблемы очистки.
Это защитный бюджет незавершённого обслуживания, а не лимит пространств.

## Часы и запуск

Локальная дата получается из свежего имени часового пояса ОС через
`iana-time-zone` и правил `jiff`. Обе зависимости уже присутствовали в lockfile;
версии закреплены. `TimeZone::try_system` не используется: его пятиминутный
кэш имени мог бы неверно учесть день после смены пояса. Для Windows используется
Windows Calendar, для Android — текущая `persist.sys.timezone`; нет fallback
на UTC или доверия дате, присланной клиентом. Базы правил поясов читаются локально.

Пятиминутная пауза идёт по `Instant` работающего процесса и не сокращается
переводом календарных часов вперёд. Опорные логическое время и календарная
метка сохраняются вместе с результатом попытки. Новый процесс возобновляет
отсчёт по неотрицательной разнице часов ОС; при откате часов ожидание
консервативно не сокращается. Между процессами доверяем часам ОС, как при
старте контроля доступа; намеренная смена часов вне процесса не является
защитной границей. При откате локального дня ждём дня позже последнего успеха.
`Instant` измеряет время, которое предоставляет платформа, включая её правила
сна/приостановки; закрытое приложение не выполняет таймер и не восполняет дни.

Worker включён в Windows shell, APK и HTTP-host; одноразовый локальный CLI
завершает проверку условий перед закрытием хранилища. Старт, успешные
изменяющие запросы и изменение локального дня вызывают проверку. Таймер
проверяет день раз в секунду; без изменений/смены дня/ошибок не сканирует
графы и не записывает копии. Повторные уведомления объединяются. Worker
принадлежит lifetime общего Service и отменяется после последнего владельца.

## Общий API и границы

`space.backups.inspect` и `.read` требуют чтения пространства; `.retry` и
`.delete` — чтения/изменения и обычного receipt с проверкой прав до replay.
Повтор ссылается на конкретную ошибку; новая ошибка меняет номер и паузу.
UI использует те же операции. Выбранный архив передаётся существующему
подтверждённому восстановлению и ставит обмен на паузу по P07.03.

Сейчас используется прежняя папка `<database>.backups`. Выбор/перенос папки
и обнаружение всех копий без базы остаются P07.05; это не скрытая новая
команда работы с путями. Бюджеты контейнера прежние: 1 MiB/10000 changes,
ошибка не заменяется усечённой копией. Power-loss, durability каталогов
Windows и физический arm64 runtime не следуют из проверки остановки процесса.
Доказательства и ограничения: [EV-157](../../agent/verification/EV-157-daily-backups.md).
