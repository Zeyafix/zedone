# Восстановление существующего пространства через общий API

Авторитетный договор — производный `api/openapi.json`. Не писать SQLite,
backup witness или файлы установки напрямую и не подменять действие импортом.
Все четыре команды доступны HTTP/CLI/IPC и используются тем же файловым UI.

| Операция | Параметры | Результат и права |
| --- | --- | --- |
| `space.recovery.inspect` | `space` | Свежие `version`, `pause_version`, `paused`, последний `backup` и `cleanup_pending`; Read |
| `space.recovery.restore` | `space`, `archive`, `expected` | ID того же пространства и непрозрачный ID `safety`; ReadWrite |
| `space.recovery.read_backup` | `space`, `safety` | `{archive}` только последнего успешного страховочного снимка; Read |
| `space.recovery.pause` | `space`, `paused`, `expected` | Состояние восстановления с явной паузой; ReadWrite |

Каждый запрос использует обычный конверт с новым случайным ненулевым ID.
Ключ передаётся отдельно и никогда не входит в намерение. Для restore сначала
выполнить inspect и сохранить его `version` как `expected`. Для pause использовать
именно `pause_version`. Не брать вместо них version из space.read или карточки.
Архив — lowercase hex полного ZEDSPACE v1, не путь на сервере. Предел — 1 MiB
бинарных байтов/10000 changes и 3 MiB транспортного JSON только для restore.
Остальные новые команды сохраняют обычный бюджет запроса 64 KiB.

Restore требует существующее исходное пространство, совпадающий ID и общую
исходную историю. Права/сроки проверяются до/после работы и при replay.
Граф не откатывается: возвращаются значения и новые причинные действия.
ID пространства/объектов, авторство и полные пары истории сохраняются;
возвращённые версии истории имеют новые технические IDs, поэтому перечитайте
историю перед последующим выбором версии. Права, ключи, peers и receipts
не импортируются и не откатываются. Старые выполненные намерения не оживают.

После restore пауза сохраняется до нового явного pause с `paused:false`.
Проверка результата, restart и replay не снимают её. До возобновления inspect
и обычные чтения позволяют проверить содержимое. Передача второму устройству
сохраняет независимые правки, включая совместимые поля и конфликтующие варианты.

Для обратного действия прочитайте `backup.id` из свежего inspect, запросите
read_backup и используйте полученные байты в новом restore с новой version.
Последний страховочный файл проверяется по committed-witness, длине и SHA-256;
папка по умолчанию не заменяется fallback. Предыдущий снимок удаляется только
после успешного следующего восстановления. Ошибка cleanup не отменяет commit;
повтор завершает очистку без нового восстановления. Orphan-файл не доказывает успех.

После outcome_unknown повторять весь исходный запрос и ID. Не обновлять
expected, архив или ID автоматически. Изменённый выполненный запрос даёт
command_mismatch после проверки текущих прав; stale_state требует свежего чтения
и нового явно подтверждённого намерения. Неподдержанный/повреждённый/чужой архив —
invalid_request без частичного восстановления. Архив содержит личный текст
и историю: не публиковать и не записывать его содержимое в диагностику.

Папка/каталог реализованы в P07.05. Восстановление отсутствующего пространства
описано ниже; аварийный откат базы остаётся P07.09. Границы и доказательства — [EV-152](verification/EV-152-existing-space-recovery.md),
[ADR-0078](../architecture/decisions/0078-existing-space-recovery.md).


## Восстановление отсутствующего пространства

`space.recovery.inspect_missing` принимает `{archive}` и возвращает
`{space, names, version}` после полной проверки контейнера/модели и SQL-проверки
отсутствия исходного ID. Не создаёт пространство, снимок или право.
`space.recovery.restore_missing` принимает `{space, archive, expected}` из
этого чтения и возвращает `{space}` с прежним ID, новой причинной операцией
и постоянной паузой обоих направлений. Обе операции используют HTTP/CLI/IPC.

Как при создании/импорте, требуется действующий локальный доступ. При успешном
восстановлении только вызывающему субъекту добавляется ReadWrite нового
локального пространства. Старые субъекты/ключи, администрация, подключения,
receipts и peer progress не переносятся из архива. Права остальных локальных
пространств и другого устройства не меняются. Повторное чтение/доставка receipt
restore_missing дополнительно требуют актуального ReadWrite восстановленного ID.
Утёкший/истёкший/отозванный ключ и read-only не могут подтвердить старый успех.

Версия связывает отсутствие с выбранным архивом. Проверка повторяется под
непрерывным writer lock перед созданием графа, прав и паузы; всё вместе с receipt
фиксируется одной транзакцией. Существующий документ любого lifecycle, пустой
или нечитаемый, даёт stale_state. Ошибка SQL не доказывает отсутствие. Нет
автоматического fallback с обычного restore, подмены expected или перезаписи
появившегося состояния. При stale_state разберите исходное намерение, затем
явно подготовьте нужную операцию заново.

После outcome_unknown сохраните исходные ID/архив/expected и повторите запрос.
Выполненный receipt не восстанавливает граф повторно и не возвращает паузу после
явного resume. Для обратного удаления используйте обычные space.trash/restore;
для последующего возврата состояния существующего ID — обычный recovery.restore
с новым страховочным снимком. Отдельных старых локальных credentials нет.
Повторное подключение и новые выдача/изменение/отзыв прав используют прежние
операции; подключение и restart не снимают pause.

Бюджеты ZEDSPACE прежние: 1 MiB/10000 changes, wire request до3 MiB; это не
продуктовый лимит пространства. Доказательства и ограничения —
[EV-162](verification/EV-162-reinstallation-recovery.md),
[ADR-0082](../architecture/decisions/0082-reinstallation-recovery.md).
