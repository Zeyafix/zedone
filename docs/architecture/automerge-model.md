# Модель Automerge после P02

Это описание проверяемого прототипа, а не выпущенная схема хранения.
Основа выбрана в [ADR-0002](decisions/0002-automerge-sync.md).
P03 определяет продуктовые границы и атомарную запись; P07 — формат копий,
полномочия, каталог и совместимость выпущенных версий.

## Авторитетное состояние и границы

SQLite содержит полный бинарный документ, actor последовательного локального
писателя и долговечное состояние обмена. Поля, история и состояния объектов
вычисляются из документа; JSON-отпечатки и отчёты не являются отдельной базой.
Обработчик команды одинаков для разработчика и агента. Пользовательские UI,
HTTP/IPC и права не появляются автоматически из проверочного CLI.

Для полного сырого снимка P02.06 использует один документ на пространство.
Нельзя сохранить несколько пространств одним документом, затем удалить чужие
видимые ключи и считать остаток изолированной копией: граф сохраняет прошлое.
Пробник создаёт отдельный однопространственный граф сразу. Полная модель порядка
и причинного каталога тегов пока проверяется прежними отдельными пробниками;
снимки и восстановление используют иерархию P02.05 с её ограниченными полями.
Это не доказательство полной продуктовой композиции всех операций.

## Снимки и восстановление

Внутренний снимок содержит идентичность пространства, формат, heads и полный
бинарный граф. Заголовок длины и метаданные проверяются до строгой загрузки
Automerge. В нём нет локального actor писателя, peer state, прав и настроек;
actor ID исторических изменений являются частью графа. Формат только для пробника,
не обещание чтения выпущенных архивов. Сырой граф содержит также прежние очищенные
значения: снимок не предназначен для избирательной публикации данных.

Восстановление требует тот же граф/идентичность и известную причинную основу.
Оно записывает отличающиеся значения снимка поверх известных изменений новым действием,
сохраняя идентификаторы пространства, колонок, карточек и тега. Известные более
поздние объекты получают состояние окончательной очистки. Ещё неизвестные правки,
версии и создания остаются независимыми при обмене. Восстановление в новую
установку — отдельная задача P07, этот пробник её не открывает.

Поля, уже совпадающие со снимком (с учётом всех вариантов), не присваиваются
повторно. Независимая правка такого поля совместима с восстановлением другого
поля и объединяется без лишнего конфликта. Присваивание требуется именно для
отличающихся полей; несовместимая независимая правка остаётся конфликтом.
Даже при совпадении всех полей записывается новая причинная отметка восстановления.

Снимок сохраняет уже принятые изменения с недоставленными зависимостями.
После записи восстановления граф снимка дополняет кандидат: отложенные изменения
не входят в обычный `get_changes()` и не должны теряться. Когда зависимости
доступны, это неизвестные восстановлению изменения с обычными правилами
совместимости/конфликтов; иначе они ждут доставки в сохранённой очереди.

Чтобы вернуть нерешённые варианты снимка, присваивания строятся на отдельных
ветвях от одной текущей основы. Последовательные присваивания одному полю
молча оставили бы один вариант. Получившийся набор изменений и основное действие
публикуются одной SQLite-транзакцией. Число изменений Automerge может быть больше
одного; частично восстановленного состояния на диске нет. Монотонные границы
очистки сохраняются; подтверждения восстанавливают нерешённые поздние создания,
а новые известные границы признаются действием восстановления.

Видимая история возвращается парами заголовок/описание. Слоты истории и
отличающиеся присваивания получают новые технические ID; связи защищённых конфликтующих
версий переназначаются. Группы корзины и идентификаторы сущностей сохраняются.
Это не окончательный формат пользовательских ID версий P04/P07.

Проверенный снимок до восстановления, документ/actor/peer и постоянная пауза
фиксируются атомарно. Отказ сохраняет прежний страховочный снимок. Возврат к нему
— ещё одно действие восстановления. Снимок можно отдельно удалить, сохраняя
другие снимки и рабочие реплики. Перезапуск не снимает паузу; возобновление явно.

## Сокращение и сохраняемый граф

Проверены два независимых слоя: переупаковка потока изменений в компактный
бинарный документ и освобождение свободных страниц SQLite. Первый слой сохраняет
все изменения, heads, объекты, варианты и недоставленные изменения без зависимостей.
Используется `save()` с сохранением orphan changes; [Rust API](https://docs.rs/automerge/0.12.0/automerge/struct.SaveOptions.html).
Все документы переупаковываются одной транзакцией без перезаписи локальных прав,
actor/peer, снимков и паузы. Прежний Store и так сохранял компактный `save()`:
на уже упакованном документе повтор не обязан уменьшать объём.

`VACUUM` выполняется отдельной стадией после commit; SQLite не допускает его
внутри обычной транзакции. Ошибка возвращается вызывающему коду, корректный
упакованный граф сохраняется, освобождение страниц можно повторить. Проверка
целостности предшествует успешному ответу. Это операция обслуживания всей
синтетической базы, не разрешение доступа к чужим пространствам в продукте.
Свойства и условия — [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html).

Удаление пользовательской истории не удаляет её прежние байты из графа.
Безопасного отбрасывания причинной истории/маркеров при неограниченном отсутствии
связи здесь не доказано. Пересоздание документа только из видимого состояния
не принимается: меняются Object ID и теряются зависимости старых реплик.
Ограниченный размер графа и гарантированное стирание прежнего содержимого
не являются результатами P02.06. Автоматического удаления данных не добавлено.
