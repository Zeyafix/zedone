# ADR-0034: публикация комплекта по свидетельству SQLite commit

Дата: 2026-11-05. Статус: технический срез P07.07.2, DEC-006 остаётся open.
Проверки — [EV-051](../../agent/verification/EV-051-migration-backup-publication.md).
Дополняет [ADR-0033](0033-pre-migration-backup-candidate.md); продуктовый договор
спецификации §1/1.1 не меняется. Цепочка миграций остаётся P07.08.

## Решение

Файловый манифест не доказывает фиксацию SQLite. `with_migration_backup`
создаёт **новый** кандидат и вызывает доверенный обработчик внутри одного
`BEGIN IMMEDIATE`. Общий capture из P07.07.1 используется без копирования
реализации. Между захватом и commit нет промежутка для другого writer.
Самостоятельный `PreparedBackup` не принимается как основание для операции.

В той же транзакции записывается служебный результат в существующий
`command_results`: ключ `\0zedone/internal/migration-backup/v1`, request
`migration-backup-commit-v1`, строгий JSON версии 1 с текущей и прежней ссылкой
на комплект. Ссылка содержит только basename и длину/SHA-256 манифеста.
Ключ длиннее 16-байтового командного ID и не принадлежит пользовательским
результатам. Предыдущие пользовательские результаты не удаляются и не меняются;
перезаписывается только это служебное свидетельство. SQL, версия схемы, lock-файл
зависимостей и переносимый формат снимка остаются прежними. Это использование
уже существующего атомарного хранилища результатов, не новое текущее хранилище.

Доверенная проверка целевого результата вызывается до commit и повторно после
него. Она обязана проверять ожидаемую целевую версию/схему, целостность и
инварианты результата, а не только возможность открыть SQLite. Пока этот
механизм проверяется на изменениях данных схемы 1; реальных миграций нет.
Обработчик не управляет транзакцией и не публикует внешние эффекты.

После commit берётся новая `BEGIN IMMEDIATE`, проверяется то же свидетельство
и целевой результат. Зазор после commit не используется как доказательство
эксклюзивности: смена свидетельства останавливает текущую публикацию. P07.08
должен закрывать обычные входы на всё время миграции и её сверки при запуске.

## Публикация и очистка

Приватная выбранная папка принадлежит одной установке. `migration.lock` —
стабильный файл блокировки, `File::try_lock` исключает другие публикации и
удаление кандидатов до конца операции. Блокировка освобождается ОС при смерти
процесса; файл не удаляется. SQLite отдельно исключает writers общей базы.
Другая папка автоматически не выбирается, каталог кандидата не переименовывается.

После фиксации и проверки заново проверяются все файлы нового комплекта,
включая привязанный к свидетельству манифест. `migration-current.json` содержит
только текущую ссылку. Индекс записывается в новый файл в той же папке, его
содержимое синхронизируется, затем `NamedTempFile::persist` атомарно заменяет
прежний индекс. Это проекция свидетельства, не самостоятельное разрешение
миграции или восстановления. Индекс ограничен 4096 байтами, ссылки принимают
только генерируемые ASCII basename без разделителей, каталоги/ссылки вместо
ожидаемых файлов отвергаются. Полная проверка архива сохраняет бюджеты P07.07.1.

Только после публикации, повторной проверки комплекта и чтения индекса удаляется
прежний каталог, названный в свидетельстве. Ошибка очистки возвращает
`cleanup_pending = true` вместе с подтверждённым успехом, а не ложный откат.
Следующая сверка повторяет очистку; новый захват не начинается при её отказе.
Дневная ротация не участвует. Без сбоев остаётся один действующий полный
предмиграционный комплект; временные остатки не становятся постоянными копиями.

## Сбой и перезапуск

- До попытки commit ошибка откатывает изменения SQLite. Прежний индекс и
  действующий комплект сохраняются. Незавершённый собственный capture удаляется
  best effort; полностью подготовленный кандидат сохраняется для разбора.
- Ошибка после попытки commit возвращает `OutcomeUnknown`: повтор изменения
  на основании этой ошибки запрещён. `recover_migration_backup` читает
  свидетельство и проверяет целевой результат, повторяет только публикацию и
  очистку. Сам обработчик операции повторно не вызывается.
- При rollback новое свидетельство отсутствует: прежний комплект остаётся
  текущим, подготовленные файлы не продвигаются. При commit свидетельство
  выбирает конкретный новый комплект; отсутствие индекса допускает его
  построение заново. Другой неожиданный/повреждённый индекс останавливает сверку.
- Пропажа/повреждение committed-кандидата или неподтверждённый целевой результат
  останавливают сверку. Старый комплект сохраняется, автоматического fallback
  или восстановления базы нет. Новая попытка при незавершённой публикации
  запрещена: сначала сверка с проверкой ожидаемого результата P07.08.
- Orphan не удаляется сканированием папки. Доверенная инфраструктура может явно
  вызвать `discard_migration_candidate` по строгому basename: под обеими
  блокировками отвергаются текущая и прежняя ссылки свидетельства и индекса.
  Чужие файлы/каталоги не очищаются. Текущую копию этот метод не удаляет;
  пользовательское управление каталогом остаётся P07.05.

Наличие старого свидетельства не подтверждает успех **любой последней попытки**.
Вызывающий код обязан проверять именно ожидаемый целевой результат. Потеря
ответа после admission не отменяет работу; drop не удаляет готовый комплект.

## Долговечность и границы

Содержимое файлов синхронизируется на обеих платформах; на Unix дополнительно
fsync каталогов комплекта и папки до изменения базы, после замены индекса и
удаления прежнего каталога. На Windows std/tempfile не предоставляют эквивалент
барьера каталога: синхронизация файлов не доказывает долговечность его entries
при отключении питания. Проверяется **остановка процесса**, не физическое
отключение питания, произвольная сетевая файловая система или отказ носителя.
Для пользовательских миграций P07.08 и итоговой приёмки T10/M04 эти ограничения
нельзя скрывать за успешными crash-тестами; при утрате кандидата запуск должен
останавливаться, сохраняя проблемное состояние для служебного режима P07.09.

Основания: [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html),
[Rust File lock/sync](https://doc.rust-lang.org/std/fs/struct.File.html),
[tempfile persist](https://docs.rs/tempfile/3.27.0/tempfile/struct.NamedTempFile.html#method.persist).
Проверен исходник закреплённого tempfile: Windows использует MoveFileExW с
REPLACE_EXISTING, без отдельного барьера долговечности каталога. Новых
зависимостей и unsafe в собственном коде нет.

Права на всю установку, источник прав/часы, startup-цепочка исторических схем,
аварийное восстановление и UI/HTTP/CLI/IPC остаются следующими шагами. Методы
являются доверенной инфраструктурой для общего core человека/агента. Они не
дают публичного обхода прав и не разрешают прямую запись агента в SQLite.
Откат всей базы не должен оживлять старые намерения по ADR-0030.
Полная предоперационная копия содержит прежнее свидетельство, чьи файловые
ссылки после следующих успешных операций могут устареть. Намеренное аварийное
восстановление P07.09 обязано согласованно переустановить это служебное состояние
вместе с защитой от повторов; нельзя запускать публикацию по откатившемуся
свидетельству как по новому подтверждению текущей установки.
