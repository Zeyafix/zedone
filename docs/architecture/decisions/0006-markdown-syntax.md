# ADR-0006: профиль Markdown и просмотр через markdown-it + DOMPurify

Дата: 2026-10-26.

Статус: принято разработчиком. Прототип P01.07 проверен локально и в Windows/Linux/Android CI,
интегрирован через PR #14; продуктовая приёмка остаётся в P05, [EV-020](../../agent/verification/EV-020-markdown.md).

## Решение

Разработчик выбрал базовый CommonMark для Markdown-текста карточек первой версии ZeDone: заголовки, выделение, списки, ссылки, цитаты и блоки кода. Расширения таблиц и текстовых чекбоксов в первую версию не входят.

Исходный текст сохраняется целиком. Строки с разделителями таблиц и маркерами вида «- [ ]» не удаляются и не преобразуются в отдельную модель данных; специальное форматирование таблиц и интерактивные чекбоксы для них не добавляются. Такие маркеры отображаются по базовым правилам CommonMark. Они не меняют самостоятельную отметку выполнения карточки.

Дополнение по решению разработчика: пользовательская HTML-разметка показывается как обычный текст. Например, `<b>важно</b>` остаётся видимым вместе с тегами, а `**важно**` форматируется средствами Markdown. Теги и скрипты из исходного текста не интерпретируются и не выполняются; исходный текст сохраняется целиком. Это явно согласованный профиль отображения ZeDone поверх базового CommonMark с отключённой интерпретацией raw HTML.

Дополнение по решению разработчика: обычные HTTP/HTTPS-ссылки открываются по нажатию вне ZeDone. На Windows — в отдельной вкладке браузера, на Android — во внешнем браузере. Просмотр карточки не заменяется внешним сайтом; само отображение карточки не открывает ссылки автоматически. Решение касается HTTP/HTTPS и не определяет поведение иных схем URI.

Дополнение по решению разработчика: удалённое изображение, указанное в Markdown, загружается внутри карточки только по отдельному нажатию. До нажатия показывается описание или понятная заглушка с действием загрузки. Сам просмотр карточки не инициирует загрузку изображения; нажатие относится к выбранному изображению. При ошибке сети показываются причина и возможность повторить загрузку, исходный Markdown сохраняется, чтение и редактирование карточки продолжаются. Адрес изображения остаётся частью текста; ограничения первой версии по вложениям сохраняются.

Одинаковый синтаксис применяется на Windows и Android. Человек и агент читают и изменяют тот же исходный Markdown через общие операции Rust-ядра; форматированный просмотр остаётся производным представлением. Правило конфликтов текста как одного поля сохраняется.

## Библиотеки и общий просмотр

По отдельному решению разработчика для просмотра выбраны markdown-it + DOMPurify. markdown-it разбирает исходный текст с базовым пресетом CommonMark и явным `html: false`; DOMPurify очищает сформированный HTML перед отображением. Редактирование остаётся простым текстовым вводом.

В общем веб-интерфейсе используется один модуль просмотра с одинаковой конфигурацией на Windows и Android. Генерируемый HTML остаётся производным от Markdown. Непроверенная HTML-разметка после очистки не добавляется; элементы управления и обработчики создаются контролируемым кодом компонента. Для DOMPurify используется HTML-профиль; конкретная конфигурация и совместимые версии проверяются в прототипе.

До нажатия на загрузку изображения формирователь просмотра не создаёт активных адресов загрузки, в том числе перед передачей результата DOMPurify. Наличие очистки HTML само по себе не выполняет требование отсутствия сетевых запросов.

Bun используется для установки зависимостей и запуска инструментов сборки/проверок; markdown-it и DOMPurify работают в общем клиентском интерфейсе, DOMPurify использует DOM браузера или Android WebView. В P01 проверить установку и импорт пакетов, сборку через Vite, TypeScript и фактический просмотр в целевых браузерах и APK. Успешная сборка под Bun не подтверждает корректность отображения и очистки в приложении.

## Границы решения

Профиль просмотра и библиотеки выбраны. Поддерживаемую версию CommonMark, совместимые версии markdown-it/DOMPurify, настройки, соответствие парсера профилю и совместимость с выбранной цепочкой Bun/Vite нужно зафиксировать и проверить при подготовке прототипа.

Политика HTML согласована: буквальный показ исходной разметки. Для HTTP/HTTPS согласовано открытие по нажатию вне ZeDone; удалённые изображения загружаются внутри карточки только по отдельному нажатию. В выбранном markdown-it необходимо явно отключить обработку пользовательского HTML (`html: false`): стандартный пресет CommonMark включает HTML, поэтому один выбор пресета не обеспечивает требуемое поведение. Отсутствие автоматической загрузки удалённых изображений подтверждено разработчиком. До нажатия сетевые запросы на изображения не должны возникать также при парсинге и очистке HTML; скрытие уже загружаемого элемента не выполняет это требование. Интеграция выбранных markdown-it + DOMPurify проверяется в прототипе.

## Проверка

В P01 проверить небольшой набор примеров базового синтаксиса; в P05 проверить продуктовый сценарий 50 и критерий A50 в целевых браузерах Windows и Android APK. Проверяется одинаковое форматирование, сохранение исходного текста, отсутствие специальных расширений таблиц и чекбоксов и независимость отметки выполнения карточки. Для HTML отдельно проверить буквальный показ тегов, сохранение исходного текста и отсутствие выполнения скриптов; обычное выделение Markdown продолжает работать. Для HTTP/HTTPS проверяются переход только по нажатию, отдельная вкладка на Windows и внешний браузер на Android без замены экрана ZeDone сайтом; конкретный механизм интеграции проверяется в прототипе. Для удалённых изображений проверить отсутствие сетевых запросов до нажатия, загрузку только выбранного изображения внутри карточки, понятное состояние при недоступной сети и повтор без изменения исходного Markdown. Одинаковое поведение проверяется на обеих платформах.

P01.07 фиксирует markdown-it 15.0.3 (CommonMark 0.31.2), DOMPurify 3.4.17
с HTML-профилем и Tauri Opener 2.7.2. Конфигурация и границы описаны в
[инструкции прототипа](../../development/markdown-prototype.md). Изображения
заменяются инертными маркерами до DOMPurify, затем контролируемый Vue-компонент
создаёт загрузочный элемент только после нажатия. На ПК ссылки открывает
браузер через `_blank`/`noopener noreferrer`, на Android — Opener с локальными
HTTP/HTTPS-полномочиями; его автоматический JS-обработчик отключён.

T01/T02 остаются partial по прототипным доказательствам, T08 — not_run;
A50 — partial в синтетическом охвате P01.07, не продуктовая приёмка.
Полное хранение/редактирование текста, выполнение карточки, конфликты и
продуктовый UI остаются в P04/P05. Требования обратимости, общего API человека
и агента, паритета Windows/Android и единого источника данных сохраняются.
