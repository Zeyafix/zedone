запрет B также при write, отсутствие удалённого управления (404).
HTTP и локальный API дают одинаковые read/snapshot; разрешённое HTTP-перемещение
видно в IPC, устаревший expected отклоняется, удаление/восстановление A
сохраняют B. Реальный SQLITE_BUSY возвращается по HTTP APK как 503;
параллельные IPC/UI остаются отзывчивыми, после освобождения блокировки

Rust проверяет отзыв уже открытого TCP-соединения и безопасный повторный запуск
на прежнем фиксированном порту после остановки. Каждый новый запуск создаёт
новый ключ. Ошибки bind/неразрешённого адреса не включают доступ, ошибочный
повтор start не повышает права текущей сессии.

В Android проверены настоящие сенсорные действия формы: начальное чтение,
отказ адреса и повтор, явное включение write и остановка. Home и сон экрана
отзывают доступ нативно; возврат не создаёт сессию. Отдельный

с новым ключом. Реальный force-stop/запуск сохраняет SQLite, удаляет сессию;
старый ключ получает 401 на том же порту нового процесса.

Добавлены ожидание WebView и отдельные процессы для двух сценариев.
Это не засчитывалось как успешная проверка; повторный полный прогон пройден.
Одна ручная команда Gradle была вызвана вне каталога проекта и отклонена;
исправлен параметр каталога. Приложение ради этих ошибок драйвера не менялось.

## Реальный сетевой прогон — 2026-10-30

Прежняя блокировка LOG-143 была действительной на момент локальных проверок.
После подтверждения готовности разработчиком выполнен отдельный прогон
ПК → физический Android. Адрес взят с реального VPN-интерфейса телефона

forward телефона направлялся на localabstract WebView, HTTP через USB не шёл.
Ответ Tailscale discovery ping через DERP сам по себе не засчитывался
как успешный HTTP; приняты реальные POST с проверкой ответов и состояния.

Повторно использована существующая матрица `checkHttpSession`, без изменения
приложения или подмены результатов. Только адрес локального start заменён
на реальный адрес Android. Проверены 401 без ключа/с неверным ключом,
Unicode echo и 422, запрет Origin, read/snapshot A и запрет B,
все изменяющие операции A/B при read, запреты B при write, отсутствие
удалённого управления, перемещение и отклонение устаревшего expected,
удаление/восстановление A при сохранении B, точное равенство HTTP и IPC,
отзыв и смена ключа на том же порту.

На реальной форме проверены read по умолчанию, ошибка запрещённого bind
и успешный повтор на Tailscale-адресе, явный write и остановка.
После Home и сна старый доступ пропал; возврат не включал сервер.
Новый явный запуск давал новый ключ, старый получал 401 через Tailscale.
Force-stop закрыл listener; новый процесс сохранил SQLite, стартовал
без сессии и после явного запуска на том же порту отвергал прежний ключ.
Дополнительный физический instrumentation-прогон проверил реальное
пересоздание Activity с loopback; сетевой HTTP при этом не приписывается ему.

Реальный обрыв выполнен через `tailscale down` на ПК при открытом APK.
Запрос перемещения не доставлен и завершился ошибкой; чтение через IPC
подтвердило неизменность данных и доступность локального API.
После `tailscale up` прямое HTTP-чтение совпало с IPC, без автоматического
повтора изменения. Новый явный запрос прошёл; исходный снимок восстановлен.
Это проверка обрыва VPN на стороне ПК. Потеря ответа уже допущенного
изменения не объявляется откатом, отключение самого Android VPN в этом
прогоне не проверялось. Политика сети пропускала выбранный порт;
её административное изменение и отрицательные ACL-сценарии не выполнялись.

### BUG-002 — прежний listener после перезапуска Android VPN

Отключение и включение выполнены только в эмуляторе через экспортированный
receiver Tailscale (`DISCONNECT_VPN`/`CONNECT_VPN`); host VPN и физический
телефон не отключались. Подтверждены исчезновение и возврат VPN-интерфейса
с тем же адресом, неизменность A через IPC после недоставленного запроса
изменения и доступность самого tailnet после возврата.

После возврата VPN IPC status продолжает сообщать endpoint и прежний ключ,
но HTTP через этот listener не восстанавливается. Повторные прогоны дали
тайм-ауты Bun fetch более 30 секунд. Независимый клиент `node:http` с
`agent:false` и новым TCP-соединением получает ECONNREFUSED — это не только
повторное использование старого клиентского соединения. Явные локальные
stop/start listener на **том же IP и порту**, без изменения Tailscale/ACL,
восстановили новый TCP HTTP 200. После этого чтение совпало с IPC, новое
явное изменение прошло, исходный снимок восстановлен. Это подтверждённое
временное восстановление, не исправление и не успешное автоматическое
восстановление прежней сессии. На момент этого прогона конкретная причина
на уровне Android/сокета ещё не была установлена; продуктовые исходники
не патчились. Последующая диагностика — ниже.

Общий сетевой прогон оставлен с кодом 1: обязательная проверка восстановления
прежнего listener не пройдена. Успешные части и неуспешные попытки сохранены
раздельно в `docs/reports/p01-10/emulator-tailnet/`, включая `verification.json`,
`network-lifecycle.json`, `run.log`, предыдущие попытки, воспроизводимый
`verify.mjs`, метаданные официального APK, отпечатки и cleanup.
Первый запуск драйвера предполагал имя tun0; фактическое имя интерфейса
отличалось. Поиск исправлен на реальный VPN-адрес среди интерфейсов,
эта ошибка драйвера не приписывается прототипу.

Условие закрытия BUG-002: определить и исправить жизненный цикл listener
при замене Android VPN-интерфейса, затем подтвердить HTTP/IPC и сохранность
данных после reconnect без ручного stop/start. Если исправление создаёт
новую сессию, старый ключ не должен получать новых полномочий; поведение
и отображение должны быть явными. Проверки прав/отзыва/фона сохраняются.

### Корень BUG-002 — диагностика 2026-10-30, LOG-150

Поручение ограничено поиском причины, без исправления приложения. Основание:
`aa3bb87` и уже подготовленные уточнения BUG-002; во время исследования
они зафиксированы отдельным коммитом `4bc635b`. Продуктовое дерево неизменно.
Повтор выполнен на том же AOSP API 33 x86_64, ядро Android 5.15.41,
с настоящим Tailscale. SHA-256 установленного APK совпал с прежним локальным
APK. Root adbd и встроенный `strace` использованы только в тестовом AVD;
физический телефон, VPN ПК, ACL и настройки маршрутизатора не менялись.
HTTP направлен с ПК непосредственно на VPN IP, без TCP adb-forward;
forward обслуживал только локальный WebView CDP для общего IPC.

Подтверждена следующая цепочка:

1. `HttpSession::execute(Start)` привязывает TCP listener к конкретному VPN IP
   (`prototypes/core/src/http_session.rs`). При отключении VPN адрес исчезает.
   В Android 13 обработчик удаления адреса в
   [NetlinkHandler.cpp](https://android.googlesource.com/platform/system/netd/+/refs/tags/android-13.0.0_r1/server/NetlinkHandler.cpp#141)
   вызывает `SockDiag::destroySockets`. Выборка по адресу в
   [SockDiag.cpp](https://android.googlesource.com/platform/system/netd/+/refs/tags/android-13.0.0_r1/server/SockDiag.cpp#153)
   исключает только `TCP_TIME_WAIT`, поэтому затрагивает и `TCP_LISTEN`;
   затем отправляет `SOCK_DESTROY`. Это системный механизм Android,
   а не сохранение привязки к прежнему имени tun-интерфейса.
2. Непосредственно в неизменённом APK до отключения `ss -lntpe` показывает
   listener, `accept4` принимает соединения и HTTP отвечает 200. Сразу после
   отключения этот listener исчезает из `LISTEN`, но тот же fd и inode
   остаются в `/proc/<pid>/fd`. PID приложения не меняется.
3. `strace -f -e trace=accept,accept4` фиксирует **42 последовательных
   `accept4` с `EINVAL` за примерно 41 секунду** на прежнем fd, начиная
   с отключения VPN и продолжая после возврата того же IP. Дескриптор открыт,
   но больше не является слушающим сокетом. Возврат адреса его не пересоздаёт.
4. Зафиксированный `axum 0.8.9` в `src/serve/listener.rs` перехватывает ошибки
   `TcpListener::accept` и повторяет вызов бесконечно; для `EINVAL` ждёт
   секунду. Ошибка не выходит из `axum::serve`, задача остаётся незавершённой.
   Поэтому строка `active.store(false, ...)` после `.await` не выполняется.
   `HttpSessionRequest::Status` проверяет только grant и `!task.is_finished()`
   и возвращает прежние endpoint/ключ, хотя listening socket уже отсутствует.
   В Android-оболочке обработаны только события окна, смена сети не обрабатывается.
5. Все свежие TCP-пробы (`node:http`, `agent:false`) после reconnect получают
   `ECONNREFUSED`. Явные stop/start на том же endpoint создают другой socket
   inode в том же процессе: HTTP 200, прежний ключ — 401, новый ключ отличается.
   Изменение Tailscale/ACL, переустановка APK и перезапуск процесса не нужны.

Итого: потерян жизненный цикл listener при системном уничтожении TCP-сокета
на удаляемом VPN-адресе; состояние сессии ошибочно приравнено к существованию
задачи Axum. Повтор `accept` на этом сокете не восстанавливает обслуживание.
Одного ожидания завершения `serve` или исправления текста UI недостаточно.

Следующий шаг реализации: обрабатывать необратимую потерю listener, согласовать
отзыв grant и правдивый IPC/UI status с его фактическим состоянием. Обработка
смены сети должна учитывать именно адрес/сеть listener, а не только default
network или Activity. Если выбирается отзыв сессии, новый запуск и новый ключ
остаются явными; автоматическое создание новых полномочий не вводится.
На момент LOG-150 исправление и его регрессионные проверки ещё не выполнены.

Локальные доказательства и воспроизводимый драйвер:
`docs/reports/p01-10/bug-002-root-cause/diagnose.mjs`, `observations.json`,
`accept.trace`, `logcat.log`, копии исходников AOSP, `verification.json`.
Сырые адреса/PID/inode не публикуются в Git; временные ключи не сохранялись.
Диагностика использует только echo и управление сессией, данные A/B не меняет.
Сессия отозвана, strace отсоединён, forward удалён, прототип остановлен,
принадлежащий проверке эмулятор выключен, авторизация Tailscale сохранена.
По результатам LOG-150 BUG-002 оставался open; P01.10 blocked, T04/A26 partial,
GAP-003 resolved. Состояние после исправления — ниже.

### Исправление BUG-002 — 2026-10-30, LOG-151

По поручению разработчика на базе `4bc635b` и диагностики LOG-150 изменён
общий `core::http_session`. Локальные исходники пока не закоммичены.
Новый Axum Listener обрабатывает уничтоженный listening socket:
`InvalidInput`/`NotConnected` от accept освобождают socket и запускают bind
на прежнем точном IP и выбранном порту. Ошибка bind повторяется раз в секунду,
без wildcard/fallback; отдельной фоновой задачи нет. Существующие token,
access и grant сохраняются, новый доступ не выдаётся. Первый неуспешный
start по-прежнему не создаёт сессию. Stop и native suspension прерывают
восстановление через прежний graceful shutdown и отзывают grant.

На Unix исходный и повторный listener используют SO_REUSEADDR, чтобы старые
соединения/TIME_WAIT не задерживали bind. На Windows этот флаг не включается.
Новый `HttpSessionStatus.recovering` отражает ожидание bind; Rust → OpenAPI → TS
перегенерированы. Форма обновляет status раз в секунду только при существующей
сессии и видимом документе и показывает/убирает сообщение о восстановлении.
Ошибки пользовательских команд сохраняются; запоздалый ответ status
не заменяет результат более новой команды. Данные SQLite не повторяются
автоматически, общий Storage и ограничения API не менялись.
