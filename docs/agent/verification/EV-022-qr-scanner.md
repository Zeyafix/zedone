## Карточка шага

Закрепить официальный Tauri Barcode Scanner. Проверить синтетические поля
`address`/`code` без продуктового протокола, хранения или запросов по адресу.
Ручной ввод и результат камеры поступают в один Rust-контракт HTTP/IPC,
модели OpenAPI/TypeScript генерируются из Rust. Отдельные состояния сканера
и ошибки данных не смешиваются. Отмена, повтор, очистка и уход приложения
в фон должны освобождать камеру и оставлять ручной путь доступным.

Проверки: `bun run check`, Chrome/Opera `bun run check:http`, обе ABI
`bun run android:build [aarch64]`, AOSP API 33 без GMS `bun run check:android`.
Нужны реальные разрешения/отмена/повтор/фон и ручной путь без сети/модели/GMS.
Чтение камерой с экрана ПК после готовности модели требует устройства с GMS;
если оно недоступно, записать непроверенную ячейку, не заменять её mock-тестом.
Пригодность физического телефона и бюджеты производительности не принимаются.

Это одна цель проверки; ожидается превышение ориентира 300 строк из-за
общего контракта, Android-поведения, двух платформенных проверок и документации.
Независимый сетевой шаг P01.10 и продуктовый процесс P03/P06 не включены.

Поручение охватывает локальную реализацию и проверки; коммит/PR/слияние в
него не входят. Физическая проверка закрыла GAP-002; исправление и повторная
проверка BUG-001 описаны в последнем разделе. Точка продолжения — CI/интеграция
по отдельному поручению; независимый P01.10 не начинался.

## Результаты реализации

Закреплены Rust/JS Barcode Scanner 2.5.3, CameraX 1.5.1 и динамическая
ML Kit 18.1.0. QR-only, задняя камера, windowed-режим с видимой кнопкой отмены;
CAMERA необязательна в manifest, запрашивается явно. Локальная capability
содержит только четыре необходимые команды, без настроек ОС/вибрации.

Один stateless Rust `invitation` принимает QR JSON или ручные address/code,
сохраняет точные строки и возвращает их через HTTP/IPC. Нет хранения,
сетевых обращений к адресу и прав доступа. Контракт и модели генерируются;
камера не обязательна для прикладной операции человека/агента.

Плагин логирует ошибку ML Kit, не завершая scan: приложение по истечении
20 секунд вызывает cancel и предлагает ручной ввод без ложной ошибки данных.
Отмена/«Назад»/фон прекращают сканирование; запоздалый ответ игнорируется.
Прочитанная строка сохраняется в форме для повтора инспекции после отказа IPC.
Неподтверждённая отмена запрещает новое сканирование до перезапуска, сохраняя
ручную форму. Product pairing и одноразовость кода этим не реализуются.

## Матрица локальных проверок

- `bun run check`: fmt/Clippy, 16 Rust-тестов, release, OpenAPI/TS/IPC,
  strict Vue/TypeScript, Vite, HTTP/Chromium — пройдены.
- Chrome/Opera `bun run check:http`: полный набор, включая равенство QR/ручного
  HTTP-ввода, точный Unicode/пробелы/буквальный HTML, неверные данные,
  отказ/повтор/очистку и отсутствие обращений по адресу — пройдены.
- Debug APK x86_64/arm64: обе сборки пройдены с закреплённым сканером.
- AOSP Android 13/API 33 без GMS, WebView 101: общий HTTP/IPC-контракт,
  ручной UI и прежние echo/SQLite/board/Markdown/QR — пройдены общим runner.
- Реальные диалоги отказа/выдачи CAMERA, отмена/повтор, «Назад», Home/возврат,
  освобождение камеры через dumpsys, режим полёта/Wi-Fi off, тайм-аут без модели:
  пройдены. Системный диалог разрешения скрывает WebView; обработчик учитывает
  это и не принимает диалог за отмену. Ранний тест выявил и помог исправить
  ошибку этого состояния. Драйвер использует фактические bounds системной кнопки.
- Доступ к камере при выданном разрешении блокировался через UID AppOps CAMERA
  ignore; возврат к ручному вводу и освобождение клиента прошли. Прежний режим
  AppOps восстанавливается. Потеря ответа cancel внедряется отдельно: новый
  scan запрещён, ручная форма доступна, предупреждение сохраняется при очистке.
- Внедрённые ответы сканера проверяют Unicode → Rust IPC, сохранение raw-строки
  при отказе/повторе, неверный JSON и игнорирование позднего результата.
  Это **не оптическое чтение** и не проверка готовой модели.

Ранние неуспешные прогоны не объявлены успешными: закреплённый Node нужен
только vue-tsc, не Node 26 из PATH; сообщения HTTP об ошибках типов могут быть
plain text, а dumpsys выводит `Client Package Name` в списке активных клиентов.
Первый Gradle-прогон использовал штатный fallback Kotlin после ошибки
инкрементального кеша путей Windows; сборка прошла. Исходники плагина,
JDK/SDK и модель распознавания ради тестов не заменялись.

## BUG-001 и закрытие GAP-002

В первом сеансе после выдачи CAMERA разработчик и агент увидели белый экран
вместо превью, с рабочей отменой и возвратом к ручному вводу через 20 секунд.
Модуль barcode загрузился через GMS, но оптического результата в этом сеансе
не было. После перезапуска только прототипа камера заработала; это подтвердили
разработчик, изображение и native-журнал. Следующие три чтения и повторный
диалог разрешения прошли. Изменений приложения или плагина не делалось.

Перезапуск — наблюдённое восстановление, **не исправление BUG-001**. При первой
проверке причина ещё не была установлена; повтор после полной переустановки
и подтверждённая причина описаны ниже. Штатные пойманные исключения при поиске
необязательных классов сами по себе не доказывают причину сбоя.
Отладчики отсоединены, их adb-forward удалены; глобальные настройки сети и GMS
не сбрасывались, личные приложения/данные не изменялись.

GAP-002 закрыт: телефон доступен, три точных оптических чтения после готовности
модуля и повторное сканирование подтверждены. Ручной путь без сети/модели/GMS
проверен на AOSP; физический телефон проверяет распознавание после готовности
модуля. На телефоне модуль уже был доступен через GMS: сетевую первую загрузку
не наблюдали и не объявляем проверенной. Сброс GMS ради её воспроизведения
не выполнялся; отдельного нового требования такой сброс не вводится.

Итог первоначальной проверки: P01.09 — blocked по BUG-001, T02/A51 — partial,
DEC-003 открыт. Тогда для завершения требовалось устранение/проверка белого экрана;
актуальный результат исправления — ниже.
Измерения производительности/памяти и полная
продуктовая приёмка телефона остаются в своих шагах. Независимый P01.10 готов,
но реализация не начиналась. APK оставлен установленным, камера не активна.

Обратимость, общий API человека/агента, документация, ручной паритет ПК/Android
и единое Rust-состояние подтверждены в синтетическом охвате. Полный продуктовый
протокол, права, подтверждение и обмен не принимаются. Доказательства конкретной
машины и логи — только в игнорируемой `docs/reports/`, коммита/PR/новых Actions нет.

## Воспроизведение BUG-001 после полной переустановки — 2026-10-29

Разработчик поручил полное удаление и повторную установку прототипа; при
воспроизведении — поиск причины. Удалён только `app.zedone.prototype` вместе
с синтетическими данными. Перед установкой подтверждено отсутствие пакета;
перед первым запуском CAMERA не выдана. Установлен тот же arm64 APK с совпавшим
SHA-256, без изменений приложения, Tauri, сканера или GMS.

Белый экран снова появился после первого разрешения «While using this app».
Разработчик подтвердил его, агент сохранил кадр, активное состояние сканера в
новом WebView и отсутствие клиента камеры у прототипа. Повтор команды в этом
процессе дал тот же результат. Попытки драйвера не объявляются успешным прогоном:
сначала исправлена обработка ненулевого кода `pm path` для отсутствующего пакета,
затем автоматический поиск кнопки застал уже подтверждённый вручную диалог.
Воспроизведение подтверждено независимыми наблюдениями и native-диагностикой.

### Подтверждённая цепочка причины

1. Системный event-log зафиксировал relaunch с `0x80000000`. У старой Activity
   `mChangingConfigurations=true`, `mConfigChangeFlags=0x80000000`; в Android 13
   это `CONFIG_ASSETS_PATHS`, изменение путей ресурсов. События create/destroy/create
   произошли в одном процессе до выдачи разрешения камеры. Конкретный системный
   инициатор обновления ресурсов не устанавливался.
2. JDWP исходного APK показал старую Activity с `mDestroyed=true`, Lifecycle
   `DESTROYED`, и новую Activity с Lifecycle `RESUMED`. `PluginManager.activity`
   указывает на новую, но `BarcodeScannerPlugin.activity`, базовый `Plugin.activity`
   и `BarcodeScannerPlugin.webView.mContext` — на старую. Две Activity и два
   WebView идентифицированы по объектам, без изменения их значений.
3. В Tauri 2.12.5 менеджер сохраняет экземпляры плагинов при уничтожении Activity;
   `onWebViewCreated` вызывает load лишь для ещё не загруженных handles.
   `PluginHandle.load` ставит `loaded=true`. У Barcode Scanner 2.5.3 Activity
   захватывается конструктором, а preview добавляется к сохранённому WebView.
   Поэтому после пересоздания остаются одновременно неверные владелец жизненного
   цикла и окно для показа камеры. У Path/Opener также обнаружены старые ссылки;
   исправление должно учитывать общий жизненный цикл нативных плагинов.
4. Исходник CameraX Lifecycle 1.5.1 подтверждает: для `DESTROYED` владельца
   `createLifecycleCamera` не регистрирует камеру, а `bindToLifecycleCamera`
   при отсутствии observer не привязывает сценарии. Поэтому ни захвата, ни
   кадров нет, хотя scan остаётся ожидающим. Трассировка пойманных исключений
   main-thread в повторе не дала исключения — это согласуется с этой веткой,
   а не доказывает ошибку разрешения или модели.

Контроль: перезапущен только процесс того же APK. Осталась одна `RESUMED`
Activity, менеджер, сканер и WebView ссылаются на неё. Native-журнал подтвердил
`STREAMING`; живое превью сохранено, отмена освободила камеру. Это контроль
причины, а не исправление. Разрешение камеры корректно; модуль GMS доступен.

На момент диагностики BUG-001 воспроизведён, оставался open/high; P01.09 blocked. Следующий шаг —
корректное пересоздание/перепривязка нативных плагинов и WebView при смене Activity
с повторной проверкой полной установки и конфигурационных пересозданий.
Изменение manifest для подавления события, автоматический restart, задержки
и форк зависимости не вводились. Коммит/PR и исправление не выполнялись.

Обратимость отмены и восстановление проверены на том же синтетическом приложении;
общий Rust API, паритет ручного пути и единый источник данных не менялись.
Глобальные настройки телефона/данные других приложений не сбрасывались.
Идентификатор телефона, объекты JDWP, event-log и кадры остаются только в
игнорируемой `docs/reports/p01-09/physical/`.

## Исправление BUG-001 и повторная проверка — 2026-10-29

По прямому поручению разработчика исправлен жизненный цикл нативных плагинов
Tauri 2.12.5. Менеджер хранит описания регистрации (класс/config/mapper), при
уничтожении владельца освобождает handles, ссылки на Activity/WebView и callbacks,
а для новой Activity создаёт новые экземпляры тем же публичным конструктором,
который использует Tauri. Поздний WebView уничтоженного владельца игнорируется.
Конфигурация сохраняется, полномочия остаются в Rust/capabilities. Barcode Scanner
2.5.3, CameraX и ML Kit не менялись; задержки/перезапуск приложения не добавлены.

Поддерживаемого API перепривязки в закреплённой версии нет. Вместо изменения
общего Cargo registry Gradle генерирует исходники Android-зависимости внутри
build-каталога, заменяя manager и добавляя небольшой lifecycle helper. SHA-256
upstream проверяется перед сборкой; изменение источника останавливает сборку
до пересмотра патча. Сохранены copyright/MIT. Это явная версионная зависимость
с обязательным пересмотром при обновлении Tauri, а не новый общий API плагинов;
обоснование и откат — ADR-0022 и README android-patches.

Проверенная рабочая копия: ветка `feat/p01-09-qr-scanner` от указанной выше базы,
локальные отпечатки исходников и APK сохранены в игнорируемом отчёте.
Пройдены:

- `bun run check`: 16 Rust-тестов, fmt/Clippy, OpenAPI/TS/IPC, strict/Vite,
  HTTP/Chromium и прежние сценарии прототипа. Это повтор после изменения Android.
- Обе `bun run android:build [aarch64]`, включая instrumentation APK обеих ABI.
  Gradle configuration cache повторно использован.
- Полный `bun run check:android` на Android 13 AOSP без GMS: реальное пересоздание
  Activity, ручной UI/HTTP/IPC, разрешения/отказ/повтор, camera cleanup,
  недоступная камера/модель, прежние SQLite/board/Markdown/QR и перезапуск.
- `PluginLifecycleTest` на AOSP и Galaxy A32: `OK (1 test)`. Реальный
  `ActivityScenario.recreate()` меняет Activity; владельцы app/path/opener/barcode-
  scanner и их WebView актуальны. Изолированный probe подтверждает новый экземпляр,
  прежнюю конфигурацию и освобождение старого владельца. Reflection есть только
  в тесте для проверки приватных полей, не в приложении.
- Две полные uninstall/install на Galaxy A32/Android 13 (попытки 2 и 5): отсутствие
  пакета до установки, CAMERA не выдана перед запуском, выдача While using this app,
  native CameraX `STREAMING`, отсутствие JS-ошибок и освобождение камеры при отмене.
  Между установкой и запуском камеры процесс не перезапускался.
- Исправленная сборка после последней полной установки прочитала с экрана ПК новый
  QR с Unicode/составным акцентом/emoji, масштаб 8: все 73 UTF-8-байта и поля
  Rust-инспекции совпали. Ответы не внедрялись; разработчик подтвердил живое превью
  и прочитанные данные. Отмена/повтор, «Назад», Home/возврат и освобождение камеры
  после каждого действия снова пройдены на телефоне.

Неуспешные попытки драйвера сохранены отдельно: список пакетов по префиксу
совпадал также с тестовым APK, диалог разрешения уже подтверждался вручную,
а первоначальный CDP target мог закрыться при реальном пересоздании WebView.
Они не засчитывались как успешные проверки. Драйвер следует текущему WebView
без перезапуска приложения; отдельно сохранены успешные результаты двух установок.

На AOSP стандартное завершение instrumentation закрывало последнее окно Tauri
раньше отчёта JUnit и давало `Process crashed` после успешных assertions.
Проверенный в установленном AndroidX Monitor 1.6.0 параметр
`waitForActivitiesToComplete=false` позволяет runner опубликовать результат до
завершения процесса. Скрипт требует итог `OK`, не принимает частичный status;
