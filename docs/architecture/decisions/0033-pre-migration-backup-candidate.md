# ADR-0033: проверенный кандидат предмиграционного комплекта

Дата: 2026-11-05.

Продолжение жизненного цикла P07.07.2 реализовано в
[ADR-0034](0034-migration-backup-publication.md). Ниже сохранены границы
самостоятельного кандидата P07.07.1; его возврат по-прежнему отпускает writer lock.

Статус: технический срез P07.07.1 в рамках DEC-006. Публикация комплекта после
успеха миграции остаётся P07.07.2; атомарная цепочка миграций — P07.08.
Продуктовый договор §1/1.1 спецификации не меняется. Проверки —
[EV-050](../../agent/verification/EV-050-pre-migration-backup-candidate.md).

## Захват

Доверенный `Storage::prepare_migration_backup` исполняется на существующем
SQLite worker. Он удерживает `BEGIN IMMEDIATE` до завершения захвата и проверки:
другие writers, включая другие worker, не могут изменить исходник. Проверяется
идентичность, версия и точная схема 1 через тот же `schema::check_layout`, который
использует открытие базы. Исходная транзакция откатывается без изменений.

Полная копия создаётся [SQLite Backup API](https://www.sqlite.org/backup.html),
через feature `backup` уже закреплённого rusqlite. Это учитывает WAL, в отличие
от копирования одного файла ОС. Для чтения используется второе read-only
соединение: [API SQLite](https://www.sqlite.org/c3ref/backup_finish.html) возвращает
`LOCKED`, если исходное соединение занято write-транзакцией. Один `step(-1)`
обязан вернуть `Done`; busy/locked/ошибка останавливают попытку без бесконечного
повтора. Начальный размер по page_count/page_size проверяется до копирования.

Копия переводится в DELETE journal mode и закрывается. Она автономна без WAL/SHM.
Из повторно открытой read-only копии создаются снимки **всех** строк `documents`,
включая пустые документы, тем же `snapshot::capture`, что и P07.01. Поэтому они
включают полный scoped журнал с ожидающими зависимостями и соответствуют одной
полной копии. Вся схема и служебные записи сохраняются в SQLite-копии, а не
добавляются в переносимые снимки пространств. Права и учётные данные в нынешней
схеме ещё не реализованы; будущие версии требуют своих проверок схемы.

## Файлы и проверка

Кандидат создаётся в отдельном эксклюзивном каталоге
`zedone-migration-candidate-*` **в указанной существующей папке**. Другой каталог
не выбирается, исходник/старые копии не перезаписываются. Каталог создаёт
закреплённый tempfile, перенесённый из dev в runtime без смены версии. Unix-права
нового каталога приватные; на Windows ACL наследуется от выбранной папки.
Доверенный вызывающий код отвечает за приватность папки, поскольку полная копия
содержит локальные служебные данные и будущие секреты установки. Шифрования нет.

Состав: `database.sqlite`, `space-0.bin` … и `manifest.json`. Числовые имена
соответствуют порядку непрозрачных ID в SQLite; ID никогда не становится путём.
Внутренний строгий JSON-манифест версии 1 хранит дату, длину и SHA-256 базы и
каждого архива. Он не является новым публичным переносимым форматом. Дата
поступает из доверенной инфраструктуры и не управляет правами/дневной ротацией.
Новые файлы создаются с `create_new`; файлы синхронизируются через `sync_all`.

Перед успешным возвратом всё повторно читается: длины/SHA-256, identity/version/
layout, полный `integrity_check`, `foreign_key_check`, точный состав пространств,
декодирование каждого архива и его побайтовое соответствие заново захваченному
журналу из копии. Допускаются только ожидаемые обычные файлы: посторонние
WAL/SHM/journal, каталоги и ссылки не принимаются. Повторная
`PreparedBackup::verify` выполняет те же проверки;
она синхронна и предназначена для инфраструктурного worker. Хеши обнаруживают
повреждение, но не удостоверяют автора или право на восстановление.

`BackupLimits` задаёт предел размера базы, числа пространств, суммы архивов и
прежние `SnapshotLimits` каждого архива. Манифест читается с пределом,
выведенным из числа записей; файлы хешируются потоково, архивы читаются с пределом
до декодирования. Бюджеты ограничивают вход/файлы, но не гарантируют пик памяти
и время: проверочный граф Automerge и отдельные архивы остаются в памяти.
Производительность всего приложения и выбор продуктовых бюджетов здесь не приняты.

## Жизненный цикл и обязательная следующая граница

Ошибка удаляет только собственный незавершённый каталог best effort, не трогая
исходник и прежние копии. Успешный кандидат сохраняется при drop/потере ответа;
его можно явно удалить через `PreparedBackup::discard`. Завершение процесса
может оставить незавершённый каталог. Наличие каталога/манифеста само по себе
никогда не разрешает миграцию; автоматического продвижения/восстановления нет.

В P07.07.1 нет замены предыдущего успешного комплекта, миграций, операций
восстановления, ротации, каталога UI или внешних HTTP/CLI/IPC-входов. Возврат
`PreparedBackup` не даёт будущей операции гарантию актуальности рабочей базы:
после отпускания writer lock новые записи разрешены.

P07.07.2 обязан связать **новый** захват с попыткой миграции под непрерывной
блокировкой writers, повторной проверкой и проверкой результата, сохранить старый
комплект до commit и безопасной публикации, определить crash/restart и ошибки
публикации/очистки. Синхронизация файлов здесь не доказывает долговечность записи
каталога при отключении питания; порядок синхронизации каталога/маркера и
восстановление после обрыва относятся к .2. P07.08 ждёт весь P07.07.
Гарантии схем всех официальных выпусков и служебный режим остаются последующими
шагами. Аварийный откат не может оживлять старые намерения по
[ADR-0030](0030-command-replay-and-freshness.md).

Будущий доступ к полной базе требует отдельных полномочий и общего core-пути
человека/агента; доступ к одному пространству их не заменяет. Кандидат —
инфраструктура без публичного обхода прав.
