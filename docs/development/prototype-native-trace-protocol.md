# P01: протокол диагностики native/JS без смены прикладного IPC

Статус: справочный протокол; реализация не продолжается после завершения
P01.11 по решению разработчика (LOG-187, 2026-11-02). Профиль не реализован,
не собран и не измерен. Ниже сохранён прежний план возможной диагностики,
который не является текущим поручением. Основание — EV-024/LOG-184, A62/GAP-006,
[методика](prototype-measurements.md#разбор-сохранённой-трассы-перед-новым-измерением).
Продуктовые требования и ADR-0026 не меняются. Подготовка этого документа
не означает прохождение A62. Машинная сверка исходников и передача —
`docs/reports/p01-11/native-trace-protocol-review.md`.

## Вопрос и минимальный охват

Для одной синтетической `move_card` и её обратной команды определить время
dispatch, ожидания/выполнения общего Storage, commit и сериализации ответа.
Получить отдельно обозначенную верхнюю границу доставки готового ответа
до наблюдаемого начала channel fetch в WebView. Операции и проверяемое
состояние A/B остаются прежними; открытия карточки/выполнения задачи здесь нет.

Выбран минимальный вариант без патчей Tauri/Wry, нового транспорта,
собственных JNI/FFI и новых библиотек. Будущий feature `prototype-native-trace`
включается только для отдельной диагностической сборки core/Android-адаптера;
обычные сборки исключают коллектор, команды управления и probes через cfg.
Имя feature пока обозначает план, доступной команды сборки ещё нет.

Точные enqueue/dequeue MainPipe, Kotlin post и запуск доставленного JS
в существующем `RustWebView.evalScript` недоступны через выбранные публичные
hooks. Поэтому путь от готового сериализованного тела до channel fetch
остаётся составным: Tauri channel queue, MainPipe, UI post, WebView/JS и
наблюдатель. Отдельные длительности этих очередей не обещаются. Патч зависимости
ради них сейчас не добавляется; при доказанной необходимости это отдельный
срез с собственным обоснованием, проверкой версии/лицензии и измерением расходов.

## Доступные точки интеграции

| Граница | Предложенная точка | Предел интерпретации |
| --- | --- | --- |
| Dispatch | `Builder::invoke_handler` перед/после прежнего generated handler | Разбор входного native JSON и предшествующая ACL-проверка уже могли завершиться |
| Handler entry | Начало async `storage`, `tauri::ipc::Request::headers()` | Это начало функции после разбора аргументов, не момент `spawn` |
| Storage/worker/commit | Feature-probes в прежнем пути `Storage::execute`/`run` | Те же semaphore, `spawn_blocking`, транзакция и алгоритм; probes не ветвят бизнес-логику |
| Serialized body ready | Feature-only `IpcResponse` wrapper, делегирующий `inner.body()` | Тело готово, но ещё не подтверждена вставка в ChannelDataIpcQueue или вызов Eval |
| Channel fetch | Прежний JS wrapper `window.fetch` | Начало существующего fetch, не начало выполнения всего доставленного JS |
| Target reply/DOM | Прежние callback и saved-DOM marks | Включены опрос 10 мс и расходы наблюдателя, не показ физической матрицы |

`InvokeResolver.callback/error` имеют `pub(crate)`; читать их через layout,
reflection или unsafe нельзя. `Invoke` отмечен Tauri как нестабильная структура:
адаптер ограничивается документированным builder-hook и публичными
`message.command()/headers()/webview_ref()`, на закреплённой версии.
`Builder::channel_interceptor` не заменяет response-ready probe: исследованный
путь `Channel::from_callback_fn` его не вызывает. `invoke_system` не используется.
Глобальное включение dependency tracing тоже не выбрано: наличие spans не
гарантирует нужную корреляцию, а некоторые поля содержат request/response целиком.

Wrapper ответа не реализует Serialize и не меняет модель StorageResponse:
один вызов прежнего `IpcResponse::body`, возврат того же `InvokeResponseBody`
или той же ошибки. Ошибки команды проходят прежний Result/error-путь, без
искусственного success/body-ready. До Android-сборки нужна проверка совместимости
с generated async handler, точных JSON-байтов успеха и прежних ошибок.

## Корреляция одного вызова

До серии host создаёт run ID, а для каждой команды — отдельный attempt ID.
Ключ: `(run_id, document_epoch, webview_label, attempt_id, callback, error)`.
ID прогрева/измерения и направление также сохраняются. Callback ID сам по себе
не уникален между документами; время, порядок команд и одинаковый payload
не используются как замена ключа. Run ID — метаданные, не токен доступа.

Будущий отдельный JS-наблюдатель, перед передачей native JSON исходному мосту,
копирует реальные callback/error ID в один ограниченный ASCII-заголовок
`x-zedone-prototype-trace` внутри существующего `options.headers`. Значение
версии 1 имеет грамматику `v1:<run>:<attempt>:<callback>:<error>`:
run — ровно 32 строчные hex-цифры, attempt — десятичное число 0–999999,
callback/error — разные десятичные u32, включая допустимый 0. Числа канонические,
без знака/пробелов/ведущих нулей, кроме самого `0`; лишние поля запрещены.
Полная длина ограничена 128 байтами.
Document epoch/WebView связываются с предварительно открытым run-контекстом.
Заголовок читает middleware и injected `Request`, не прикладная модель.

Это намеренное отличие нового профиля от LOG-183: native envelope получает
диагностические метаданные. Нельзя утверждать побайтное равенство всего сообщения.
Обязательны равенство `cmd/callback/error/payload`, invoke key и всех прежних
options/headers; меняется только добавленный заголовок. Полные native JSON,
payload, invoke key и тексты карточек в telemetry не записываются. Существующий
одноимённый заголовок не перезаписывается. После click сбой наблюдателя не
подавляет исходную команду: она передаётся один раз, а диагностика отклоняется.

Native registry разрешает один ожидаемый attempt; проверяет заголовок,
WebView, command/action и повторное использование ID. Нарушение делает evidence
непригодным, но не меняет разрешения/валидацию/результат прикладной команды.
Копия callback ID в заголовке сверяется с исходной JS-регистрацией, целевым
ответом и обратным IPC-чтением состояния; это не native доступ к приватному
resolver. Чужая конкурентная команда не приписывается текущему attempt.

Контекст передаётся через scoped Tokio task-local только вокруг существующего
`Storage::execute`. До `spawn_blocking` извлекается явный handle контекста,
который захватывает worker closure. Thread-local, «последний запрос» и предположение
о наследовании контекста новым task/worker запрещены. Обычная сигнатура execute
и единый алгоритм сохраняются; без trace-контекста нет событий чужой операции.
Wrapper ответа также владеет явным handle: `body()` может выполняться после
выхода из task-local scope и не должен искать «текущий» завершившийся запрос.

## Часы и схема событий

Все native-события используют один process-local `std::time::Instant` origin
одного коллектора. Он создаётся при arm вне измеряемого интервала. Ns от origin
сериализуются десятичными строками; арифметика анализа — целочисленная.
Arm run создаёт origin один раз; arm следующего attempt меняет ключ и буфер,
но не origin. Новые события завершённого attempt не переходят в следующий.
Событие содержит только schema/run/epoch/attempt/ordinal/name/ns/outcome
и согласованные callback/error ID. Неограниченных строк/произвольных полей нет.
При перезапуске процесса/Activity или смене документа run заканчивается;
прежний origin не переносится и не сравнивается с новым.

JS сохраняет `performance.now`, `timeOrigin` и свой порядковый номер на том же
ключе попытки. Host и Perfetto остаются отдельными шкалами. Никакого вычитания
Instant/performance/elapsedRealtime или смещения по началу evaluation нет.
`clock_snapshot`, wall time и имя trace-секции не заменяют общей метки.

Native timestamp снимается до записи в буфер. Порядок сохранения при конкуренции
может отличаться от порядка timestamps; ordinal не доказывает причинность.
Коллектор заранее выделяет до 64 событий на attempt, не пишет файлы/сеть/SQLite
внутри команды и не ждёт mutex: при contention/overflow/poison выставляет
отдельный sticky error и сохраняет доступные записи. Прикладная команда
продолжается, попытка диагностики считается failed. Ничего не теряется молча.

События нормального успешного пути, имена ещё не реализованы:

| Группа | Native-события |
| --- | --- |
| Dispatch | `dispatch_enter`, `dispatch_return` |
| Async handler | `handler_enter`, `handler_return` |
| Storage | `permit_wait_begin`, `permit_acquired`, `worker_submit`, `worker_enter`, `worker_return`, `storage_return` |
| Commit | `commit_begin`, `commit_end` |
| Serialization | `serialize_begin`, `serialized_body_ready` |
| Delivery observation | `channel_fetch_ack` в отдельном варианте профиля |

Обязательный частичный порядок: dispatch_enter → handler_enter → permit_wait_begin
→ permit_acquired → worker_submit → worker_enter → commit_begin → commit_end
→ worker_return → storage_return → handler_return → serialize_begin
→ serialized_body_ready. `dispatch_return` следует за dispatch_enter, но может
оказаться после начала/окончания async-работы. Worker может стартовать до возврата
spawn_blocking. Native send return на JS-часах не является началом всей Rust-работы.
Нельзя навязывать общий порядок на основании порядка строк в буфере.

`commit_end` пишется только после успешного возврата прежнего commit;
`commit_begin→commit_end` — wall-интервал вызова commit с probes, не чистые
CPU/дисковые затраты SQLite. Worker-интервал также включает чтение/проверки,
вычисления, сохранение и планирование. Границы не переименовываются в «SQLite time».

## Причинная верхняя граница доставки без JNI

Чтобы ограничить путь ready→наблюдаемый fetch на native-часах, отдельный
вариант профиля отправляет одну metadata-only команду `trace_ack` через тот же
Tauri IPC сразу после входа wrapper в целевой channel fetch. Это ещё не
существующая команда. Она feature-gated, не имеет HTTP-маршрута, не читает и не
меняет Storage и не даёт доступа к файлам. Её handler записывает native
`channel_fetch_ack` и возвращает только подтверждение метаданных.

Связь причинная: serialized_body_ready → Tauri/Wry/JS → вход fetch wrapper
→ отправка ack → вход native ack handler. Поэтому разность native
`channel_fetch_ack - serialized_body_ready` даёт только верхнюю границу до
JS-наблюдения fetch, включая задержку ack. Она не даёт точного момента JS-entry,
задержки отдельной очереди или поправки на observer. Из неё нельзя вычитать
медиану ack/no-op. Ack может исполняться одновременно с worker/fetch-доставкой.

Исходный fetch вызывается ровно один раз с прежними this/args и возвращает
тот же Promise, без добавленного then. Отдельный Promise ack хранится наблюдателем,
имеет обработку ошибки и проверяется после основного host/OS-интервала; его отказ
не повторяет мутацию. Исключения/результат исходных callbacks сохраняются.
Регистрации/доставки metadata-команд явно различаются от business/channel
callbacks; отсутствие, дубликат или неверный ключ ack отклоняют измерение.
Дополнительная IPC-нагрузка ack входит в результат и требует отдельного контроля.

Native управление arm/read/disarm также выполняется metadata-only командами
того же Tauri IPC вне интервалов действий. Не добавляются JavaScriptInterface,
собственные JNI/FFI, обход приватных полей или новый канал доставки Storage.
ADR-0024 не расширяется; в core/хранении сохраняется forbid(unsafe_code).
В обычных сборках этих диагностических команд и состояния нет.

## Контроли и условия отклонения

Планируемые отдельные варианты одной диагностической сборки:

- C0: диагностический заголовок и wrapper ответа есть, native probes и ack выключены.
- C1: тот же код/заголовок, native probes включены, ack выключен.
- C2: C1 плюс один channel-fetch ack и его регистрации/ответ.

LOG-183/обычный APK — отдельная исходная популяция, не C0. В каждом варианте
сохраняются 5 прогревов и 30 измерений каждого направления, прежние APK/исходники
фиксируются заново; будущий диагностический APK получает собственный hash и путь.
Последовательность C0→C1→C0→C2→C0 фиксируется до запуска, без параллельных сборок
и измерений. Условия устройства/фона/температурных ограничений записываются.
Различия распределений описывают условия наблюдения, не доказывают чистую цену
probes и не вычитаются. Неполные/разные варианты не объединяются в одну серию.

Для C2 отдельно вне мутаций снять metadata round trip/no-op с теми же границами
и размерами; проверять включение расходов JSON/заголовка/коллектора/ack в полный
host-интервал. «Маленький» расход до измерений не заявляется; новое наблюдение
не переносит приёмку и статистику со старого APK.

Проверки до телефона: точные успешные байты/ошибки сериализации; неизменность
cmd/payload/ключей/прежних headers; частичный порядок с ранним worker и
миграцией task; изоляция конкурентных попыток; коллизия/подмена/stale epoch/
неверный ack; late reply/timeout/cancellation; overflow/contention/poison;
ошибка до и после commit, потеря ответа после commit; очистка hooks/контекста.
Сбой диагностики сохраняет исходный результат операции, не становится rollback
и не вызывает retry. Родственные host-проверки исполняются на Windows/Linux;
core/API/прикладной паритет не меняются. Физическая проверка — отдельный шаг.

На устройстве сохраняются калибровка/эталоны/старое или скрытое изображение/
искусственно задержанное завершение, PNG/RGBA/zlib-сверки, все OS-пиксели и
полные интервалы. События commit сами по себе не заменяют чтение состояния
через прежний IPC. Поиск/запуск/IME/свет матрицы в этот профиль не входят.

## Артефакты и восстановление

Raw сохраняет schema/profile/variant, source/APK hashes, run/attempt/epoch,
native и JS-отметки без смешения часов, потерянные/дублированные события,
ack success/failure, наблюдения OS/снимки A/B и причины отклонения. Частичный
buffer читается вне интервала после каждой попытки и до переустановки APK.
При падении процесса текущие native-записи могут быть утрачены: это missing
evidence, не успешная попытка и не доказанный rollback. Host сохраняет последнее
доступное состояние и отказ без повторения команды.

Заранее архивируются исходный установленный debug APK, его сертификаты,
test APK при наличии, A/B через общий IPC, экранная настройка и ADB forwards.
Диагностическая сборка non-debuggable с прежним application ID и совместимой
тестовой подписью; это локальный тестовый APK, не distribution release.
Сверки подписи/контракта/backup завершаются до замены APK.

Finally снимает JS hooks, закрывает run и экспортирует доступную telemetry,
завершает/копирует собственную трассу при её наличии, возвращает исходные
APK/A/B/test package/настройку/forwards. Затем независимый verifier повторно
сверяет hashes и A/B через исходный debug IPC и останавливает приложение.
Нельзя очищать журналы или память диагностики до экспорта; удаляются только
собственные временные файлы устройства после проверки локальной копии.

## Последовательность реализации

1. Без Android-сборки реализовать и проверить изолированный safe Rust-коллектор,
   ключ попытки и bounded metadata/header parser под выключенным по умолчанию
   feature. Ни probes в Storage, ни новые IPC-команды пока не добавлять.
2. Отдельно проверить adapter hooks, scoped propagation и wrapper ответа на
   host; затем добавить probes в единый путь без изменения бизнес-алгоритма.
3. Отдельно реализовать gated control/ack и host/JS-наблюдатель; проверить
   generated handler/ошибки/точность payload и отсутствие диагностических
   команд в обычной сборке. Команда сборки не появляется в документации заранее.
4. После прохождения проверок собрать отдельные diagnostic application/test
   APK обеих ABI. Проверить disabled/enabled parity, затем AOSP lifecycle.
5. Только при готовом выбранном API 33 ARM64 телефоне, совместимом backup и
   проверяемом восстановлении выполнить заранее выбранные C0/C1/C2-серии.

Каждый следующий срез обновляет EV-024/журнал и точную локальную передачу.
Текущий документ завершает подготовку протокола, а не перечисленные реализации.
