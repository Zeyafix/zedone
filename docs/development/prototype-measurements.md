# Измерения итогового среза P01.11

Сценарии измеряют существующий прототип без новых прикладных операций.
Подготовка и число повторов заданы в [методике P01](prototypes.md#методика-времени-для-p01).
Они не входят в `bun run check`: шум времени CI не является приёмкой устройства.

## Windows

Из `prototypes/` после успешного `bun run check`:

```powershell
$env:PROTOTYPE_BROWSER_PATH = 'C:/Program Files/Google/Chrome/Application/chrome.exe'
bun run measure:desktop chrome
if ($LASTEXITCODE -ne 0) { throw 'Chrome measurement failed.' }
# Повторить отдельно с фактическим исполняемым файлом Opera и меткой opera.
```

Путь браузера выбирают из установленной среды, не загружают инструмент при замере.
Для Opera нужен непосредственный бинарник в каталоге её версии: корневой launcher
может оставлять процесс после закрытия тестового браузера и искажать серию запусков.
Каждый запуск создаёт собственную SQLite в системном временном каталоге и
временные профили браузера. Удаление ограничено каталогом, созданным этим runner.
На ПК используются Rust release и Vite production; по умолчанию браузер запускается headless.
Это автоматизированный контроль доступного среза, не измерение физического экрана.

### Уровень доказательства результата

Команды `measure:desktop` и `measure:android` записывают `ui_measurement_evidence` из общего источника
`measure-scenarios.mjs`: `level: diagnostic`,
`presentation_validation: not_validated`, `ui_acceptance_eligible: false`.
Успешный `passed_available_slice` означает прохождение сценария и проверок
сохранности. Он не доказывает отображение результата и не закрывает UI-бюджет
A62. Значение `over_budget: 0` относится только к указанной границе наблюдателя.
Поле применяется также к временам запуска, завершающимся этим UI-наблюдателем.
HTTP/IPC-ответ и сохранённый снимок остаются отдельными доказательствами.

Наличие обычного окна, `document.hasFocus()` и `page.bringToFront()` не заменяет
проверку видимости и переднего окна в ОС. Desktop-отчёт сохраняет источник выбора
браузера и его исполняемый файл, чтобы ошибочная метка серии не скрывала запуск
браузера Playwright по умолчанию.

Для независимого контроля нужен второй наблюдатель: начало перед системным
вводом и конец по ожидаемым пикселям окна на монотонных часах одного процесса.
Записываются последнее наблюдение прежнего состояния и первое наблюдение
ожидаемого, длительность захвата и интервал неопределённости. Накладные расходы
не вычитаются. Если верхняя граница укладывается в бюджет, это достаточное
свидетельство для измеряемого интервала; пересечение границ с бюджетом означает
неопределённый результат. Требуются положительный контроль, искусственная задержка,
тайм-аут, отказ при уже видимом результате и отказ при недоступном тестовом окне.

Допустим отдельный консервативный вариант: наблюдатель запускается **до**
отправки DOM-команды, а конец определяется ожидаемыми пикселями рабочего стола.
Он даёт верхнюю границу задержки команды с включёнными передачей команды,
выравниванием viewport, если оно нужно, и накладными расходами захвата.
Это не точечная оценка и не нижняя граница задержки команды. Верхняя граница
выше бюджета сама по себе не доказывает превышение приложением: такой результат
неопределённый и требует более точного наблюдения. Учитывать только пиксели
тестового окна, отклонять перекрытый участок и сохранять все неудачные попытки.

Захват изображения рабочего стола Windows подтверждает границу изображения ОС,
а не физический свет экрана. Разницу с физическим показом указывать отдельно;
она требует внешнего наблюдения. Основание монотонных часов —
[Windows QueryPerformanceCounter](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps).
Отдельные кадры браузерного screenshot или отметки DOM не считать независимым
измерением появления результата на рабочем столе. Результаты и статус проверки
наблюдателя хранятся только в `docs/reports/p01-11/`.

Для проверки в обычном окне того же установленного Opera после явного выбора
его исполняемого файла в `PROTOTYPE_BROWSER_PATH`:

```powershell
bun run measure:desktop opera-headed --headed
if ($LASTEXITCODE -ne 0) { throw 'Opera headed measurement failed.' }
```

`--headed` открывает обычное тестовое окно со свежим временным профилем;
runner сам закрывает созданные окна. Без флага сохраняется headless-режим.
Режим записывается в `environment.browser_mode` и описание сборки отчёта;
используйте отдельные метки, чтобы различать серии. Флаг меняет только способ
запуска браузера: команды, границы времени, прогревы, повторы и проверки
снимков остаются общими. Лимиты кадров не отключаются. Headed-прогон также
не является независимым подтверждением физического показа.

Десять отдельных запусков Rust/HTTP и Vite preview измеряются с уже запущенным
браузером. В интервал включены запуск серверов, создание страницы, навигация,
явное чтение сохранённой доски и готовность поля ввода. Запуск браузера измеряется
отдельно. Затем десять перезагрузок страницы измеряются при работающих серверах.
Первый запуск после установки и холодный дисковый кеш ОС не проверяются.

## Android

Существующий [debug APK](android-prototype.md) должен соответствовать проверенным
исходникам. Запустить подготовленный AOSP API 33 AVD без GMS. Из `prototypes/`:

```powershell
$env:ANDROID_SERIAL = 'emulator-5562' # serial именно своего тестового AVD
bun run measure:android
if ($LASTEXITCODE -ne 0) { throw 'Android measurement failed.' }
```

Runner допускает только явно выбранный эмулятор, устанавливает prototype APK,
сохраняет исходный снимок A и восстанавливает его общим API после проверки.
B не изменяется. Он убирает собственный CDP-forward и останавливает APK;
сам AVD останавливает тот, кто его запустил. Debug APK и эмулятор дают только
диагностические результаты. Релизная сборка и Galaxy A32 остаются отдельными
ячейками приёмки; этот runner намеренно не меняет физический телефон.

Десять запусков после `am force-stop` измеряются от команды запуска до рабочего
экрана с сохранённой доской; включены adb/CDP и ожидание сокета WebView.
Повторные десять открытий — возврат через Home при работающем процессе.
Все отметки этой серии берутся с монотонных часов драйвера; системный `am start`
не подменяет время рабочего экрана. Накладные расходы не вычитаются.

## Общий сценарий и границы результата

Оба runner используют `measure-scenarios.mjs`. Каждая серия интерактивного
действия выполняет пять прогревов и тридцать измеряемых повторов:

- Подтверждённое перемещение карточки кнопкой диалога и отдельная обратная команда.
- Поиск `Карточка 0030` с одним результатом и отдельный сброс поиска с 30 результатами.
- Перемещение и обратная команда через API, отдельно от отображения UI.

До каждой пары серий создаётся исходный синтетический набор по общему API.
Подтверждение UI измеряется от DOM-команды существующей кнопки до результата
Rust и обновления DOM с двумя `requestAnimationFrame`. Это граница кадра,
а не доказательство физического показа пикселей. Время передачи мыши/касания,
заполнения диалога и всего жеста не входит; этот результат относится к явной
команде. Часы UI — `performance.now()` самой страницы, без вычитания CDP.
HTTP-ответ на ПК и IPC-ответ через CDP на Android — отдельные диагностические
интервалы драйвера, не сравнительный тест скорости HTTP против IPC.

После каждого перемещения проверяется авторитетный снимок Rust и положение
карточки в UI, после обратной команды — полное равенство исходному снимку.
Поиск проверяет число результатов. Ошибка останавливает серию, сохраняет
частичный отчёт и текущую попытку; пропуски не превращаются в нули или успех.
Тайм-аут UI сохраняется отдельным неуспешным отсчётом.

Отчёты с уникальными именами находятся только в `docs/reports/p01-11/`:
сырые миллисекунды, минимум/медиана/p95 ближайшего ранга/максимум,
число отказов и превышений ориентира, хеш/размер/строки набора, ревизия,
отпечатки исходников сценария/клиента/контракта и бинарника/APK, среда и cleanup.
Не объединять разные браузеры, сборки и устройства в общую статистику.
При ошибке или прерывании проверить cleanup отчёта; при принудительном завершении
процесса автоматическое восстановление не гарантируется.

Открытие содержимого карточки, выполнение/снятие отметки пока отсутствуют.
История, корзина, конфликты, обмен и копирование не реализованы в срезе.
Измерение памяти и масштабирования не подменяется размером APK/пустого процесса.
Даже успешные серии доступных действий не закрывают A62. Состояние проверки —
[EV-024](../agent/verification/EV-024-prototype-review.md).

## Диагностика кадрового наблюдателя: GAP-006

Прежде чем объяснять задержку стоимостью чтения доски, разделить сохранение,
обновление DOM, выдачу кадров браузером и физический показ. Использовать одну
production-сборку, одинаковые данные, viewport и свежие профили браузера:

- Сравнить headless и обычное окно того же браузера без изменения приложения
  или добавления флагов, отключающих лимиты кадров. Проверить чтение, перемещение
  и обратную команду, авторитетный снимок и восстановление исходного состояния.
- Записать интервалы rAF до/после чтения, перемещения и reload; дополнительно
  проверить прокрутку доски в viewport, visibility/focus, таймеры и long tasks.
  `visible` и наличие фокуса сами по себе не доказывают нормальную выдачу кадров.
- Проверить статический HTML без приложения: отдельно fetch без изменения DOM
  и изменение текста. Сохранить как воспроизведения, так и повторы без симптома.
- Снять CDP Tracing с категориями `viz`, `cc`, `devtools.timeline` и
  `renderer.scheduler`. Сопоставить `FireAnimationFrame` renderer страницы с
  `SendBeginFrameDecision`, включая причины `ThrottleUndrawnFrames` и
  `ThrottleUnresponsiveClient`. Общие счётчики без frame sink ID не приписывать
  целиком странице. Механизм решений описан в
  [исходниках Chromium](https://chromium.googlesource.com/chromium/src/+/c4d4f3344d83d2cbc51d57ce6e3efbab91ea2b3b/components/viz/service/frame_sinks/compositor_frame_sink_support.cc).
- DOM-команду и подтверждение DOM отмечать внутри одного вызова страницы.
  Если observer установлен предыдущим CDP-вызовом, явно учитывать этот промежуток
  в названии и трактовке диагностического интервала.

Флаги вроде `--disable-frame-rate-limit` допускаются только как отдельное
диагностическое вмешательство. Исчезновение симптома с таким флагом не означает
прохождение A62. Смена headless на обычное окно также требует отдельного отчёта,
полных серий и независимого наблюдения показа; прежние превышения сохраняются.
Результаты, трассы, их хеши и локальное продолжение — только в
`docs/reports/p01-11/GAP-006-root-cause.md` и связанных файлах.

## Независимые верхние границы по пикселям Windows

После подготовки production-сборки и явного выбора прямого исполняемого файла
Chrome или Opera в `PROTOTYPE_BROWSER_PATH`, из `prototypes/`:

```powershell
bun run measure:desktop:pixels opera
if ($LASTEXITCODE -ne 0) { throw 'Desktop pixel measurement failed.' }
```

Этот отдельный Windows runner использует `desktop-pixel-observer.ps1` с
Windows PowerShell/System.Drawing, без новых зависимостей приложения. Он открывает
собственное headed-окно с временным профилем и синтетической SQLite. Только это
окно временно показывается поверх остальных; переключение фокуса и системный
ввод не требуются. Перед захватом проверяются границы и принадлежность участка
тестовому окну. Перекрытие, недоступный рабочий стол, неподдержанная геометрия
или тайм-аут останавливают прогон и сохраняются в отчёте.
Пиксельные измерители запускаются последовательно: параллельные окна-наблюдатели
взаимно меняют порядок окон и условия захвата, поэтому такие серии не объединяют.

Калибровка ищет полный прямоугольный маркер внутри собственного окна, не
предполагая одинаковые панели Chrome и Opera. PNG калибровки сохраняется в отчёте.
Этот Windows-профиль требует масштаба один пиксель ОС на CSS-пиксель; другой
масштаб отклоняется явно, без отключения проверок DPI или видимости.

Начало интервала — запуск независимого наблюдателя **до** DOM-команды существующей
кнопки. Конец — обнаружение ожидаемого изображения через захват рабочего стола
ОС, без браузерного screenshot и ожидания rAF. Все отметки принадлежат одним
часам Windows QPC. `upper_bound_ms` включает передачу команды/CDP, захват и
выравнивание viewport, если оно нужно; ничего не вычитается. Это верхняя граница,
а не точное время отклика или интервал от мыши/касания. Поле
`arm_to_pixels_lower_ms` относится к наблюдателю и не задаёт нижнюю границу
задержки команды. Проверка матрицы физического монитора сюда не входит.

Перед сериями runner проверяет отказ при уже видимом результате, искусственную
задержку сохранения и тайм-аут скрытого результата при подтверждённом commit.
После контролей исходный снимок восстанавливается. Затем выполняются пять
прогревов и тридцать измерений отдельно для переноса/отмены и поиска/сброса;
сохранённые снимки и число результатов проверяются общим API.

Эталоны строятся отдельно для каждого состояния и проверяются целиком:
перенос — заголовки в исходной и целевой колонках, поиск — полный заголовок
первой карточки, включая перенос строки. Геометрия поиска может различаться
между одним результатом и всем набором. Нельзя считать различие хешей двух
обрезанных участков доказательством правильного результата.

Запуск — две серии по десять. Первая перезапускает Rust/Vite при уже работающих
браузере и наблюдателе; вторая повторно открывает страницу при работающих
серверах. В обоих случаях включены чтение сохранённой доски и выравнивание
показываемого участка. Это отдельный профиль, который нельзя объединять с
прежними reload/force-stop сериями. Создание браузера, первый запуск после
установки и холодный кеш ОС этим runner не измеряются.

Отчёт `<label>-pixels-<timestamp>.json` и PNG остаются в `docs/reports/p01-11/`.
Он содержит все наблюдения/отказы, отдельные контроли, прогревы и отсчёты,
проверки снимков, хеши наблюдателя, клиента, release-бинарника и фактического
production-bundle, геометрию и cleanup. Для статистики явно указан
`metric: conservative_upper_bound_ms`. Верхняя граница в пределах ориентира
подтверждает только измеряемую границу изображения ОС; `upper_bounds_above_budget`
означает неопределённый результат, а не доказанную задержку самого приложения.

Это средство проверки прототипа, а не функциональность выпуска. Переносимость
метода на другие браузеры/геометрию и Android требует отдельной валидации.
Windows runner не запускается в headless CI. Обычные rAF-runner сохраняют
`ui_acceptance_eligible: false`; отдельный пиксельный отчёт не переоценивает их
задним числом и не закрывает A62 целиком. Текущие локальные доказательства и
продолжение — `docs/reports/p01-11/windows-pixel-review.md`.

## Независимые верхние границы по пикселям Android

На явно выбранном тестовом AOSP API 33 эмуляторе без GMS, после подготовки
debug APK и `ANDROID_HOME`/`ANDROID_SERIAL`, из `prototypes/`:

```powershell
bun run measure:android:pixels
if ($LASTEXITCODE -ne 0) { throw 'Android pixel measurement failed.' }
```

Команда использует жизненный цикл и восстановление снимка прежнего Android
runner. Физические устройства отклоняются до установки APK. Изображение
получается через [`adb exec-out screencap -p`](https://developer.android.com/tools/adb#screencap),
не через screenshot WebView или rAF. Начало — часы драйвера до DOM-команды,
конец — получение и проверка PNG ОС. Захват начинается после подготовки DOM,
но часы запускаются до команды; ожидание DOM не завершает интервал и не
заменяет совпадение изображения. ADB, декодирование PNG, CDP и необходимая
прокрутка включены в консервативную верхнюю границу, ничего не вычитается.
Верхняя граница выше ориентира означает неопределённость; она не доказывает,
что само приложение превысило бюджет.

Полный цветной маркер ниже системной строки состояния задаёт масштаб и
смещение WebView. Калибровка ожидает его в реальном изображении, сохраняет
попытки и отвергает неполный маркер, изменение размеров экрана или обрезанные
заголовки. Системные панели не скрываются. Эталоны и первые совпавшие изображения
сохраняются для проверки; успешный DOM сам по себе не завершает наблюдение.

На узком экране карточка 1 перемещается с первого на второе место в колонке 0:
в эталон входят оба изменившихся заголовка. Это отдельный профиль, его нельзя
смешивать с межколоночным переносом Windows. Поиск/сброс проверяют полный заголовок
первого результата и число карточек. Каждое направление имеет пять прогревов и
тридцать измерений; сохранённый снимок проверяется после переноса и отмены.

Контроли отклоняют уже видимое изображение до команды, задерживают один
debug callback с сохранённым результатом на 450 мс и проверяют тайм-аут скрытого
результата при commit в Rust. Временный перехват callback проверяется и снимается
перед сериями. Исходный снимок восстанавливается после контролей.

Запуск — две серии по десять: force-stop/новый процесс и Home/возврат в работающий.
До запуска старое изображение должно исчезнуть в двух захватах ОС; переход Home
не входит в интервал. Время включает запуск Activity, подключение CDP при новом
процессе, чтение сохранённой доски и показ обоих заголовков. Это отдельный профиль,
без первого запуска после установки, сброса кеша ОС или измерения физической матрицы.

Отчёты `android-pixels-<timestamp>.json`/PNG, попытки, исходники наблюдателя и
APK-хеш остаются в `docs/reports/p01-11/`. При ошибке сохраняется текущая попытка;
при прерывании незавершённые операции заканчиваются до восстановления исходного A,
чтобы поздняя команда не изменила данные после очистки. Затем закрываются CDP,
forward и приложение. Принудительное убийство процесса не гарантирует восстановление.

Обычный `measure:android` сохраняет диагностический rAF-профиль. Независимый
эмуляторный захват не подтверждает физический телефон, release APK, системный ввод
или полный A62. Результаты и продолжение — `docs/reports/p01-11/platform-pixel-review.md`.

## Release Android без CDP

Для отдельного release-профиля на том же явно выбранном AOSP API 33 эмуляторе,
из `prototypes/`, с закреплёнными Bun/JDK/SDK/NDK:

```powershell
bun run android:build x86_64 --measurement-release
if ($LASTEXITCODE -ne 0) { throw 'Release measurement build failed.' }
bun run measure:android:release:pixels
if ($LASTEXITCODE -ne 0) { throw 'Release pixel measurement failed.' }
```

`--measurement-release` убирает `--debug` из Tauri-сборки, выбирает release
для [instrumentation tests](https://developer.android.com/studio/test/advanced-test-setup)
и явно включает локальную подпись debug-ключом для совместимой установки тестового
APK. Приложение остаётся non-debuggable; это не настройка продуктовой подписи
или готовый артефакт распространения. Без флага прежняя debug-сборка и её тесты
не меняются. Для второй ABI доступна та же сборка с `aarch64`; измеритель этого
шага по-прежнему принимает только x86_64 эмулятор.

Отдельный `ReleaseMeasurementInstrumentation` находится только в `androidTest`.
Это небольшой Java-драйвер на стандартном Android Instrumentation API: он не
зависит от AndroidX/Kotlin test runtime, классы которого R8 может удалить из
приложения как неиспользуемые. Он находит
WebView через дерево View и вызывает стандартный
[`WebView.evaluateJavascript`](https://developer.android.com/reference/android/webkit/WebView#evaluateJavascript(java.lang.String,android.webkit.ValueCallback%3Cjava.lang.String%3E)).
Адаптер использует локальный Android socket, доступный через временный ADB forward;
соединение принимается только от UID adbd (root/shell). Никакого драйвера, сервера
или JS-интерфейса в основной APK не добавляется. Release не получает CDP/DevTools
подключения: драйвер проверяет флаг приложения и отдельно записывает наличие
WebView debug socket, а instrumentation проверяет `FLAG_DEBUGGABLE` до команд.
Chromium [принудительно включает WebView debugging на eng/userdebug ОС](https://chromium.googlesource.com/chromium/src/+/101.0.4951.61/android_webview/glue/java/src/com/android/webview/chromium/WebViewChromiumAwInit.java);
такой AOSP-эмулятор явно отмечается в отчёте и не подтверждает отсутствие сокета
на обычной user ОС. На user ОС неожиданный debug socket останавливает прогон.
Отключение debugging в retail-окружении остаётся отдельной проверкой; система
и измеряемое приложение ради эмуляторного результата не перенастраиваются.
Тестовый код исчезает из процесса после остановки instrumentation.

Переиспользуется общий Android pixel-сценарий: тот же набор, DOM-кнопки,
снимок Rust/Storage, полные эталоны, контроли прежнего/скрытого изображения,
задержанный callback, пять прогревов и тридцать повторов. Карта callbacks
поставляется закреплённой версией Tauri и в release; наличие карты не включает
WebView debugging. Перехват снимается перед сериями. Начало интервала предшествует
команде, конец подтверждается независимым PNG изображения ОС. Все расходы instrumentation,
ожидания DOM, выравнивания, ADB и PNG включены; ничего не вычитается.

При force-stop завершается и тестовый драйвер в процессе APK. Поэтому серия
запуска включает новый instrumentation process/Activity и подключение
драйвера, помимо запуска/чтения доски. При Home остаётся прежний драйвер.
Эти серии нельзя объединять с debug/CDP или считать обычным запуском пользователя.
Первый запуск после установки, холодный кеш и неинструментированный старт
не проверяются. Верхняя граница выше бюджета сохраняет неопределённый вердикт.

Отчёты `android-release-pixels-<timestamp>.json`, PNG и instrumentation-логи
остаются в `docs/reports/p01-11/`. Сохраняются SHA-256 обоих APK и исходников
драйвера; очистка дожидается текущей команды, восстанавливает исходный A,
снимает ADB forward и останавливает приложение. Установка использует `-r`,
данные приложения не очищаются. Для возврата к прежнему профилю пересоберите
и установите debug APK обычной командой; профиль подписи включается только
в текущем процессе сборки, постоянных изменений окружения нет.

Этот профиль остаётся эмуляторным наблюдением изображения ОС: физическое
устройство, матрица экрана, системный ввод, полный UI/IME и весь A62 не приняты.
Без явного физического профиля скрипт отвергает физический serial до установки.

### OS-захват release через UiAutomation

Release-профиль использует стандартный
[`UiAutomation.takeScreenshot()`](https://developer.android.com/reference/android/app/UiAutomation#takeScreenshot())
в отдельном test APK. API получает изображение дисплея ОС, не `WebView.draw`,
снимок DOM или callback кадра. После полного захвата драйвер обрезает проверяемый
участок и передаёт его PNG по существующему ADB-forward соединению. Так не нужно
запускать `screencap` и передавать весь экран для каждого отсчёта. Приложение,
его release-оптимизация и зависимости не меняются.

Часы по-прежнему запускаются на host до DOM-команды и заканчиваются после
декодирования и совпадения PNG. Захват, обрезка, кодирование, USB/ADB, ожидание
DOM и выравнивание включены без вычитаний. `capture_diagnostics` отдельно сохраняет
длительность host-запроса и внутреннего захвата/кодирования; эти интервалы нужны
для диагностики и не подменяют полный `upper_bound_ms`. Разные часы не вычитаются.
Команда, ожидание сохранённого результата в DOM и выравнивание передаются одной
evaluation-командой, чтобы не платить за отдельный host round trip между ними.
Перед первым release-захватом внутри того же интервала есть пауза 50 мс
(`first_capture_delay_ms`): ранний снимок может застать старый кадр и потратить
полный readback/PNG на его передачу. Пауза не форсирует рендеринг, не вычитается
из времени и не подтверждает показ: при несовпадении наблюдатель продолжает
получать OS-снимки до совпадения или тайм-аута.

Калибровка использует полный OS-снимок. До контролей неподвижный участок с полными
заголовками побайтно сверяется с независимым `adb screencap`; оба PNG и SHA-256
сохраняются в `controls.os_capture_agreement`. Несовпадение останавливает прогон.
Каждый эталон готовится вне измеряемых интервалов: два последовательных ADB PNG
должны совпасть, затем с ними сверяется native-захват. Хеши всех попыток записываются
в `templates[].preparation`. Так ещё не отрисованная прокрутка не принимается
за эталон только по готовности DOM. Само совпадение кадров дополняется проверкой
сохранённых PNG на полный правильный заголовок; неподвижный неверный участок
не является доказательством результата.
Сохраняются прежние контроли старого результата, задержки callback и скрытого
commit. При остановленном instrumentation ADB используется только для проверки
исчезновения старого экрана до запуска часов; после соединения конец интервала
подтверждается UiAutomation. Никакого fallback на DOM/rAF нет.

Соединение UiAutomation не подавляет пользовательские accessibility services
(`FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES`). Геометрия экрана и целостность PNG
проверяются на host; недоступный снимок, изменившийся экран или обрезанный участок
дают отказ. Новые серии содержат `image_source` и хеши обоих APK/исходников;
их нельзя объединять с прежними сериями полного ADB PNG. Физическая матрица,
системный ввод и полная приёмка A62 остаются отдельным непроверенным охватом.

## Release на физическом Android

### Lossless RGBA без PNG-кодирования

Для отдельного эксперимента с тем же OS-участком добавьте последним аргументом
`--raw-pixels`; основной режим по-прежнему использует PNG:

```powershell
# Явный ANDROID_SERIAL, ранее собранный measurement-release и условия backup обязательны.
bun ./scripts/measure-android.mjs --pixels --release --physical --trace-moves --raw-pixels
# Полные серии без Perfetto (перемещение/обратная команда, поиск/очистка, запуск):
bun ./scripts/measure-android.mjs --pixels --release --physical --raw-pixels
```

Отдельный test APK получает полный OS bitmap через прежний UiAutomation API.
[`Bitmap.getPixels`](https://developer.android.com/reference/android/graphics/Bitmap#getPixels(int[],int,int,int,int,int,int))
читает выбранный участок в непремноженном sRGB ARGB; драйвер явно записывает
каналы R/G/B/A в плотные строки. Это устраняет зависимость от native stride и
порядка байтов. После JSON-строки с размерами идут ровно `width*height*4` бинарных
байтов без base64 и PNG. Host разбирает фрагменты TCP независимо от их границ,
проверяет размеры/длину и ограничивает RGBA-кадр 64 MiB. Старые JSON/PNG-ответы
поддерживаются тем же соединением; чисто локальная проверка протокола входит в
`bun run check`. Продуктовый API и основной APK не меняются.

До серий для каждого устойчивого эталона дополнительно кодируется PNG **того же
bitmap** и побайтно сравнивается с RGBA, а затем с двумя независимыми ADB PNG.
Исходные `.rgba` и `.png`, SHA-256, размеры и все попытки подготовки сохраняются
в `same_bitmap_checks`/`templates[].preparation`; несовпадение останавливает тест.
Проверка того же bitmap выполняется только вне измеряемых интервалов. В обычных
RGBA-запросах наличие PNG считается ошибкой. Допуски, масштабирование и
сравнение только части заголовка не вводятся.

Полный host-интервал, пауза 50 мс, калибровка, отрицательные контроли и восстановление
остаются прежними. Получение полного OS bitmap всё ещё необходимо; его стоимость
не вычитается. `capture_and_encode_ms` в RGBA-режиме означает readback и извлечение
каналов, а не PNG. Секция трассы называется `zedone:extract-RGBA`; host/устройство
имеют разные часы. Каждый наблюдаемый отсчёт сохраняется как диагностический PNG
на host **после** окончания интервала; это не device PNG-кодирование в измерении.
Без Perfetto также сохраняются стадии захвата измеряемых действий. Исходные
отсчёты и превышения PNG-профиля остаются отдельными данными.

Имя raw-отчёта содержит `-rgba`, `pixel_transport` равно `rgba8`. Трассировка
остаётся отдельной диагностикой без бюджетной приёмки; серии без неё — верхние
границы по изображению ОС. Увеличение размера USB-передачи и расходы наблюдателя
остаются внутри часов. Смена транспорта не доказывает достижение 300 мс,
физический показ или полный A62. Машинные доказательства и ограничения —
`docs/reports/p01-11/android-rgba-review.md`.

### Lossless-сжатие RGBA

Для проверки расходов несжатого wire payload доступен отдельный opt-in
`--deflate-pixels` вместо `--raw-pixels`. После release measurement-сборки и
явного выбора разблокированного API 33 устройства, из `prototypes/`:

```powershell
bun run measure:android:physical:release:pixels --deflate-pixels
# Отдельный несжатый контроль на тех же APK:
bun run measure:android:physical:release:pixels --raw-pixels
# PNG-default остаётся доступен без обоих флагов.
```

С `--trace-moves` флаг транспорта ставится последним. Несовместимые/повторные
флаги отвергаются до действий на устройстве. `Deflater(BEST_SPEED)` из стандартной
Java-библиотеки сжимает прежние packed RGBA8-байты в независимый zlib stream
каждого bitmap; приложение и зависимости не меняются. JSON `format: rgba8-zlib`
содержит `byte_length` распакованных данных и `wire_byte_length` binary body.
Host проверяет геометрию, лимиты 64 MiB RGBA / 65 MiB wire, целостность/конец
потока и точную длину после распаковки. Лишние данные и повреждения дают отказ.

До серий распакованный RGBA побайтно совпадает с PNG того же bitmap и устойчивыми
независимыми ADB PNG. Сохраняются `.zlib`, `.rgba`, `.png` и SHA-256; в обычных
измеряемых захватах device PNG запрещён. Полный host-интервал включает сжатие,
USB/ADB и распаковку, прежнюю задержку первого захвата и сравнение всех пикселей.
`compression_ms` — диагностические часы устройства, уже включённые в
`capture_and_encode_ms`; они не вычитаются из host и не суммируются с его медианами.
PNG/SHA-256 наблюдений пишутся после интервала, отрицательные контроли,
snapshot-проверки и восстановление телефона прежние.

Raw-отчёт содержит `-rgba-zlib`, `pixel_transport: rgba8-zlib`; остальные режимы
пишут отдельные отчёты. Последовательные прогоны разных транспортов не являются
рандомизированной оценкой выигрыша. Сжатие не подтверждает ориентиры само по себе.
Локальные серии, точные исходники/APK, проверки и передача —
`docs/reports/p01-11/android-deflate-review.md`. A62 partial/GAP-006 in_progress;
физическая матрица, системный ввод и полный UI/IME требуют отдельной проверки.

### Повтор транспортов на эмуляторе

Для отдельного сравнения текущей версии на явно выбранном AOSP API 33 x86_64
эмуляторе, после сверки исходников и application/test APK с manifest:

```powershell
bun run measure:android:release:pixels --deflate-pixels
bun run measure:android:release:pixels --raw-pixels
bun run measure:android:release:pixels
```

Запускать последовательно без сборок/других измерений. Каждый профиль сохраняет
полные 5+30 и 10+10, прежние контроли и верхние границы целиком. До/после
независимо сверять A/B через общий Rust IPC. При использовании собственного
read-only/no-snapshot AVD проверять сохранность постоянных образов и останавливать
только свой процесс. Телефон этим профилем не проверяется и не изменяется.

Сравнение с телефоном должно отдельно показывать host-интервалы запросов захвата
и диагностический capture_and_encode_ms устройства; compression_ms уже входит
в последнюю метрику. Для per-action стадий доступны RGBA/zlib; PNG-default
сохраняет общую native-диагностику без diagnostic_stages каждого действия.
Явно задавайте популяцию статистики: подготовка/контроли/startup не равны
тридцати измеренным перемещениям. У PNG byte_length — размер PNG до base64,
а не фактическая длина JSON/base64 на проводе. Медианы стадий не складывать,
часы host/device не вычитать, чистое время приложения из остатка не выводить.

ОС/WebView/ABI, полный экран и участок, GPU/эмуляция и USB/ADB различаются:
последовательное сравнение не является причинным экспериментом о железе.
Отказ already-visible до команды сохраняется отдельно; неполный профиль не
принимается и guard не отключается. DOM-сброс после подготовки эталона поиска
сам по себе не доказывает возврат исходного OS-изображения перед запуском часов.
После сброса `search-one` runner проверяет прежнюю геометрию `search-all` и
до первого поискового прогрева ждёт совпадения с **ранее проверенным** полным
эталоном: два последовательных ADB-снимка и снимок текущего OS-наблюдателя.
Одинаковые устаревшие изображения не принимаются за новый эталон. Подготовка
имеет дедлайн 10 с; опоздавший захват, тайм-аут или ошибка останавливают профиль.
`search_preparation` сохраняет статус, ожидаемый SHA-256, источники/хеши/совпадения
всех попыток и время подготовки, включая отказ. Это ожидание относится только
к возврату исходного состояния после создания эталонов и остаётся вне серий.
Guard already-visible по-прежнему отдельно проверяется непосредственно перед
командой; начало часов, команда поиска/очистки, выравнивание и прежняя пауза
первого захвата остаются внутри полного измеряемого интервала.
`bun scripts/check-android-pixel-baseline.mjs` из `prototypes/` проверяет
устаревший кадр, краткое совпадение, расхождение ADB/наблюдателя, опоздание,
тайм-аут и ошибку захвата; проверка включена в `bun run check`.
Локальные результаты, исходные отказы, manifest, сравнение и дальнейшая
передача — `docs/reports/p01-11/emulator-transports-review.md`.
Ограниченное исправление подготовки и отдельные повторные серии —
`docs/reports/p01-11/search-preparation-review.md`; прежние отчёты не меняются.

### Диагностическая системная трасса перемещения

Следующий профиль предназначен для локализации GAP-006. После той же release-сборки
и явного выбора устройства добавьте последний аргумент `--trace-moves`:

```powershell
# AOSP-эмулятор; для выбранного телефона добавьте --physical перед --trace-moves.
bun ./scripts/measure-android.mjs --pixels --release --trace-moves
if ($LASTEXITCODE -ne 0) { throw 'Move trace failed; inspect cleanup and trace evidence.' }
```

Калибровка, устойчивые эталоны, ADB/UiAutomation-сверка и отрицательные контроли
остаются обязательными. Perfetto записывается только во время пяти прогревов и
тридцати перемещений в каждом направлении; поиск и запуск в этом профиле
не выполняются. Это отдельный диагностический запуск, который не заменяет
прежние серии без трассировки и не переоценивает их превышения.

[`Perfetto`](https://perfetto.dev/docs/getting-started/system-tracing) запускается
с подтверждением готовности источников (`--background-wait`), ограниченными
буфером/файлом/временем и локальным выводом. Записываются планировщик, категории
Android gfx/view/webview/wm/binder и FrameTimeline. Секции
[`android.os.Trace`](https://perfetto.dev/docs/getting-started/atrace) находятся
только в test APK: идентификатор действия, evaluation, OS-readback и
crop/PNG/base64. Они включаются только диагностическим запросом. Основной APK,
release-оптимизация и API приложения не меняются.

`diagnostic_stages` связывает идентификатор секции с окончанием команды,
началом первого захвата и временем каждого PNG на монотонных часах host.
Каждый PNG сохраняется с SHA-256 после окончания полного интервала; снимки
нужны для различения старого и ожидаемого изображения. Интервалы host и
Perfetto не вычитаются друг из друга. Системный кадр без совпавшего PNG не
подтверждает отображение конкретных заголовков; FrameTimeline не заменяет
наблюдение физической матрицы. Накладные расходы трассировки остаются частью
диагностического профиля.

В `finally` останавливается только созданная Perfetto-сессия, затем трасса
копируется в `docs/reports/p01-11/` и удаляется её собственный файл на устройстве.
Трасса/конфигурация, raw JSON, PNG и результаты SQL-анализа остаются локальными.
Проверяйте полноту секций, статистику потерь и совпадение PNG до выводов.
Недоступная трасса или отсутствие нужных событий — ограничение диагностики,
а не подтверждение быстродействия. Возврат исходных данных/APK/настроек
выполняется прежним внешним `finally`, включая ошибку трассировки.

Для отдельной zlib-трассы используйте
`--pixels --release --physical --trace-moves --deflate-pixels` на выбранном
телефоне. В ней `zedone:deflate-RGBA` вложена в `zedone:extract-RGBA`, которая
уже включает сжатие; складывать эти длительности нельзя. Для каждого действия
сверяйте evaluation, число capture и вложенность OS-readback/extract/deflate,
а каждый сохранённый PNG — с ожидаемым эталоном. Статистика host относится
к действиям, device readback/extract/deflate — к отдельным захватам; при повторных
захватах размеры популяций различаются. Прогревы исключаются отдельно.
Отсутствие потерь буфера не отменяет ошибок timestamps/scheduler и незавершённых
FrameTimeline: они ограничивают выводы о кадрах и чистом времени приложения.
Отдельная диагностика, исходники/APK, независимые проверки восстановления
и актуальная передача — `docs/reports/p01-11/zlib-move-trace-review.md`.
Статический контроль наблюдателя проводится отдельно от действий;
его расходы не вычитаются из полных интервалов и не заменяют приёмку A62.

### Статический контроль OS-наблюдателя

После прежней подготовки/backup телефона, без пересборки неизменных APK:

```powershell
bun ./scripts/measure-android.mjs --pixels --release --physical --trace-static --deflate-pixels
if ($LASTEXITCODE -ne 0) { throw 'Static control failed; inspect raw, trace and restoration.' }
```

`--trace-static` требует release/zlib и исключает `--trace-moves`. Прежние
калибровка, эталоны, ADB/same-bitmap и отрицательные контроли выполняются до
статической серии. Затем известный normal-эталон подтверждается двумя ADB
снимками и текущим наблюдателем. Пять прогревов и тридцать измерений содержат
только захваты — без evaluate, команд приложения, IPC, DOM-выравнивания и retry.
Каждый кадр сохраняется; несовпадение/ошибка прерывают профиль с диагностикой.
`static_observer` содержит повторы/метки/PNG/SHA-256, проверку DOM-мутаций,
неизменности HTML и A/B. Снимки Storage читаются только вне статической серии.

`capture_request_ms` — host-запрос до декодированного OS-изображения, включая
захват/извлечение/zlib/передачу/inflate. Пауза 50 мс между запросами и сохранение
PNG выполняются отдельно от этой метрики; это не полный интервал UI-действия.
Прежний `observe()` и его часы/guard не меняются. В статической трассе ожидается
один capture/readback/extract/вложенный deflate на повтор и ноль evaluation.
Сравниваются отдельные популяции с явными N/каденсом, без сложения медиан или
вычитаний из действий. Отсутствие событий FrameTimeline не доказывает отсутствие
всех перерисовок ОС. Подробности, точные исходники/APK, ошибки трассы и
восстановление — `docs/reports/p01-11/static-observer-review.md`.
`bun scripts/check-android-static-pixels.mjs` включён в общий check: 5+30,
отказ без retry, раздельные часы, ошибки capture/file output, сброс метки и CLI.

### Контроль пустого native evaluation

Отдельный no-op профиль использует тот же test APK и ADB socket:

```powershell
bun ./scripts/measure-android.mjs --pixels --release --physical --trace-noop --deflate-pixels
if ($LASTEXITCODE -ne 0) { throw 'No-op control failed; inspect setup, raw, trace and restoration.' }
```

`--trace-noop` требует release и прежний zlib для подготовительных OS-контролей,
исключает другие trace-профили. В серии нет бинарного zlib payload: только
5 прогревов и 30 фиксированных `() => null` через прежний JSON/evaluate-драйвер.
Ожидается ровно `null`; неожиданный ответ или ошибка сохраняются и прерывают
профиль без retry. Захватов/DOM-выравнивания/Storage-команд в серии нет.

`evaluation_request_ms` — host-запрос до декодированного ответа, без паузы
50 мс между запросами. Native `:evaluate` включает dispatch/poll/запись ответа
и последующую WebView cleanup; его конец отличается от конца host-запроса.
После серии отдельный запрос без метки дожидается завершения последней
помеченной секции до остановки/flush Perfetto. В трассе ожидается 35 завершённых
помеченных evaluation и ноль capture. DOM/HTML/A/B и OS-участок проверяются
вне серии; прежние калибровка/контроли/backup/восстановление обязательны.
Проверки 5+30/часов/ошибок/ответа/сброса метки и CLI включены в общий check.
Результаты не вычитаются из команд и не заменяют приёмку A62.
Точные исходники/APK, исходные отказы до серии, отдельные host/native
популяции, ошибки трассы и независимое восстановление —
`docs/reports/p01-11/noop-evaluation-review.md`.

### Фазы команды внутри WebView

Отдельный `--trace-webview` требует `--pixels --release --deflate-pixels`
и исключает `--trace-moves`, `--trace-static`, `--trace-noop`, `--trace-ipc`. Для явно выбранного
готового телефона из `prototypes/`:

```powershell
bun ./scripts/measure-android.mjs --pixels --release --physical --trace-webview --deflate-pixels
if ($LASTEXITCODE -ne 0) { throw 'WebView phase diagnosis failed; inspect raw evidence and restoration.' }
```

Это отдельная диагностическая серия с прежними application/test APK, а не
новый вариант приёмочных измерений. Android-пересборка не нужна, если хеши APK
и их исходников совпадают с проверенной версией. Изменяется только JavaScript,
передаваемый прежнему драйверу: команда, ожидание результата и выравнивание
по-прежнему выполняются одной evaluation. Обычный профиль использует ту же
функцию без сбора фаз. Приложение, общий Rust API и Storage не меняются.

`webview_phases.entries` связывает каждый из 5+30 переносов и обратных команд
с попыткой и селектором. `result.phases` содержит `performance.timeOrigin`,
монотонные отметки `start`, `click_start`, `click_end`, `saved_dom`, `aligned`
на одних WebView-часах, число проверок и прежний шаг опроса 10 мс.
`durations_ms` вычисляется только между этими отметками: подготовка до click,
синхронный click, ожидание сохранённого DOM, выравнивание и общий интервал.
Ожидание DOM включает шаг опроса и работу WebView, поэтому не является чистым
временем Rust/SQLite. Эти часы не вычитаются из host или Perfetto.

При отказе сохраняются доступные отметки и ошибка, команда не повторяется.
Неверный порядок/отсутствие отметок, геометрия или транспортный отказ прерывают
профиль. Отрицательные контроли, исходные снимки, независимые OS-пиксели,
пауза первого захвата и полный host-интервал остаются прежними. Perfetto
охватывает перемещения в отдельной сессии `webview`; каждому действию требуется
evaluation и захваты с соответствующими PNG. Поиск и запуск не измеряются.
Восстановление исходных APK/A/B/настроек выполняет прежний `finally`.

`bun scripts/check-android-webview-phases.mjs` проверяет сериализацию функции,
ожидание асинхронного результата, прежний результат без диагностики, частичные
ошибки без retry, отметки/геометрию и CLI до доступа к устройству; включён
в общий check. Детерминированные проверки не заменяют телефонную серию.
Локальные исходники, APK, результаты, ошибки трассы и передача —
`docs/reports/p01-11/webview-phases-review.md`. A62/GAP-006 этим режимом
автоматически не закрываются; no-op/статический захват из действий не вычитаются.

### Доставка ответа IPC и наблюдение сохранённого DOM

Отдельный `--trace-ipc` требует `--pixels --release --deflate-pixels` и исключает
остальные `--trace-*`. На явно выбранном готовом телефоне из `prototypes/`:

```powershell
bun ./scripts/measure-android.mjs --pixels --release --physical --trace-ipc --deflate-pixels
if ($LASTEXITCODE -ne 0) { throw 'IPC phase diagnosis failed; inspect partial evidence and restoration.' }
```

Режим повторяет 5+30 перемещений и обратных команд с прежними APK, операциями,
контролями, OS-пикселями и полным host-интервалом. Поиск/запуск не выполняются.
Внутри прежней одной evaluation временный собственный метод `callbacks.set`
наблюдает регистрацию и доставку существующего ответа Tauri IPC. Установленный
чужой метод не заменяется. Исходный callback получает те же аргументы и `this`,
его результат/исключение передаются без повторного вызова. Дополнительных
команд сохранения, задержек и изменений приложения/Storage нет.

`webview_phases.entries[*].result.phases.ipc` содержит регистрации и доставки
callback: отметку входа, окончания синхронного callback, признак ожидаемого
снимка и результат очистки. Ожидается ровно один ответ со снимком из 30 карточек
и запрошенным порядком первых карточек колонки 0 у callback, зарегистрированного
синхронно обработчиком click (`during_click`). Tauri может отдельно получать
крупный ответ из внутреннего кеша через новый invoke и затем передавать тот же
снимок исходному callback. Последующие регистрации и доставки тоже сохраняются,
но не принимаются за ответ обработчику кнопки. Часы — тот же `performance.now` и
`timeOrigin`, что у click/сохранённого DOM/выравнивания. `ipc_durations_ms`
различает click→ответ, ответ→наблюдаемый DOM, синхронный callback и
окончание callback→DOM. Callback вложен в ответ→DOM: длительности не складываются.
Опрос DOM сохраняет шаг 10 мс и не доказывает точный момент DOM-мутации.

`finally` удаляет только собственный метод и возвращает исходные callbacks
для ещё ожидающих ответов, чтобы поздняя доставка после тайм-аута не оставила
наблюдатель. Ошибка очистки/отсутствие либо повтор ожидаемого ответа прерывает
профиль с частичными evidence без retry. Прежний внешний `finally` восстанавливает
APK/A/B/test package/настройку экрана; проверка восстановления независимая.

`check-android-ipc-phases.mjs` включён в общий check: аргументы/this/результат
callback, асинхронный ответ и DOM, неверный/повторный ответ, ошибки без retry,
поздняя доставка после тайм-аута и владение методом. Эти проверки не заменяют
телефонную серию. Точные исходники/APK, raw/PNG/Perfetto, статистика/ошибки
и передача — `docs/reports/p01-11/ipc-phases-review.md`.
Click→ответ включает обработчик, мост и планирование, а также работу ядра;
это не чистое время Rust/SQLite. Отдельные контроли/часы/медианы не вычитаются,
свет физической матрицы и полная приёмка A62 этим режимом не подтверждаются.

### Подготовка и восстановление телефона

После явного выбора тестового телефона с Android 13/ARM64 и разрешённой USB-отладкой,
при установленном debug-прототипе с совместимым контрактом, из `prototypes/`:

```powershell
bun run android:build aarch64 --measurement-release
if ($LASTEXITCODE -ne 0) { throw 'ARM64 release measurement build failed.' }
# ANDROID_SERIAL задаётся явно по adb devices; не выбирать первый доступный телефон.
bun run measure:android:physical:release:pixels
if ($LASTEXITCODE -ne 0) { throw 'Physical release measurement failed; inspect restoration evidence.' }
```

Профиль требует отдельного `--physical`, проверяет API/ABI и отвергает эмулятор.
Требование отсутствия GMS относится к AOSP-профилю; установленный GMS телефона
не удаляется и не отключается. `android-physical-backup.mjs` сохраняет исходный
APK, сертификаты, тестовый APK при его наличии и снимки A/B через тот же IPC.
CDP используется только для резервной копии/проверки исходного debug APK, вне
измеряемого интервала release. Если исходный APK не debug или сертификаты не
совпадают, прогон останавливается до замены приложения. Автоматического удаления
основного приложения или прямого доступа к SQLite нет.

После `install -r` сверяются A/B. На время теста включается удержание экрана
при USB-питании; прежнее значение `stay_on_while_plugged_in`, включая отсутствие
ключа, записывается и восстанавливается в `finally`. Телефон должен быть разблокирован:
драйвер не обходит экран блокировки и не меняет яркость/масштаб/системные панели.

Измеряемый release использует тот же instrumentation-драйвер без CDP и тот же
OS-image сценарий. На user ОС наличие WebView debug socket является отказом.
Все расходы USB/ADB, native evaluation и PNG включены. Выход верхней границы
за ориентир — неопределённость метода, а не доказанное превышение самим приложением.
После серий восстанавливается A, проверяется неизменность B, возвращаются исходный
APK и прежний тестовый APK (либо удаляется созданный измерителем), через IPC
повторно сверяются A/B и восстанавливается настройка экрана. Ошибка любого
восстановления даёт ненулевой код и отдельное поле отчёта; резервные копии сохраняются.

Общий защитный лимит физического драйвера — десять минут, эмуляторного — пять.
Он записывается как `driver_deadline_ms` и не меняет ориентиры отдельных действий
300/1000/3000 мс. Захват и передача PNG входят в каждую измеряемую верхнюю границу.
Прерванные попытки сохраняются целиком и не засчитываются как полные.

Отчёты `android-physical-release-pixels-<timestamp>.json`, PNG, резервные копии,
сертификаты и исходные отказы остаются в `docs/reports/p01-11/`. Это изображение ОС
реального устройства, без подтверждения света физической матрицы, системного
ввода, первого запуска после установки или полного A62. Свидетельства эмулятора
и телефона не объединяются. Принудительное убийство host-процесса/отключение
кабеля не гарантирует автоматическое восстановление: при таком отказе сначала
вернуть исходный APK/настройку и сверить сохранённые снимки, затем повторять тест.
