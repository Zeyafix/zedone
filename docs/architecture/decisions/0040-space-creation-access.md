# ADR-0040: создание пространств без отдельного разрешения

Дата: 2026-11-06. Продуктовое решение разработчика — LOG-296/297.
Техническая подготовка P04.01.1 — [EV-062](../../agent/verification/EV-062-combined-access.md).

## Правило продукта

Любой субъект с действующим доступом, включая администратора и субъекта
с доступом только для чтения, может создавать пространства. Отдельного
выдаваемого права создания нет. Аутентификация, отзыв, срок и проверка времени
сохраняются; один лишь известный ID субъекта не даёт доступа.

При создании субъект получает чтение и изменение нового пространства.
Прежние права на остальные пространства остаются прежними. Администратор
сохраняет администрирование и получает только точный доступ к новому
пространству; права на существующие чужие пространства из этого не следуют.
Доступ создателя принадлежит тому же субъекту и его действующему разрешению,
не становится бессрочным или неотзываемым правом владельца. Правило одинаково
для человека и агента через общий API Windows/Android.

Это уточняет взаимоисключение областей из ADR-0037. Принцип ADR-0029
«администрирование само по себе не даёт доступа к данным» сохраняется:
совмещаются явные полномочия, а не вводится обход проверок пространств.

## Подготовка модели P04.01.1

`GrantScope::AdministrationAndSpaces` хранит администрирование и непустую
карту точных пространств с Read/ReadWrite. Обычные Administration и Spaces
сохраняются. Общий guard проверяет эти составляющие независимо. Требование
`RequiredAccess::ActiveGrant` означает любое текущее допустимое разрешение
для будущего обработчика создания, не отдельное выдаваемое полномочие
и не разрешение работать с произвольным существующим пространством.

Используются прежние таблицы access_principals/access_spaces/access_keys.
Схема v4 имеет тот же DDL, что v3, но допускает одновременную администрацию
и точные права на пространства. Версия нужна для нового семантического
инварианта: прежний бинарный файл должен отказаться от неизвестной схемы,
а исторические validators v2/v3 должны продолжать отклонять повреждённое
состояние, где области совмещены. Такое повреждение не становится допустимым
только из-за запуска новой версии.

Переход v3→v4 проходит штатный защищённый startup: проверка исходной версии,
полный проверенный комплект копий, одна транзакция и проверка целевого состояния,
публикация свидетельства. Данные и права не преобразуются и не расширяются.
Прямой переход с v1/v2 сохраняет прежние переходы и их проверки. Watermark,
ключи/tombstones, субъекты, actor, журналы, peers и receipts сохраняются.
Формат снимка пространства остаётся v1; локальные права в него не входят.

Доверенные issue/replace/revoke поддерживают совмещённую область с теми же
правилами: выдача только на существующие пространства, новый ключ при замене,
прежний субъект/receipts и запрет оживлять старые ключи. Можно снять только
данные, оставив администрирование, либо после передачи управления снять
администрирование. Последний бессрочный администратор защищён и при совмещении.
Снятие и повторная выдача прав не удаляют данные пространства.

`access.inspect`/`access.revoke` возвращают строгую область
`{kind: "administration_and_spaces", spaces: {<id>: "read" | "read_write"}}`.
Те же Rust-типы выводят OpenAPI/TypeScript/standalone validator; отдельной
клиентской модели прав нет. Операций выдачи прав через HTTP/CLI/IPC этот срез
не добавляет, доверенная инфраструктура не становится пользовательским API.

## Следующий срез

Создание самого пространства и атомарное добавление точного RW создателю
в одной транзакции с данными/receipt, а также чтение, переименование и обратимое
удаление пустого пространства — P04.01.2 после интеграции P04.01.1.
Обработчик сам проверяет ActiveGrant, не принимает готовые полномочия от клиента
и не возвращает успех до commit. Проигранный/отменённый запрос, отказ прав
или диска не должен оставить пространство без доступа либо доступ без
пространства. Повтор не создаёт второй объект и не возвращает снятые позже права.
Этот договор ещё не означает, что прикладные операции уже реализованы.
