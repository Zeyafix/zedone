# ADR-0030: актуальность и атомарный повтор команды

Дата: 2026-11-05.

Статус: техническое решение P03.04. Договор ADR-0007/0008/0014 не меняется.
Проверки и ограничения — [EV-047](../../agent/verification/EV-047-command-replay.md).

## Решение

`core::replay::execute` работает внутри доверенной сериализуемой транзакции.
Обработчик core валидирует неизменные параметры, определяет все требуемые права
и передаёт типизированную команду; транспорт не передаёт callback/права/субъекта.
После ожидания worker общий `with_authorized` заново проверяет учётные данные,
текущие права и часы. Только после этого разрешены чтение результата и цели.

ID — 16 байт, ненулевой; новое намерение требует нового случайного ID с
криптографически надёжным источником на клиенте. Формат HTTP/CLI/IPC и генерация
клиентом будут закреплены P03.05/P05. Область ID — аутентифицированный стабильный
субъект в локальной базе установки. Субъект не является отображаемым именем или
секретом; смена технического ключа того же субъекта не создаёт новое намерение.
Внутренний ключ — JSON-кортеж `("zedone.command.v1", subject, id)`, без склейки
разделителями. Операция не входит в ключ, чтобы её изменение давало mismatch.

Исходный запрос сохраняется как JSON-кортеж `(1, Command::NAME, command)`:
типизированные значения, стабильный порядок ключей объектов через Serde JSON
Value, все цели, параметры и исходные условия. Это внутреннее представление
закреплённых Rust-типов, не сравнение байтов транспортного JSON и не общий
стандарт канонизации произвольного JSON. Порядок массивов значим; транспорт не
может самовольно нормализовать параметры. Версия имени операции отражает её
договор, а не выбранный транспорт. Изменения формата требуют сохранения чтения
прежних записей или явного безопасного отказа, а не нового исполнения старого ID.

- Для уже зафиксированного ключа иной запрос даёт `command_mismatch`.
  Идентичный возвращает исходный результат с внутренним `replayed=true`, без
  вызова обработчика, проверки старого условия и новой правки. Текущие данные,
  история, последующее восстановление/обратное действие остаются прежними.
- Для отсутствующего результата обработчик читает авторитетное состояние и
  вызывает общий `require_current` до мутации в той же транзакции.
  `stale_state` требует перечитывания и нового явного действия; подмены версии нет.
- Успешный результат сериализуется и вставляется вместе с изменениями.
  SQL/сериализация/ошибка обработчика откатывают запись; ошибка commit, паника
  и потерянный ответ остаются `outcome_unknown`. Клиенту нельзя передавать
  промежуточный успех `execute` до успешного завершения `Storage::transact`.
- Отказы не сохраняются как выполненные команды и не разрешают автоматического
  изменения намерения. Защита mismatch опирается на существующую долговечную
  запись выполненной команды. Повтор после неизвестного исхода сохраняет весь
  первоначальный запрос и ID; для нового намерения нужен новый ID.
- Повреждённый/нечитаемый результат даёт отказ, а не повторное исполнение.
  Права повторно проверяются даже для результата, которого уже нет в текущем UI.

## Признак актуальности

`StateVersion` — непрозрачные 32 байта SHA-256. Storage вычисляет его из
версионированной области (пространство, вид и ID цели, формат проекции) и
согласованной проекции проверяемого состояния. Права этим признаком не выдаются.
SHA-256 берётся из уже закреплённого транзитивного `sha2 0.11.1`; core не
получает зависимостей SQL/Automerge/хеширования, версии пакетов не обновляются.

Проекция включает проверяемые данные, сохранённые варианты и причинные
идентичности соответствующих операций. Для контейнера включаются данные и
состав содержимого, включая причинные сведения добавления/удаления. Поэтому
изменение с возвратом прежнего значения/состава не оживляет старый признак.
Для карточки обязательны все данные ADR-0007; техническая фиксация истории и
правка другой карточки без влияния на эти данные не входят в её проекцию.
Все множества и варианты упорядочиваются стабильно.

Глобальные heads пространства слишком широки для карточки, а хеш только
видимых значений пропускает изменение с возвратом. Независимая таблица счётчиков
создаёт вторую модель состояния и сложность при обмене. Выбрана производная
проекция из того же графа, без нового кэша или схемы. Точные продуктовые проекции
создаются и проверяются вместе с операциями P04; синтетическая карточка P03.04
не становится продуктовой моделью. Тест вложенной проекции не принимает
продуктовое удаление контейнера.

## Хранение и границы

`ReplayTransaction` задаёт минимальный порт. `Storage::transact` получает
`BEGIN IMMEDIATE`, проверяет схему 1 и фиксирует граф/actor/peer/результат одной
транзакцией. `WriteContext::record` только вставляет результат; перехват ошибки
записи всё равно запрещает commit. Прежний низкоуровневый `Storage::write`
сохраняется для инфраструктуры и не становится альтернативным API.

Результаты не истекают и не ротируются автоматически. Их рост пока не ограничен
и относится к DEC-009; техническое удаление записей по сроку небезопасно, поскольку
превратит старую команду в новую. Потеря/подмена базы, откат на старую копию и
очистка сведений не входят в гарантию обычного restart. До включения таких
сценариев P07 обязан сохранить сведения о выполнении либо обеспечить безопасный
отказ старым намерениям/области установки. Переустановка не восстанавливает права
из копии пространства (ADR-0016). Полное аварийное восстановление требует
отдельной защиты; текущий executor её не предоставляет.

Ограниченный обработчик и источник прав существуют только в `cfg(test)`.
Реальных источника прав/часов, их персистентности/согласования, bootstrap,
продуктовых команд, транспорта и UI пока нет. Схема 1 не меняется; до изменения
сохраняемой пользовательской схемы обязательны P07.07/P07.08.
Клиентские число попыток/паузы/таймауты, полная матрица карточек/контейнеров,
адаптеры и бюджет приложения не приняты; DEC-003 и T06 остаются открыты/partial.
