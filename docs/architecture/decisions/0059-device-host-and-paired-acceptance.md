# ADR-0059: постоянный защищённый host и сквозная приёмка подключения

Дата: 2026-11-15. P06.01.2.5, EV-102. Продолжает ADR-0055–0058.

## Host и транспорт

DeviceHost связывает прежние PairingHost, Service и SessionLifecycle.
SecureListener принимает TCP по явно заданному SocketAddr и обслуживает только
TLS 1.3 с сохранённой identity. Нет plaintext fallback, redirect или получения
pin из непроверенного соединения. Одновременно допускаются не более восьми
соединений; handshake ограничен пятью секундами, вся серверная обработка —
пятнадцатью. Число задач ограничено, завершённые задачи удаляются. Shutdown
закрывает приём и ожидает допущенные задачи; потерянный ответ остаётся unknown.

TLS listener объединяет `/v1/pairing/*`, прежний `/v1/commands/*` и отдельные
высокоуровневые `/v1/host/session.*`. Обычные команды проходят неизменённый
Service с актуальными SQLite access_*, включая проверки перед replay и commit.
Pending secret не открывает обычные команды и не подтверждает собственный запрос.
Все HTTP-маршруты отклоняют неоднозначную аутентификацию и браузерный Origin;
контрольные операции не раскрывают сырые ключи, слоты или callback хранилища.

Высокоуровневым операциям локального host требуется ManageDevices. Они
подготавливают/отправляют/просматривают/обновляют/отменяют/отвязывают собственную
сессию. Универсального remote-data proxy в этом API нет: администрирование
локального устройства не даёт неявных прав на пространства другого principal.
Trusted native `peer_command` заимствует сохранённый ключ и вызывает тот же
удалённый Service; это не JSON/HTTP/renderer-операция. Агент обращается к обычному
API с собственным явно выданным доступом. Формы и обмен пространствами отдельно.

## Сохранение и композиция платформ

ZDPN v2 добавляет SocketAddr к прежней защищённой записи с pin/ключами/request.
Адрес публикуется и сохраняется вместе с намерением до первого сетевого запроса.
ZDPN v1 остаётся читаемым; без сохранённого адреса автоматическое подключение
недоступно, адрес не угадывается. Перенос pending→connected сохраняет точные байты
обеих версий и правила ADR-0058. IP-адрес/порт и pin не подменяются при retry.

Публичный случайный namespace установки сохраняется отдельно от SQLite через
create_new и точное чтение; повреждённый файл не заменяется. Windows использует
Credential Manager, Android — прежний AndroidSecrets→PluginHandle→Kotlin Keystore.
Никакого нового plaintext fallback для сетевых секретов нет.

CLI `--listen` держит явный listener до сигнала завершения, загружая существующую
базу и проверяя административный ключ; bootstrap отсутствует. `--endpoint`
доставляет исходный JSON по pinned TLS, читая pin и ключ из файлов, не argv.
Android composition предоставляет device_host_start/stop/device_session через
native IPC и использует тот же DeviceHost. Слушатель живёт в процессе приложения;
автостарт ОС/foreground service/фоновая работа закрытого APK остаются P08.

## Отрицательная попытка

При неверном коде открытого приглашения транзакция сохраняет отрицательный
receipt конкретной неизменной попытки вместе со счётчиком failures. Повтор
неизменной попытки не расходует ещё одну попытку; изменение намерения с тем же
идентификатором запрещено. Ни код, ни pending key в receipt не попадают, только
verifiers/исходный запрос. Ошибка записи откатывает также счётчик.

Известный отказ такой попытке позволяет удалить временный OS-слот: поздний
повтор не создаст доступ после потери секрета. Неизвестное приглашение отвечает
unavailable и сохраняет сессию, поскольку его публикация могла быть в процессе.
Неизвестные ID не выделяют отрицательных receipts; locked/expired/cancelled/used
не создают новых receipts для бесконечных запросов. Записи отрицательных попыток
ограничены пятью на приглашение. Терминальные состояния приглашения не оживают;
доверенные часы не возвращают истёкшее приглашение к активности.

## Сквозная проверка

Отдельный debug feature pairing-acceptance создаёт изолированный APK-стенд.
В обычном APK его кода нет; release с этим feature отвергается компилятором.
Тестовый bootstrap/фиктивный локальный ключ и тестовый маршрут peer_command
существуют только в этом стенде, не становятся возможностями продукта.

Windows fixture использует настоящий Credential Manager; Android fixture —
настоящий Rust→Kotlin Keystore bridge внутри APK. CLI доставляет session.* и
административные команды по TLS, а тестовый APK-адаптер вызывает trusted native
peer_command для чтения/изменения через обычный удалённый API. Проверяются
подтверждение/сроки и ограничения прав, отмена/отклонение/отвязка/отзыв, replay,
повторное подключение и процессный restart APK с прежними pin/сессией.

Локальный runner запускает/перезапускает APK только командой Device. Он сохраняет
и восстанавливает исходный APK и файлы по SHA-256, удаляет только свои тестовые
ключи и правила перенаправления. CI добавляет проверку после прежней shell/UI
матрицы, сохраняя порядок и budgets; host CI на Linux использует Memory fixture,
поэтому такой CI не подменяет Windows OS-store доказательства. Физический arm64,
реальный Tailscale и обмен пространствами не принимаются этим шагом.
