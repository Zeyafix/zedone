# ADR-0053: явная регистрация и смена доступа через общий API

Дата: 2026-11-14. Техническое решение P06.01.1;
[EV-093](../../agent/verification/EV-093-access-issuance.md).

## Контекст и граница

P03.05 хранит только SHA-256 проверочные значения ключей и выполняет
административные изменения вместе с данными/receipts в одной транзакции.
Внутренние issue_access/replace_access не определяют публичную выдачу:
генерировать секрет на сервере и возвращать его в обычном результате нельзя,
иначе он попадёт в receipts и сохранённые ответы. При этом P06 нужен общий
контракт для явной выдачи и изменения прав человека и агента.

Этот шаг определяет регистрацию уже подготовленного получателем ключа.
Приглашения, проверка устройства, подтверждение на ПК, защищённый канал,
защищённое хранение ключа host и UI остаются P06.01.2–.4. Регистрация сама
не является подтверждением подключения или синхронизацией. DEC-003 целиком
не закрывается; продуктовые правила ADR-0009/0010/0037/0038 сохраняются.

## Решение

Получатель один раз генерирует независимые случайные 128-битный subject
и 256-битный ключ системным CSPRNG. Сохраняет исходный ключ у себя до
выяснения исхода. Администратору передаются только subject и verifier:
`SHA-256(UTF-8("zedone/access-key/v1\0") || raw_key)` — тот же формат,
который storage уже использует при аутентификации. В строке префикса `\0`
означает один нулевой байт. API не принимает verifier как Bearer: обычная
аутентификация по-прежнему хеширует предъявленный исходный 32-байтный ключ.

- `access.issue` принимает новый subject, verifier, явную scope и необязательный
  expires_at_unix_ms. Существующий subject никогда не перезаписывается.
- `access.replace` принимает те же поля и expected из свежего access.inspect.
  Сохраняет subject и receipts, требует новый verifier и выключает все старые
  ключи. Это явное изменение прав или новая выдача после отзыва/истечения.
- `access.list` принимает необязательный исключительный cursor after и выдаёт
  до 50 снимков по возрастанию subject. next — последний выданный subject,
  если есть продолжение. Список включает отозванные и истёкшие доступы,
  не содержит ключей/verifiers. Каждая страница — отдельное чтение, общей
  транзакции всех страниц нет; для обновления нужен новый command ID.

Все команды требуют ManageAccess через прежний core guard, включая
повтор и просмотр списка. JSON не определяет личность вызывающего, часы
или права. Scope задаётся явно: administration, spaces или
administration_and_spaces. Обычный доступ не предоставляет администрирование;
администрирование само по себе не открывает данные. Пустая карта пространств,
неверные ID, неизвестные пространства и нулевой verifier отклоняются.
Новая конечная граница срока должна быть позже доверенного времени операции;
отсутствие/null означает «До отзыва». Форма с исходными чтением/«До отзыва»
и явным подтверждением выдачи будет реализована отдельно по ADR-0010.
Общий диапазон API — 0…253402300799999 Unix-миллисекунд (конец 9999 года UTC):
значения точно представимы в JavaScript и SystemTime обеих платформ. Значения
выше границы одинаково отклоняются, без различий переполнения Windows/Android.

Выдача, смена, проверка актуальности и receipt атомарны. Повтор возвращает
исходный результат и не восстанавливает позднее отозванные права/ключи.
Отозванный или лишённый администрирования вызывающий не получает прежний
receipt до нового разрешения. Все прошлые verifiers остаются tombstones:
переиспользовать чужой, текущий или старый ключ нельзя. Сохранение последнего
бессрочного администратора обязательно; сначала передать полномочия другому,
затем понизить/отозвать прежнего. Неотзываемого владельца не появляется.

## Источники истины и обратимость

Новых таблиц, зависимостей, схем и источников разрешений нет. Публичный
контракт принадлежит core, storage использует прежние access_* и общий
store_verifier как для внутренних, так и публичных операций. OpenAPI/типы/
валидаторы производны от Rust. HTTP/CLI/IPC вызывают один Service.

Секретов нет в JSON-команде, pending intentions, receipts, ответах,
графе или снимке пространства. Verifier — только регистрационные данные
в команде/receipt; access.inspect/list по-прежнему его не возвращают.
Доставка subject/verifier сама по себе не подтверждает личность устройства:
это обязанность будущего процесса подключения и защищённого канала.

Отзыв остаётся access.revoke с expected. Понижение/повышение, снятие
администрирования и повторная выдача используют access.replace с новым
ключом. Ни одна из этих операций не удаляет локальные данные устройств.
Список не является текущим кэшем прав и не разрешает обход серверного guard.

Проверки: разрешённые/запрещённые действия, отзыв/новая выдача/старые повторы,
stale/коллизии/конкурентные смены, последний администратор, исключительная
граница срока, SQL-отказ receipt, restart и отсутствие исходного секрета.
Матрица Windows/native Android и её ограничения фиксируются в EV-093.
