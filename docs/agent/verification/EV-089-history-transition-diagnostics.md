## Диагностика head 19a5a3f и воспроизведение

Linux shell/job 132349509136: desktop history passed; touch снова остановился
на переходе после ввода. Теперь bounded trace зафиксировал pointer/click
в `P`, на 98px выше актуальной кнопки, затем поздний фокус card-title.
Диалог/редактор остались открыты, history отсутствовала. Это промах по
устаревшей геометрии, а не отказ `card.history`. Linux aggregate 132350976753
строго получил `RESULT: failure` и корректно отказал.

Сценарий нажимал «Редактировать» и начинал ввод сразу после появления полей,
пока `begin_editing` и начальный фокус ещё могли выполняться. Настоящий HTTP
ответ `begin_editing` локально удержан, затем доставлен между выбором координат
и native touch. Старый сценарий воспроизвёл тот же pointer/click в абзац,
открытый редактор/отсутствующую history и прежний TimeoutError. Кнопка ушла
с y=399 на y=503 при уже подготовленном tap y=421. Искусственная задержка
нужна только локальному fault probe, не добавляется в штатный драйвер.

Общий сценарий теперь ждёт точное подтверждённое «Сохранено» после открытия
редактора, до первого ввода. Это завершает подготовку `begin_editing`/фокуса,
как в существующем editor suite. После новой пары текстов history tap по-прежнему
следует сразу, без ожидания autosave; все прежние проверки одной новой версии,
точной пары и удаления черновика сохраняются. Продукт/driver геометрии/API,
само касание, его количество, assertions и прежний 10s deadline не меняются.

Тот же delayed-response/native-handoff probe после правки прошёл весь touch
history, без незавершённого старта при касании. Полные целевые desktop/touch
матрицы Chrome и Opera passed, включая failure/replay/stale/pagination/reverse.
Host/Android routing guards passed. Исходные e4f24a3/c975d0f не содержали
event trace; тождественность их механизма не доказывается. GAP-025 остаётся
открытым до нового реального Linux CI. Прежний native Android history 19a5a3f
passed; shared test-only правка отдельно должна пройти новый CI.

Пять правил сохранены в инфраструктурном срезе: Git-обратимость; одинаковый
Service/API человека и агента; developer/agent docs обновлены; продуктовый
ПК/Android паритет не меняется; история остаётся единственной в Service.
Все 98 определения/состояния критериев прежние, полные P05/T08/A21/A54 partial.
Два новых синтетических fault-probe каталога в системном temp оставлены:
автоматическая проверка отклонила их удаление как `blocked by policy`.
Продуктовые файлы и репозиторий они не меняют. LOG-493.

Исправление опубликовано в PR #87/head 4f0d59a. Body/две hosted картинки
прочитаны обратно; Windows environment SUCCESS, 14 runtime suites IN_PROGRESS,
три aggregates ожидаются. GAP-025 открыт до нового CI; все 18 SUCCESS/readiness
обязательны перед порученными merge/delete. LOG-494.

По отдельному поручению «Найди корень проблемы» прочитаны актуальные проверки
[PR #87](https://github.com/Zeyafix/zedone/pull/87) и raw failed logs
[Android shell/job 132353197010](https://github.com/Zeyafix/zedone/actions/runs/43563834763/job/132353197010).
На head 4f0d59a завершены все 18 checks: 16 SUCCESS; FAILURE только у
`android (shell)` и его строгого aggregate `android`. Linux/Windows shell и
Android shell-arm64 SUCCESS. Aggregate/job 132355752451 корректно отклонил
`RESULT: failure`; второй независимой причины у него нет. В shell failure state
поле `stage: trash` осталось от предыдущего сценария, реальный стек указывает

Trace Android: pointerdown/up/click попали в `P` при y≈415, хотя верх кнопки
«История версий» уже находился при y≈497 (центр ≈519). Диалог и редактор
остались открыты, history отсутствует, alerts/pageErrors отсутствуют.
Начальный фокус здесь не требуется для объяснения отказа: остаётся другая
гонка, при завершении обычного autosave.

В опубликованном `CardEditor.vue` `confirmDelivery` устанавливает `pending`
до ожидания ответа `deliverMutation`, включая нормальный запрос в полёте.
Две recovery-кнопки показываются по одному `v-if="pending"`. При успешном
ответе `pending` очищается, кнопки исчезают. Если диалог прокручен близко к низу,
уменьшение scrollHeight заставляет браузер уменьшить scrollTop, сдвигая
кнопку истории вниз уже после выбора координат касания. Проверка геометрии
на соседних кадрах в nativeControls не защищает от последующего ответа сети.

Механизм независимо перепроверен bounded host-экспериментом
`docs/reports/p05-09/root-cause-audit.mjs`: Vite собирает отдельно CardEditor
из `git show HEAD` и исходное рабочее дерево; tracked исходники и обычный
`ui/dist` не перезаписываются. Снимок history-сценария побайтово сверен с HEAD
после нормализации CRLF. Используются настоящий HTTP Service, подтверждённый
успешный ответ card.autosave и native CDP touch. Ответ освобождается между
получением координат и touchStart; повторы касания/DOM click не добавляются.

- HEAD: recovery 2→0, scrollHeight 1171→1067, scrollTop 445→341;
  кнопка y399.140625→503.140625, приготовленное касание y421.140625 попадает
  в абзац; тот же TimeoutError 10000ms. Отказ ожидаемый, аудит его проверяет.
- Исходная незакоммиченная правка `pending && blocked` в рабочем дереве:
  recovery 0→0, scrollHeight 1067→1067, scrollTop 341→341, y503.140625
  неизменен. Тот же транспортный handoff проходит весь history-сценарий,
  включая точную пару/одну новую версию, stale/pagination/failure/replay.

Итог аудита — exit 0. Raw CI, оба локальных лога и структурированное
доказательство сохранены в ignored `docs/reports/p05-09/root-cause-*` и
`history-autosave-handoff-audit-*.json`; две собственные синтетические базы из
`temp/pr87-root-cause/` удалены после проверки разрешённых абсолютных путей.
Диагностические сборки оставлены в этом ignored каталоге. Это host-воспроизведение механизма, совпадающее с
Android trace, а не новый прогон native Android. Локальный Android-драйвер
не запускался. Старые отказы без trace не переатрибутируются.

Исправление уже присутствовало среди восьми dirty файлов при начале этой
диагностики; агент его не создавал и не публиковал. Корректное направление:
показывать recovery только для неразрешённого результата и сохранить проверку
перехода при незавершённом autosave. Увеличение таймаута/повтор tap/ожидание
autosave перед tap скрыли бы дефект. Полная проверка правки, новый Android CI
и интеграция остаются следующей работой; GAP-025 открыт, критерии T08/A21 и
остальные полные критерии не повышаются. Пять правил в диагностическом срезе:
изменения документации обратимы; общий Service/API и источник истины прежние;
доказательства записаны; паритет ПК/Android не объявляется вновь принятым.
LOG-495.

## Исправление по поручению разработчика

После поручения «Исправь эту проблему и продолжи работу» локальная правка
`pending && blocked` принята в scope CI.06: recovery-действия относятся к
неразрешённому результату, обычный autosave не меняет ими высоту диалога.
UI/API/модель хранения не получают нового состояния или второго источника
истины. Сценарии отказа по-прежнему должны предлагать проверку исходного
намерения и явное удаление записи с предупреждением.

В общий history-сценарий добавлен host regression: настоящий успешный ответ
autosave удерживается; recovery-кнопок быть не должно, а нажатие истории
не может открыть её до освобождения ответа. После освобождения проверяются
одна новая версия с точной парой и удаление черновика. Native-вариант сохраняет
реальные IPC/IME/единственное касание без HTTP interception. Ожидание admission
и fetch ограничены 10s; cleanup завершает route handler до unroute, чтобы не
продолжать уже обрабатываемый запрос и не заменять первичную ошибку ошибкой
протокола. Добавлена точная stage-метка history для Android failure state.

Negative control с финальным тестом и собранным UI опубликованного head
отклонён ожидаемым assertion 2 !== 0; обработчик ответа корректно завершён,
позднего `Route is already handled` нет. Проверка exit 0;
`docs/reports/p05-09/autosave-regression-negative.json`.

поля, light theme, viewport и кадрирование; удержан настоящий успешный ответ.
