# ADR-0028: атомарная запись и журнал изменений пространства

Дата: 2026-11-05.

Статус: техническое решение P03.02. Продуктовый договор не меняется;
проверки и ограничения — [EV-045](../../agent/verification/EV-045-product-atomic-storage.md).

## Основание

P02 подтвердил правила Automerge, сохранность отложенных изменений и стабильного
actor. Полные view/save дорожают с ростом истории (EV-043). ADR-0027 требует
отдельный storage без SQLite/Automerge в core и рабочего контекста вне UI/сети.
Согласованная фиксация должна включать результат команды до отправки ответа.

## Решение

- `zedone-storage` владеет одной SQLite устройства. Один поток владеет одним
  соединением; ограниченная очередь из 32 заданий и ожидание ответа асинхронны.
  Синхронный SQL, граф и сериализация результата выполняются в рабочем потоке.
  Запись использует `BEGIN IMMEDIATE`, чтение — согласованную read-транзакцию.
  SQLite сериализует также случайно открытый второй worker той же базы;
  документы перечитываются после получения блокировки, устаревшего кэша нет.
- Одно пространство — один граф. `documents` хранит стабильный локальный actor;
  `changes` — неизменяемые Automerge changes с ключом `(space, hash)`.
  В память загружаются только документы, запрошенные в текущей транзакции.
  Чтение полей и пользовательской истории идёт из одного графа. Производных
  таблиц полей, глобального view и общего кэша документов пока нет.
- Локальная правка дописывает только новое change. Входящие changes сохраняются
  непосредственно, включая изменения без зависимостей: `get_changes`/`save_after`
  таких изменений не возвращают. При загрузке каждый change разбирается,
  сверяется с hash и применяется вместе с остальными; очередь зависимостей и
  конкурирующие значения сохраняются. Полный граф не пересоздаётся из видимых полей.
- Пользовательская история является частью той же прикладной правки графа.
  Этот слой не изобретает версии карточек, правила серий и очистки P04:
  обработчик обязан изменять поля и их историю в одном `WriteContext::edit`.
- `peers` хранит только долговечный `State::encode()` Automerge по пространству
  и peer. Shared heads должны существовать в том же графе. In-flight состояние,
  транспорт, права, подключения и явная пауза не выдаются за этот progress;
  их продуктовые правила реализуются соответствующими следующими шагами.
- `command_results` хранит непрозрачный внутренний ключ, исходный запрос и
  JSON результата. `Storage::write` автоматически сохраняет результат вместе
  с графами, actor и peer. При существующем ключе callback не запускается;
  `AlreadyRecorded` — внутренняя коллизия записи, не результат проверки прав
  или сравнения параметров. В P03.04 core определит формат/область/срок и возврат
  прежнего результата. Автоматической ротации или повторного выполнения здесь нет.
- Ошибка изменяющего примитива помечает весь рабочий контекст неуспешным,
  даже если callback её перехватил. Отказы до commit откатывают всю запись.
  Ошибка commit, паника или потеря ответа после принятия задания не объявляются
  достоверным отказом: `OutcomeUnknown`. Успех возвращается только после commit.
  Отмена ожидающего future после постановки задания не отменяет принятую запись;
  результат остаётся на диске. Проверка прав при получении результата впереди.
- WAL, `synchronous=FULL`, включённые FK и busy timeout в одну секунду закреплены
  явно. При открытии проверяется `quick_check`; это не защита от всех повреждений
  накопителя или доказательство устойчивости к отключению питания.
- Начальная схема 1 создаётся атомарно только при `user_version=0`, нулевом
  `application_id` и пустом `sqlite_schema`. Текущая схема проверяется по
  идентичности приложения, версии и точному составу SQL-объектов; неизвестная,
  чужая или неполная база не чинится и не пересоздаётся. При отказе не меняется
  режим журнала. Версия/идентичность перепроверяются и внутри операций.

## Граница и цена решения

`ReadContext`/`WriteContext` — доверенные инфраструктурные callbacks на worker,
не агентский или пользовательский API. Automerge-типы доступны только на этой
низкоуровневой границе; в `zedone-core`, OpenAPI и будущие адаптеры они не входят.
При появлении обработчика его порт задаётся в core, а реализация в storage
инкапсулирует эти callbacks. Пустой универсальный порт сейчас не добавляется.
Callback не должен ожидать тот же worker, выполнять сетевой I/O или публиковать
внешние эффекты до commit. Пользовательских входов к этому слою ещё нет.

Сохранение маленькой правки не переписывает весь граф. При этом выбранный граф
полностью загружается для каждой транзакции; цена загрузки растёт с его историей.
Нет доказанного ограничения роста, физического стирания или бюджета всего
приложения. Переупаковка/кэш/проекции добавляются по фактической потребности
с отдельными проверками, без потери orphan changes и причинной истории.
DEC-002/DEC-009 остаются открыты до продуктовой композиции и измерений.

Начальная схема проверяется на изолированных синтетических базах. До изменения
схемы уже сохраняемых пользовательских данных или ранее выпущенной базы
обязательны P07.07/P07.08: проверенная копия и атомарная миграция. Если зависимости
создают цикл, сначала выделяется минимальная подготовка защиты; удаление базы,
`IF NOT EXISTS` или смена `user_version` не заменяют миграцию.

## Альтернативы

Полный save на каждую локальную правку сохраняет прежнюю стоимость P02.
Отдельная изменяемая таблица текущих полей требует второй модели согласованности.
Кэш живых документов требует правил публикации/отката после SQL-сбоя и чужой
записи; до продуктовых нагрузок он не добавлен. Политика повторов и публичный
транспорт не смешиваются с проверкой атомарности этого шага.

Основания API: [Automerge 0.12.0](https://docs.rs/automerge/0.12.0/automerge/struct.Automerge.html),
[sync State](https://docs.rs/automerge/0.12.0/automerge/sync/struct.State.html),
[SQLite PRAGMA](https://www.sqlite.org/pragma.html).
