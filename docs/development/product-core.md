# Разработка продуктового Rust-ядра

`storage/schema/v1.sql` — неизменяемое описание схемы 1; новая схема добавляется
отдельным SQL и записью реестра, вместе с защищённым переходом. Переписывать
исторический layout или сбрасывать базу ради изменения схемы нельзя.
`tests/fixtures/schema-v1.sqlite` — синтетический эталон SQL ревизии 1fd2de7,
SHA-256 `08683246876eb7e32592efe22be11737406fccfa15e787742b3505c9f1e6a044`.
Не регенерировать его по текущему runtime при изменении схемы: тесты открывают
копию. Источник эталона и допуск описаны в
[ADR-0035](../architecture/decisions/0035-schema-admission.md) и
[EV-052](../agent/verification/EV-052-schema-admission.md).

Архитектура — [границы ядра](../architecture/core-boundaries.md).
Жизненный цикл пустых колонок — [ADR-0043](../architecture/decisions/0043-column-lifecycle.md),
контракт и доставка — [инструкция агента](../agent/columns.md).
`core::columns::ColumnStore` расширяет SpaceStore; WriteContext хранит
колонки в том же графе, без отдельной SQL-таблицы текущих полей.
Тесты `columns` проверяют обратимость/причинную проекцию, конфликты, права,
SQL/commit/конкуренцию, а adapter tests — HTTP/IPC/реальный CLI и restart.
Группировка операций для проекций списка выполняется за один проход;
корневая history исключена, прежний алгоритм space.version сохранён.
Продукт находится в корневом Cargo workspace; `prototypes/` проверяется отдельно.
Версии Rust/Bun берутся из `scripts/environment-versions.json`, зависимости —
из корневого Cargo.lock. Новых инструментов относительно подготовленной среды нет.

Из корня репозитория:

```powershell
$productVersions = Get-Content -Raw scripts/environment-versions.json | ConvertFrom-Json
cargo "+$($productVersions.rust)" fetch --locked
bun install --frozen-lockfile --ignore-scripts
bun scripts/check-product.mjs
```

Команда выполняет fmt, Clippy всех targets/features с запретом предупреждений,
тесты, release-сборку всех targets/features, проверку границы зависимостей и
наследования `forbid(unsafe_code)`, негативную компиляцию каждого Rust-target
в отдельной временной копии и побайтовую сверку OpenAPI. Собственные исходники
не изменяются; временная копия удаляется даже при отказе. Запрет относится к
собственному продукту, не распространяется на исходники зависимостей.

Проверяется также `zedone-storage`: начальная схема/отказы неподдерживаемой базе,
согласованная запись графа/истории/actor/peer/результата, заполнение SQLite,
ошибки SQL/commit, параллельные writers, паника и отмена ожидающего future.
Пять отдельных дочерних процессов завершаются без деструкторов в контрольных
точках до/после commit; родитель повторно открывает изолированную базу и проверяет
полное прежнее или полное новое состояние и продолжение записи тем же actor.
Это проверка остановки процесса, не физического отключения питания.

Хранилище — доверенная инфраструктура. Публичные команды используют только
`zedone-adapters::Service`, не произвольный callback storage. Его callbacks
исполняются на выделенном worker: внутри запрещены ожидание этого же worker,
сетевой I/O и публикация внешних эффектов до commit. `Storage::write` сам
сериализует результат и сохраняет его вместе с изменениями. Перехваченная ошибка
мутации всё равно запрещает commit. После принятия задания отмена ожидания не
отменяет запись; нужно проверять прежний результат, не создавать новое намерение.
Коллизия ключа низкоуровневого `write` не является политикой повтора: команда
проходит общий `core::replay::execute` внутри `Storage::transact`.
Модель и границы начальной схемы — [ADR-0028](../architecture/decisions/0028-atomic-storage.md).

`Storage::shutdown` завершает работу всех clones: при получении Stop worker
закрывает приём в очередь, выполняет уже принятые задания, закрывает SQLite
и только затем подтверждает остановку всем принятым запросам shutdown.
После подтверждения новые задания получают `Unavailable` до принятия;
потеря ответа уже принятого задания по-прежнему означает `OutcomeUnknown`.
Регрессия проверяет очередь за Stop, несколько shutdown и оставшийся clone
без задержек по таймеру; EV-064/LOG-314.

В `core::access` находится единый `with_authorized`: он разрешает учётные данные
через доверенный `AccessTransaction` на каждом обращении и проверяет все
`RequiredAccess` до вызова синхронного обработчика. Требования определяет core,
не клиент. Проверки нельзя выносить перед ожиданием worker или заменять
признаком локального интерфейса; чтение прежнего результата также требует прав.
Транзакция должна исключать параллельное изменение прав до конца операции.
`Clock` получает доверенное время; при недостоверном времени требуется отказ.

`WriteContext` реализует оба транзакционных порта: `AccessTransaction` и
`ReplayTransaction`. Аутентификация, разрешения и отзыв хранятся в той же SQLite.
`access::{PendingAccess, AccessKey}` генерируют субъект/ключ; подготовка не
предоставляет доступ. `bootstrap_access` предназначен только доверенной точке
сборки для начальной подтверждённой выдачи. `issue_access`, `replace_access`,
`revoke_access`, `inspect_access` сами требуют ManageAccess через общий guard.
Изменения фиксируются только вместе с успешным commit `Storage::transact`.
Ключ сохраняется вызывающим кодом до выяснения результата; его нельзя
сериализовать в receipts, выводить в логи или менять при неизвестном исходе.
Доверенные часы и ограниченные адаптеры реализованы P03.05.3/.4;
тестовый Clock не переносится в приложение. Права не входят в граф/экспорт пространства.
Подробности — [ADR-0037](../architecture/decisions/0037-persistent-access.md),
[инструкция агента](../agent/access.md).
Product-check запускает общие тесты матрицы чтения/изменения/администрирования,
точных ID, всех целей, субъекта, срока/отзыва и отказов источников.

## Актуальность и повторы

Договор — [ADR-0030](../architecture/decisions/0030-command-replay-and-freshness.md).
`ReplayTransaction` совмещает текущую авторизацию и долговечные результаты.
Обработчик core определяет требования, валидирует вход и вызывает `execute`
на worker внутри транзакции. Для невыполненной команды он получает согласованную
проекцию, сравнивает `StateVersion` через `require_current` и только затем меняет
данные. Успех callback не является успехом клиенту до commit `Storage::transact`.
`WriteContext::record` не заменяет запись и запрещает commit после ошибки,
даже перехваченной. Выполненный ID с другим исходным запросом даёт mismatch.
Прежний тестовый session/команда не включаются в продукт. Дополнительные
access-тесты используют настоящий источник прав на `WriteContext` и тот же executor.

`state_version` хеширует область и проекцию SHA-256. Обязательны проверяемые
значения/варианты/состав и причинные идентичности их изменений: один хеш значений
пропускает изменение с возвратом, а heads всего пространства отклоняют несвязанные
правки. Продуктовые проекции создаются вместе с P04, без второго источника полей.
Порядок коллекций в проекции стабилен; формат области версионирован и связан с ID.
Ошибка сериализации авторитетной проекции — `unavailable`, не ошибка запроса.

Повтор сохраняет ID/операцию/цели/параметры/исходные условия. Его результат —
подтверждение прежнего выполнения, а не свежий объект для замены клиентского view.
Записи результатов не истекают; автоматическая ротация запрещена. Безопасность
при откате/утрате базы или очистке требует отдельной защиты до сценариев P07.
Число попыток/паузы/таймауты клиентов остаются P03.05/P05.

Product-check включает `replay_tests`: ограниченную синтетическую команду
выполнения/снятия выполнения, смысловую актуальность и изменение с возвратом,
параллельные доставки через два worker, права до receipt lookup, отмену ответа,
сериализацию/SQL/паники и пять дополнительных дочерних crash/reopen на платформу.
Тест вложенной проекции не принимает удаление контейнеров P04.

После намеренного изменения Rust-контракта:

```powershell
bun scripts/check-product.mjs --write-openapi
bun scripts/check-product.mjs
```

`api/openapi.json` не редактируется вручную. Ошибка компиляции или проверки
не перезаписывает артефакт; явная генерация восстанавливает удалённый файл.
Он содержит ошибки, общий конверт запроса/ответа и `StateVersion`; `paths` пуст.
Это не сервер и не агентский интерфейс. Подключение HTTP/CLI/IPC — P03.05.4,
после персистентных прав и доверенного времени P03.05.2/.3.

После изменения Rust/OpenAPI сгенерировать TypeScript:

```powershell
bun scripts/check-product.mjs --write-types
bun scripts/check-product.mjs
```

Root `package.json`/`bun.lock` закрепляют openapi-typescript и TypeScript отдельно
от прототипов. `api/schema.d.ts` генерируется из того же вывода Rust, а не из
вручную исправленного JSON. Обычный прогон и `--android` проверяют дрейф обоих
артефактов и компилируют `tests/contract-types.ts`. `--check-types` и
`--check-openapi` выполняют эти проверки без полного Rust-прогона. Генерация
OpenAPI выполняется отдельно; затем `--write-types` обновляет только TS.
Отсутствующий/устаревший артефакт даёт отказ, обычная проверка его не исправляет.
Сначала формируется полный новый вывод; ошибки генератора не перезаписывают файл.

`wire::decode_request<C>` принимает только точное имя конкретной команды,
ненулевой 16-байтовый ID и строгие параметры. JSON не содержит учётных данных,
субъекта или разрешений. Ответ `CommandResponse` строится после commit;
`replayed` относится к прежнему результату, а не к актуальности объекта.
Типизация TS не заменяет runtime-валидацию Rust: диапазон байтов/ненулевой ID
и 32-байтовая длина версии не выражены полностью в производных TS-типах.
Полный договор — [ADR-0031](../architecture/decisions/0031-shared-command-wire-contract.md).

## Формат снимка пространства

`zedone_storage::snapshot::{SpaceSnapshot, SnapshotLimits}` и
`Storage::snapshot(space, created_at_unix_ms, limits)` — внутренняя инфраструктура
P07.01. Она захватывает полный журнал одного пространства на worker, включая
ещё не применённые изменения. `encode(limits)`/`decode(&bytes, limits)`
проверяют версию, метаданные, SHA-256, записи и их совместимость. Исходный файл
не изменяется. Значения бюджетов задаёт доверенный вызывающий код; это ограничения
входа, а не гарантия пика памяти. Перед будущим файловым чтением нужен свой
предел количества байтов. Договор и границы —
[ADR-0032](../architecture/decisions/0032-space-snapshot-format.md).

Нельзя подключать метод как публичную операцию: аутентификация/права и захват
должны быть объединены одной транзакцией после ожидания worker. Метаданные
архива не являются доверенным источником прав или времени. Декодер не импортирует
и не восстанавливает данные; тестовый граф не является продуктовой моделью P04.
Исходник и прежние эталоны при будущем преобразовании сохраняются.

Семь `snapshot::tests` включены в обычный product-check и нативные Android-тесты:
полный scoped журнал/конфликты/история/orphans, обратная правка/restart,
конкурентная запись другим worker, повреждения всех байтов и все обрезки,
поддельные длины/метаданные/записи/checksum, бюджеты, ошибочная база и
побайтовое чтение эталона v1. Эталон включён через `include_bytes!`, поэтому
одни байты проверяются на обеих платформах; он не генерируется заново в тесте.
Новых инструментов, зависимостей и настроек CI нет.

## Подготовка предмиграционного комплекта

`Storage::prepare_migration_backup` и `migration_backup::BackupLimits` создают
проверенный отдельный кандидат в указанной существующей папке. Полная база
копируется SQLite Backup API, архивы пространств читаются из этой копии;
`BEGIN IMMEDIATE` исключает другие writers до окончания проверки. Файлы повторно
открываются, проверяются SHA-256/размеры, полный integrity/FK, схема, журналы
и соответствие всех архивов SQLite. `PreparedBackup::verify` повторяет проверку,
`discard` явно удаляет только свой кандидат; drop/потеря ответа сохраняют его.

Договор и ограничения — [ADR-0033](../architecture/decisions/0033-pre-migration-backup-candidate.md).
11 новых тестов включены в host/Android product-check. Feature `backup` включён
у закреплённого rusqlite; закреплённый tempfile теперь runtime-зависимость.
Схема/версии/lock не меняются. Синхронные verify/discard выполняются вне
async-потока UI. Пик памяти/время и продуктовые бюджеты ещё не приняты.

P07.07.2 добавляет доверенные `with_migration_backup`, `recover_migration_backup`
и `discard_migration_candidate`. Первый метод сам захватывает новый комплект
и выполняет callback внутри той же writer-транзакции. Callback не управляет
транзакцией и не публикует внешние эффекты. Обязательный validator проверяет
ожидаемую целевую версию/схему и инварианты до/после commit. Служебный результат
в прежнем `command_results` фиксируется вместе с операцией; его зарезервированный
ключ длиннее wire CommandId, он не относится к пользовательским receipts.
Индекс в папке — только проекция. Подробности и файловый протокол —
[ADR-0034](../architecture/decisions/0034-migration-backup-publication.md).

После ошибки commit/публикации возвращается OutcomeUnknown; повтор обработчика
не допускается, сначала сверка с проверкой ожидаемого целевого результата.
`cleanup_pending` — успех с необходимостью повторить очистку. Полностью
подготовленные orphan сохраняются и удаляются явно. Папка предназначена одной
установке, приватна и блокируется стабильным `migration.lock` на всё время
захвата, фиксации, публикации и удаления. Нельзя использовать другие папки как
автоматический fallback. Отсутствующий/повреждённый committed-комплект
останавливает сверку; автоматического восстановления нет.
Guard явно освобождает `migration.lock` при завершении операции. Обычный close
может оставить блокировку у дубликата/унаследованного дескриптора; это не должно
блокировать следующую операцию после завершения владельца. Запрет конкурирующей
публикации до выхода из guard сохраняется.

15 дополнительных тестов проверяют ошибки, два worker, потерю ответа, живой
дубликат после освобождения guard и семь
дочерних crash/restart до/после commit, публикации и очистки. Файлы sync_all на
обеих платформах, каталоги fsync на Unix; Windows-барьер долговечности каталога
std/tempfile не дают. Остановка процесса не доказывает power-loss. Цепочка миграций, source/target-адаптеры и startup gating реализованы
в P07.08 (см. ниже); служебный режим — P07.09. Обычные пользовательские входы этим
срезом не открываются. Схема 1 и синтетическая транзакция в тестах не заменяют
приёмку продуктовых миграций.

## Запуск и миграции

Владелец приложения создаёт один `zedone_storage::startup::Startup` на запуск
установки и вызывает `automatic(Some(MigrationOptions { folder,
created_at_unix_ms, limits }))`. Все настройки доверенные; папка уже существует.
Новая/текущая база без свидетельства допускается и без options. `Storage::open`
сохраняется как сокращение этого пути без options; если требуется миграция
или сверка commit, оно возвращает ошибку, а не выдаёт непроверенный worker.

Полученный Storage передаётся обычным обработчикам core/обмену лишь после
успешного запуска. При ошибке причина находится в `StartupState::Failed`;
повторный automatic возвращает `RetryRequired`. После устранения причины
владелец явно вызывает `retry` с актуальными настройками/временем/бюджетами.
Новый запуск создаёт новый Startup. Отмена ожидания сохраняет Running и
receiver результата; retry в Running ждёт ту же попытку. После Ready повтор
через этот контроллер не создаёт второй worker.

При новой продуктовой версии схемы нужно добавить неизменяемый SQL layout,
переход от предыдущей записи и архивный адаптер исторической версии в реестр
`storage/schema`, сохранить прежние переходы/адаптеры/эталоны и расширить матрицу
всех реализованных схем. SQL layout содержит DDL; необходимое начальное
состояние новой базы и семантические инварианты новой модели должны быть
спроектированы и проверены при добавлении реальной версии. Общий механизм
проверяет версии, layout, целостность и семантический validator версии;
он не выводит доменные преобразования из SQL. Runtime v2 добавляет постоянные
права: неизменённый `schema/v1.sql` плюс `schema/access-v2.sql`, переход v1→v2
не выдаёт разрешений. Исторический формат снимка пространства не меняется.
Тестовые v2/v3 прежнего синтетического реестра в продуктовую линейку не входят.

Вся цепочка и служебное свидетельство фиксируются одной транзакцией; проверенный
комплект захватывается с source-adapter под непрерывным writer lock.
Postcommit-сверка завершает публикацию без повторного перехода. До успешного
результата Storage недоступен. Отказы hot-journal/повреждения сохраняют исходник;
аварийное восстановление остаётся P07.09 с ADR-0030. Детали/границы —
[ADR-0036](../architecture/decisions/0036-atomic-migration-startup.md),
[EV-053](../agent/verification/EV-053-atomic-migration-chain.md) и
[EV-054](../agent/verification/EV-054-startup-attempts.md).

## Android

С подготовленными `ANDROID_HOME`, закреплённым `NDK_HOME` и явно выбранным
тестовым AOSP API33/x86_64-эмулятором:

```powershell
$env:ANDROID_SERIAL = 'emulator-5554'
bun scripts/check-product.mjs --android
```

Команда проверяет свойства эмулятора и NDK, собирает release всех targets/features
для x86_64 и arm64, проверяет отказ unsafe каждого target для обеих ABI,
запускает те же Rust-тесты нативными x86_64-процессами и сравнивает OpenAPI
нативного генератора с host. Созданный каталог `/data/local/tmp/zedone-product-*`
удаляется в finally. Физические устройства не принимаются этим драйвером;
arm64-сборка не является нативной проверкой arm64.

Для bundled SQLite драйвер задаёт NDK clang/llvm-ar и API33 одновременно
для Rust linker и C-компилятора. Нативные тесты используют `TMPDIR` внутри
собственного удаляемого каталога; дочерние crash-тесты наследуют его.

Драйвер использует существующий явно выбранный эмулятор, не запускает и не
останавливает его. Жизненным циклом собственного read-only AVD владеет вызывающий
локальный прогон или существующий Android CI. APK/WebView в этом срезе нет.

Product-check включён в существующие Windows/Linux jobs и Android emulator
workflow. Изменения Cargo/crates/api/драйвера запускают соответствующие checks;
обе Cargo-рабочие области кэшируются независимо. До публикации PR факт успешного
CI не заявляется. Логи и данные конкретной машины — только в `docs/reports/`
соответствующего шага (`p03-01/`, `p03-02/`, `p03-03/`, `p03-04/`).

## Пространства P04.01.2

Шесть space-команд реализованы в `core::spaces`; Service фиксирует конкретные
decoder/handler, HTTP/CLI/IPC используют один вход. SpaceStore реализован
на WriteContext и прежнем scoped Automerge/SQLite. Создание добавляет header
format/name/lifecycle, точный access_spaces RW аутентифицированному субъекту
и receipt в одной транзакции; administration/ключ/срок/другие права прежние.
Схема v4, исторические SQL/фикстуры и формат контейнера архива не меняются.

Причинная версия вычисляется из декодированных операций закреплённого Automerge,
включая удалённые объекты, исключая зарезервированную history и её потомков.
Стабильная карта причинных ID/операций не заменяется часами/heads или отдельным
счётчиком. Расширение модели требует соответствующей матрицы stale/ABA/конфликтов.
Список посещает текущие разрешённые документы по одному, освобождает прочитанные
графы и проверяет все цели сохранённого результата одним guard перед возвратом.

Product-check выводит из конкретных OpenAPI paths Operation/Parameters/Response,
операции и standalone validators с operation-specific wrapper. После изменения
Rust DTO/paths: `--write-openapi`, затем `--write-types`; --check-types сверяет всё.
Клиентские prepare/store/HTTP/IPC используют этот набор и проверяют ответ
ожидаемой команды. Не дублировать список операций и DTO в клиенте вручную.

`conflict` — машинный отказ обычной правки спорного состояния, не автоматический
выбор варианта. UI, содержимое и полное удаление контейнеров — P04/P05/P06.
Правила — [ADR-0041](../architecture/decisions/0041-space-lifecycle.md),
доказательства — [EV-063](../agent/verification/EV-063-space-lifecycle.md),
пользовательские команды — [инструкция агента](../agent/spaces.md).

## Общий вход P03.05

Продолжение P04.01.1: схема v4 имеет DDL v3 и новый семантический validator,
разрешающий `GrantScope::AdministrationAndSpaces` (администрирование плюс
непустая карта точных пространств). Прежние validators и их layout/эталоны
сохраняются. Переход v3→v4 требует обычных MigrationOptions/проверенной полной
копии; не понижать user_version и не менять исторические SQL для обхода startup.
Переход сохраняет все права/ключи/receipts без автоматической выдачи новых.
Guard проверяет данные и администрирование независимо. Снятие прав/замена
ключа проходят существующие доверенные методы с защитой последнего admin.

`RequiredAccess::ActiveGrant` проверяет действующее разрешение для будущего
создания без отдельного права. Адаптеру нельзя принимать его от клиента вместо
реальных требований команды. Создание объекта и добавление точного RW создателю
должны коммититься с одним receipt в P04.01.2; доверенный callback не заменяет
публичную команду. Новый kind `administration_and_spaces` выведен из Rust для
access.inspect/access.revoke; после изменения запускать `--write-openapi`,
затем `--write-types`. Прикладных paths P04 срез .1 не регистрирует;
продолжение .2 описано выше.
Решение — [ADR-0040](../architecture/decisions/0040-space-creation-access.md),
матрица — [EV-062](../agent/verification/EV-062-combined-access.md).

`zedone-adapters::Service::new` получает Storage после успешного startup.
`http::router` работает без browser origins; `router_with_origin` разрешает
только явно заданный origin host. Даже этому origin нужен предъявленный ключ.
Host передаёт router в Axum listener, сам управляет bind/shutdown и защищённым
каналом. Адаптер не начинает слушать сеть автоматически и не выдаёт права.
Для Tauri Android включить feature `tauri`, передать Service в `manage` и
подключить `ipc::tauri_handler()`. Bridge использует производный IpcInvocation,
JSON сохраняется строкой; `Result<String, ()>` нужен async Tauri State,
результат команды находится внутри JSON-конверта, а не Rust Result.
Полноценная оболочка/APK/lifecycle остаются P05/P06.

CLI binary `zedone` читает исходный JSON со stdin и одобренный ключ из
отдельного key-file. Он выбирает существующую установку и не инициирует
миграцию без настроек полной копии. Формат — [инструкция агента](../agent/access.md).

Service декодирует конкретный Rust-тип и вызывает фиксированный core handler.
Первые команды — `access.inspect`/`access.revoke`; обе административные.
Отзыв сверяет expected с семантической версией прав/ключей. Выдача/замена
остаются доверенными инфраструктурными действиями до подтверждённого
пользовательского протокола P06; сетевого bootstrap нет.

`Storage::timed_transact` удерживает writer lock, применяет доверенные часы и
внешнюю транзакцию для watermark. Ошибка/паника откатывает savepoint команды;
наблюдённое время сохраняется. После flush проверяется наиболее ранний срок,
затем commit; успех наружу только после него. Схема v3 добавляет clock-table
и seed через реестр; исторические layout и эталон v1 не переписываются.
[ADR-0038](../architecture/decisions/0038-trusted-access-time.md) описывает
границу commit, откат, restart и ограничения доверия к ОС.

`client/commands.ts` использует Rust/OpenAPI-типы и openapi-fetch, создаёт ID
через Web Crypto, сохраняет JSON до отправки и ограничивает число повторов.
Передача ключа через callback host отделена от pending store. Store служит
только доставке намерения, не хранению данных или авторизации.
[ADR-0039](../architecture/decisions/0039-command-adapters-and-delivery.md)
закрепляет framing, origin, таймауты и явное продолжение.
Product-check выполняет также клиентские failure/restart/timeout-тесты.
Android-проверка переносит native CLI вместе с test binaries в собственный
удаляемый sandbox; child test проверяет настоящий процесс CLI на Android.

Pending-намерение также хранит ID исходного субъекта отдельно от JSON-команды.
Одобренный credential provider host возвращает пару субъект/ключ. Смена ключа
того же субъекта допускает повтор, а смена субъекта останавливает доставку с
identity_changed: прежний запрос не отправляется от другого участника. Этот ID
не выдаёт полномочий и не заменяет независимую аутентификацию Rust по ключу.

Проверка ответа в клиенте также выводится из Rust/OpenAPI: закреплённый
Ajv 8.20.0 генерирует standalone ESM `api/validate-response.js` и его d.ts при
`--write-types`. Product-check сверяет оба артефакта побайтово. Некорректный
конверт или вложенный результат не удаляет pending и не подтверждает успех.
Ajv — только dev-зависимость; в клиент не включаются библиотека или runtime eval.
Источник: [Ajv standalone](https://ajv.js.org/standalone.html).

Сгенерированные `api/validate-response.js` и `api/validate-response.d.ts`, как
OpenAPI и schema.d.ts, имеют явное `text eol=lf` в .gitattributes. Это сохраняет
строгую побайтовую проверку при Windows checkout с core.autocrlf=true; не
нормализовать сравнение и не перегенерировать артефакты для сокрытия drift в CI.
