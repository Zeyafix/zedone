# ADR-0036: атомарная цепочка миграций и управление запуском

Дата: 2026-11-05. P07.08.2/.3; DEC-006 остаётся open для остальных сценариев.
Требования: спецификация §1/1.1, T10/A45/A46/M01–M04/M08.
Основания: ADR-0030/0033/0034/0035. Проверки —
[EV-053](../../agent/verification/EV-053-atomic-migration-chain.md) и
[EV-054](../../agent/verification/EV-054-startup-attempts.md).

## Цепочка и архивы

Каждая запись внутреннего реестра задаёт неизменяемый layout, переход от
предыдущей записи и адаптер чтения снимков данной исторической схемы.
Порядок версий строго возрастающий; первая запись не имеет перехода, все
следующие имеют. Это проверяется тестом реестра. При добавлении версии
сохраняются прежние SQL, адаптеры, переходы и независимые эталоны.
В runtime остаётся схема 1. Добавление искусственной продуктовой схемы ради
проверки механизма не требуется: версии 2/3 существуют только в unit-тестах.

После read-only preflight worker повторяет допуск под BEGIN IMMEDIATE.
Если нужна миграция, выбранная папка должна быть явно передана из доверенных
настроек установки. Папка уже существует, приватна и принадлежит одной
установке. Автоматического выбора другого расположения нет.

Протокол ADR-0034 используется и для запуска: блокировка папки, повторная
проверка схемы под writer lock, сверка предыдущего commit, новый полный
комплект, все необходимые переходы и служебное свидетельство одной транзакцией.
Захват использует адаптер исходной схемы; проверка исторической SQLite-копии
и соответствия всех архивов выбирает адаптер её версии, а не текущей схемы.
После каждого перехода проверяются layout, quick_check и FK; перед/после
commit целевой результат проверяется по версии, layout, integrity_check и FK.
Любой отказ до commit откатывает всю цепочку, включая служебные записи.

После commit сначала публикуется и проверяется индекс нового комплекта,
затем удаляется прежний. Ошибка commit/публикации — OutcomeUnknown.
Следующий запуск сверяет свидетельство и завершает публикацию без повторного
выполнения переходов. Отсутствующий/повреждённый committed-комплект останавливает
обычный запуск; fallback к старому комплекту и автоматическое восстановление
запрещены. Если другой запуск уже обновил базу, проверка под writer lock
обнаруживает целевую версию и не создаёт ещё одну копию. Незавершённые
кандидаты остаются orphan; удаление явное по прежнему протоколу.

## Управление попытками и допуск

Владелец жизненного цикла приложения хранит один `startup::Startup` на запуск
установки. `automatic(options)` разрешён один раз. При отказе состояние содержит
категорию ошибки, нормальный Storage не выдаётся; следующий `automatic` даёт
RetryRequired. `retry(options)` после отказа открывает базу заново, повторяет
read-only допуск/проверки папки/бюджетов/целостности и при необходимой миграции
создаёт новый проверенный комплект. Настройки и время передаются заново.
Новый запуск приложения создаёт новый контроллер и снова допускает automatic.

Состояния: New, Running, Failed(error), Ready. Пока Running, receiver результата
и очередь worker принадлежат контроллеру. Отмена async-ожидания не уничтожает
сведения о выполняющейся попытке. Явный retry в этом состоянии ждёт ту же
попытку; переданные новые настройки не запускают параллельную операцию.
После Ready этот контроллер больше не создаёт хранилищ.

Storage появляется только после проверки/фиксации/сверки и настройки WAL/FULL.
Чтение, запись, транзакции core и снимки используют один допущенный worker.
`Storage::open(path)` — сокращение запуска без настроек копий: текущая или новая
база без свидетельства допускается, историческая база или база со свидетельством
без настроек папки отклоняется. Через этот метод нельзя обойти сверку.

## Границы

Это общая доверенная инфраструктура, а не публичная команда миграции и не
право на всю базу. Будущие UI/HTTP/CLI/IPC и обмен получают worker только после
Ready; внешние адаптеры/полномочия остаются P03/P07.09. API человека и агента
не получает обхода проверки через прямой доступ к SQLite.

Read-only preflight по-прежнему отказывает при hot journal, требующем recovery
writes. В crash-тестах такой отказ проверяется до явного тестового восстановления
синтетической базы средствами SQLite. Продуктового автоматического восстановления
нет; сохранение проблемного состояния/служебный режим — P07.09. Downgrade схемы
не реализуется; до commit обратное состояние — полный rollback, после успеха
обычная обратная правка сохраняет архив. Намеренный откат всей базы требует
защиты старых намерений ADR-0030 и согласования устаревшего свидетеля ADR-0034.

Факты находятся в одной SQLite, реестр описывает правила, файловый индекс —
проекция. Сохраняются ограничения ADR-0034 на power-loss и Windows directory
durability. Производительность стартовых проверок больших баз и общий бюджет
приложения ещё не приняты. Новых схем/зависимостей/unsafe/публичных контрактов нет.
