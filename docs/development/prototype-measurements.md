# Измерения итогового среза P01.11

Сценарии измеряют существующий прототип без новых прикладных операций.
Подготовка и число повторов заданы в [методике P01](prototypes.md#методика-времени-для-p01).
Они не входят в `bun run check`: шум времени CI не является приёмкой устройства.

## Windows

Из `prototypes/` после успешного `bun run check`:

```powershell
$env:PROTOTYPE_BROWSER_PATH = 'C:/Program Files/Google/Chrome/Application/chrome.exe'
bun run measure:desktop chrome
if ($LASTEXITCODE -ne 0) { throw 'Chrome measurement failed.' }
# Повторить отдельно с фактическим исполняемым файлом Opera и меткой opera.
```

Путь браузера выбирают из установленной среды, не загружают инструмент при замере.
Для Opera нужен непосредственный бинарник в каталоге её версии: корневой launcher
может оставлять процесс после закрытия тестового браузера и искажать серию запусков.
Каждый запуск создаёт собственную SQLite в системном временном каталоге и
временные профили браузера. Удаление ограничено каталогом, созданным этим runner.
На ПК используются Rust release и Vite production; по умолчанию браузер запускается headless.
Это автоматизированный контроль доступного среза, не измерение физического экрана.

### Уровень доказательства результата

Команды `measure:desktop` и `measure:android` записывают `ui_measurement_evidence` из общего источника
`measure-scenarios.mjs`: `level: diagnostic`,
`presentation_validation: not_validated`, `ui_acceptance_eligible: false`.
Успешный `passed_available_slice` означает прохождение сценария и проверок
сохранности. Он не доказывает отображение результата и не закрывает UI-бюджет
A62. Значение `over_budget: 0` относится только к указанной границе наблюдателя.
Поле применяется также к временам запуска, завершающимся этим UI-наблюдателем.
HTTP/IPC-ответ и сохранённый снимок остаются отдельными доказательствами.

Наличие обычного окна, `document.hasFocus()` и `page.bringToFront()` не заменяет
проверку видимости и переднего окна в ОС. Desktop-отчёт сохраняет источник выбора
браузера и его исполняемый файл, чтобы ошибочная метка серии не скрывала запуск
браузера Playwright по умолчанию.

Для независимого контроля нужен второй наблюдатель: начало перед системным
вводом и конец по ожидаемым пикселям окна на монотонных часах одного процесса.
Записываются последнее наблюдение прежнего состояния и первое наблюдение
ожидаемого, длительность захвата и интервал неопределённости. Накладные расходы
не вычитаются. Если верхняя граница укладывается в бюджет, это достаточное
свидетельство для измеряемого интервала; пересечение границ с бюджетом означает
неопределённый результат. Требуются положительный контроль, искусственная задержка,
тайм-аут, отказ при уже видимом результате и отказ при недоступном тестовом окне.

Допустим отдельный консервативный вариант: наблюдатель запускается **до**
отправки DOM-команды, а конец определяется ожидаемыми пикселями рабочего стола.
Он даёт верхнюю границу задержки команды с включёнными передачей команды,
выравниванием viewport, если оно нужно, и накладными расходами захвата.
Это не точечная оценка и не нижняя граница задержки команды. Верхняя граница
выше бюджета сама по себе не доказывает превышение приложением: такой результат
неопределённый и требует более точного наблюдения. Учитывать только пиксели
тестового окна, отклонять перекрытый участок и сохранять все неудачные попытки.

Захват изображения рабочего стола Windows подтверждает границу изображения ОС,
а не физический свет экрана. Разницу с физическим показом указывать отдельно;
она требует внешнего наблюдения. Основание монотонных часов —
[Windows QueryPerformanceCounter](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps).
Отдельные кадры браузерного screenshot или отметки DOM не считать независимым
измерением появления результата на рабочем столе. Результаты и статус проверки
наблюдателя хранятся только в `docs/reports/p01-11/`.

Для проверки в обычном окне того же установленного Opera после явного выбора
его исполняемого файла в `PROTOTYPE_BROWSER_PATH`:

```powershell
bun run measure:desktop opera-headed --headed
if ($LASTEXITCODE -ne 0) { throw 'Opera headed measurement failed.' }
```

`--headed` открывает обычное тестовое окно со свежим временным профилем;
runner сам закрывает созданные окна. Без флага сохраняется headless-режим.
Режим записывается в `environment.browser_mode` и описание сборки отчёта;
используйте отдельные метки, чтобы различать серии. Флаг меняет только способ
запуска браузера: команды, границы времени, прогревы, повторы и проверки
снимков остаются общими. Лимиты кадров не отключаются. Headed-прогон также
не является независимым подтверждением физического показа.

Десять отдельных запусков Rust/HTTP и Vite preview измеряются с уже запущенным
браузером. В интервал включены запуск серверов, создание страницы, навигация,
явное чтение сохранённой доски и готовность поля ввода. Запуск браузера измеряется
отдельно. Затем десять перезагрузок страницы измеряются при работающих серверах.
Первый запуск после установки и холодный дисковый кеш ОС не проверяются.

## Android

Существующий [debug APK](android-prototype.md) должен соответствовать проверенным
исходникам. Запустить подготовленный AOSP API 33 AVD без GMS. Из `prototypes/`:

```powershell
$env:ANDROID_SERIAL = 'emulator-5562' # serial именно своего тестового AVD
bun run measure:android
if ($LASTEXITCODE -ne 0) { throw 'Android measurement failed.' }
```

Runner допускает только явно выбранный эмулятор, устанавливает prototype APK,
сохраняет исходный снимок A и восстанавливает его общим API после проверки.
B не изменяется. Он убирает собственный CDP-forward и останавливает APK;
сам AVD останавливает тот, кто его запустил. Debug APK и эмулятор дают только
диагностические результаты. Релизная сборка и Galaxy A32 остаются отдельными
ячейками приёмки; этот runner намеренно не меняет физический телефон.

Десять запусков после `am force-stop` измеряются от команды запуска до рабочего
экрана с сохранённой доской; включены adb/CDP и ожидание сокета WebView.
Повторные десять открытий — возврат через Home при работающем процессе.
Все отметки этой серии берутся с монотонных часов драйвера; системный `am start`
не подменяет время рабочего экрана. Накладные расходы не вычитаются.

## Общий сценарий и границы результата

Оба runner используют `measure-scenarios.mjs`. Каждая серия интерактивного
действия выполняет пять прогревов и тридцать измеряемых повторов:

- Подтверждённое перемещение карточки кнопкой диалога и отдельная обратная команда.
- Поиск `Карточка 0030` с одним результатом и отдельный сброс поиска с 30 результатами.
- Перемещение и обратная команда через API, отдельно от отображения UI.

До каждой пары серий создаётся исходный синтетический набор по общему API.
Подтверждение UI измеряется от DOM-команды существующей кнопки до результата
Rust и обновления DOM с двумя `requestAnimationFrame`. Это граница кадра,
а не доказательство физического показа пикселей. Время передачи мыши/касания,
заполнения диалога и всего жеста не входит; этот результат относится к явной
команде. Часы UI — `performance.now()` самой страницы, без вычитания CDP.
HTTP-ответ на ПК и IPC-ответ через CDP на Android — отдельные диагностические
интервалы драйвера, не сравнительный тест скорости HTTP против IPC.

После каждого перемещения проверяется авторитетный снимок Rust и положение
карточки в UI, после обратной команды — полное равенство исходному снимку.
Поиск проверяет число результатов. Ошибка останавливает серию, сохраняет
частичный отчёт и текущую попытку; пропуски не превращаются в нули или успех.
Тайм-аут UI сохраняется отдельным неуспешным отсчётом.

Отчёты с уникальными именами находятся только в `docs/reports/p01-11/`:
сырые миллисекунды, минимум/медиана/p95 ближайшего ранга/максимум,
число отказов и превышений ориентира, хеш/размер/строки набора, ревизия,
отпечатки исходников сценария/клиента/контракта и бинарника/APK, среда и cleanup.
Не объединять разные браузеры, сборки и устройства в общую статистику.
При ошибке или прерывании проверить cleanup отчёта; при принудительном завершении
процесса автоматическое восстановление не гарантируется.

Открытие содержимого карточки, выполнение/снятие отметки пока отсутствуют.
История, корзина, конфликты, обмен и копирование не реализованы в срезе.
Измерение памяти и масштабирования не подменяется размером APK/пустого процесса.
Даже успешные серии доступных действий не закрывают A62. Состояние проверки —
[EV-024](../agent/verification/EV-024-prototype-review.md).

## Диагностика кадрового наблюдателя: GAP-006

Прежде чем объяснять задержку стоимостью чтения доски, разделить сохранение,
обновление DOM, выдачу кадров браузером и физический показ. Использовать одну
production-сборку, одинаковые данные, viewport и свежие профили браузера:

- Сравнить headless и обычное окно того же браузера без изменения приложения
  или добавления флагов, отключающих лимиты кадров. Проверить чтение, перемещение
  и обратную команду, авторитетный снимок и восстановление исходного состояния.
- Записать интервалы rAF до/после чтения, перемещения и reload; дополнительно
  проверить прокрутку доски в viewport, visibility/focus, таймеры и long tasks.
  `visible` и наличие фокуса сами по себе не доказывают нормальную выдачу кадров.
- Проверить статический HTML без приложения: отдельно fetch без изменения DOM
  и изменение текста. Сохранить как воспроизведения, так и повторы без симптома.
- Снять CDP Tracing с категориями `viz`, `cc`, `devtools.timeline` и
  `renderer.scheduler`. Сопоставить `FireAnimationFrame` renderer страницы с
  `SendBeginFrameDecision`, включая причины `ThrottleUndrawnFrames` и
  `ThrottleUnresponsiveClient`. Общие счётчики без frame sink ID не приписывать
  целиком странице. Механизм решений описан в
  [исходниках Chromium](https://chromium.googlesource.com/chromium/src/+/c4d4f3344d83d2cbc51d57ce6e3efbab91ea2b3b/components/viz/service/frame_sinks/compositor_frame_sink_support.cc).
- DOM-команду и подтверждение DOM отмечать внутри одного вызова страницы.
  Если observer установлен предыдущим CDP-вызовом, явно учитывать этот промежуток
  в названии и трактовке диагностического интервала.

Флаги вроде `--disable-frame-rate-limit` допускаются только как отдельное
диагностическое вмешательство. Исчезновение симптома с таким флагом не означает
прохождение A62. Смена headless на обычное окно также требует отдельного отчёта,
полных серий и независимого наблюдения показа; прежние превышения сохраняются.
Результаты, трассы, их хеши и локальное продолжение — только в
`docs/reports/p01-11/GAP-006-root-cause.md` и связанных файлах.

## Независимые верхние границы по пикселям Windows

После подготовки production-сборки и явного выбора прямого исполняемого файла
Opera в `PROTOTYPE_BROWSER_PATH`, из `prototypes/`:

```powershell
bun run measure:desktop:pixels opera
if ($LASTEXITCODE -ne 0) { throw 'Desktop pixel measurement failed.' }
```

Этот отдельный Windows runner использует `desktop-pixel-observer.ps1` с
Windows PowerShell/System.Drawing, без новых зависимостей приложения. Он открывает
собственное headed-окно с временным профилем и синтетической SQLite. Только это
окно временно показывается поверх остальных; переключение фокуса и системный
ввод не требуются. Перед захватом проверяются границы и принадлежность участка
тестовому окну. Перекрытие, недоступный рабочий стол, неподдержанная геометрия
или тайм-аут останавливают прогон и сохраняются в отчёте.
Пиксельные измерители запускаются последовательно: параллельные окна-наблюдатели
взаимно меняют порядок окон и условия захвата, поэтому такие серии не объединяют.

Начало интервала — запуск независимого наблюдателя **до** DOM-команды существующей
кнопки. Конец — обнаружение ожидаемого изображения через захват рабочего стола
ОС, без браузерного screenshot и ожидания rAF. Все отметки принадлежат одним
часам Windows QPC. `upper_bound_ms` включает передачу команды/CDP, захват и
выравнивание viewport, если оно нужно; ничего не вычитается. Это верхняя граница,
а не точное время отклика или интервал от мыши/касания. Поле
`arm_to_pixels_lower_ms` относится к наблюдателю и не задаёт нижнюю границу
задержки команды. Проверка матрицы физического монитора сюда не входит.

Перед сериями runner проверяет отказ при уже видимом результате, искусственную
задержку сохранения и тайм-аут скрытого результата при подтверждённом commit.
После контролей исходный снимок восстанавливается. Затем выполняются пять
прогревов и тридцать измерений отдельно для переноса/отмены и поиска/сброса;
сохранённые снимки и число результатов проверяются общим API.

Эталоны строятся отдельно для каждого состояния и проверяются целиком:
перенос — заголовки в исходной и целевой колонках, поиск — полный заголовок
первой карточки, включая перенос строки. Геометрия поиска может различаться
между одним результатом и всем набором. Нельзя считать различие хешей двух
обрезанных участков доказательством правильного результата.

Запуск — две серии по десять. Первая перезапускает Rust/Vite при уже работающих
браузере и наблюдателе; вторая повторно открывает страницу при работающих
серверах. В обоих случаях включены чтение сохранённой доски и выравнивание
показываемого участка. Это отдельный профиль, который нельзя объединять с
прежними reload/force-stop сериями. Создание браузера, первый запуск после
установки и холодный кеш ОС этим runner не измеряются.

Отчёт `<label>-pixels-<timestamp>.json` и PNG остаются в `docs/reports/p01-11/`.
Он содержит все наблюдения/отказы, отдельные контроли, прогревы и отсчёты,
проверки снимков, хеши наблюдателя, клиента, release-бинарника и фактического
production-bundle, геометрию и cleanup. Для статистики явно указан
`metric: conservative_upper_bound_ms`. Верхняя граница в пределах ориентира
подтверждает только измеряемую границу изображения ОС; `upper_bounds_above_budget`
означает неопределённый результат, а не доказанную задержку самого приложения.

Это средство проверки прототипа, а не функциональность выпуска. Переносимость
метода на другие браузеры/геометрию и Android требует отдельной валидации.
Windows runner не запускается в headless CI. Обычные rAF-runner сохраняют
`ui_acceptance_eligible: false`; отдельный пиксельный отчёт не переоценивает их
задним числом и не закрывает A62 целиком. Текущие локальные доказательства и
продолжение — `docs/reports/p01-11/windows-pixel-review.md`.
