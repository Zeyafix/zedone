# ADR-0038: время и граница фиксации доступа

Дата: 2026-11-05. Статус: техническое решение P03.05.3.

Публичный вход использует только часы storage, после захвата SQLite writer lock.
В стартовой схеме v1 (ADR-0047) одна строка access_clock хранит две верхние
отметки: calendar_ms для календаря и effective_ms для срока доступа.
Они не входят в снимки пространств и обновляются также при отказе команды.
Новая установка начинает с двух нулей, без выдачи прав. Промежуточные базы
разработки с прежним layout не мигрируют и не сбрасываются автоматически.

SystemTime ОС — доверенный календарный источник; Instant задаёт нижнюю границу
прошедшего времени внутри процесса. Время клиента не принимается. Откат ниже
сохранённой календарной отметки, переполнение или отказ источника дают unavailable.
Обе сохранённые отметки читаются вновь под writer lock каждым процессом.
При восстановлении календарного времени работа возобновляется; обхода или
сброса отметки через API нет. Истёкшее наблюдённое разрешение не оживает при
restart или откате часов; требуется новая явная выдача с новым ключом.

Авторизация проверяет срок перед обработчиком и после него. Storage повторяет
проверку наиболее раннего использованного срока после flush непосредственно
перед commit. Истечение до этой точки отменяет весь эффект и receipt. После
финальной проверки уже начатый commit завершается: истечение во время самого
commit не отменяет зафиксированную команду. Отзыв сериализован writer lock.
Ответ и внешние эффекты разрешены только после успешного commit.

Операция работает внутри savepoint. При отказе/панике откатываются её данные,
но обе максимальные отметки времени фиксируются внешней транзакцией. Ошибка
фиксации остаётся outcome_unknown; потеря ответа не доказывает отсутствие эффекта.

Это защита относительно наблюдённого времени и доверенной ОС. Без внешнего
источника нельзя обнаружить неизвестное время, проведённое с выключенным
устройством и изменёнными часами. Instant не обещает учитывать сон на каждой
платформе. Подмена ОС, удаление/откат всей SQLite относятся к границе доверия
и P07.09; эта работа не открывает восстановление старой базы.

## Уточнение FIX.01 от 2026-11-09

Разработчик явно разрешил разделить календарную и эффективную отметки.
Прежняя общая observed_ms могла опережать растущий raw calendar из-за
монотонной проекции; сравнение raw с ней приводило к unavailable (GAP-014).
Отказ ниже общей проекции заменяется следующими правилами:

- Календарь сравнивается только с calendar_ms; реальный откат даже на 1ms
  по-прежнему отклоняется. Tolerance, sleep/retry и подмена raw не вводятся.
- Эффективное время — максимум raw calendar, прежнего effective_ms и
  process-local монотонной проекции. Оно всегда не ниже calendar_ms.
- Замерший календарь не останавливает монотонное истечение. Календарь ниже
  effective_ms допустим, если не ниже calendar_ms: это не откат сам по себе.
- Если другой worker повысил persisted effective_ms, текущий worker поднимает
  свою монотонную опору до этой отметки. Иначе effective время могло бы
  остановиться, пока устаревшая опора догоняет сохранённое значение.
- Ошибка/паника/отказ срока сохраняют обе отметки без частичного эффекта
  команды. Restart начинает эффективное время не ниже сохранённого;
  наблюдённое истечение не отменяется при рестарте или замершем календаре.

Схема v1 и её синтетический эталон обновляются на месте по ADR-0047.
Старый одноколоночный layout отклоняется без записи. Публичный API, права,
проверки перед commit и ограничения доверия к ОС сохраняются.
Проверки и ограничения — [EV-081](../../agent/verification/EV-081-trusted-clock-readings.md).

Основание: [SystemTime](https://doc.rust-lang.org/std/time/struct.SystemTime.html)
не монотонен; [Instant](https://doc.rust-lang.org/std/time/struct.Instant.html)
монотонен, но не определяет календарное время и одинаковый учёт сна.
