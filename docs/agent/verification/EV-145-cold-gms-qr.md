# EV-145 — первый запуск QR-сканера до загрузки GMS-модели

Дата: 2026-11-22. Шаг P06.13.2.1.2, GAP-052/A51.

Текущий итог — LOG-792: P06.13.2.1.2 `done`, GAP-052 `resolved` на прежнем
интегрированном продукте `d25f673`. В отдельном Google Play AVD наблюдались
отсутствие модели без сети, ручной путь, настоящая загрузка и готовое чтение
текущего QR тем же APK; дополнительный повтор без сети с действующим приглашением
прошёл точно и без отправки запроса. Cleanup подтверждён. Общие A51/P06/T09
сохраняют прежние состояния до сводной приёмки P06.13.2.1. Нижние итоги
LOG-790/791 описывают промежуточные блокировки, а не текущую готовность.

## Рабочая карточка

- База: `d25f673a04181d5e3815e9ffee26402a25ca417e`, отдельная ветка
  `test/p06-13-2-1-2-cold-gms` по поручению разработчика.

  локальный state сохранены побайтно и проверены SHA-256 в ignored reports.
  Изменения сохранены при создании ветки; продуктовые исходники прежние.
- Цель: наблюдать в одной отдельной GMS-среде неготовое распознавание при
  первом запуске без сети, доступный ручной путь без ложной ошибки приглашения,
  затем загрузку модели и повторное чтение текущего продуктового QR.
- Требования: A51, спецификация §11.51, ADR-0009/0022/0023/0062;
  зависимости P06.02/EV-107 интегрированы, EV-144 определяет оставшийся охват.

  APK/общего API и необходимые доказательства. Продуктовый код меняется только
  при подтверждённом относящемся к этому шагу дефекте.
- Проверки: Device inventory; исходные версии/отпечатки APK; отсутствие готовой
  модели; offline scan/manual/cancel; готовность после включения сети и точное
  чтение QR без автоматической отправки; сохранность, cleanup и итоговый diff.
  UI/lifecycle выполняются только через Device/agent-device.
- Обратимость: использовать собственную новую среду, сохранить её исходное
  состояние и тестовые артефакты, удалить собственную установку/данные и вернуть
  изменённые настройки. Данные GMS физического телефона не очищать.
- Границы: отдельные AOSP/manual и готовая модель не доказывают переход.
  Инъекция результата сканера не доказывает работу модели. Оптическая камера
  телефона и камера эмулятора имеют раздельный охват. Прежние критерии/DEC/GAP
  сохраняются; A47/GAP-050 остаются в POST.01, CI-оптимизация на паузе.
- Начальный результат: ветка и сохранение подготовлены; подходящая холодная
  GMS-среда ещё не подтверждена. GAP-052 и полные P06/T09/A51 не закрыты.

## Подготовка среды

Device inventory показывает AOSP API33 x86_64 и физический Galaxy A32/Android13.
На телефоне ранее проверялась готовая модель EV-107; он не используется для
сброса общих данных Google Play Services. Установленный образ SDK — только AOSP.
Проверяется возможность добавить отдельный Google APIs AVD и открыть его через
Device, сохранив прежний AOSP AVD и телефон.

Модель выбранной unbundled-зависимости хранится в Google Play Services и может
загружаться при первом использовании; переустановка ZeDone сама по себе не
гарантирует холодное состояние. Источники:
[ML Kit installation paths](https://developers.google.com/ml-kit/tips/installation-paths),
[Barcode scanning](https://developers.google.com/ml-kit/vision/barcode-scanning/android).
Камера Android Emulator поддерживает изображение QR в виртуальной сцене:
[Camera support](https://developer.android.com/studio/run/emulator-use-camera).
Это возможность стенда, а не уже полученное доказательство распознавания.

## Диагностика доставки — LOG-791

Продолжение выполнено в той же отдельной ветке от `d25f673`; все исходные
dirty документы/local state снова сохранены SHA-256. Для уточнения отказа
собрана отдельная локальная diagnostic APK: тот же ML Kit18.1.0 и base18.1.0,
официальные `ModuleInstallClient.areModulesAvailable/installModules`, настоящий
listener состояний/байтов. Продукт/плагин не менялись, fake-клиента нет.
Локальный Gradle-проект и APK остаются в ignored reports; сборка offline
прошла после согласования уже кешированных AndroidX с продуктовым набором.
Первые ошибки разрешения кеша не являются runtime-результатом.

На Google APIs API35 пакет vending оказался `LicenseChecker`1.8, GMS24.23.35;
availability GMS0, модель false, запрос установки завершился state5/error8.
Этот факт не доказывает единственную причину отказа всех Google APIs образов.
Дополнительно создан собственный Google Play API35 x86_64/rev9 AVD с настоящим
Phonesky41.3.25 и первоначально тем же GMS24.23.35. До первого scan отключены
сеть и Wi-Fi через agent-device; native ML Kit подтвердил отсутствие модуля,
нейтральный timeout20s/manual/camera release повторены тем же APK.

Первый запуск offline также прервал начальную регистрацию Google. В журнале
есть Checkin FAILURE/DNS/network и перенос следующей попытки примерно на2h.
После включения VALIDATED-сети ModuleDelivery возвращал HTTP400 при android-id0
и пустом check-in token; диагностическая установка тоже дала state5/error8.
Одного Phonesky оказалось недостаточно. Данные регистрационных токенов/ID
не публикуются, сырые журналы остаются локальными.

Для восстановления использован
[документированный Google ручной check-in](https://support.google.com/pixelphone/answer/6212917)
через собственное приложение «Телефон» в Device/agent-device. GMS имеет
соответствующий зарегистрированный обработчик; signature-права не обходились,
время/приватные флаги/кеши GMS не подменялись. Native журнал подтвердил manual
Checkin SUCCESS, затем ещё один автоматический SUCCESS. Вход в Google-аккаунт
не использовался. Драйвер вернул `Android fill verification failed`, поскольку
Phone обработал и очистил служебный код; фактическое действие подтверждено
нативным журналом, ввод не повторялся вслепую.
