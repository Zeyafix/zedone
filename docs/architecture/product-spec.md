# ZeDone: продукт и архитектурные требования

Статус: рабочая концепция для составления плана. Подтверждённые требования согласованы в обсуждении; архитектурные предложения и технические проверки отмечены отдельно. Документ не является планом реализации.

Даты обсуждения: 2026-10-25 — 2026-10-26.

Документ предназначен для разработчика и агента, который впоследствии составит план реализации. Подтверждённые требования отделены от предложений. Открытые вопросы нельзя молча считать решёнными. Здесь описывается желаемое приложение; реализованного функционала пока нет.

## 1. Подтверждённые требования

- ZeDone — личное приложение для заметок и дел. Совместная работа разных пользователей не входит в первую версию.
- Иерархия: пространство → колонки → карточки. Заголовок карточки обязателен; отдельный текст может быть пустым.
- В первой версии карточки перемещаются между колонками одного пространства. Перенос между пространствами не входит в первую версию.
- Колонки и карточки упорядочиваются вручную. Порядок сохраняется и синхронизируется между устройствами.
- Пространства с нерешённым конфликтом названия показываются один раз в группе «Конфликты названий» в начале списка пространств и поиска по всем пространствам. Остальные пространства автоматически упорядочиваются по имени. После разрешения конфликта названия пространство возвращается в обычный порядок; варианты названия доступны до разрешения конфликта.
- Теги существуют отдельно в каждом пространстве. Одинаковые названия в разных пространствах независимы.
- Имена тегов внутри пространства сравниваются без учёта регистра и пробелов по краям: «Работа» и «работа» обозначают один тег. Буквы «е» и «ё» различаются: «Все» и «Всё» — разные имена, «ВСЁ» и «Всё» — одно имя. Правило общее для создания, переименования, синхронизации и разрешения имён через интерфейс, HTTP и CLI на Windows/Android; ADR-0012.
- Независимо созданные без связи одноимённые теги одного пространства при синхронизации автоматически объединяются в один тег с сохранением всех назначений карточкам. Имена сравниваются по общему правилу без учёта регистра и пробелов по краям с различием «е» и «ё». Само такое создание не требует ручного разрешения конфликта; правило одинаково для интерфейса, HTTP и CLI на Windows и Android. При объединении вариантов с разным регистром автоматически сохраняется одно из введённых написаний, одинаковое на устройствах для одного набора изменений независимо от порядка/повторов доставки. После объединения имя можно изменить обычным переименованием с сохранением назначений; интерфейс, HTTP и CLI получают одно написание из общего ядра. Конкретный алгоритм выбора и согласование идентификаторов проектируются отдельно; ADR-0012.
- Переименование тега в имя другого существующего тега этого пространства отклоняется с понятной ошибкой. Объединение существующих тегов при таком переименовании в первую версию не входит.
- Если на устройствах без связи два разных существующих тега одного пространства независимо переименовали в одно имя, после обмена показывается конфликт. Оба тега, их идентификаторы и назначения карточкам сохраняются; пользователь явно выбирает разные имена по общему правилу сравнения. Автоматического слияния или добавления суффиксов нет; [ADR-0012](decisions/0012-tag-rename-conflicts.md).
- Если на одном устройстве существующий тег пространства переименован в имя независимо созданного на другом устройстве нового тега того же пространства, после обмена также показывается явный конфликт. Оба тега, их идентификаторы и назначения сохраняются; разные имена выбираются явно, автоматического объединения нет. Применяются те же правила разрешения и доступных действий, что и при коллизии двух переименований; ADR-0012.
- При таком конфликте спорные теги явно помечены. Если у карточки спорно только имя назначенного тега, доступны изменения заголовка, текста, статуса выполнения и колонки в пределах пространства; имена тегов разрешаются отдельно. До выбора разных имён назначение и снятие обоих спорных тегов приостановлены для всех карточек пространства; существующие назначения сохраняются, после допустимого решения эти операции снова доступны. Карточки с собственными конфликтами по-прежнему заблокированы. Правила одинаковы для интерфейса, HTTP и CLI на Windows/Android.
- Удаление назначенного тега удаляет его и снимает со всех карточек этого пространства. Карточки и их текст сохраняются.
- Удалённые теги не попадают в корзину; отдельного восстановления удалённого тега вместе с прежними назначениями нет. Теги считаются примитивными объектами; это согласованное исключение из общего требования обратимости. Повторное создание тега с тем же именем не возвращает прежние назначения: их нужно задать заново.
- Восстановление всего пространства из снимка возвращает теги и назначения, которые были в снимке, даже если их удалили позже. Отдельное восстановление удалённого тега по-прежнему недоступно.
- Текст карточки — базовый CommonMark: простой текстовый редактор и просмотр форматирования. Расширения таблиц и текстовых чекбоксов в первую версию не входят; исходные текстовые маркеры сохраняются. Выбор синтаксиса оформлен в [ADR-0006](decisions/0006-markdown-syntax.md); пользовательская HTML-разметка показывается как обычный текст, HTTP/HTTPS-ссылки открываются по нажатию вне ZeDone — в отдельной вкладке браузера на Windows и во внешнем браузере на Android; удалённые изображения загружаются внутри карточки только по отдельному нажатию; для просмотра выбраны markdown-it + DOMPurify с обязательной технической проверкой.
- Заголовок и текст карточки сохраняются автоматически. Интерфейс показывает состояния «сохранение», «сохранено» и «ошибка».
- Все команды изменения существующей карточки используют единую проверку актуальности заголовка, описания, тегов, отметки выполнения, положения на доске (колонка и порядок карточки) и состояния «активна/в корзине». Если эти данные изменились после чтения, подготовленная ранее команда отклоняется с понятной причиной: нужно перечитать карточку и подготовить действие заново. Правило включает редактирование, теги, выполнение, перемещение/порядок, удаление и восстановление. При отказе текущие данные и история сохраняются, новый конфликт, версия истории и ложный успех не создаются; введённый текст остаётся в редакторе. Правило одинаково для человека и агента через общий API на Windows/Android; [ADR-0007](decisions/0007-stale-text-edits.md). Независимые уже сохранённые правки при синхронизации сохраняют правила раздела 1.2.
- Отправка активной колонки в корзину проверяет актуальность её состава, данных самой колонки и каждой входящей карточки. Изменение любых из этих данных после чтения отклоняет всю команду без частичного удаления, даже при прежнем наборе карточек. Клиент показывает актуальные состав и данные; после перечитывания требуется новое явное действие, автоматическая подстановка свежего состояния с повтором старой команды запрещена. Правило общее для интерфейса, HTTP и CLI на Windows/Android; [ADR-0014](decisions/0014-column-deletion-membership.md).
- Отправка пространства в корзину использует ту же строгую проверку актуальности его данных и содержимого: колонок, карточек и тегов пространства. Если они изменились после чтения, вся команда отклоняется без частичного удаления. Клиент показывает актуальное состояние, после перечитывания требуется новое явное действие; автоматическая подстановка свежего состояния с повтором старой команды запрещена. Правило одинаково для человека и агента на Windows/Android; ADR-0014.
- При неизвестном результате команд карточки или обычных действий с колонками/пространствами (создание, переименование, порядок колонок, отправка в корзину и восстановление из неё) клиент ограниченно повторяет ту же команду автоматически, затем предлагает ручной повтор. Идентификатор, операция, цель и параметры, включая исходные предусмотренные условия актуальности, сохраняются. Уже выполненная команда возвращает прежний результат без повторного действия, лишней версии истории, новой границы серии или группы удаления; более новые правки сохраняются. При отсутствии подтверждения показываются неизвестный результат и кнопка «Повторить»; успех не показывается. Явные отказы не повторяются автоматически. Правило общее для человека и агента на Windows/Android; [ADR-0008](decisions/0008-safe-card-creation-retries.md). Параметры попыток, хранение результатов, перезапуск и истечение срока проектируются отдельно.
- Ввод с временно пустым обязательным заголовком считается несохранённым. При обычном уходе приложение предупреждает пользователя; при принудительной остановке такой ввод может потеряться. Статус «сохранено» для него недопустим.
- У карточки есть самостоятельная отметка «выполнено». Она не зависит от колонки. Отметку можно снять.
- На Windows приложение поднимает локальный сервер, интерфейс открывается в браузере.
- В первой версии Windows-приложение запускается только вручную. Автозапуск вместе с ОС в первую версию не входит.
- Windows-приложение распространяется установщиком с GitHub и запускается ярлыком. Пользовательский интерфейс остаётся браузерным, данные хранятся отдельно от файлов программы.
- Для создания Windows-установщика выбран Inno Setup. Установка и установка обновлений выполняются только для текущей учётной записи без запроса прав администратора. Установка сразу для всех пользователей ПК в первую версию не входит; версия инструмента и параметры сборки ещё определяются. [ADR-0017](decisions/0017-windows-per-user-installation.md).
- В Windows-деинсталляторе доступны отдельные независимые выборы удаления рабочих данных текущей установки и удаления её автоматических резервных копий, с явным подтверждением состава. По умолчанию оба выбора выключены; без выбора данные сохраняются. Ручные экспорты и данные других устройств не удаляются. Окончательная локальная очистка после предупреждения и подтверждения разрешена как явное исключение из обратимости: при отсутствии других источников восстановление средствами ZeDone может стать невозможным; [ADR-0021](decisions/0021-uninstall-data-cleanup.md).
- ZeDone уведомляет о новой версии; пользователь самостоятельно скачивает и запускает установщик обновления. Данные сохраняются, перед миграцией создаётся страховочная копия. Автоматическая установка обновлений не выбрана.
- Сведения о новых версиях берутся из GitHub Releases: при работающем приложении выполняется автоматическая проверка раз в сутки, также доступна ручная команда «Проверить обновления». Автопроверку можно выключить и включить обратно; ошибка сети не мешает работе с пространствами. Скачивание и установка остаются ручными. Правило общее для Windows и Android; [ADR-0018](decisions/0018-update-checks-github-releases.md).
- После закрытия вкладки локальный сервер Windows продолжает работу до явного завершения приложения. Пока ПК работает и процесс запущен, сохраняется возможность синхронизации и доступа агента.
- Управление фоновым процессом Windows доступно через значок в трее: открыть браузерный интерфейс и завершить приложение. Те же действия доступны через CLI.
- На Android приложение устанавливается как APK и самостоятельно работает с локальными данными.
- Целевая ОС ПК — Windows 11. Целевой телефон — Samsung Galaxy A32 с Android 13 и 4 ГБ ОЗУ.
- Контрольный ПК разработчика: AMD Ryzen 7 7700X, 8 ядер/16 логических процессоров, 64 ГБ установленной ОЗУ. Расход ОЗУ ZeDone не должен превышать 4 ГБ на ПК и 2 ГБ на Android, включая интерфейс и пиковые нагрузки. На ПК учитываются Rust-сервер и браузерный интерфейс ZeDone без других сайтов, на Android — всё приложение с Rust и WebView. [ADR-0019](decisions/0019-memory-budgets.md).
- Стартовые ориентиры прототипа: открыть карточку, переместить её или изменить отметку выполнения — до 300 мс; первые результаты поиска — до 1 секунды; первый рабочий экран после запуска — до 3 секунд. На ПК запуск самого браузера измеряется отдельно. В дальнейшем задержки должны становиться как можно меньше; это цели измерений, не достигнутые результаты. [ADR-0020](decisions/0020-prototype-latency-targets.md).
- Браузерный интерфейс Windows проверяется в Google Chrome и Opera. Номера проверенных версий фиксируются при проверке.
- В первой версии синхронизируются один ПК и один Android-телефон. Постоянно включённого устройства для хранения реплики нет.
- Ожидаемый масштаб — тысячи карточек. Точное число для приёмочных измерений и распределение карточек по пространствам ещё не согласованы.
- Действия доступны на обеих платформах. Размещение элементов и способы управления могут адаптироваться к экрану и ОС.
- Используется собственный дизайн ZeDone на обеих платформах. Перетаскивание карточек и колонок требуется и на ПК, и на телефоне; явные команды перемещения также сохраняются.
- Основная логика, хранение и синхронизация пишутся на Rust. В собственном коде ядра, хранения и синхронизации unsafe запрещён. Минимальные платформенные исключения допускаются только с отдельным обоснованием.
- Для локального хранения выбраны SQLite и rusqlite с `bundled`: SQLite поставляется вместе с приложением. Обязательна техническая проверка на Windows и Android. Схема данных, миграции, версии зависимостей и подробный набор проверок определяются отдельно.
- Для синхронизации выбран Automerge для Rust с обязательной технической проверкой согласованных правил ZeDone. Выбор и основания оформлены в [ADR-0002](decisions/0002-automerge-sync.md); обязательное сравнение двух реализаций заменено прототипом выбранной библиотеки.
- Для первой версии выбрана одна SQLite-база на устройство. Снимки и восстановление отдельных пространств выполняются логически через общее Rust-ядро с сохранением остальных пространств.
- Для HTTP API на Windows и Android выбраны Axum и Tokio как адаптер к общему Rust-ядру. Прикладные правила и доступ к данным остаются в общем ядре. Работа HTTP-сервера в составе APK проходит обязательную техническую проверку.
- Для общего веб-интерфейса выбраны Vue + TypeScript в строгом режиме + Vite. Типы API генерируются из Rust. Выбранный интерфейс и Android-оболочка проходят техническую проверку.
- Для HTTP-контракта и клиента выбрана цепочка utoipa + OpenAPI + openapi-typescript + openapi-fetch: Rust-описания данных и операций → OpenAPI → типы TypeScript → HTTP-клиент на openapi-fetch. Решение оформлено в [ADR-0003](decisions/0003-api-contract-toolchain.md).
- Для управления JavaScript-зависимостями и запуска инструментов разработки интерфейса и CI выбран Bun. Обязательна проверка всей выбранной цепочки Vue/TypeScript/Vite/Tauri на Windows и в CI, включая фактически используемую среду запуска каждого шага. Конкретная версия Bun и команды определяются при подготовке прототипа.
- Совместимость выбранной цепочки генерации API с Bun пока не подтверждена и обязательно проверяется в P01 на Windows и в CI: установка пакетов, запуск openapi-typescript под Bun, импорт/сборка openapi-fetch и проверка типов. Для каждого шага фиксируются команда и фактическая среда выполнения. Если требуется Node.js, явно указываются затронутый шаг, причина и версия как дополнительное требование разработки/CI; такой запуск не считается успешной проверкой выполнения под Bun. Bun остаётся менеджером пакетов; Node.js не становится зависимостью готового приложения.
- Для Android-оболочки выбран Tauri 2. Резерв — собственная оболочка Kotlin + Android WebView с подключением общего Rust-ядра. Обязательная техническая проверка выбранной оболочки входит в P01; выбор оформлен в [ADR-0001](decisions/0001-android-shell.md).
- В прототипе Tauri 2 первым проверяется IPC через команды Tauri между интерфейсом APK и Rust-ядром. IPC и внешний HTTP на Axum вызывают одни прикладные операции общего ядра. Окончательный выбор внутреннего транспорта подтверждается по результатам прототипа.
- Kotlin допустим для необходимой платформенной интеграции Android. Основная логика, хранение и синхронизация остаются на Rust.
- Для сложных компонентов интерфейса выбран Reka UI; простые кнопки и поля используют стандартные семантические HTML-элементы. Подключаются только необходимые компоненты, оформление ZeDone остаётся собственным и общим для обеих платформ. Решение и обязательная техническая проверка зафиксированы в [ADR-0004](decisions/0004-ui-components.md). Для перетаскивания выбраны SortableJS через VueDraggablePlus; [ADR-0005](decisions/0005-drag-and-drop.md). Для просмотра Markdown выбраны markdown-it + DOMPurify; [ADR-0006](decisions/0006-markdown-syntax.md). Дополнительные зависимости требуют обоснования.
- Внешнее редактирование карточек как обычных Markdown-файлов не требуется: работа выполняется через ZeDone и его API, перенос — через экспорт и импорт.
- Основная разработка и автоматические проверки Android выполняются через эмулятор Android 13, локально на Windows 11. Целевым телефоном остаётся Galaxy A32; измерения эмулятора не считаются подтверждением производительности телефона.
- GitHub Actions дополняет локальные проверки только в пределах бесплатных возможностей. Для удалённых проверок Windows используется Windows, для Android-эмулятора — Linux. Установка Linux на ПК разработчика не требуется.
- Все устройства полноценно работают без сети. Изменения объединяются, когда устройства доступны друг другу.
- Для связи между устройствами используется Tailscale. «Без облачных сервисов» означает хранение заметок на устройствах; собственное размещение всей сетевой инфраструктуры не запрошено.
- При уже настроенном Tailscale телефон подключается к ПК в ZeDone через QR-код на экране ПК и сканирование на телефоне. Запасной способ без камеры — ручной ввод адреса ПК в Tailscale и одноразового кода подключения. Пространства для синхронизации выбираются явно; [ADR-0009](decisions/0009-device-pairing-qr-and-code.md). После QR или ручного ввода на ПК появляется запрос, который нужно явно подтвердить. До подтверждения телефон показывает ожидание, не считается подключённым и не начинает обмен пространствами. Протокол и срок действия приглашения ещё определяются.
- Для чтения QR-кода камерой Android выбран официальный Tauri Barcode Scanner с обязательной технической проверкой совместимости, разрешений, отмены, недоступной камеры/модели и ручного ввода. Для генерации QR в общем Rust-ядре выбран qrcodegen с общим отображением в SVG и обязательной проверкой чтения; [ADR-0023](decisions/0023-qr-generation.md). Выбор сканера не меняет общий процесс подключения и подтверждение на ПК; [ADR-0022](decisions/0022-android-qr-scanner.md).
- Допустима первая загрузка модели распознавания сканера. До её готовности доступен ручной ввод адреса и кода; неготовность сканера не считается неверным приглашением. После готовности распознавание можно повторить. Мгновенная готовность QR после установки без загрузки модели не требуется; [ADR-0022](decisions/0022-android-qr-scanner.md).
- Для синхронизации допускаются разные версии ZeDone на ПК и телефоне, если совместимость протокола и формата данных явно поддержана и проверена. Одинаковый номер версии приложения не является обязательным условием.
- Обмен, остановленный из-за несовместимости протокола или формата данных, возобновляется автоматически после успешной проверки совместимости. Явная пауза пространства после восстановления сохраняется до отдельной команды возобновления.
- Выбранные пространства синхронизируются с указанными устройствами. Обмен запускается автоматически при открытии приложения и доступности устройств. Есть ручной запуск. На Android фоновая работа выполняется по возможности.
- При независимых изменениях одного текста сохраняются обе версии. Пользователь выбирает одну или вручную объединяет их.
- Независимые изменения разных полей карточки объединяются автоматически: например, заголовок с ПК и текст с телефона. Разные независимые правки одного поля требуют ручного разрешения конфликта.
- До разрешения всех собственных конфликтов карточки редактирование всей карточки заблокировано, включая неконфликтующие поля. Просмотр карточки и явное разрешение конфликтов остаются доступны. После разрешения всех конфликтов редактирование возобновляется. Правило одинаково для интерфейса, HTTP и CLI на Windows и Android.
- При независимом перемещении одной карточки в разные колонки сохраняются оба варианта. Пользователь разрешает конфликт, выбирая колонку; решение синхронизируется между устройствами.
- До разрешения конфликта перемещения карточка отображается в отдельной области «Конфликты» вместо спорных колонок. После выбора она появляется в выбранной колонке. Карточка остаётся одним объектом.
- Если конфликт касается только заголовка или текста, а колонка определена однозначно, карточка остаётся в своей колонке с отметкой конфликта. Редактирование всей карточки заблокировано; просмотр и явное разрешение конфликта доступны.
- Независимые добавления разных тегов одной карточке объединяются автоматически: после обмена сохраняются оба тега.
- Если на одном устройстве удалили сам тег из пространства, а на другом независимо назначили его карточке, показывается конфликт. Пользователь выбирает, сохранить тег с назначениями или подтвердить удаление со снятием всех его назначений. До решения конфликтующие варианты сохраняются; решение синхронизируется между устройствами.
- До разрешения конфликта удаления тега против назначения карточки со спорными назначениями остаются в своих однозначно определённых колонках с отметкой конфликта. Спорный тег явно помечен; редактирование карточек заблокировано по общему правилу. Просмотр и явное разрешение конфликта доступны.
- Удаление карточки, колонки и пространства перемещает объект в корзину. Есть восстановление. Окончательная очистка — отдельное действие.
- Корзина очищается только вручную: объекты хранятся до явной окончательной очистки. Автоматическая очистка, в том числе по сроку хранения, в первую версию не входит.
- В корзине одного пространства доступны оба варианта окончательной очистки: выбранные объекты либо вся корзина этого пространства.
- Окончательная очистка колонки или пространства охватывает все их вложенные объекты, которые ещё находятся в корзине, включая удалённые раньше самого контейнера. Перед очисткой показывается состав затронутых объектов. Активные объекты и карточки, уже восстановленные в другую колонку, не затрагиваются.
- Если среди выбранных для окончательной очистки объектов или их вложенных объектов есть нерешённый конфликт, останавливается вся выбранная операция: ни один объект из её области не очищается. Показывается список конфликтов; сначала нужно разрешить их, затем заново запустить очистку.
- Если после окончательной очистки с другого устройства приходит независимая правка очищенной карточки, правка сохраняется в области «Конфликты». Пользователь явно выбирает восстановление карточки или подтверждение окончательной очистки. Автоматического восстановления карточки на доске нет; решение синхронизируется между устройствами.
- Если карточку удалили на одном устройстве и независимо отредактировали на другом, показывается конфликт. Правка сохраняется; пользователь выбирает, оставить карточку в корзине или восстановить с изменениями.
- То же правило применяется при удалении колонки или пространства на одном устройстве и независимой правке карточки внутри на другом: правка сохраняется, удаление или восстановление выбирается явно при разрешении конфликта.
- Конфликт удаления карточки, колонки или пространства против независимой правки карточки до решения показывается в отдельной области «Конфликты». Доступны просмотр сохранённой правки и состав затронутых объектов, чтобы оценить охват удаления или восстановления.
- Колонка или пространство восстанавливаются вместе с объектами, удалёнными тем же действием. Ранее удалённые карточки остаются в корзине.
- Если нужная карточка находится в пространстве, которое тоже в корзине, сначала явно восстанавливается пространство со всеми объектами, удалёнными вместе с ним. Если карточка осталась в корзине, её затем восстанавливают отдельно. Частичное восстановление пространства только ради одной карточки в первую версию не входит.
- Если пространство существует, а исходная колонка карточки находится в корзине, пользователь выбирает существующую колонку того же пространства и восстанавливает туда только выбранную карточку.
- Нужна история версий карточки с просмотром и восстановлением прежних заголовка и описания, в том числе после действий агента. Каждая видимая версия хранит оба поля из одного сохранённого состояния; изменение только заголовка также участвует в истории по общим правилам. [ADR-0013](decisions/0013-history-participant-boundaries.md). Восстановление выбранной версии записывает её заголовок и описание как новую правку и фиксирует новую видимую версию; вся предшествующая история сохраняется, включая более поздние версии относительно выбранной.
- Для исправления результатов действий используются обычные обратные операции и восстановление версий карточек. Единая команда отмены серии действий человека или агента отложена и в первую версию не входит.
- Непрерывное редактирование одним участником объединяется в одну видимую версию истории, которая фиксируется при завершении редактирования, существенной паузе (30 секунд без новых правок заголовка или описания) или смене участника. Последовательность «человек → агент → человек» образует три раздельных этапа с доступом к заголовку и описанию каждого, даже без долгой паузы между этапами. Каждая отдельная прикладная команда, успешно изменившая заголовок или описание, фиксирует собственную видимую версию; две команды одного агента подряд не объединяются по времени. Группировка автосохранений непрерывного ввода сохраняется. Локальное автосохранение выполняется чаще; [ADR-0013](decisions/0013-history-participant-boundaries.md). После неожиданной остановки и перезапуска сохранённая незавершённая серия фиксируется отдельной версией с последними успешно сохранёнными заголовком и описанием; дальнейший ввод начинает новую серию даже тем же участником и без существенной паузы. Повторные перезапуски без новых правок не создают лишних версий.
- История версий не удаляется автоматически. Пользователь может видеть её объём и вручную очищать её. Это не означает разрешения удалять технические данные, необходимые для корректной синхронизации.
- История карточки общая для пространства и синхронизируется между устройствами. Ручная очистка истории передаётся подключённому устройству при обмене. Ранее созданные резервные копии от очистки не меняются.
- Очистка истории доступна без связи со вторым устройством и затрагивает известные на момент команды версии. Независимые новые правки сохраняются при следующем обмене.
- Ручная очистка истории доступна для отдельной карточки и для всего пространства, с ясным указанием области и объёма. Текущее содержимое, нерешённые конфликты и независимые новые версии сохраняются.
- Первая версия включает поиск. Сроки, напоминания, вложения и самостоятельная модель чек-листов в неё не входят.
- Обычный поиск по заголовкам и текущему тексту карточек работает без учёта регистра: запрос «работа» находит «Работа» и «РАБОТА». По умолчанию поиск ограничен активным пространством; пользователь может переключиться на все локальные пространства.
- В начале результатов поиска каждого пространства найденные карточки со спорным местом карточки или её колонки показываются один раз в группе «Конфликты». Остальные результаты следуют сохранённому порядку колонок, затем карточек внутри них. При поиске по всем локальным пространствам сначала идут пространства с конфликтующим названием в группе «Конфликты названий», затем остальные пространства по именам; группа «Конфликты» находится внутри своего пространства. Правило действует для непустого и пустого после обрезки запросов, с соблюдением области и прав. После разрешения места карточки и колонки при последующем поиске подходящая запросу карточка возвращается в обычный порядок. Интерфейс, HTTP и CLI на Windows/Android используют одно авторитетное локальное состояние. Конкретное сравнение имён, устойчивый порядок при одинаковых именах и внутри группы «Конфликты названий» уточняются при техническом проектировании; ADR-0011.
- Пунктуация и специальные символы в поисковом запросе ищутся буквально: «C++» ищет фрагмент «C++», «план*» — текст со звёздочкой, кавычки — сами кавычки. Маски, регулярные выражения и поисковые операторы не добавляются; символы не удаляются и не интерпретируются как команды. Сохраняются обрезка краёв запроса, отсутствие учёта регистра и остальные согласованные правила. Правило одинаково для интерфейса, HTTP и CLI на Windows/Android; ADR-0011.
- Если запрос после обрезки краёв пуст, включая пустую строку или ввод одних краевых пробелов, текстовое условие снимается и возвращаются все доступные карточки выбранной области поиска. Выбранная область не переключается; права доступа и один результат на карточку сохраняются. Правило одинаково для интерфейса, HTTP и CLI на Windows/Android; ADR-0011.
- При текстовом поиске «е» и «ё» различаются: «елка» не совпадает с «ёлка», но «ЁЛКА» совпадает с «ёлка» по правилу отсутствия учёта регистра. Исходное написание текста сохраняется; [ADR-0011](decisions/0011-search-matching.md).
- При поиске обрезаются пробелы по краям запроса; внутри фразы пробелы, табуляция и переносы строк учитываются точно. Один пробел не заменяет два пробела, табуляцию или перенос строки. Текст карточек не изменяется; [ADR-0011](decisions/0011-search-matching.md).
- Одиночный поисковый запрос совпадает с любой частью слова: «план» находит «план», «планирование» и «перепланировка», включая отличия регистра. Правило общее для интерфейса, HTTP и CLI на Windows и Android; [ADR-0011](decisions/0011-search-matching.md). Запрос из нескольких слов ищется как один непрерывный фрагмент: слова рядом и в указанном порядке, без учёта регистра.
- При нерешённом конфликте заголовка или текста обычный поиск учитывает все сохранённые конфликтующие варианты этих полей. Совпадения в нескольких вариантах одной карточки дают один результат с отметкой конфликта. Правило одинаково для интерфейса, HTTP и CLI на Windows и Android.
- В первой версии достаточно текстового поиска. Дополнительные фильтры, включая фильтры по тегам и выполнению и скрытие выполненных карточек, отложены.
- Внешние AI-агенты работают через CLI и HTTP API. MCP и встроенная языковая модель в первую версию не запрошены.
- Агент получает отдельный доступ к выбранным пространствам: чтение либо чтение и изменение. Доступ можно отозвать.
- Агенту можно отдельно выдать и отозвать административный доступ для управления подключёнными устройствами и правами доступа. Обычное чтение или изменение пространств само по себе не даёт административных прав.
- В форме выдачи агенту доступа к выбранным пространствам по умолчанию выбран режим «Чтение». Чтение и изменение разрешаются только явным выбором; доступ создаётся после подтверждения выдачи. Срок обычного доступа по умолчанию — «До отзыва»; при выдаче можно задать ограниченный срок, после которого доступ прекращается и продолжение требует нового явного разрешения. Любой доступ можно отозвать раньше. Административные права остаются отдельными; [ADR-0010](decisions/0010-agent-access.md).
- К открытому Android-приложению нужен прямой HTTP-доступ агента через Tailscale в пределах выданных прав. Работа этого API при закрытом APK не гарантируется.
- Первая версия включает ручной экспорт/импорт и автоматические локальные резервные копии.
- Автоматический снимок пространства включает полное состояние: текущие данные пространства и его объектов, корзину, всю пользовательскую историю версий, нерешённые конфликты и необходимые сведения восстановления. Формат и конкретный технический состав проектируются отдельно.
- По умолчанию автоматические копии хранятся в локальном каталоге данных приложения. На Windows и Android можно выбрать другую локальную папку, повторно изменить выбор или вернуться к каталогу по умолчанию. При смене папки существующие автоматические копии ZeDone сначала копируются и проверяются; затем сохраняется новое расположение и удаляются исходные копии.
- Если выбранная папка автоматических копий недоступна, приложение сообщает об ошибке и повторяет попытки в ту же папку при работающем приложении. Работа с пространствами продолжается; автоматического переключения на другую папку нет.
- После явного выбора папки с резервными копиями ZeDone автоматически находит свои копии и показывает пространства и даты, в том числе после переустановки без прежней базы и настроек. Восстановление запускается только отдельной явной командой. Просмотр каталога доступен через общий API в пределах прав на Windows и Android.
- Ручной экспорт пространства создаёт полный переносимый архив: колонки, карточки, теги, корзина и история версий.
- Для ручного экспорта достаточно файла, который читает ZeDone. Открытие обычным архиватором и читаемое без ZeDone представление данных не обязательны; конкретный контейнер и схема сериализации выбираются при техническом проектировании.
- Обычный импорт такого архива создаёт новое независимое пространство. Восстановление исходного пространства из резервной копии — отдельная операция.
- Восстановление автоматической резервной копии возвращает исходное пространство к состоянию выбранного снимка.
- При восстановлении копии пространства после переустановки сохраняется идентичность самого пространства. Новая установка ZeDone подключается к другому устройству заново по общему порядку с подтверждением; права агентов на новой установке выдаются заново и не восстанавливаются автоматически из копии пространства. Полное аварийное восстановление всей базы имеет отдельные правила.
- Восстановление в новую установку после переустановки при подтверждённом отсутствии текущего состояния исходного пространства разрешено без страховочной копии отсутствующего состояния, после проверки резервной копии и с сохранением её исходного файла. Для существующего пространства новый проверенный страховочный снимок остаётся обязательным.
- После восстановления на этом устройстве приостанавливается входящий и исходящий обмен восстановленного пространства до явной команды возобновления. Перезапуск приложения не снимает паузу. Перед возобновлением можно проверить восстановленное состояние.
- После явного возобновления обмена восстановление передаётся другому устройству как новое действие. Независимые правки второго устройства сохраняются: совместимые объединяются по обычным правилам, несовместимые становятся конфликтами.
- Обычные автоматические резервные копии создаются отдельно для каждого пространства при работе приложения с лимитом одного успешного ежедневного снимка за календарный день устройства и только после изменений со времени предыдущего успешного ежедневного снимка. Если данные не менялись, новый ежедневный снимок не создаётся и ротация не выполняется. Для каждого пространства хранятся последние 7 успешных ежедневных снимков; более старые снимки этого пространства удаляются автоматически при успешном создании новых. Когда приложение работает и условия изменений/частоты выполнены, создание запускается при первой подходящей возможности; [ADR-0015](decisions/0015-daily-backup-trigger.md). Лимит действует для каждого пространства отдельно на каждом устройстве; новый календарный день снова разрешает копию при наличии изменений, в том числе менее чем через 24 часа. При недоступной выбранной папке следующая автоматическая попытка ежедневной копии выполняется через 5 минут после завершения неудачной попытки при работающем приложении; ошибка не занимает дневной лимит и не запускает ротацию. После ошибки доступно «Повторить сейчас» через интерфейс и общий API: досрочная попытка сохраняет условия изменений, дневной лимит и проверки прав; повторная доставка запроса не создаёт ещё одну попытку.
- Последний страховочный снимок перед миграцией каждого пространства хранится сверх 7 ежедневных и заменяется после следующей успешной миграции.
- Для каждого пространства отдельно хранится последний страховочный снимок его состояния перед восстановлением. Он хранится сверх 7 ежедневных снимков и отдельного снимка перед миграцией; заменяется только после следующего успешного восстановления.
- Миграция базы и восстановление пространства не начинаются, пока в выбранной папке копий не создан и не проверен новый страховочный снимок. Недоступность папки не разрешает выполнять эти операции без снимка или автоматически сохранять его в другом месте.
- Необходимая миграция базы запускается автоматически при первом запуске новой версии после установки обновления, после обязательных проверок и создания проверенного страховочного снимка. Отдельное подтверждение через интерфейс или API не требуется.
- Если старая версия ZeDone обнаружила более новую схему базы, которую не поддерживает для записи, она отказывает в открытии и предлагает установить подходящую новую версию. База сохраняется без изменений; режим чтения такой схемы в первой версии не предусмотрен.
- Окончательное удаление пространства на устройстве сохраняет его автоматические резервные копии. Их удаление является отдельным явным действием; ручные экспорты не меняются.
- Пока достаточно защиты локальных данных средствами ОС. Разблокированное устройство считается доверенным; отдельный пароль и собственное шифрование хранилища не требуются.
- Тёмная тема: базовые оттенки `#111514` и `#84b7a8`. Светлая: `#e4e8e6` и `#315b50`.
- Архитектура должна поддерживать единый источник истины, одинаковые правила для человека и агента, обратимые действия с согласованным исключением для удаления тегов, лёгкость и производительность.
- Проект публичный. Для собственного программного кода и документации выбрана CC BY-NC-SA 4.0. После предупреждения о применении CC к программам разработчик подтвердил выбор и принял указанные ограничения; другая лицензия не требуется.

### 1.1. Уточнения миграций и аварийного восстановления — 2026-10-26

Следующие восемь решений подтверждены разработчиком. Они описывают требуемое поведение; реализация и технические проверки ещё не выполнены. Правила одинаковы на Windows и Android, для интерфейса и общего API в пределах выданных прав. Полномочия для операций над всей базой ещё требуют отдельного проектирования.

1. **Атомарность всей цепочки.** Вся необходимая при обновлении цепочка миграций общей базы, включая служебные данные, применяется целиком. При ошибке до успешной фиксации возвращается исходное состояние; при успехе получается целевая схема. Например, ошибка второго перехода в цепочке 1 → 2 → 3 возвращает схему 1; схема 2 не остаётся результатом обновления.
2. **Повтор после ошибки.** Текущая попытка останавливается с понятной причиной. В этом запуске повтор выполняется только явно, после устранения причины. При следующем запуске необходимая миграция снова стартует автоматически. Каждая новая попытка требует обязательных проверок и нового проверенного страховочного снимка. Обычная работа новой версии ждёт успешной миграции.
3. **Полная страховочная копия.** Помимо согласованных снимков отдельных пространств перед миграцией создаётся и проверяется согласованная копия всей SQLite-базы со служебными данными. Она сохраняется в выбранной папке копий. Дополнительный расход места принят; отдельные снимки пространств сохраняются.
4. **Хранение полной копии.** Постоянно хранится одна полная копия перед последней успешной миграцией. Новый снимок создаётся отдельно и заменяет прежний только после следующей успешной миграции и проверки результата. Ошибка не удаляет прежние исправные копии; ежедневная ротация их не затрагивает. Обработка незавершённых снимков-кандидатов уточняется технически.
5. **Служебный режим при неподтверждённой целостности.** Если после сбоя нельзя подтвердить целостность рабочей базы, обычная работа и обмен останавливаются, проблемное состояние сохраняется отдельно. Восстановление всей базы из проверенной полной предмиграционной копии запускается только явной командой после показа причины, выбранной копии и охвата операции. Автоматическое восстановление не выполняется; повтор миграции в этом запуске остаётся ручным.
6. **Предусловия аварийного восстановления.** Отдельная аварийная операция восстановления всей базы разрешена, даже если повреждённое текущее состояние не позволяет создать исправный новый снимок. До неё проблемное состояние сохраняется отдельно, предмиграционная копия проверяется. Сохранённая повреждённая база не считается исправным снимком. Обычное восстановление пространства по-прежнему требует нового проверенного снимка текущего состояния.
7. **Совместимость снимков пространств.** Поддерживается восстановление исправных снимков всех ранее официально выпущенных форматов. При необходимости преобразуется рабочая копия с сохранением исходного файла. Поддерживаются преобразования и проверки исторических снимков. Эта гарантия не разрешает старой версии приложения открывать новую неподдерживаемую схему базы.
8. **Обновление исторических схем.** Новая версия напрямую обновляет рабочую базу любой ранее официально выпущенной схемы, сама выполняя всю необходимую цепочку. Промежуточные установки не требуются. Миграции и проверки исторических схем сохраняются; атомарность всей цепочки и обязательные страховочные копии соблюдаются.

### 1.2. Уточнения синхронизации — 2026-10-26

Следующие десять решений подтверждены разработчиком. Все правила конфликтов, блокировок, восстановления и состояния обмена одинаковы для интерфейса, HTTP и CLI на обеих платформах. Наличие нескольких конфликтов не отменяет ранее согласованных блокировок карточки или контейнера.

1. **Порядок одной карточки.** Независимая перестановка одной карточки в разные позиции одной колонки создаёт явный конфликт порядка. Обе позиции сохраняются, карточка остаётся одним объектом и показывается в области «Конфликты» вместо спорных позиций. Пользователь выбирает позицию; до решения действует общая блокировка редактирования карточки. Решение синхронизируется.
2. **Порядок одной колонки.** Независимая перестановка одной колонки в разные позиции создаёт явный конфликт порядка. Колонка с её карточками показывается в области «Конфликты» вместо спорных позиций доски. Позиция выбирается вручную; обычные изменения самой колонки заблокированы до разрешения. Работа с её карточками без собственных конфликтов продолжается.
3. **Названия контейнеров.** Разные независимые переименования одной колонки или пространства сохраняются как варианты конфликта названия для ручного разрешения. При конфликте только названия пространство остаётся доступным в списке, колонка — на доске, с отметкой конфликта и доступом к обоим названиям. Обычные изменения самого контейнера заблокированы; работа с его содержимым продолжается с учётом собственных конфликтов вложенных объектов. Пространство с нерешённым конфликтом названия показывается один раз в группе «Конфликты названий» в начале списка пространств и поиска везде; остальные пространства идут по именам. После разрешения названия пространство возвращается в обычный порядок, работа с его содержимым сохраняет согласованные правила.
4. **Конкурирующие решения конфликта.** Если устройства независимо разрешили один конфликт по-разному, оба результата становятся вариантами нового конфликта для явного выбора или объединения. Ни одно решение не перезаписывается молча. Для карточки до разрешения действует обычная блокировка редактирования.
5. **Снятие и повторное назначение тега.** Если тег сняли с карточки на одном устройстве, а на другом независимо сняли и назначили ей снова, создаётся конфликт назначения. Сам тег остаётся в пространстве. Пользователь выбирает, оставить назначение или снять его. Карточка остаётся в своей однозначно определённой колонке с отметкой конфликта; до решения редактирование заблокировано.
6. **Удаление контейнера против новых объектов.** Удаление колонки против независимого создания в ней карточки, а также удаление пространства против создания в нём колонок или карточек создаёт явный конфликт с сохранением новых объектов. Пользователь выбирает восстановление контейнера с новым содержимым либо сохранение контейнера и новых объектов в корзине. При подтверждении удаления новые объекты включаются в группу этого удаления, чтобы позже восстанавливаться вместе с контейнером.
7. **Долгое отсутствие связи.** Срок отсутствия связи подключённого устройства не ограничивается, автоматической отвязки из-за неактивности нет. При доступности, действующих правах, совместимых версиях и отсутствии явной паузы обмен возобновляется автоматически без повторного подключения и потери независимых правок. Необходимые технические сведения сохраняются либо безопасно заменяются эквивалентом. Отзыв доступа и несовместимость версий рассматриваются отдельно.
8. **Разные объекты в одном промежутке.** Разные карточки или колонки, независимо поставленные между одними соседями, объединяются автоматически без ручного конфликта взаимного порядка, если у каждого объекта нет собственных конкурирующих позиций. Оба объекта сохраняются в промежутке; взаимный порядок задаётся устойчивым правилом, одинаковым на устройствах и не зависящим от порядка доставки. Например, независимые X и Y между A и B сохраняются обе; выбор взаимного порядка X и Y автоматический.
9. **Поздние правки после очистки контейнера.** Если после окончательной очистки колонки или пространства пришла независимая новая карточка либо правка карточки внутри контейнера, данные сохраняются в области «Конфликты». При выборе восстановления возвращаются только независимые новые или изменённые объекты и необходимые для них исходные контейнеры с сохранением идентификаторов. Остальные ранее очищенные объекты остаются очищенными. Перед действием показывается состав восстановления. Это отдельный случай окончательной очистки, не обычное восстановление контейнера из корзины.
10. **Выбранная основа и техническая проверка.** Для синхронизации выбран Automerge для Rust; [ADR-0002](decisions/0002-automerge-sync.md). Прежнее требование сравнить две реализации заменено ограниченным прототипом Automerge. Проверяются согласованные правила ZeDone, интеграция с SQLite, повторы и перестановка сообщений, очистка, возврат долго отключённого устройства, память, рост технических данных и сложность сопровождения AI-агентом. Выбор библиотеки принят; её техническая пригодность пока не подтверждена. Модель из отдельных компонентов, например MVReg из `crdts`, остаётся рассмотренной альтернативой и не входит в выбранную основу.

## 2. Термины и модель продукта

Используются определения из корневого `AGENTS.md`: разработчик, пространство, колонка, карточка. Текст карточки соответствует её описанию; в API следует выбрать одно последовательное название поля.

Предлагается:

- Колонки произвольные: приложение не приписывает именам вроде «Готово» специального поведения.
- Карточка принадлежит одной колонке, колонка — одному пространству. Связи задаются устойчивыми идентификаторами, а не именами.
- Идентификаторы создаются без сети и сохраняются при перемещении и синхронизации. Алгоритм генерации ещё не выбран.
- Подтверждено: порядок колонок и карточек задаётся пользователем и синхронизируется. Предлагается хранить его явно вместе с данными пространства. Завершение дела само по себе не меняет порядок и колонку.
- Подтверждено: пространства с нерешённым конфликтом названия идут в группе «Конфликты названий» в начале списка пространств и поиска везде; остальные автоматически упорядочиваются по имени. После разрешения названия пространство возвращается в обычный порядок. Правило одинаково для интерфейса, HTTP и CLI на Windows и Android. Конкретные правила сравнения имён и устойчивый порядок при одинаковых именах остаются техническим выбором.
- При перемещении между колонками сохраняются идентификатор карточки, её история, теги и отметка выполнения.
- Заголовок из одних пробелов предлагается отклонять одинаково через интерфейс и API; несохранённый ввод в форме создания не является созданной карточкой.
- Подтверждено: теги сравниваются без учёта регистра и пробелов по краям внутри своего пространства с различием «е» и «ё»: «Все» и «Всё» могут существовать отдельно, «ВСЁ» и «Всё» обозначают одно имя. Общее сравнение применяется при создании, переименовании, автоматическом объединении независимых созданий и разрешении коллизий; ADR-0012. Переименование тега не затрагивает независимые теги других пространств. При попытке занять имя другого тега того же пространства операция отклоняется с понятной ошибкой и не изменяет связи с карточками. Слияние существующих тегов при переименовании в первую версию не входит.
- Подтверждено: удаление назначенного тега снимает его со всех карточек этого пространства, сохраняя карточки и их текст. Независимый одноимённый тег другого пространства не затрагивается. Предлагается выполнять изменение тега и его связей одной прикладной операцией с корректной передачей результата при синхронизации.
- Предлагается хранить отображаемое имя тега вместе с ключом сравнения, формируемым Rust-ядром. Те же правила применяются к созданию, поиску и переименованию через интерфейс и API. Вход из CLI и HTTP не должен обходить ограничение одинаковых имён.
- Подтверждено: независимо созданные без связи «Работа» и «работа» в одном пространстве автоматически объединяются при синхронизации в один тег, сохраняя все назначения карточкам. Повторы и перестановки доставки не создают дубликатов тега или назначений; результат сходится на устройствах. Другие конфликты, включая удаление против независимого назначения, обрабатываются по своим согласованным правилам. При объединении вариантов с разным регистром автоматически сохраняется одно из введённых написаний, одинаковое на устройствах для одного набора изменений независимо от порядка/повторов доставки. После объединения имя можно изменить обычным переименованием с сохранением назначений; интерфейс, HTTP и CLI получают одно написание из общего ядра. Конкретный алгоритм выбора и согласование идентификаторов проектируются отдельно; ADR-0012.
- Подтверждено: независимое переименование двух уже существующих разных тегов одного пространства в одно имя создаёт явный конфликт после обмена. Сохраняются оба тега, их идентификаторы и назначения; пользователь выбирает разные имена с проверкой общего правила уникальности. Спорные имена представлены конфликтом и не объявляются согласованным состоянием двух одинаково названных тегов; конкретное представление проектируется в P02/P03. Это отдельный случай от автоматического объединения независимо созданных одноимённых тегов; [ADR-0012](decisions/0012-tag-rename-conflicts.md).
- Подтверждено: Если на одном устройстве существующий тег пространства переименован в имя независимо созданного на другом устройстве нового тега того же пространства, после обмена также показывается явный конфликт. Оба тега, их идентификаторы и назначения сохраняются; разные имена выбираются явно, автоматического объединения нет. Применяются те же правила разрешения и доступных действий, что и при коллизии двух переименований; ADR-0012.
- Подтверждено: При таком конфликте спорные теги явно помечены. Если у карточки спорно только имя назначенного тега, доступны изменения заголовка, текста, статуса выполнения и колонки в пределах пространства; имена тегов разрешаются отдельно. До выбора разных имён назначение и снятие обоих спорных тегов приостановлены для всех карточек пространства; существующие назначения сохраняются, после допустимого решения эти операции снова доступны. Карточки с собственными конфликтами по-прежнему заблокированы. Правила одинаковы для интерфейса, HTTP и CLI на Windows/Android.
- Подтверждено: поиск по заголовкам и текущему Markdown-тексту работает без учёта регистра: запрос «работа» находит «Работа» и «РАБОТА». По умолчанию поиск ограничен активным пространством, с переключением на все локальные пространства. Правило совпадения без учёта регистра одинаково для интерфейса, HTTP и CLI на Windows и Android. Дополнительные фильтры по тегам и выполнению отложены и не входят в первую версию.
- Подтверждено: в начале результатов поиска каждого пространства найденные карточки со спорным местом карточки или её колонки показываются один раз в группе «Конфликты». Остальные результаты следуют сохранённому порядку колонок, затем карточек внутри них. При поиске по всем локальным пространствам сначала идут пространства с конфликтующим названием в группе «Конфликты названий», затем остальные пространства по именам; группа «Конфликты» находится внутри своего пространства. Правило действует для непустого и пустого после обрезки запросов, с соблюдением области и прав. После разрешения места карточки и колонки при последующем поиске подходящая запросу карточка возвращается в обычный порядок. Интерфейс, HTTP и CLI на Windows/Android используют одно авторитетное локальное состояние. Конкретное сравнение имён, устойчивый порядок при одинаковых именах и внутри группы «Конфликты названий» уточняются при техническом проектировании; ADR-0011.
- Подтверждено: Если запрос после обрезки краёв пуст, включая пустую строку или ввод одних краевых пробелов, текстовое условие снимается и возвращаются все доступные карточки выбранной области поиска. Выбранная область не переключается; права доступа и один результат на карточку сохраняются. Правило одинаково для интерфейса, HTTP и CLI на Windows/Android; ADR-0011.
- Подтверждено: для одиночного запроса достаточно вхождения в любую часть слова; «план» находит «план», «планирование» и «перепланировка» без учёта регистра. Совпадение не ограничивается началом или целым словом; [ADR-0011](decisions/0011-search-matching.md). Запрос из нескольких слов ищется как один непрерывный фрагмент в указанном порядке, без учёта регистра. Фрагмент целиком совпадает в заголовке либо текущем тексте; его нельзя составить из разных полей или конфликтующих вариантов. При текстовом поиске «е» и «ё» различаются, регистр игнорируется отдельно; исходное написание сохраняется. Пробелы по краям запроса обрезаются; внутри фразы пробелы, табуляция и переносы строк учитываются точно, без схлопывания и взаимной замены. Остальные правила совпадения и реализация Unicode-сравнения ещё уточняются.
- Подтверждено: Пунктуация и специальные символы в поисковом запросе ищутся буквально: «C++» ищет фрагмент «C++», «план*» — текст со звёздочкой, кавычки — сами кавычки. Маски, регулярные выражения и поисковые операторы не добавляются; символы не удаляются и не интерпретируются как команды. Сохраняются обрезка краёв запроса, отсутствие учёта регистра и остальные согласованные правила. Правило одинаково для интерфейса, HTTP и CLI на Windows/Android; ADR-0011.
- Подтверждено: при нерешённом конфликте заголовка или текста поиск выполняется по всем сохранённым конфликтующим вариантам этих полей. Карточка появляется в результатах один раз с отметкой конфликта, даже если запрос совпал с несколькими вариантами. Общий API предоставляет те же результаты и сведения о конфликте на обеих платформах.
- В режиме всех локальных пространств предлагается искать только данные, доступные на этом устройстве. Для агента результат дополнительно ограничен разрешёнными ему пространствами; поиск не расширяет его доступ.
- Выполненная карточка остаётся на своём месте на доске с отметкой выполнения. Скрытие выполненных карточек относится к отложенным фильтрам.

Открыто: предельные размеры полей и остальные правила совпадения текста, включая Unicode-сравнение и точный набор краевых пробельных символов. Обязательность заголовка, допустимость пустого текста, граница перемещения, автоматический порядок пространств по имени с группой «Конфликты названий» в начале, ручной порядок колонок и карточек, область и сравнение тегов, область обычного поиска, поиск без учёта регистра, совпадение одиночного запроса с любой частью слова, непрерывный фрагмент из нескольких слов, различие «е»/«ё» в именах тегов и текстовом поиске, обрезка краёв запроса с точным совпадением внутренних пробелов/переносов, снятие текстового условия при пустом после обрезки запросе, буквальный поиск пунктуации/специальных символов без операторов, порядок результатов по доске с группой «Конфликты» в начале каждого пространства для спорного места, предварительный порядок пространств по именам при поиске везде и откладывание дополнительных фильтров уже подтверждены. Отдельный поиск в корзине или истории не входит в подтверждённый состав первой версии.

## 3. Предлагаемое устройство приложения

Предложение: модульное приложение с общим Rust-ядром и небольшими адаптерами платформ. Отдельные микросервисы и плагинная система сейчас не обоснованы.

### Windows

Подтверждено 2026-10-27: для создания Windows-установщика выбран Inno Setup; установка и установка обновлений выполняются только для текущей учётной записи без запроса прав администратора. Установка для всех пользователей ПК в первую версию не входит. Версия Inno Setup, сценарий и параметры сборки ещё определяются; [ADR-0017](decisions/0017-windows-per-user-installation.md). Сохраняются ручной запуск, браузерный интерфейс, отдельное хранение данных и ручная установка обновлений.

Подтверждено: приложение устанавливается через установщик, запускается ярлыком, обслуживает API и встроенные файлы веб-интерфейса, затем открывает браузер. Для работы пользователя не должны требоваться Rust, Node.js, Bun или сервер разработки.

Подтверждено: первая версия запускается вручную и загружается с GitHub. Вся работа с пространствами происходит в Google Chrome или Opera через локальный сервер. Исполняемый компонент обеспечивает Rust-ядро, сервер и трей. Формат поставки — EXE-установщик на Inno Setup; версия инструмента и сценарий сборки ещё определяются. Данные хранятся отдельно от файлов программы.

Обычный интерфейс слушает только loopback. Доступ к синхронизации через Tailscale включается отдельно для явно подключённых устройств. Нельзя случайно сделать весь API доступным на всех сетевых интерфейсах.

Отсутствие интернета не мешает работе. Остановка локального процесса мешает сохранению из браузера: интерфейс должен отличать это состояние от отсутствия сети между устройствами. Несколько вкладок используют тот же локальный процесс и хранилище.

Подтверждено: закрытие вкладки не завершает локальный сервер. Пока ПК работает и приложение явно не завершено, сервер продолжает обслуживать разрешённые запросы агента и обмен с телефоном. Закрытие вкладки, завершение приложения и выключение ПК — разные события. Это не гарантирует работу при сне или выключении ПК и не означает обязательного автозапуска Windows.

Подтверждено: значок в трее Windows предоставляет действия открытия браузерного интерфейса и завершения приложения. Те же действия доступны через CLI. Трей управляет тем же локальным процессом и не создаёт отдельного хранилища или набора бизнес-правил.

Предлагается корректное завершение с закрытием хранилища и завершением либо безопасной остановкой текущего обмена. Агент с доступом только к выбранному пространству не получает вследствие этого права управлять всем локальным процессом. Повторный запуск предлагается направлять в существующий экземпляр процесса с открытием интерфейса, сохраняя одно авторитетное локальное состояние.

Подтверждено: приложение уведомляет о новой версии, пользователь скачивает и запускает установщик обновления. Для создания установщика выбран Inno Setup. Сведения о версиях берутся из GitHub Releases: автопроверка раз в сутки при работающем приложении и ручная команда, выключение и повторное включение автоматики, ошибка сети без остановки работы с пространствами; [ADR-0018](decisions/0018-update-checks-github-releases.md). Сохраняются данные и страховочная копия перед миграцией. Открыты версия и параметры Inno Setup, техническое расписание и реализация проверки обновлений. Ручной запуск без автозапуска, управление через трей и CLI, работа после закрытия вкладки, загрузка с GitHub и браузерный интерфейс уже подтверждены.

Подтверждено 2026-10-27: Windows-деинсталлятор предлагает отдельно удалить рабочие данные текущей установки (пространства и настройки) и отдельно её автоматические резервные копии. Оба выбора независимы и первоначально выключены. Перед выбранной очисткой показывается состав и требуется явное подтверждение; отказ от выбора или от подтверждения сохраняет соответствующие данные. Выбор рабочих данных не включает удаление копий автоматически. Ручные экспорты не затрагиваются. Очистка локальна: не отправляет другому устройству команд удаления пространств и не удаляет его данные. Обычное обновление программы не запускает выбранную для деинсталляции очистку; [ADR-0021](decisions/0021-uninstall-data-cleanup.md).

Подтверждено 2026-10-27: разработчик разрешил окончательную локальную очистку после явного предупреждения и подтверждения как исключение из общего требования обратимости. Если выбраны рабочие данные и все автоматические копии, а другого источника восстановления нет, данные нельзя будет восстановить средствами ZeDone. Сохранение последней проверенной копии при таком выборе не требуется; ручные экспорты и другие устройства сохраняются. Исключение касается этой отдельной очистки и не отменяет прежние правила корзины, обычного восстановления или миграции. Прикладная очистка, её доступ через общий Rust API для человека и агента, отдельные полномочия на всю установку, паритет Android, согласование с работающим процессом/обменом и обработка сбоев проектируются до реализации. Удаление файлов программы остаётся платформенной частью Inno Setup.

### Android

Подтверждено 2026-10-27: для чтения QR камерой выбран Tauri Barcode Scanner, [ADR-0022](decisions/0022-android-qr-scanner.md). В P01 обязательны установка/сборка, совместимость выбранной цепочки, разрешения камеры и команд плагина, отмена/повторный вход, недоступная камера, ручной ввод и работа с состоянием модели распознавания. В просмотренном исходном коде Android-части ветки `v2` используется Google Play Services ML Kit с динамически загружаемой моделью. Разработчик разрешил первую загрузку модели: до готовности ручной ввод остаётся доступным, неготовность распознавания не считается неверным приглашением; после готовности сканирование можно повторить. Готовность QR сразу после установки без загрузки модели не требуется. Проверить первый запуск вручную установленного APK без сети и ранее загруженной модели, недоступные Google Play Services и понятное состояние с ручным путём. Документация и ветка исходников не подтверждают поведение ещё не выбранной версии ZeDone; фактическая пригодность проверяется прототипом. Для генерации QR в Rust выбран qrcodegen; общий модуль отображения в SVG и чтение итогового кода проверяются в P01, [ADR-0023](decisions/0023-qr-generation.md).

Предлагается использовать тот же собранный веб-интерфейс в WebView, а Rust-ядро и данные размещать внутри APK и приватного каталога приложения. APK не должен загружать интерфейс или данные с ПК для обычной работы.

Подтверждено: Tauri 2 выбран Android-оболочкой; Kotlin + Android WebView с подключением Rust остаётся резервом при выявленных ограничениях, мешающих выполнить обязательные требования ZeDone. Решение принято разработчиком и оформлено в [ADR-0001](decisions/0001-android-shell.md). Техническая проверка выбранной оболочки обязательна. Нужно проверить ввод текста, клавиатуру, системную кнопку «Назад», импорт и экспорт файлов, жизненный цикл и возможность фонового обмена.

Подтверждено: в прототипе Tauri 2 первым проверяется IPC через команды Tauri между веб-интерфейсом APK и Rust-ядром. Команды IPC и внешний HTTP на Axum вызывают одни прикладные операции общего ядра с общими правилами доступа к данным. Окончательный выбор внутреннего транспорта подтверждается по результатам прототипа. Открытому APK требуется внешний HTTP-доступ для агента через Tailscale. Подтверждено: для необходимого платформенного слоя допустим Kotlin; основная логика, хранение и синхронизация остаются на Rust.

Подтверждено: прямой доступ ограничен выданными агенту правами и доступностью работающего приложения. Предлагается обслуживать локальный интерфейс и удалённого агента через один экземпляр ядра и хранилища. Открытое приложение, сворачивание, сон устройства и завершение процесса должны давать понятные состояния доступности; постоянная работа HTTP-сервера при закрытом APK не является обещанием продукта.

### Выбранные технологии и оставшиеся кандидаты

Подтверждена основа интерфейса Vue + TypeScript + Vite. Для сложных компонентов выбран Reka UI, для простых кнопок и полей — стандартные HTML-элементы; [ADR-0004](decisions/0004-ui-components.md). Используются только необходимые компоненты с собственным оформлением ZeDone. Совместимость с Bun/Vue/TypeScript/Vite/Tauri, клавиатура, фокус и сенсорное управление проверяются в P01/P05. Для перетаскивания выбраны SortableJS через VueDraggablePlus с обязательной проверкой интеграции и жестов на обеих платформах; [ADR-0005](decisions/0005-drag-and-drop.md). Для просмотра Markdown выбраны markdown-it + DOMPurify с обязательной проверкой профиля, совместимости с Bun/Vite и работы в целевых браузерах и Android WebView; [ADR-0006](decisions/0006-markdown-syntax.md). Необходимость дополнительных зависимостей и стоимость сопровождения нужно обосновать. Перетаскивание на обеих платформах остаётся обязательным независимо от способа реализации.

Подтверждено: для локального хранения выбраны SQLite с rusqlite и включённым `bundled`, с обязательной технической проверкой на Windows и Android. Для HTTP API на обеих платформах выбраны Axum и Tokio как адаптер к общему Rust-ядру; работа сервера в APK требует обязательной технической проверки. Для APK выбран Tauri 2, резерв — Kotlin + Android WebView с подключением Rust; пригодность выбранной оболочки проверяется прототипом. Для управления JavaScript-зависимостями и запуска инструментов разработки интерфейса и CI выбран Bun с обязательной проверкой всей цепочки Vue/TypeScript/Vite/Tauri. Номера версий намеренно не зафиксированы.

Документальная проверка от 2026-10-25 и обоснование выбора и рекомендаций находятся в [оценке стека](stack-candidates.md). SQLite/rusqlite с `bundled`, Axum/Tokio и Bun как менеджер пакетов и среда запуска инструментов выбраны. Tauri 2 выбран Android-оболочкой, Kotlin + Android WebView указан резервом; обязательная техническая проверка пригодности Tauri 2 сохраняется. Node.js/npm и pnpm рассмотрены как альтернативы. Выделены проверки Unicode-поиска, снимка отдельного пространства, прямого HTTP-доступа к открытому APK и совместимости всей цепочки инструментов с Bun. Сборки и прототипы в рамках этой оценки не выполнялись.

Мотивы выбора и предложений: Axum даёт типизированную обработку запросов и общую инфраструктуру middleware; SQLite подходит для локального приложения; rusqlite позволяет работать с ней без отдельного сервера БД; готовая Android-оболочка уменьшает объём собственного платформенного кода. Это не утверждения о достигнутой производительности ZeDone.

У выбранной rusqlite синхронный интерфейс: операции хранения нельзя выполнять на потоке интерфейса или блокировать ими обработку сети. Организация рабочих потоков и соединений уточняется при технической проверке. Для HTTP-контракта выбраны utoipa + OpenAPI + openapi-typescript + openapi-fetch; [ADR-0003](decisions/0003-api-contract-toolchain.md). utoipa создаёт OpenAPI из Rust-описаний, openapi-typescript генерирует типы, openapi-fetch использует их для HTTP-вызовов. Совместимость инструментов с Bun обязательно проверяется; готовых результатов пока нет. OpenAPI само по себе не генерирует команды Tauri IPC: использование общих сгенерированных типов и соответствие имён команд, параметров, результатов и ошибок Android-адаптера Rust-контракту проверяются отдельно.

### Критерии технической проверки веб-интерфейса и оболочки

Подтверждено: Vue + TypeScript + Vite выбраны для интерфейса; Tauri 2 выбран Android-оболочкой, Kotlin + Android WebView указан резервом; техническая пригодность Tauri 2 проверяется прототипом. Пригодность реализации и оболочки проверяются с учётом Android и поддерживаемости. Основная разработка и автоматические проверки выполняются в эмуляторе Android 13. Проверка на реальном Galaxy A32 рекомендована перед выпуском; измерения эмулятора не подтверждают производительность телефона. Следующий набор критериев предлагается для проверки:

- Общий статически собранный интерфейс работает в Google Chrome и Opera на Windows 11 и в выбранной оболочке APK на Android 13. Результаты записываются для каждого целевого браузера отдельно. Для обычного запуска используются локальные ресурсы приложения.
- TypeScript strict проверяется в CI; клиент использует типы из Rust-контракта через utoipa/OpenAPI/openapi-typescript, HTTP-вызовы выполняет openapi-fetch. Генерация воспроизводима; CI проверяет согласованность генерируемых представлений с Rust-источником. Адаптеры HTTP и Android обращаются к одним прикладным операциям. В прототипе Android первым проверяется IPC через команды Tauri; при одинаковых исходных данных и правах одна команда через IPC и HTTP должна давать одинаковый прикладной результат.
- В эмуляторе Android 13 проверяются русский ввод, многострочный Markdown, выделение и вставка текста, экранная клавиатура, системная кнопка «Назад» и сохранение при смене состояния приложения. Повторение основных сценариев на Galaxy A32 с 4 ГБ ОЗУ рекомендовано перед выпуском.
- На одинаковом контрольном наборе сравниваются время открытия доски и карточки, поиск и расход памяти приложения с WebView. Объём данных, схема порционной загрузки, версия WebView и способ измерения фиксируются вместе с результатами.
- Перетаскивание карточек и колонок работает на ПК и телефоне, включая прокрутку доски и взаимодействие жестов. Изменение порядка и перенос карточки также доступны через явные команды; управление работает с клавиатурой и сенсорным экраном. Проверяются семантика элементов и видимый фокус.
- Оцениваются сложность сборки и обновления зависимостей, качество типизации и тестирования, необходимые платформенные обходы, лицензии и объём собственного кода сопровождения.
- Платформенная интеграция сохраняет строгий запрет unsafe в ядре, хранении и синхронизации. Каждое необходимое платформенное исключение получает отдельное обоснование.
- На работающем APK в эмуляторе проверяется прямой вызов HTTP API с ПК через Tailscale: разрешённое чтение и изменение, отказ вне выданных прав, отзыв доступа и работа с локальными правками, ещё не переданными на ПК. При изменении состояния APK отдельно проверяется доступность сервера. Повторение на реальном целевом телефоне рекомендовано перед выпуском.

Предлагается ограничить проверку небольшим срезом: доска с перетаскиванием, редактор карточки, просмотр Markdown и вызов общего API. Подтверждено: проверяется выбранный Tauri 2 с Vue + TypeScript + Vite; ограничения, мешающие выполнить обязательные требования, могут обосновать переход к резерву Kotlin + Android WebView с отдельной фиксацией решения. Реализация всего приложения для проверки оболочки не требуется.

Выбор Tauri 2 и резерв Kotlin + Android WebView оформлены в [ADR-0001](decisions/0001-android-shell.md). По результатам технической проверки фиксируются версии, условия, измерения, пригодность реализации и существенные ограничения; при необходимости изменения выбора оформляется отдельное архитектурное решение. Vue + TypeScript + Vite остаются выбранной основой интерфейса; Svelte и React могут рассматриваться как альтернативы при обоснованной необходимости её изменения.

### Публичное распространение и выбранная лицензия

Подтверждено: разработчик планирует публичный проект с CC BY-NC-SA 4.0 для собственного программного кода и документации и загрузку приложения с GitHub. После предупреждения о применении CC к программам он подтвердил этот выбор. Для Windows выбран установщик, для Android — APK; конкретные средства упаковки и оформление выпуска ещё предстоит определить. GitHub Releases предлагается как канал готовых сборок Windows и Android; это предложение о публикации, а не уже созданный выпуск.

Обнаруженное ограничение: Creative Commons официально рекомендует программные лицензии для кода. CC-лицензии не определяют специальные условия предоставления исходного кода; патентные права также не входят в предоставляемые права CC BY-NC-SA 4.0. Это создаёт риск несовпадения выбранной лицензии с ожидаемыми правилами распространения программных модификаций. См. [Creative Commons FAQ](https://creativecommons.org/faq/#can-i-apply-a-creative-commons-license-to-software) и [официальный текст CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/legalcode.en).

Элемент NC ограничивает использование в коммерческих целях и шире запрета продажи копии. Такой запрет не соответствует определению Open Source Initiative, допускающему коммерческую деятельность. Публичность репозитория и статус Open Source нужно различать. См. [условия CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/) и [Open Source Definition](https://opensource.org/osd).

Принятый риск: CC BY-NC-SA 4.0 применяется к собственному программному коду и документации несмотря на официальную рекомендацию Creative Commons использовать программные лицензии для кода. Разработчик принимает отсутствие специальных условий предоставления исходников и патентного разрешения, а также ограничения NC и их отличие от условий Open Source. Выбор лицензии закрыт и не должен автоматически заменяться программной лицензией или разделяться между кодом и документацией последующим агентом.

При подготовке публичного репозитория и выпусков нужно оформить выбранную лицензию и обязательные уведомления сторонних компонентов. Условия зависимостей проверяются отдельно: лицензия собственного кода не перелицензирует чужие компоненты. Пользовательские заметки рассматриваются отдельно от лицензии кода ZeDone. Этот документ фиксирует решение; файл лицензии и публикация выпуска на данном этапе не создаются.

## 4. Единый источник истины

Следствие автономной работы: пока устройства разъединены, их состояния могут различаться. Требование нельзя трактовать как наличие единственной мгновенно актуальной копии на всех устройствах.

Предлагаемая трактовка для согласования:

1. Одно авторитетное локальное хранилище на устройстве содержит пользовательские данные, версии и необходимые сведения об обмене.
2. Все изменения проходят через одно Rust-ядро с общими правилами. Интерфейс, CLI и HTTP не реализуют собственную бизнес-логику.
3. Между устройствами передаются версии изменений. После доставки одних и тех же изменений устройства сходятся к одинаковым данным и одинаковому набору нерешённых конфликтов.
4. Неразрешённый конфликт является частью данных: обе версии сохраняются. Его разрешение становится новым синхронизируемым изменением.
5. Поисковый индекс, отформатированный HTML и состояние отображения являются производными. Они не становятся вторым независимо изменяемым хранилищем заметок.
6. Rust-описание контракта служит источником схем API и типов клиента. Выбраны utoipa для OpenAPI, openapi-typescript для типов TypeScript и openapi-fetch для HTTP-вызовов. Ручные независимые копии моделей Rust и TypeScript и ручное редактирование генерируемых представлений не допускаются. Генерация выполняется воспроизводимой командой; CI проверяет согласованность артефактов с источником и типы. Проверка типов не заменяет проверку входных данных и прав в Rust-ядре.

Для локального хранения выбраны SQLite и rusqlite с `bundled`, с обязательной технической проверкой на Windows и Android. Для первой версии выбрана одна база на устройство; снимки и восстановление отдельных пространств выполняются логически через общее Rust-ядро. Схема данных, миграции и модель хранения версий пока не выбраны.

Сравнение вариантов и основание выбора находятся в [оценке организации SQLite](sqlite-layout.md). Подтверждены одна база на устройство и логические снимки и восстановление отдельных пространств, с учётом уже обязательного экспорта и восстановления как нового действия. Отдельные базы пространств со служебной базой устройства рассмотрены как альтернатива. Формат снимков и механизм миграций ещё не утверждены.

Синхронизация должна обмениваться изменениями или версиями сущностей. Простое взаимное копирование файлов открытой SQLite-базы не обеспечивает объединение независимых правок.

## 5. Общий API человека и агента

Предлагается версионированный API прикладных команд и запросов. HTTP и CLI — адаптеры к нему. Человек через интерфейс вызывает те же операции с теми же проверками и результатами. Различие транспорта не создаёт отдельную модель поведения.

Подтверждено: HTTP-адаптер на Windows и Android строится на Axum и Tokio и вызывает общее Rust-ядро. Прикладные правила, проверка выданных прав и доступ к данным остаются общими для интерфейса, HTTP и CLI. В прототипе Tauri 2 первым проверяется IPC через команды Tauri для интерфейса APK; эти команды вызывают те же прикладные операции ядра. Работу HTTP-сервера в составе APK требуется подтвердить технической проверкой.

Контракт должен охватывать весь функционал: работу с пространствами, колонками, карточками и тегами; порядок и перемещение; выполнение и его отмену; поиск; корзину и восстановление; окончательную очистку; подключение устройств и выбор пространств; запуск и состояние обмена; просмотр и разрешение конфликтов; поддержанные настройки и операции с резервными копиями.

Подтверждено: подключение телефона к ПК при уже настроенном Tailscale использует QR-код, показанный на ПК и считываемый телефоном, либо запасной ручной ввод адреса ПК и одноразового кода; [ADR-0009](decisions/0009-device-pairing-qr-and-code.md). Оба способа требуют отдельного явного подтверждения запроса на стороне ПК; телефон до этого показывает ожидание, не считается подключённым и не начинает обмен пространствами. Пространства выбираются явно. Человек и агент создают приглашение, запрашивают и подтверждают подключение и управляют доступом через общий API с необходимыми правами; управление устройствами входит в ранее согласованный административный доступ. Само предъявление кода не даёт телефону права подтвердить собственный запрос. Камера не обязательна для прикладной операции. Незавершённое подключение можно отменить, запрос на ПК — отклонить, подключённое устройство — отвязать по общим правилам. Состав QR, формат и срок действия кода, техническая проверка подключаемого устройства, сведения в запросе подтверждения и выдача постоянных учётных данных остаются техническими и продуктовыми вопросами DEC-003.

Подтверждено: все команды изменения существующей карточки используют единую проверку актуальности её заголовка, описания, тегов, отметки выполнения, положения на доске (колонка и порядок карточки) и состояния «активна/в корзине». Если после чтения эти данные изменились, подготовленная ранее команда отклоняется без изменения текущих данных и истории, нового конфликта, ложной версии и ложного успеха. Правило включает редактирование, назначение/снятие тегов, установку/снятие выполнения, перемещение/порядок, удаление, восстановление из корзины и восстановление версии. Например, новые пункты в описании отклоняют старую команду отметить выполненной. Клиент получает понятную причину и указание перечитать карточку и подготовить действие заново; введённый текст сохраняется в редакторе. Автоматически подставлять свежую версию и повторять прежнюю команду нельзя. Правило действует через интерфейс, HTTP, CLI и Android-адаптер общего ядра; [ADR-0007](decisions/0007-stale-text-edits.md). Проверка и применение команды согласованы в общем ядре. Чтение, техническая фиксация серии истории без изменения данных карточки и изменение другой карточки сами по себе не делают команду устаревшей. Состав видимой версии остаётся заголовком и описанием. Формат признака версии, дополнительные предусловия конкретных операций и условия команд других объектов проектируются отдельно. Создание и безопасные повторы команд изменения карточки следуют ADR-0008: возврат подтверждённого прежнего результата сохраняет более новые изменения; ещё не выполненная команда проверяется по исходному условию актуальности. Независимые уже сохранённые изменения при синхронизации сохраняют отдельные правила.

Подтверждено: отправка активной колонки в корзину проверяет актуальность прочитанного состава и данных колонки с карточками. Проверяются название, положение и состояние активна/в корзине самой колонки, набор активных карточек и данные каждой карточки по ADR-0007: заголовок, описание, теги, выполнение, положение и состояние активна/в корзине. Добавление, удаление, перенос, восстановление или замена карточки при том же количестве, как и изменение данных при прежнем наборе, отклоняют всю старую команду без изменения текущих данных и истории. Клиент получает понятную причину и показывает актуальные состав и данные; HTTP/CLI дают равнозначные сведения через общие операции ядра. После перечитывания требуется новое явное действие; автоматическая подстановка свежего признака состояния с повтором старой команды запрещена. Проверка и удаление согласованы в ядре, чтобы параллельное изменение состава или данных не обходило условие. Чтение, техническая фиксация серии истории без изменения проверяемых данных и изменения другой колонки, не затрагивающие проверяемое состояние, сами по себе не вызывают отказа. Правило общее для человека и агента на Windows/Android; [ADR-0014](decisions/0014-column-deletion-membership.md). Дополнительные условия остальных команд контейнеров проектируются отдельно; безопасные повторы перечисленных обычных действий подтверждены в ADR-0008. Независимые уже сохранённые изменения при синхронизации сохраняют отдельные правила.

Подтверждено: отправка активного пространства в корзину использует ту же строгую проверку актуальности. Проверяются данные самого пространства (название и состояние активна/в корзине), состав и данные его колонок и карточек, теги пространства и их назначения; данные колонок и карточек определены в ADR-0014/ADR-0007. Изменение состава или данных при прежнем составе после чтения отклоняет всю команду без частичного удаления, нового конфликта, пользовательской версии истории и ложного успеха. Клиент показывает актуальное состояние; после перечитывания требуется новое явное действие. Проверка и отправка в корзину согласованы в ядре, автоматическая подстановка свежего признака состояния с повтором прежней команды запрещена. Чтение, техническая фиксация серии истории без изменения проверяемых данных и изменение другого пространства сами по себе не вызывают отказа. Правило общее для интерфейса, HTTP и CLI на Windows/Android; ADR-0014. Группы удаления, восстановление ранее удалённых объектов, окончательная очистка и независимые сохранённые изменения при синхронизации сохраняют прежние правила. Безопасные повторы перечисленных обычных действий с колонками и пространствами подтверждены в ADR-0008.

Подтверждено: создание и все изменения карточки, а также обычные действия с колонками и пространствами — создание, переименование, порядок колонок, отправка в корзину и восстановление из неё — при неизвестном результате после обрыва связи имеют ограниченные автоматические повторы одной логической команды, затем ручной повтор; [ADR-0008](decisions/0008-safe-card-creation-retries.md). Клиент сохраняет идентификатор, операцию, цель и параметры, включая исходные предусмотренные условия актуальности. Уже выполненная команда возвращает прежний результат без повторного действия, версии истории, границы серии или группы удаления; позднейшие правки, восстановление из корзины и актуальное представление клиента сохраняются. Такой возврат подтверждает прежнее выполнение; ещё не выполненная команда проходит обычную предусмотренную проверку актуальности по ADR-0007/ADR-0014 и остальные проверки. Повтор с изменёнными параметрами в области идентификатора отклоняется. Параллельные доставки не дублируют действие; данные и результат команды фиксируются согласованно. После исчерпания автоматических попыток без подтверждения интерфейс показывает «Результат сохранения пока неизвестен» и кнопку «Повторить»; API/CLI дают равнозначные состояние и действие. Это не успех и не утверждение, что команда не выполнилась. Проверки доступа сохраняются; явные отказы, включая устаревшую версию и отсутствие прав, не превращаются в автоматический повтор. Число попыток, интервалы, таймауты, область и формат идентификаторов, хранение результатов, перезапуск и срок действия уточняются в P03/P05. Утрата сведений или истечение срока не превращают повтор в незаметное новое выполнение; безопасная обработка проектируется отдельно.

Предлагаемые свойства:

- Машиночитаемые ответы, устойчивые коды ошибок, явные идентификаторы и номера версий. CLI поддерживает JSON-вывод и понятные коды завершения.
- Подтверждена единая проверка актуальности для всех команд изменения существующей карточки по ADR-0007. Дополнительные предусловия конкретных операций и условия команд других объектов проектируются отдельно. Для отправки колонки или пространства в корзину подтверждена проверка состава и данных целевого контейнера с содержимым по ADR-0014; остальные условия команд контейнеров ещё проектируются.
- Подтверждены безопасные повторы команд карточки и перечисленных обычных действий с колонками/пространствами по ADR-0008. Повторы операций вне этой области проектируются отдельно; правила миграций, копий, импорта, синхронизации и окончательной очистки этим уточнением автоматически не расширяются.
- Успех сохранения возвращается после фиксации локальной транзакции. Состояние «сохранено локально» отделено от «передано другому устройству».
- Изменение данных и запись необходимой информации для синхронизации атомарны.
- Агент не пишет напрямую в базу, Markdown-файлы или внутренний журнал.
- Сетевые изменения проверяются Rust-ядром с сохранением идентичности и причинных связей исходных изменений.
- Подтверждены отдельные доступы агентов к выбранным пространствам, режимы чтения и чтения с изменением, а также отзыв доступа. В форме выдачи по умолчанию выбрано чтение; изменения включаются явно, а выдача доступа требует подтверждения; [ADR-0010](decisions/0010-agent-access.md). Для обычного доступа по умолчанию выбран срок «До отзыва», при выдаче можно задать ограниченный срок. После истечения доступ прекращается; продолжение требует нового явного разрешения. Любой доступ можно отозвать раньше. Форма передаёт выбранные режим и срок в общий API; просмотр формы не выдаёт доступ. Административные права остаются отдельными. Выпуск, хранение и обновление учётных данных, техническая реализация отзыва и истечения ещё обсуждаются; срок разрешения не определяет срок технического ключа.

Подтверждено: агенту можно отдельно выдать и отозвать административный доступ для управления подключёнными устройствами и правами доступа. Этот доступ выдаётся независимо от чтения и изменения выбранных пространств; обычные права работы с данными не предоставляют административных полномочий. Те же административные операции доступны человеку и агенту через общий API на Windows и Android. Механизм выпуска, хранения и отзыва учётных данных остаётся техническим решением.

Подтверждено: агент может прямо обращаться по HTTP через Tailscale к открытому Android-приложению и работать с его локальными данными, в том числе ещё не синхронизированными с ПК. Работа при закрытом APK не гарантируется. Недоступность телефона должна отличаться от отказа в доступе и от отсутствия данных.

Предлагается проверять права в Rust-ядре для каждого прикладного обращения независимо от транспорта. Локальный интерфейс, CLI и удалённый HTTP-клиент используют одинаковые правила доступа и изменения данных. CLI предлагается снабдить выбором конечной точки, чтобы агент на ПК мог работать с API нужного устройства. Механизм выдачи, хранения и отзыва учётных данных остаётся техническим решением.

## 6. Синхронизация и конфликты

Tailscale даёт сетевую связность и защищённую передачу. Протокол обмена данными ZeDone, выбор пространств, версии и конфликты остаются ответственностью приложения.

Подтверждено: ПК и телефон могут синхронизироваться с разными версиями ZeDone, если совместимость протокола и формата данных для этих версий явно поддержана и проверена. Одинаковый номер версии приложения не требуется. Совместимость должна сохранять данные и согласованные правила объединения изменений и разрешения конфликтов. Локальная схема базы, формат передаваемых данных и протокол обмена рассматриваются отдельно; возможность синхронизации не означает, что одна версия приложения умеет открывать локальную базу другой версии. Конкретные поддерживаемые сочетания версий, механизм проверки и критерии совместимости определяются при техническом проектировании и проверяются на обеих платформах.

Подтверждено: обмен с устройством, остановленный из-за несовместимости протокола или формата данных, возобновляется автоматически после успешной проверки совместимости при доступном соединении. Дополнительная команда для устранённой несовместимости не требуется. Во время несовместимости локальная работа продолжается, изменения сохраняются до обмена. Явная пауза пространства после восстановления сохраняется: входящий и исходящий обмен этого пространства ждёт отдельной команды возобновления даже после обновления приложения и успешной проверки совместимости. Причина остановки и состояние явной паузы различимы через интерфейс и общий API на Windows и Android. Механизм и периодичность повторных проверок совместимости проектируются отдельно.

Предлагаемые требования к протоколу:

- Обмен продолжается после обрыва, допускает повторные сообщения и сохраняет результат независимо от порядка доставки.
- Состояние синхронизации ведётся для конкретного пространства и устройства. Успешная отправка не приравнивается к подтверждённой фиксации на другой стороне.
- Независимые правки определяются по версиям и причинным связям. Время на часах устройства не является единственным критерием выбора победителя.
- Подтверждено: независимые изменения разных полей карточки объединяются автоматически. Разные независимые изменения одного поля сохраняются как варианты и требуют ручного разрешения. Текст рассматривается как одно поле; автоматическое объединение фрагментов Markdown не запрошено.
- Подтверждено: независимое перемещение одной карточки в разные колонки создаёт конфликт с сохранением обоих вариантов. Пользователь выбирает колонку, решение передаётся другому устройству. Это не создаёт две независимые карточки.
- Подтверждено: до разрешения конфликта перемещения карточка показывается в отдельной области «Конфликты» вместо спорных колонок. После выбора она появляется в выбранной колонке. Правило одинаково на Windows и Android; через общий API доступны тот же конфликт и выбор колонки.
- Подтверждено: независимые добавления разных тегов одной карточке объединяются без конфликта; оба назначения сохраняются.
- Подтверждено: удаление самого тега из пространства против его независимого назначения карточке создаёт явный конфликт. Сохраняются варианты удаления и назначения. Пользователь выбирает сохранение тега с назначениями либо удаление со снятием всех назначений; карточки и их текст сохраняются в обоих случаях. Решение передаётся другому устройству.
- Подтверждено: карточки со спорными назначениями остаются в своих однозначно определённых колонках с отметкой конфликта; спорный тег явно помечен. Редактирование карточек заблокировано до разрешения конфликтов по общему правилу. Это поведение одинаково на Windows и Android; интерфейс, HTTP и CLI предоставляют те же сведения о конфликте и возможность его разрешения.
- Подтверждено: удаление карточки или её контейнера против независимой правки карточки создаёт явный конфликт с сохранением правки. Выбор удаления либо восстановления выполняется пользователем и передаётся другим устройствам.
- Подтверждено: до выбора удаления или восстановления такой конфликт показывается в отдельной области «Конфликты» с просмотром сохранённой правки и состава затронутых объектов. Это правило одинаково для карточки, колонки и пространства на обеих платформах; общий API предоставляет те же данные для разрешения конфликта.
- Конфликт не должен останавливать работу со всем пространством. Пользователь видит его наличие и может открыть варианты.
- Подтверждено: до разрешения всех конфликтов карточки заблокировано редактирование всей карточки, включая неконфликтующие поля. Просмотр и явное разрешение конфликтов доступны; после разрешения редактирование возобновляется. Блокировка применяется одинаково через интерфейс, HTTP и CLI на обеих платформах. Работа с остальными карточками продолжается.
- Подтверждено: при конфликте только заголовка или текста карточка остаётся в своей однозначно определённой колонке с отметкой конфликта. Отдельная область «Конфликты» вместо колонок используется при конфликте перемещения по правилу выше. Правило отображения одинаково на Windows и Android; общий API предоставляет сведения о конфликте и доступ к его разрешению.
- Разрешение конфликта доступно через интерфейс, HTTP и CLI. Если до разрешения пришла новая версия, нельзя молча потерять её.
- Несовместимые версии протокола или формата данных дают понятную ошибку без повреждения локальных данных.
- Удаление передаётся как изменение. Технические сведения об удалении не равнозначны содержимому корзины.

Правила конкурирующих перестановок, переименований колонки и пространства, разных решений одного конфликта, новых объектов в удаляемом контейнере и возвращения долго отключённого устройства подтверждены в разделе 1.2. Техническое проектирование должно реализовать эти правила и безопасное сокращение служебных данных; для независимо созданных одноимённых тегов подтверждено автоматическое объединение с сохранением всех назначений; для независимого переименования двух существующих тегов в одно имя подтверждён явный конфликт с сохранением тегов/назначений и выбором разных имён; такой же конфликт согласован при переименовании существующего тега против независимого создания нового тега с тем же именем (ADR-0012). Для отображаемого имени после объединения сохраняется одно из исходных написаний, одинаковое на устройствах; после объединения доступно обычное переименование. Конкретный алгоритм выбора написания, согласование идентификаторов и остальные коллизии имён ещё уточняются. Если спорно только имя назначенного тега, заголовок, текст, статус выполнения и колонка карточки изменяются по обычным правилам; спорные теги помечены, имена разрешаются отдельно. Назначение и снятие обоих спорных тегов приостановлены до выбора разных имён, после допустимого решения возобновляются; существующие назначения сохраняются. Собственные конфликты карточки по-прежнему блокируют её редактирование. Продуктовые правила перемещения одной карточки в разные колонки, независимого добавления разных тегов и удаления тега против его назначения уже определены выше. Правило удаления контейнера против правки его карточки также определено: явный конфликт без потери правки. Реализация должна сохранить корректную иерархию и связи при каждом варианте разрешения. Блокировка редактирования всей карточки до разрешения её собственных конфликтов и отдельная область для карточек с конфликтом перемещения подтверждены. Конфликт удаления карточки или её контейнера против правки также показывается в области «Конфликты» с просмотром сохранённой правки и состава затронутых объектов. При конфликте только заголовка или текста карточка остаётся в своей колонке с отметкой конфликта; поиск учитывает все сохранённые конфликтующие варианты этих полей и показывает карточку один раз с отметкой конфликта. При конфликте удаления тега против назначения карточки со спорными назначениями остаются в своих однозначно определённых колонках с отметкой конфликта; спорный тег помечен, редактирование карточек заблокировано. Обычное удаление тега выполняется без корзины и восстановления, как определено в разделе 7.

Подтверждено: выбрана основа синхронизации Automerge для Rust; [ADR-0002](decisions/0002-automerge-sync.md). Прежнее сравнение двух реализаций заменено ограниченным прототипом выбранной библиотеки. Порядок и критерии технической проверки описаны в разделе 1.2 и [оценке стека](stack-candidates.md). Модель прикладных данных, интеграция с SQLite и техническая пригодность для всех правил ZeDone ещё проверяются. Разные значения одного поля требуют явного чтения всех конкурирующих вариантов; одиночное значение обычного чтения не считается разрешением конфликта. Использование библиотеки сосредотачивается в одном внутреннем модуле Rust-ядра. Ручное разрешение конфликтов текста сохраняется; автоматическое объединение фрагментов Markdown не добавляется.

Примеры поведения со статусом решения:

- Подтверждено: на ПК меняется заголовок, на телефоне — текст той же карточки; независимые поля объединяются без диалога конфликта.
- Подтверждено: на обоих устройствах меняется текст; показываются обе версии для выбора или ручного объединения.
- Подтверждено: на ПК карточку перемещают в колонку «Работа», на телефоне независимо — в «Личное»; показывается конфликт и предлагается выбрать колонку.
- Подтверждено: на ПК карточке добавляют тег «Работа», на телефоне независимо — «Важно»; после обмена карточка получает оба тега без диалога конфликта.
- Подтверждено: на ПК удаляют сам тег «Работа» из пространства, на телефоне независимо назначают его карточке; показывается конфликт с выбором сохранения тега с назначениями либо подтверждения удаления со снятием назначений.
- Следствие подтверждённого правила разных полей: на ПК карточку перемещают, на телефоне отмечают выполненной; оба независимых изменения сохраняются при соблюдении корректности иерархии.
- Подтверждено: на одном устройстве карточку удаляют, на другом меняют её текст; показывается конфликт, правка сохраняется. Пользователь выбирает, оставить карточку в корзине либо восстановить с изменениями. Ни удаление, ни правка не выбираются молча.
- Подтверждено: на одном устройстве удаляют колонку или пространство, на другом меняют текст карточки внутри; показывается конфликт с сохранением правки и явным выбором удаления либо восстановления. Объём затрагиваемых объектов должен быть виден до решения.

Подтверждённая схема первой версии — один ПК и один телефон без постоянно включённой реплики. Следствие: обмен происходит, когда оба устройства одновременно доступны через Tailscale и процессы ZeDone могут выполнять работу. На ПК нужен запущенный локальный процесс; на Android — открытое приложение либо разрешённая ОС возможность фонового выполнения. Наличие интернета на каждом устройстве в разное время само по себе не доставляет изменения.

Если ПК выключен, спит или его процесс ZeDone остановлен, телефон продолжает локальную работу и хранит изменения до следующего соединения. То же относится к недоступному телефону. Ручная кнопка запускает попытку обмена, но не делает недоступное устройство доступным. Интерфейс показывает последнее подтверждённое состояние обмена и наличие ожидающих передачи изменений; локальное сохранение не должно ждать соединения.

Ретрансляторы Tailscale не заменяют постоянное хранилище заметок. В первой версии не требуется инфраструктура нескольких постоянно доступных реплик; базовая идентичность устройств и пространства при этом не должна зависеть от жёстко заданных имён «ПК» и «телефон».

Отвязка устройства прекращает дальнейший разрешённый обмен, но сама по себе не стирает уже полученные им данные. Правила повторного подключения нужно определить отдельно.

## 7. Корзина и обратимость

Подтверждено: удаление карточки, колонки и пространства выполняется через корзину; восстановление доступно; окончательная очистка выделена в отдельную операцию.

Подтверждено: изменившиеся после чтения состав или данные колонки или пространства с содержимым останавливают всю команду отправки соответствующего контейнера в корзину без частичного удаления. После показа актуального состояния и перечитывания удаление запускается новым явным действием; ADR-0014. Успешная операция сохраняет согласованные правила группы удаления и восстановления.

Подтверждено: окончательная очистка корзины запускается только вручную. Объекты сохраняются до явной окончательной очистки; автоматического удаления по сроку хранения или другим условиям в первой версии нет. Правило одинаково для интерфейса, HTTP и CLI на Windows и Android.

Подтверждено: доступны окончательная очистка выбранных объектов корзины и очистка всей корзины одного пространства. Обе операции доступны через интерфейс, HTTP и CLI на Windows и Android; область очистки ограничена указанным пространством. Перед очисткой показывается состав затронутых объектов; те же сведения доступны через общий API.

Подтверждено: при окончательной очистке колонки или пространства очищаются все их вложенные объекты, которые ещё находятся в корзине, включая удалённые раньше самого контейнера. Например, если карточка A удалена раньше, а колонка с карточкой B — позже, окончательная очистка колонки охватывает и A, и B. Активные объекты и карточки, уже восстановленные в другую колонку, не затрагиваются. Эти правила охвата одинаковы на обеих платформах и для агентского API.

Подтверждено: нерешённый конфликт в любом выбранном или вложенном объекте останавливает всю выбранную окончательную очистку без частичного удаления объектов. Это относится и к очистке всей корзины пространства. Интерфейс показывает список препятствующих конфликтов; HTTP и CLI возвращают те же сведения. Сначала конфликты разрешаются, затем очистка запускается заново. Правило одинаково на Windows и Android.

Подтверждено: независимая правка окончательно очищенной карточки, пришедшая позже с другого устройства, сохраняется в области «Конфликты». Например, очистка на ПК при недоступном телефоне не уничтожает его независимую правку после восстановления связи. Пользователь явно выбирает восстановление карточки или подтверждение окончательной очистки; автоматически карточка на доске не восстанавливается. Это разрешение конфликта, доступное через интерфейс, HTTP и CLI на обеих платформах; решение передаётся другому устройству. Общая блокировка обычной очистки при нерешённом конфликте сохраняется.

Протокол должен отличать повторную доставку уже очищенных данных от независимой правки и сохранять достаточно технических сведений для этого. Конкретное представление границы очистки и сокращение технических записей выбираются при проектировании синхронизации.

Подтверждено: удаление тега — явное исключение из общего требования обратимости для отдельного тега. Тег не помещается в корзину; отдельное восстановление тега вместе с прежними назначениями не предусмотрено. Создать тег с тем же именем можно, но его нужно заново назначить карточкам. Правило одинаково для интерфейса, HTTP и CLI на Windows и Android.

Подтверждено: при восстановлении всего пространства из снимка возвращаются теги и назначения из этого снимка, даже если после его создания их удалили. Это полное восстановление пространства по правилам раздела 10. Отдельной операции восстановления удалённого тега нет. Поведение одинаково для интерфейса, HTTP и CLI на обеих платформах.

Если удаление тега конфликтует с его независимым назначением на другом устройстве, сохраняется согласованный выбор из раздела 6: оставить тег с назначениями либо подтвердить удаление. Сохранение варианта при разрешении конфликта не является восстановлением из корзины. Отсутствие пользовательского восстановления не разрешает удалять технические сведения, необходимые для корректной синхронизации.

Подтверждено: восстановление колонки или пространства возвращает вложенные объекты, удалённые тем же действием. Карточки, которые уже находились в корзине до удаления контейнера, остаются в корзине. Например, если карточка A удалена раньше, а колонка с карточкой B — позже, восстановление колонки возвращает B, но не A.

Подтверждено: для восстановления отдельной карточки из пространства, которое само находится в корзине, сначала явно восстанавливается пространство вместе со всеми объектами, удалёнными тем же действием. Если нужная карточка была удалена раньше и осталась в корзине, её затем восстанавливают отдельно по правилам существующего пространства. Частичное восстановление пространства только с нужной колонкой и карточкой в первую версию не входит. Последовательность одинакова для интерфейса, HTTP и CLI на Windows и Android.

Подтверждено: если пространство существует, а исходная колонка находится в корзине, отдельную карточку можно восстановить в выбранную существующую колонку того же пространства. Восстанавливается только выбранная карточка; исходная колонка остаётся в корзине. Предлагается сохранять идентификатор и историю карточки и проверять, что выбранная колонка активна и относится к этому пространству. Последующее восстановление исходной колонки не должно создавать дубликат карточки или переносить уже восстановленную карточку обратно.

Для соблюдения этого правила предлагается сохранять принадлежность объектов конкретному действию удаления и не определять её только по близости временных меток. Независимые офлайн-действия и повторная доставка сообщения не должны смешивать группы удаления.

Предложения:

- Удаление контейнера сохраняет связь с вложенными объектами для корректного восстановления.
- Удаление не вызывает незаметное перемещение или потерю карточек. Перед действием понятен его охват.
- Корзина синхронизируется в пределах подключённого пространства. Отключение синхронизации и удаление локальной копии должны быть различимыми действиями.
- Окончательная очистка удаляет содержимое согласно явно описанным правилам, но может сохранять минимальные технические сведения, предотвращающие воскрешение удалённого при обмене.
- Очистка на одном устройстве не гарантирует немедленное удаление данных на недоступных устройствах или в ранее сделанных резервных копиях.

Подтверждена история версий карточки с просмотром и восстановлением прежних заголовка и описания. Каждая версия содержит оба поля из одного сохранённого состояния; переименование без изменения описания также участвует в истории. Подтверждено: восстановление выбранной версии записывает её заголовок и описание как новую правку и сразу фиксирует новую видимую версию. Вся предшествующая история сохраняется, включая версии после выбранной. Например, после 1 → 2 → 3 восстановление первой даёт версию 4 с её содержимым; затем можно восстановить третью как версию 5 и вернуть состояние до первого восстановления. Восстановление выполняется через общий API с применимыми проверками доступа, актуальности и конфликтов и синхронизируется как новая правка. Ошибка записи или отклонённая команда не меняют карточку и не создают ложную версию. Технический механизм согласованной записи проектируется отдельно; ADR-0013.

Подтверждено: для исправления результатов действий человека или агента достаточно обычных обратных операций и восстановления версий карточек. Единая команда отмены серии действий отложена и в первую версию не входит. Согласованные исключения из обратимости сохраняются. Доступные обратные операции одинаковы для интерфейса, HTTP и CLI на Windows и Android.

Подтверждено: серия непрерывного редактирования одним участником создаёт одну видимую версию истории. Она фиксируется при завершении редактирования, существенной паузе (30 секунд без новых правок заголовка или описания) или смене участника. При этом текущее состояние локально сохраняется чаще. Пользовательская версия истории и отдельная техническая запись автосохранения — разные понятия.

Подтверждено: смена участника при успешно сохранённом изменении заголовка или описания завершает прежнюю серию и начинает новую, даже без долгой паузы. Последовательность «человек → агент → человек» сохраняет три раздельных этапа; возврат прежнего участника не объединяет его новую серию с предыдущей через правку агента. Заголовок и описание каждого этапа доступны в истории по общим правилам фиксации. Чтение и отклонённое сохранение сами не создают версию и не меняют участника открытой серии. Интерфейс, HTTP и CLI на Windows/Android используют общие операции ядра; история остаётся общей для пространства и синхронизируется. Идентификация участника и остальные границы серий проектируются отдельно; [ADR-0013](decisions/0013-history-participant-boundaries.md).

Подтверждено: каждая отдельная прикладная команда, успешно изменившая заголовок или описание карточки, фиксирует свою видимую версию при сохранении результата. Две отдельные команды одного агента подряд дают две версии с заголовком и описанием после каждого шага независимо от короткой паузы. Для той же дискретной команды человека действует то же правило; несколько автосохранений непрерывного ввода остаются одной серией. Тип клиента или транспорт сам по себе не выбирает группировку, правило задаётся общим контрактом и ядром. Одна команда изменения обоих полей создаёт одну версию. Запись заголовка, описания и соответствующей версии согласованна; чтение и отклонённое сохранение не создают версии. [ADR-0013](decisions/0013-history-participant-boundaries.md).

Подтверждено: если после успешного автосохранения вкладка Windows или APK Android неожиданно завершились до фиксации видимой версии, после перезапуска сохранённая серия завершается одной видимой версией с последними успешно записанными заголовком и описанием этой серии. Дальнейший ввод начинает новую серию даже при быстром перезапуске тем же участником. Повторные перезапуски без ввода и уже завершённая серия не создают дубликатов или пустых версий. Граница восстанавливается по сохранённым данным серии; текущее авторитетное состояние и более новые правки других клиентов сохраняются по общим правилам. Техническая фиксация границы после сбоя проектируется в P03/P04; ADR-0013. Группировка не должна скрывать независимые изменения с другого устройства, вкладки или от агента. Остальные границы серии и логическая идентификация команд/серий ещё проектируются; интервал существенной паузы подтверждён — 30 секунд без новых правок; смена участника, отдельная прикладная команда и перезапуск после неожиданной остановки уже определяют границы видимых версий.

Подтверждено: автоматического удаления истории по возрасту или числу версий нет. Пользователь видит занимаемый ею объём и может запустить очистку вручную. Ротация резервных копий не сокращает историю в рабочем хранилище. Ограничение размеров тестового набора не является ограничением хранения истории в продукте.

Подтверждено: пользовательская история общая для пространства. Синхронизируются и версии, и ручная очистка истории. На отключённом устройстве очистка применяется после следующего обмена; ранее созданные резервные копии не переписываются. Следовательно, отдельная локальная очистка не должна называться очисткой общей истории пространства.

Предлагается отдельно учитывать пользовательскую историю, нерешённые конфликтующие версии и технические сведения об обмене. Очистка истории не должна удалять текущее состояние, незаметно разрешать конфликт или нарушать последующую синхронизацию. До выбора алгоритма нельзя обещать, что очистка пользовательской истории полностью удалит все связанные с ней байты из внутреннего журнала, других устройств и ранее созданных резервных копий.

Подтверждённая семантика конкурирующих операций: очистку можно выполнить сразу без доступности второго устройства; она затрагивает известные на момент команды версии. Если в это время на телефоне независимо создана новая версия, поступившая позже, она сохраняется. Более поздняя дата очистки на часах ПК не является основанием удалить независимую правку телефона.

Подтверждено: ручная очистка доступна для одной карточки и для всего пространства. До действия пользователь видит область и объём очистки. Текущее содержимое, нерешённые конфликтующие варианты и независимые новые версии сохраняются. Эти правила одинаковы для интерфейса и агентского API.

Для очистки всего пространства предлагается фиксировать множество затронутых карточек и известных версий в момент операции. Команда не должна превращаться в бессрочное правило удаления истории карточек или версий, которые позже пришли с другого устройства. Для агента проверяется право изменения именно этого пространства. Способ указания области, расчёт объёма и обработка изменения данных между показом объёма и выполнением команды уточняются при проектировании API.

Предлагается передавать вместе с очисткой достаточно сведений о её причинной границе: повторный обмен не возвращает уже очищенные пользовательские версии как обычную историю и не затрагивает независимые новые правки. Конкретное представление границы и безопасное сокращение технических записей выбираются при проектировании протокола.

Открыто: технический механизм завершения сохранённой серии после сбоя. Интервал существенной паузы подтверждён — 30 секунд без новых правок. Единая отмена серии действий отложена; для исправления используются обычные обратные операции и восстановление версий карточек. Подтверждена только ручная окончательная очистка без автоматического удаления: выбранные объекты либо вся корзина одного пространства. Подтверждены показ состава перед очисткой и охват всех оставшихся в корзине вложенных объектов колонки или пространства, включая удалённые раньше контейнера. При наличии любого нерешённого конфликта в области операции очистка останавливается без частичного удаления и показывает конфликты; после их разрешения её запускают заново. Поздняя независимая правка очищенной карточки сохраняется в области «Конфликты» с явным выбором восстановления или подтверждения окончательной очистки. Правила конфликтов удаления карточки или контейнера против правки, восстановления контейнера и отдельной карточки при существующем пространстве, предварительного восстановления пространства из корзины, общей истории, её очистки на уровне карточки или пространства без связи и группировки непрерывного редактирования уже подтверждены. Корзина сама по себе не даёт историю текста и не заменяет резервную копию.

## 8. Интерфейс и Markdown

Подтверждено: сложные компоненты интерфейса строятся на Reka UI, простые кнопки и поля — на стандартных семантических HTML-элементах. Подключаются только необходимые компоненты; собственное оформление ZeDone используется на обеих платформах. Выбор не подтверждает корректность интеграции: клавиатура, фокус, доступные названия, сенсорное управление, экранная клавиатура и системная кнопка «Назад» Android проверяются в P01/P05; [ADR-0004](decisions/0004-ui-components.md).

Предлагается общий адаптивный интерфейс с семантическими цветовыми токенами. Заданные четыре оттенка определяют основу тем; состояния ошибок, фокуса, границы и дополнительный текст нужно подобрать с проверкой читаемости.

Подтверждено: собственный дизайн ZeDone используется на обеих платформах. Для перетаскивания карточек и колонок выбраны SortableJS через VueDraggablePlus, см. [ADR-0005](decisions/0005-drag-and-drop.md). Перетаскивание требуется на ПК и телефоне; перенос и изменение порядка также выполняются через явные команды, доступные на телефоне и с клавиатуры. Все способы управления вызывают те же прикладные операции, что HTTP и CLI.

Подтверждено: заголовок и текст сохраняются автоматически с состояниями «сохранение», «сохранено» и «ошибка».

Предлагаемые уточнения автосохранения:

- «Сохранено» означает фиксацию последнего редактируемого состояния в локальном авторитетном хранилище. Статус обмена с другим устройством показывается отдельно. Ответ на более раннее сохранение не должен помечать более свежий ввод как уже сохранённый.
- Ввод в памяти редактора до фиксации не считается сохранённым. Частота объединения ввода в запросы, повтор после ошибки и обработка приостановки Android и закрытия страницы должны быть определены и проверены.
- Подтверждено: ввод с временно пустым обязательным заголовком остаётся несохранённым. Предлагается отклонять запись некорректного состояния, оставляя последнюю корректную версию в хранилище и введённый текст в редакторе с понятной причиной невозможности сохранить. При обычном уходе пользователь получает предупреждение о несохранённом вводе. При принудительной остановке процесса такой ввод может потеряться; его автоматическое восстановление не является требованием первой версии.
- При ошибке записи или устаревшей версии запрос не должен молча отбрасывать введённый текст или заменять его другим вариантом. Состояние ошибки сохраняется до успешного повторного сохранения либо явного решения пользователя.
- Нужна защита от применения запросов в обратном порядке при быстром вводе. Способ последовательного сохранения и проверки версий выбирается в реализации.
- Подтверждено: локальное автосохранение выполняется чаще создания видимых версий истории. Непрерывный ввод одного участника объединяется в одну версию, фиксируемую при завершении редактирования, существенной паузе (30 секунд без новых правок заголовка или описания) или смене участника. После неожиданной остановки и перезапуска прежняя сохранённая серия завершается, новый ввод начинает новую. Частота автосохранения и техническая фиксация завершения серии после сбоя уточняются отдельно; 30 секунд задают группировку истории, а не задержку локального сохранения. Отдельная прикладная команда изменения заголовка или описания фиксирует свою видимую версию при успешном сохранении; то же правило действует для человека и агента по общему контракту, сохраняя группировку автосохранений непрерывного ввода. Каждая видимая версия содержит заголовок и описание из одного сохранённого состояния, включая неизменившееся поле; переименование участвует в истории по тем же правилам.

Принятый риск: незаписанный ввод с пустым обязательным заголовком может быть потерян при принудительном завершении браузера или APK. Предупреждение при обычном уходе не гарантирует сохранность при таком завершении. Это ограничение относится к несохранённому вводу; успешное локальное сохранение и уже записанная история должны оставаться надёжными.

Исходный Markdown является сохраняемым содержимым. HTML для просмотра — производное представление.

Подтверждено: синтаксис первой версии — базовый CommonMark с заголовками, выделением, списками, ссылками, цитатами и блоками кода; [ADR-0006](decisions/0006-markdown-syntax.md). Расширения таблиц и текстовых чекбоксов не входят в первую версию. Строки с разделителями таблиц и маркерами вида «- [ ]» сохраняются и отображаются по базовым правилам CommonMark, без специального форматирования таблиц или интерактивных чекбоксов. Они не меняют самостоятельную отметку выполнения карточки. Правило одинаково для интерфейса и общего API на Windows и Android.

Для парсинга и безопасного просмотра выбраны markdown-it + DOMPurify. markdown-it разбирает исходный текст по базовому пресету CommonMark с явным `html: false`, DOMPurify очищает сформированный HTML перед отображением. Один модуль общего интерфейса задаёт одинаковый профиль на Windows и Android; непроверенная HTML-разметка после очистки не добавляется. Версии CommonMark и библиотек, HTML-профиль DOMPurify и настройки фиксируются при подготовке прототипа. Обязательны установка/импорт через выбранные инструменты, сборка и проверка типов с Bun/Vite, а также фактический просмотр и очистка в целевых браузерах и Android WebView. Подтверждено: пользовательская HTML-разметка показывается как обычный текст, например `<b>важно</b>` виден вместе с тегами; обычное выделение `**важно**` продолжает работать. HTML и скрипты из исходного текста не интерпретируются и не выполняются, исходный текст сохраняется целиком. Это профиль отображения ZeDone поверх базового CommonMark с отключённой интерпретацией raw HTML; [ADR-0006](decisions/0006-markdown-syntax.md). В markdown-it требуется явное `html: false`, поскольку стандартный пресет CommonMark включает HTML; DOMPurify применяется к результату перед показом. Само наличие очистки не гарантирует отсутствие запросов на изображения: загрузочные адреса подавляются до нажатия, в том числе до передачи HTML на очистку. Подтверждено: обычные HTTP/HTTPS-ссылки открываются по нажатию вне ZeDone — в отдельной вкладке браузера на Windows и во внешнем браузере на Android. Просмотр карточки не заменяется внешним сайтом, отображение текста не открывает ссылки автоматически. Подтверждено: удалённое изображение из Markdown загружается внутри карточки только по отдельному нажатию. До этого показывается описание или понятная заглушка с действием загрузки; просмотр карточки не запускает загрузку, нажатие относится к выбранному изображению. При ошибке сети показываются причина и возможность повтора, исходный текст сохраняется, работа с карточкой продолжается. До нажатия запросы на изображения не возникают также при парсинге и очистке HTML; скрытие загружаемого элемента не выполняет это требование. Адрес остаётся частью исходного Markdown; ограничения первой версии по вложениям сохраняются.

Предложения для проверки: русскоязычный ввод, экранная клавиатура, длинный текст, вставка из буфера, масштабирование, видимый фокус, контраст и доступность управления без мыши.

## 9. Ограничения разработки

Подтверждено: разработкой полностью занимается AI-агент; разработчик определяет поведение и оценивает результат как продвинутый пользователь. При выборе инструментов приоритетны снижение риска ошибок агента, уменьшение объёма собственной сложной логики, возможность автоматической проверки, зрелость документации и поддерживаемость. Утверждения о снижении частоты ошибок должны отделяться от инженерных оценок; измерений ZeDone пока нет.

Подтверждено: GitHub Actions дополняет локальные проверки в пределах бесплатных возможностей. Для Windows-сборки используются стандартные Windows-машины, для Android-сборки и эмулятора — Linux. Локальная разработка и эмулятор остаются на Windows 11. Конкретные workflows, сроки хранения артефактов и лимиты кеша ещё предстоит настроить; использование платной инфраструктуры не планируется.

Подтверждённая граница запрета unsafe:

- В собственном коде ядра, хранения и синхронизации unsafe запрещён. Минимальные исключения возможны только на платформенной границе и требуют отдельного обоснования. Необходимость одной платформенной функции не ослабляет правило для остальных компонентов.

Предлагаемый способ технического обеспечения и остальные правила Rust:

- Применять `unsafe_code = "forbid"` в собственных пакетах ядра, хранения и синхронизации ко всем их целям сборки. Проверять наследование настроек в workspace и отсутствие обхода при сборке Windows и Android.
- Платформенную границу держать в отдельном адаптере с безопасным интерфейсом для ядра. Код, принимающий бизнес-решения, работающий с данными карточек или реализующий протокол обмена, не переносится в этот адаптер ради обхода запрета.
- Для каждого платформенного исключения фиксировать назначение, причину отсутствия подходящего безопасного API, область действия, условия корректности и способ проверки. В коде требуется локальное объяснение безопасности; архитектурное обоснование хранится в `docs/architecture/decisions`. Обоснование общего исключения для всего проекта не соответствует выбранному правилу.
- Генерируемая точка входа и платформенные макросы оцениваются вместе с оболочкой. Если они требуют unsafe-атрибутов или unsafe-кода, их относят к минимальной платформенной границе и документируют по тем же правилам.
- Ограничение собственного кода не запрещает unsafe внутри стандартной библиотеки и сторонних зависимостей. Состав зависимостей, происхождение, лицензии, известные уязвимости и используемые безопасные API проверяются отдельно.
- Фиксируются toolchain и зависимости приложения. Обновления выполняются осознанно.
- Обязательны форматирование, Clippy и проверки сборки обеих платформ. Набор lint-правил должен предотвращать реальные ошибки, а не заставлять обходить анализатор.
- Ожидаемые ошибки ввода, диска и сети обрабатываются через типизированные результаты. Необоснованные `unwrap`, `expect` и паники в рабочем коде запрещаются; правила для тестов оговариваются отдельно.
- Собственная криптография не разрабатывается. Новые зависимости требуют понятного назначения.

Предложения для TypeScript: `strict`, дополнительные проверки необязательных полей и индексированного доступа, запрет необоснованного `any` и подавления ошибок. Сгенерированные типы не заменяют проверку входящих данных во время выполнения и правил на стороне Rust.

Проверки будущей реализации должны в первую очередь охватывать сохранность данных, миграции, повторные запросы, обмен при обрывах и конфликтах, восстановление и паритет API. Сейчас эти проверки ещё не выполнялись: приложение не реализовано.

## 10. Локальные данные и восстановление

Подтверждено: собственное шифрование хранилища пока не требуется. Это не исключает защиту сетевого API и учётных данных устройств и агентов.

Подтверждено: подключение устройств явное. При уже настроенном Tailscale ПК показывает QR-код для телефона; доступен запасной ручной ввод адреса ПК и одноразового кода. В обоих случаях запрос требует дополнительного явного подтверждения на ПК; до него телефон ожидает без подключения и обмена пространствами. Явный выбор пространств сохраняется; [ADR-0009](decisions/0009-device-pairing-qr-and-code.md).

Предложения:

- Локальный HTTP API проверяет разрешённый источник запросов и доступ. Привязка к localhost сама по себе не является полной моделью защиты от запросов из посторонних страниц.
- Принадлежность одной сети Tailscale сама по себе не открывает все пространства; протокол подключения, проверка устройства и выдача учётных данных ещё проектируются в DEC-003.
- Данные приложения исключаются из автоматической облачной резервной копии Android. Правила проверяются для поддерживаемых версий ОС. На Windows стандартный каталог данных выбирается вне папок, автоматически синхронизируемых в облако.
- Интерфейс, шрифты и необходимые ресурсы поставляются локально. Для запуска не нужен CDN. Диагностика по умолчанию не содержит тексты карточек и секреты.
- Подтверждены автоматические локальные резервные копии и ручной экспорт/импорт. Восстановление должно быть проверяемым. Синхронизация распространяет и ошибочные изменения, поэтому не заменяет резервное копирование.
- Снимок работающей базы создаётся согласованным способом, а не произвольным копированием одного файла.
- При восстановлении копии нужно учитывать идентичность устройства и историю обмена, чтобы старые версии не выдавались за новые и не воскрешали удалённое.

### Подтверждённые экспорт и импорт

Ручной экспорт содержит пространство целиком: его колонки, карточки, теги, корзину и пользовательскую историю версий. Обычный импорт создаёт новое независимое пространство. Он не объединяет данные с исходным пространством и не подменяет восстановление исходных данных из резервной копии.

Подтверждено 2026-10-27: достаточно файла, который читает ZeDone. Открытие обычным архиватором и наличие читаемого без ZeDone представления, например JSON, не требуются. Это не выбирает двоичный формат или собственный контейнер: конкретное представление проектируется отдельно. Полнота переноса и проверки при импорте сохраняются.

Предлагаемые следствия и требования к формату:

- Архив описывает структуру пространства, связи и состояния объектов. Нерешённые конфликтующие варианты также следует сохранять, чтобы полный перенос не терял пользовательские данные.
- При импорте назначаются новые идентификаторы пространства и его объектов с согласованным преобразованием всех внутренних ссылок. Содержимое, история и связи сохраняются; протокольные операции исходной реплики не выдаются за новые операции исходного пространства.
- Подключения синхронизации и права агентов исходного пространства не переносятся автоматически. Пользователь отдельно подключает созданное пространство и выдаёт доступ. Учётные данные устройств и агентов не являются содержимым переносимого архива.
- Ранее созданный экспорт остаётся самостоятельным файлом. Дальнейшая очистка истории или корзины в работающем пространстве не переписывает этот файл.
- Архив имеет версию формата; импорт проверяет совместимость, целостность структуры и ссылки до публикации пространства в рабочем списке. Повреждённый или несовместимый файл не создаёт частично импортированное пространство.
- Повтор доставки одного и того же запроса импорта не должен создавать дубликат его результата. Новый явно запущенный импорт может создавать ещё одну независимую копию.
- Экспорт должен быть согласованным снимком, даже если агент или интерфейс в это время редактирует карточку.

Конкретный контейнер архива, схема сериализации, проверка размера и способ преобразования идентификаторов выбираются на этапе технического проектирования. Продуктовый состав архива и создание независимого пространства уже определены.

### Подтверждённая политика автоматических копий

Подтверждено 2026-10-27: после явного выбора папки со старыми резервными копиями ZeDone автоматически находит свои копии и показывает пространства и даты. Это работает и после переустановки, когда прежняя локальная база и настройки недоступны. Восстановление запускается только отдельной явной командой; само обнаружение копий не восстанавливает данные и не возобновляет обмен. Просмотр каталога доступен одинаково человеку и агенту через общий API в пределах выданных прав на Windows и Android. Выбор папки для просмотра сам по себе не запускает перенос или ротацию копий и не меняет настройку папки создания новых копий.

Инженерное следствие для проектирования: сведения для списка должны извлекаться из доступных копий; возможный индекс каталога должен восстанавливаться без прежней базы и настроек. Формат распознавания, состав метаданных и проверки файлов уточняются технически. Отображение найденной копии не подменяет проверку её совместимости и целостности перед восстановлением и не выдаёт дополнительных прав на эту операцию.

Подтверждено: автоматические копии создаются отдельно для каждого пространства. Для каждого пространства отдельно на каждом устройстве допускается не более одного успешно завершённого ежедневного снимка за календарную дату по локальному часовому поясу устройства, при работающем приложении и после изменений с предыдущего успешного ежедневного снимка. Новый календарный день снова разрешает копию при наличии изменений: снимки в 23:50 и 00:10 следующего дня допустимы. Когда приложение работает и условия частоты/изменений выполнены, попытка создания запускается при первой подходящей возможности без ожидания фиксированного часа. Проверка условий действует при запуске и в ходе работы приложения, включая первое сохранённое изменение и наступление следующего разрешённого момента без перезапуска; [ADR-0015](decisions/0015-daily-backup-trigger.md). Если данные не менялись, новый ежедневный снимок не создаётся и ротация не выполняется. Для этого пространства сохраняются последние 7 успешно завершённых ежедневных снимков; более старые его снимки автоматически удаляются при успешном создании новых. Лимит не является общим для всех пространств: создание восьмой копии пространства A не удаляет копию пространства B. Создание нового пространства учитывается для первого снимка. Новые правки после границы состояния успешной копии сохраняются для следующей разрешённой копии; повторный запуск и параллельные проверки не обходят ограничение частоты. Ошибка не отмечает успех и не запускает ротацию; действуют согласованные повторные попытки в выбранную папку. Сведения об успешном снимке текущего календарного дня сохраняются после перезапуска; неуспешная попытка не занимает дневной лимит. Отсчёт времени, обработка изменения часов/пояса и техническое планирование проектируются в P07.

Это 7 снимков каждого пространства, а не обещание наличия копии за каждый календарный день: если приложение не работало, данные не менялись или создание копии завершилось ошибкой, пропущенные дни не восполняются задним числом. Отдельный еженедельный набор не требуется.

Подтверждено: по умолчанию автоматические копии хранятся в локальном каталоге данных приложения; пользователь может выбрать другую локальную папку на Windows и Android. Выбранное расположение сохраняется локально на устройстве. Доступны повторная смена папки и возврат к каталогу по умолчанию; просмотр настройки и изменение разрешённого расположения доступны через общий API в пределах выданных прав. На Android файлы в каталоге приложения удаляются при удалении приложения с устройства. [Android: файлы приложения](https://developer.android.com/training/data-storage/app-specific).

Подтверждено: при смене папки существующие автоматические копии ZeDone переносятся. Сначала они копируются в выбранную папку и проверяются, затем сохраняется новое расположение, после чего удаляются исходные копии. Это относится к ежедневным и страховочным снимкам, включая сохранённые копии удалённых пространств. Возврат к каталогу по умолчанию выполняется по тому же правилу. Смена папки не создаёт новый снимок и сама по себе не запускает ротацию.

Требования к надёжности переноса: ошибка копирования или проверки до переключения сохраняет прежнюю настройку и исходные копии. Если после переключения не удалось удалить исходные копии, новое расположение остаётся действующим, проверенные копии сохраняются, а приложение сообщает о незавершённом удалении дубликатов. Перенос затрагивает только управляемые ZeDone автоматические копии; посторонние файлы в обеих папках не изменяются. Механизм проверки, согласование с созданием снимков и восстановление операции после сбоя проектируются отдельно.

Подтверждено: если выбранная папка недоступна, например отключён накопитель или отозван доступ, приложение сообщает об ошибке и повторяет попытки создания копий в ту же папку при работающем приложении: следующая автоматическая попытка ежедневной копии выполняется через 5 минут после завершения неудачной; после очередной такой ошибки отсчёт начинается заново. Работа с пространствами продолжается. Настройка автоматически не меняется, временные копии в другой папке не создаются. Неуспешная попытка не обновляет сведения о последнем успешном снимке и не запускает ротацию. После возврата доступа создание снимков продолжается по согласованным правилам частоты и изменений; пропущенные дни не восполняются задним числом. Состояние ошибки и сведения о последней успешной копии доступны через интерфейс и общий API в пределах выданных прав на Windows и Android. Новые правки и автоматические события проверки условий не обходят паузу и не создают параллельных повторов. Исходные условия календарной частоты/изменений сохраняются; возобновление ожидания после перезапуска и обработка прочих ошибок проектируются в P07. ADR-0015.

Подтверждено: после ошибки ежедневной копии доступно явное действие «Повторить сейчас» для пространства через интерфейс, HTTP и CLI на Windows/Android. Оно запускает нужную попытку досрочно в выбранную папку, сохраняя проверки прав, изменений и лимит успешного ежедневного снимка; отдельный дополнительный снимок сверх лимита не создаётся. При уже выполняющейся копии возвращается её состояние, при отсутствии изменений или занятом дневном лимите — понятная причина без новой попытки и ложного успеха. Повторная доставка одного запроса, одновременные запросы и автоматический таймер не дублируют попытку. После успеха действует обычное ежедневное планирование. После новой ошибки доступа к папке автоматический повтор назначается через 5 минут от завершения ручной попытки, прежний отложенный повтор не дублирует ручную попытку и не обходит новую паузу. Формат запроса/результата и идентификация явного действия проектируются в P03/P07; ADR-0015.

Подтверждено: миграция базы и восстановление существующего пространства начинаются только после создания и проверки нового страховочного снимка текущего состояния в выбранной папке копий. Если обязательный снимок не удалось создать или проверить, в том числе из-за недоступности папки, операция не начинается и исходное состояние не изменяется этой операцией. Прежний страховочный снимок не заменяет новый снимок текущего состояния и сохраняется по согласованным правилам хранения. Автоматического сохранения в другую папку нет. Причина отказа доступна через интерфейс и общий API в пределах выданных прав на Windows и Android. Исключение для восстановления в новую установку после переустановки при подтверждённом отсутствии текущего состояния исходного пространства определено ниже и в сценарии 59; требования миграции оно не отменяет. Конкретный состав снимков для миграции общей базы, включая служебные данные, проектируется отдельно.

Подтверждено: после установки обновления необходимая миграция базы запускается автоматически при первом запуске новой версии. Отдельная команда или подтверждение пользователя либо агента не требуются. До изменения схемы выполняются обязательные проверки, создание и проверка нового страховочного снимка в выбранной папке. Если эти условия не выполнены, миграция не начинается и отображается причина отказа. При требуемой миграции обычные операции новой версии с этой базой становятся доступны после её успешного завершения; интерфейс и общий API используют один порядок на Windows и Android. Механизм миграций и конкретные проверки проектируются отдельно.

Подтверждено: если старая версия приложения обнаружила более новую схему базы, которую не поддерживает для записи, приложение отказывает в открытии и предлагает установить подходящую новую версию ZeDone. Проверка совместимости предшествует миграции и обычным операциям с базой; схема, пользовательские данные и служебные записи сохраняются без изменений. Режим чтения такой схемы в первую версию не входит; автоматического отката схемы нет. Причина отказа доступна через интерфейс и общий API на Windows и Android. Конкретные версии и механизм проверки совместимости определяются при техническом проектировании.

Предлагается вести копии на каждом устройстве локально и ротировать их независимо по пространствам. Новую копию сначала полностью записывают и проверяют, а затем удаляют лишние старые снимки того же пространства. Ошибка создания новой копии не должна приводить к удалению уже имеющихся исправных снимков. Удаление старого снимка не очищает историю или корзину в рабочей базе.

Подтверждено: на устройстве используется одна SQLite-база, а раздельные копии пространств создаются логически через общее Rust-ядро. Автоматический снимок включает полное согласованное состояние пространства: текущие данные пространства и его объектов, корзину, всю пользовательскую историю версий, нерешённые конфликты и необходимые сведения восстановления. Его применение сохраняет остальные пространства. Правило одинаково для интерфейса, HTTP и CLI на Windows и Android. Формат и конкретные технические сведения ещё проектируются. Если миграция затрагивает несколько пространств или общее хранилище, техническое проектирование должно обеспечить согласованное восстановление всей затронутой области.

Подтверждено: для каждого пространства сохраняется последний страховочный снимок перед миграцией сверх 7 ежедневных. Он заменяется после следующей успешной миграции. Обычная ежедневная ротация его не удаляет, и само успешное создание ежедневной копии не является основанием удалить страховочный снимок.

Предлагается создавать обязательный новый снимок перед миграцией как отдельный снимок-кандидат, сохраняя прежний страховочный. Прежний заменяется только после успешной миграции и проверки результата. При ошибке прежний снимок не удаляется; порядок восстановления и работы с временным кандидатом должен быть определён технически.

Подтверждено: для каждого пространства хранится последний страховочный снимок состояния перед восстановлением, чтобы можно было вернуться к прежнему состоянию. Он хранится отдельно и сверх 7 ежедневных снимков и страховочного снимка перед миграцией. При следующем успешном восстановлении его заменяет снимок состояния перед этой операцией; неуспешная попытка сохраняет прежний страховочный снимок. Эта политика одинакова на Windows и Android и при восстановлении через интерфейс, HTTP и CLI.

Подтверждено: окончательное удаление пространства на этом устройстве не удаляет его автоматические копии. Они остаются доступными для отдельного явного удаления или восстановления. Предлагается сохранять в каталоге копий возможность найти снимки удалённого пространства, видеть их объём и управлять ими. Ручные экспорты в отдельных файлах этой операцией не изменяются. Локальное управление резервными копиями не означает удаления файлов на другом устройстве.

Подтверждено: восстановление автоматической резервной копии возвращает исходное пространство к состоянию выбранного снимка, включая теги и назначения из снимка, удалённые позднее. Отсутствие отдельного восстановления удалённого тега не ограничивает полное восстановление пространства. Эта отдельная операция доступна через интерфейс, HTTP и CLI на Windows и Android.

Подтверждено 2026-10-27: при восстановлении резервной копии пространства после переустановки сохраняется идентичность исходного пространства. Новая установка ZeDone подключается к другому устройству заново по общему протоколу с явным подтверждением. На новой установке доступ агентам, включая ранее выданные административные разрешения, автоматически из копии пространства не возвращается и при необходимости выдаётся заново по общим правилам. Это локальное правило новой установки; актуальные разрешения на сохранившемся другом устройстве продолжают управляться отдельно. Пауза восстановленного пространства до явного возобновления и сохранение независимых правок второго устройства остаются обязательными. Решение — [ADR-0016](decisions/0016-reinstallation-pairing-and-access.md).

Подтверждено 2026-10-27: восстановление в новую установку после переустановки при проверенном отсутствии текущего состояния исходного пространства допускается без страховочной копии отсутствующего состояния. Резервная копия проверяется на совместимость и целостность; её исходный файл сохраняется. Проверка отсутствия и применение восстановления должны быть согласованы: появление существующего состояния до применения не разрешает его перезаписать по этому исключению. Ошибка чтения локальных данных не считается подтверждением отсутствия. Если пространство уже существует, в том числе находится в корзине, обязателен новый проверенный страховочный снимок по обычному правилу. Исключение не заменяет проверки прав и не разрешает автоматическое восстановление; общие правила паузы и повторного подключения сохраняются. Полное аварийное восстановление всей базы имеет отдельные условия и полномочия; требования миграции также сохраняются. [ADR-0016](decisions/0016-reinstallation-pairing-and-access.md), сценарий 59/A59.

Подтверждено: после восстановления на этом устройстве приостанавливается входящий и исходящий обмен восстановленного пространства. Пауза действует до явной команды возобновления и сохраняется после перезапуска приложения; автоматический обмен до этой команды не выполняется. Пользователь может проверить восстановленное состояние перед возобновлением. Состояние паузы и команда возобновления доступны одинаково через интерфейс, HTTP и CLI на Windows и Android.

Подтверждено: после явного возобновления обмена восстановление передаётся другому устройству как новое действие. Независимые правки другого устройства сохраняются: совместимые объединяются по обычным правилам раздела 6, несовместимые становятся конфликтами. Правило одинаково при восстановлении на Windows и Android и при вызове операции через интерфейс, HTTP и CLI. Технический механизм должен сохранять причинные сведения, необходимые для распознавания независимых изменений.

Открыто: формат автоматического снимка и конкретные технические сведения восстановления, механизм полной копии и аварийного восстановления общей базы вместе со служебными данными, конкретные платформенные пути и доступ к выбранной папке, техническое возобновление ожидания повтора и обработка прочих ошибок копирования, механизм проверки и восстановления переноса после сбоя и техническая обработка календарного ограничения при изменении часов/пояса; момент первой подходящей возможности, лимит по календарному дню устройства и пауза 5 минут после недоступности выбранной папки подтверждены по ADR-0015; перенос на новое устройство; последствия потери устройства и переустановки APK. Полное состояние пространства в автоматическом снимке, включая корзину, историю и конфликты, и хранение по умолчанию в каталоге данных приложения с выбором другой локальной папки на обеих платформах подтверждены. При смене папки существующие копии переносятся: копирование и проверка, переключение расположения, удаление исходных копий. При недоступности папки приложение сообщает об ошибке и повторяет попытки в неё, сохраняя работу с пространствами без автоматического выбора другой папки. Миграция базы и восстановление пространства не начинаются без нового проверенного страховочного снимка текущего состояния в выбранной папке. Также подтверждены отдельные автоматические копии с лимитом 7 на пространство и пропуском дней без изменений, отдельные последние снимки перед миграцией и перед восстановлением, сохранение копий удалённого пространства, полный ручной экспорт, импорт независимого пространства, возврат исходного пространства к состоянию автоматической копии, пауза его обмена до явного возобновления и передача восстановления как нового действия с сохранением независимых правок. Технический механизм синхронизации восстановления, идентичность восстановленной реплики и подключение существующей реплики проектируются отдельно. Нельзя обещать восстановление без сохранившейся копии данных. Подтверждённые атомарность всей цепочки миграций, полная предмиграционная копия и её хранение, повторные попытки, служебный режим и отдельное аварийное восстановление, поддержка исторических схем и форматов снимков описаны в разделе 1.1. Требование нового исправного снимка текущего состояния относится к обычному восстановлению пространства; предусловия аварийного восстановления всей повреждённой базы определены отдельно.

Дополнительно проверяются все подтверждённые уточнения разделов 1.1 и 1.2. Для миграций нужны прерывания каждого этапа цепочки, проверки пользовательских и служебных данных, полной копии и её замены, ручного повтора, служебного режима, аварийного восстановления и всех выпущенных схем и форматов снимков. Для синхронизации сценарии выполняются с повторами и разным порядком доставки, включая конкурирующие перестановки и решения конфликтов, создание объектов при удалении контейнера, очистку и возврат долго отключённого устройства. Критерии одинаковы для общего API и интерфейса на обеих платформах; механизмы и конкретный набор данных определяются в будущем плане.

1. Без интернета на каждой платформе создаются пространство, колонка и карточка; текст сохраняется и остаётся после перезапуска.
2. Отметка выполнения ставится и снимается в любой колонке одинаково через интерфейс и агентский API.
3. Изменения с двух устройств доставляются после восстановления связи. Повтор обмена не создаёт дубликатов.
4. Разные независимые тексты одной карточки сохраняются; конфликт можно разрешить на любой платформе и через API.
5. При обрыве во время сохранения или обмена приложение не сообщает ложный успех и корректно продолжает работу. Для создания и всех изменений карточки, а также обычных действий с колонками/пространствами (создание, переименование, порядок колонок, отправка в корзину и восстановление из неё) проверить потерю запроса до выполнения и ответа после выполнения: ограниченные автоматические, затем ручной повтор сохраняют идентификатор, операцию, цель, параметры и исходные предусмотренные условия актуальности. Одна команда выполняется один раз; повторы не добавляют карточку, побочное действие, версию истории, границу серии или группу удаления. Уже выполненная команда возвращает прежний результат и сохраняет более новые правки, включая последующее снятие выполнения после старой команды установить его; клиент не заменяет актуальное состояние старым результатом. Если первая доставка не выполнилась, а карточка изменилась другим клиентом, повтор с исходным условием отклоняется по ADR-0007/ADR-0014 без автоматической подстановки свежей версии. Проверить параллельные доставки, отказ при изменённых параметрах того же идентификатора, согласованную запись данных и результата при сбое, права возврата результата и запрет автоматического повтора явных отказов. После исчерпания попыток без подтверждения показываются неизвестный результат и кнопка «Повторить» с той же командой; API/CLI дают равнозначные состояние и действие. Охват Windows/Android, общий контракт P03 и клиент P05; обрывы входят в A05/P06. Перезапуск и истечение срока сведений о команде проверяются по контракту P03 без незаметного нового выполнения. Для восстановления версии одна логическая команда даёт одну новую версию, повтор доставки не создаёт ещё одну; ADR-0008/ADR-0013. Для колонки и пространства проверить также позднейшее переименование, перестановку или восстановление после выполненного удаления: повтор возвращает исходный результат и сохраняет эти поздние изменения. Повтор создания не создаёт дубликат контейнера; повтор отправки в корзину после восстановления не удаляет объект заново.
6. Удалённые объекты восстанавливаются вместе с необходимыми связями. Корзина не очищается автоматически: объекты хранятся до явной окончательной очистки. Через интерфейс и агентский API на обеих платформах можно очистить выбранные объекты либо всю корзину одного пространства; другие пространства не затрагиваются. Перед очисткой показывается состав. Очистка колонки или пространства охватывает все их вложенные объекты, ещё находящиеся в корзине, включая удалённые раньше контейнера; активные объекты и уже восстановленные в другую колонку карточки сохраняются. Нерешённый конфликт в любом выбранном или вложенном объекте останавливает всю операцию без частичного удаления и возвращает список конфликтов; после их разрешения очистку запускают заново. После очистки старое устройство не возвращает их незаметно.
7. Клиент читает карточку, затем другой клиент меняет её заголовок, описание, теги, выполнение, положение на доске или состояние «активна/в корзине». Подготовленная ранее команда изменения карточки отклоняется с понятной причиной и указанием перечитать карточку и подготовить действие заново. Проверить общую матрицу применимых случаев: редактирование заголовка/описания, назначение/снятие тегов, установка/снятие выполнения, перемещение/порядок, отправка в корзину, восстановление из корзины и восстановление версии. Включить оба симметричных случая изменения текстовых полей, назначение и снятие тега, установку и снятие выполнения, перенос в другую колонку, изменение порядка и пример «новые пункты в описании → старая команда отметить выполненной». Отказ сохраняет все текущие данные, историю и введённый текст клиента без нового конфликта, ложной версии или успеха. После перечитывания карточки и подготовки нового действия допустимая команда проходит, если проверяемые данные снова не изменились. Чтение, фиксация серии истории без изменения данных этой карточки и изменение другой карточки сами по себе не вызывают отказа. Два параллельных запроса из одного прочитанного состояния, реально изменяющие карточку, не обходят общую проверку; после первого изменения второму требуется перечитывание. Общий контракт проверяется в T06/P03, интерфейс и паритет Windows/Android через HTTP/CLI/Android-адаптер — в A07/P05; независимые уже сохранённые изменения при синхронизации проверяются отдельно. Состав видимых версий остаётся заголовком и описанием; ADR-0007/ADR-0013.
8. В форме выдачи доступа агенту к выбранным пространствам по умолчанию выбрано чтение; до подтверждения выдачи разрешение не создаётся. Выданное чтение позволяет изучать данные, но отклоняет создание, изменение, перемещение и удаление объектов. Чтение и изменение включаются явно. Срок обычного доступа по умолчанию — «До отзыва»; при выдаче можно выбрать ограниченный срок. Проверить доступ до истечения, прекращение доступа после него, необходимость нового явного разрешения для продолжения и возможность раннего отзыва. Форма передаёт выбранные режим и срок в общий API. Отключение устройства или агента прекращает его разрешённый доступ; смысл уже имеющихся локальных копий явно описан. Административный доступ агента для управления устройствами и правами можно выдать и отозвать отдельно от чтения и изменения пространств. Обычные права записи не разрешают административные операции. Проверки одинаковы для человека и агента на обеих платформах; режим формы и проверку API проверить отдельно.
9. Из одной SQLite-базы устройства логически создаётся снимок полного состояния выбранного пространства: текущие данные, корзина, вся пользовательская история, нерешённые конфликты и необходимые сведения восстановления. Автоматическая резервная копия восстанавливает исходное пространство к состоянию выбранного снимка и сохраняет остальные пространства одинаково через интерфейс и агентский API на обеих платформах. После восстановления обмен этого пространства приостановлен до явной команды возобновления; перезапуск приложения сохраняет паузу. Состояние паузы и команда возобновления доступны человеку и агенту. После возобновления восстановление передаётся как новое действие: независимые правки второго устройства сохраняются, совместимые объединяются, несовместимые становятся конфликтами. Последний страховочный снимок перед восстановлением хранится отдельно от ежедневных и предмиграционного; заменяется после следующего успешного восстановления, а при неуспешной попытке сохраняется. Несовместимое обновление не повреждает единственную копию.
10. Все действия доступны на Android без зависимости от перетаскивания, постоянного ПК и постоянного фонового процесса.
11. После закрытия вкладки Windows разрешённый агентский запрос и обмен с доступным телефоном продолжают обслуживаться до явного завершения приложения.
12. История не сокращается автоматически по возрасту или числу версий. Ручная очистка не повреждает текущую карточку, нерешённые конфликты и синхронизацию.
13. После успешного создания восьмого ежедневного снимка одного пространства остаются последние 7 его ежедневных копий; копии остальных пространств не затрагиваются. Если после предыдущего успешного ежедневного снимка данные не менялись, новый снимок не создаётся и прежние копии сохраняются без ротации. При сбое создания новой копии предыдущие исправные снимки сохраняются. История в рабочем хранилище от ротации не меняется. При выполнении условий частоты/изменений первая подходящая возможность запускает копию: при старте с накопленными правками, после первого сохранённого изменения или при наступлении следующего разрешённого момента без перезапуска. Проверить первый снимок нового пространства, повторный запуск после успеха, параллельные проверки без лишнего снимка и изменение во время записи с сохранением ещё не скопированных данных для следующей копии. Ошибка не отмечает успешный снимок, после доступности выбранной папки действуют согласованные повторы; пропущенные дни не восполняются. Windows/Android, состояние через общий API; T10/A13 в P07, ADR-0015. Проверить успешные снимки в 23:50 и 00:10 следующего календарного дня устройства при новых изменениях, отказ дополнительной копии в ту же локальную дату после успеха даже после перезапуска, повтор после ошибки без занятия дневного лимита и новый день без изменений без копии/ротации. Локальная дата, включая её отличие от UTC-даты, определяется отдельно на каждом устройстве; копия на ПК не занимает лимит телефона. Обработка изменения часов/пояса и пересечения полуночи при записи проверяется технически в P07. После ошибки из-за недоступной выбранной папки следующий автоматический повтор — через 5 минут от завершения неудачной попытки; ошибка не занимает дневной лимит, календарная частота/изменения сохраняются. Пауза и сведения об ошибке проверяются также по сценарию 43/A43. «Повторить сейчас» после ошибки также сохраняет дневной лимит и условия изменений; ручной успех считается обычным ежедневным снимком, сценарий 43/A43.
14. При независимых удалении и правке одной карточки сохраняется правка и появляется конфликт. Оба варианта решения — оставить в корзине или восстановить с изменениями — доступны через интерфейс, HTTP и CLI и сходятся после обмена.
15. Восстановление колонки или пространства возвращает только объекты, удалённые тем же действием. Ранее удалённая карточка остаётся в корзине после восстановления и повторной синхронизации. Для восстановления отдельной карточки из пространства в корзине сначала явно восстанавливается пространство по этому правилу; при необходимости карточка восстанавливается отдельным действием после этого. Последовательность одинакова для интерфейса и агентского API на обеих платформах.
16. Очистка общей истории выполняется без доступности второго устройства, применяется на нём после обмена и не меняет уже созданные резервные копии. Независимо созданная новая версия сохраняется. Повторная доставка старых данных не должна возвращать очищенные версии в обычную историю.
17. Проверки сборки Windows и Android применяют запрет unsafe к собственным пакетам ядра, хранения и синхронизации. Необходимые платформенные исключения изолированы и имеют отдельное обоснование; выбранная оболочка сохраняет эту границу.
18. Заголовок и текст сохраняются автоматически. Статус «сохранено» подтверждает последнюю локально записанную правку и не зависит от доступности другого устройства. Проверяются быстрый ввод, ответы в обратном порядке, ошибка записи и временно пустой заголовок.
19. Обычный поиск начинается в активном пространстве; переключение расширяет область до всех локальных пространств. Поиск не учитывает регистр: запрос «работа» находит «Работа» и «РАБОТА» одинаково через интерфейс и агентский API на обеих платформах. Буквы «е» и «ё» различаются: «елка» не находит «ёлка» и наоборот, а «ЁЛКА» находит «ёлка». Исходное написание текста сохраняется. Одиночный запрос совпадает с любой частью слова в заголовке или текущем тексте: «план» находит «план», «ПЛАНИРОВАНИЕ» и «перепланировка». Запрос из нескольких слов ищется как один непрерывный фрагмент без учёта регистра: «купить молоко» находит «Нужно купить молоко сегодня», но не «Купить вечером молоко» и не «Молоко купить». Пробелы по краям запроса обрезаются. Внутри фразы пробелы, табуляция и переносы строк совпадают точно: запрос с одним пробелом не совпадает с двумя пробелами, табуляцией или переносом строки между словами; запрос с тем же внутренним разделителем совпадает. Текст карточки поиском не изменяется. Фрагмент целиком должен находиться в заголовке либо текущем тексте и не составляется из разных полей или конфликтующих вариантов. Вызов агента не возвращает данные пространств вне его доступа. При нерешённом конфликте заголовка или текста совпадение с любым сохранённым конфликтующим вариантом находит карточку; совпадения с несколькими вариантами дают один результат с отметкой конфликта. Правила части слова и непрерывного фрагмента проверяются также для конфликтующих вариантов. Пустая строка, ввод одних обычных пробелов и очистка ранее непустого запроса снимают текстовое условие и возвращают все доступные карточки выбранной области. Проверить активное пространство и все локальные пространства без самопроизвольного переключения области, ограниченные права агента, отсутствие доступных карточек и один результат на карточку с конфликтующими текстами. Данные карточек не меняются. Пунктуация и специальные символы ищутся буквально, без масок, регулярных выражений или операторов: «C++» совпадает с «C++», но не с «C»; «план*» — с «план*», но не с «планирование». Кавычки входят в искомый фрагмент; фраза с кавычками не совпадает с фразой без них. Проверить одиночную кавычку, «%», «_», «?», скобки и обратную косую черту без ошибки поискового синтаксиса и без их трактовки как масок. Правило проверяется также для конфликтующих текстов. Для непустого и пустого после обрезки запроса результаты в одном пространстве следуют сохранённому порядку колонок, затем карточек внутри них; при поиске по всем локальным пространствам сначала идут пространства с конфликтующим названием в группе «Конфликты названий», затем остальные по именам. Проверить несколько колонок с ручным порядком карточек и несколько пространств с разными именами, последующий поиск после сохранённой перестановки колонок/карточек, одинаковый порядок через интерфейс и общий API. Использовать данные, у которых ручной порядок отличается от алфавитного порядка заголовков и времени изменения. Карточка с конфликтующим текстом и однозначным местом возвращается один раз на этом месте с отметкой конфликта. При конфликте перемещения карточки, её порядка в одной колонке или позиции колонки найденные карточки показываются один раз в группе «Конфликты» перед обычными результатами своего пространства. Проверить фильтрацию группы по запросу/области/правам, отсутствие дубликатов по спорным позициям, непустой и пустой запросы, поиск в одном и во всех пространствах через интерфейс и общий API на обеих платформах. После полного разрешения места карточки и колонки подходящая запросу карточка возвращается в обычный порядок; при оставшемся конфликте места остаётся в группе. Группировка не меняет сохранённые позиции и согласованные правила блокировки собственных конфликтов. Проверить список пространств и поиск везде с группой «Конфликты названий» перед остальными пространствами по именам, один объект с доступом ко всем сохранённым вариантам названия, возврат в обычный порядок после разрешения названия. Поиск показывает спорное пространство только при наличии доступных найденных карточек; проверить ограничения прав и отсутствие совпадений. При одновременном конфликте места карточки её группа «Конфликты» остаётся внутри своего пространства и сохраняется после разрешения только названия пространства. Сохранить данные, согласованные блокировки контейнера и работу с содержимым. Устойчивый порядок при одинаковых именах и внутри групп проверяется после технического выбора.
20. «Работа», «работа» и вариант с пробелами по краям обозначают один тег внутри пространства. В другом пространстве такой тег независим. После обмена двух независимо созданных вариантов не теряются связи с карточками. «Все» и «Всё» — разные имена: оба тега могут существовать в одном пространстве с независимыми идентификаторами и назначениями. «ВСЁ», «Всё» и вариант с краевыми пробелами обозначают одно имя. Проверить общие правила через интерфейс и API на Windows/Android, сохранение обоих тегов/назначений после перезапуска и обмена.
21. Несколько локальных автосохранений в одной непрерывной серии одного участника не создают отдельную видимую версию на каждый запрос. При завершении редактирования, существенной паузе (30 секунд без новых правок заголовка или описания) или смене участника появляется версия завершённой серии. Для паузы проверить на управляемом отсчёте: при 29 секундах без других границ серия остаётся открытой; новая правка до 30 секунд продолжает её и запускает новый отсчёт. По достижении 30 секунд без новых правок серия завершается одной видимой версией, дальнейший ввод начинает новую. Длительное отсутствие правок не создаёт дополнительных версий; чтение и повторные автосохранения неизменившегося содержимого не сдвигают границу. Проверить заголовок и описание через общий контракт на обеих платформах; частота автосохранения остаётся отдельным параметром. Последовательные успешные изменения текста «человек → агент → человек» без существенных пауз создают три раздельных этапа; после фиксации последнего этапа доступен текст каждого. Новая серия человека не поглощает его прежнюю серию или этап агента. Проверить несколько автосохранений внутри каждого этапа, чтение другим участником и отклонённое устаревшее сохранение без ложной границы/версии, общий результат интерфейса/HTTP/CLI на Windows/Android, перезапуск после фиксации версий и передачу общей истории на другое устройство. Две отдельные команды одного агента подряд, добавляющие абзац и исправляющие формулировку, дают две видимые версии с промежуточным и итоговым текстом сразу после успешного сохранения каждой команды. Для той же дискретной команды человека действует то же правило. Проверить регрессию группировки автосохранений непрерывного ввода, перезапуск, обмен историей, отказ сохранения без ложной версии и отсутствие дополнительной пустой версии при сочетании смены участника и отдельной команды. Ошибка записи не оставляет версию без соответствующей сохранённой правки или успешный результат без его версии. Проверить изменение только заголовка с неизменным описанием, только описания с неизменным заголовком и обоих полей одной командой: каждая версия содержит соответствующую пару из одного сохранённого состояния, одна команда создаёт одну версию независимо от числа изменённых полей. Две отдельные команды переименования дают две версии. Прежние заголовок и описание доступны для просмотра и восстановления после перезапуска и обмена через общий API на обеих платформах. Группировка непрерывного ввода и граница при смене участника применяются также к заголовку; временно пустой обязательный заголовок и ошибка записи не создают ложную версию и не меняют последнюю успешно сохранённую пару с её историей. После нескольких успешных автосохранений принудительно завершить вкладку Windows или APK Android до штатного завершения серии. Быстро перезапустить: последние сохранённые заголовок и описание доступны в одной видимой версии прежней серии. Дальнейший ввод тем же участником начинает новую серию; после её завершения обе версии доступны отдельно. Проверить повторные перезапуски без ввода, уже завершённую серию и сбой во время фиксации границы без дубликатов или пустых версий; сохранность более новых правок другого клиента и передачу истории через общий API. Риск потери несохранённого ввода с пустым обязательным заголовком не расширяется, сценарий 33 сохраняется.
22. Отдельная карточка из удалённой колонки восстанавливается в выбранную активную колонку того же существующего пространства. Исходная колонка остаётся в корзине. Повторная синхронизация и последующее восстановление исходной колонки не создают дубликат и не перемещают карточку обратно.
23. Независимые изменения заголовка и текста одной карточки объединяются автоматически, а разные независимые изменения одного поля доступны для ручного разрешения. Проверяется одинаковый результат при разном порядке и повторной доставке сообщений.
24. Удаление колонки или пространства против независимой правки карточки внутри создаёт конфликт с сохранением правки. Оба варианта решения доступны через интерфейс и API, сохраняют корректность иерархии и дают одинаковый результат после обмена.
25. Полный экспорт и импорт сохраняют колонки, карточки, теги, корзину, историю и связи в новом независимом пространстве. Исходное пространство от импорта не меняется. Предлагаемый дополнительный сценарий: изменение импортированной карточки не изменяет исходную через прежнее подключение синхронизации и не выдаёт прежнему агенту доступ к новой копии.
26. Агент обращается с ПК напрямую к открытому APK по HTTP через Tailscale, видит разрешённые локальные данные телефона до синхронизации и может изменять их при наличии права записи. Чтение вне разрешённых пространств, запись с правом только чтения и обращение после отзыва доступа отклоняются. Закрытие APK даёт понятную ошибку недоступности, если сервер больше не работает.
27. Трей Windows и CLI открывают интерфейс и завершают один и тот же процесс приложения. Закрытие браузерной вкладки сохраняет работу процесса. Завершение не повреждает уже записанные данные и сведения о текущем обмене.
28. Для пространства обычная ротация сохраняет 7 ежедневных копий и не удаляет отдельный последний снимок перед миграцией. Прежний страховочный снимок заменяется после следующей успешной миграции; неудачная миграция не удаляет его.
29. Окончательное удаление пространства сохраняет локальные автоматические копии. Удалить их можно отдельным явным действием через поддержанный интерфейс и API. Ручные экспорты и копии других пространств не затрагиваются.
30. Переименование тега в нормализованное имя другого существующего тега того же пространства возвращает понятную ошибку без изменения обоих тегов и их связей. Отдельные одноимённые теги в разных пространствах не мешают переименованию. При свободном имени переименование «Все» в «Всё» допустимо и сохраняет идентификатор и назначения. Если имя «Всё» уже занято другим тегом, варианты «ВСЁ» и с краевыми пробелами также считаются занятыми; отказ не меняет теги и назначения. Проверить одинаковое сравнение в интерфейсе и общем API обеих платформ.
31. Очистка истории работает для одной карточки и для всего пространства, показывает область и объём и сохраняет текущее содержимое, конфликты и независимые новые версии. Агент с правом записи в одном пространстве не может этой командой очистить историю другого. Операция уровня пространства не удаляет историю позднее полученной независимой карточки.
32. Удаление назначенного тега снимает его со всех карточек соответствующего пространства без удаления карточек или текста. Карточки и независимый одноимённый тег другого пространства сохраняются. Тег не появляется в корзине; отдельного восстановления удалённого тега нет. Повторное создание тега с тем же именем не возвращает прежние назначения. Полное восстановление пространства из снимка, созданного до удаления тега, возвращает тег и назначения из снимка. Повторный запрос и повторный обмен не создают некорректные связи. Правило проверяется на обеих платформах через интерфейс, HTTP и CLI; независимое назначение с другого устройства обрабатывается по сценарию 40.
33. При временно пустом обязательном заголовке интерфейс сообщает о несохранённом состоянии и предупреждает при обычном уходе. До успешной записи нельзя показывать «сохранено». Проверка принудительной остановки не требует восстановления этого несохранённого ввода, но должна подтверждать сохранность последней успешно записанной версии.
34. Первая версия предоставляет текстовый поиск в выбранной области. Фильтры по тегам и выполнению и скрытие выполненных карточек относятся к последующим расширениям; выполненная карточка сохраняет своё место на доске.
35. Ручное изменение порядка колонок и карточек сохраняется после перезапуска и передаётся на другое устройство. Повторный обмен сохраняет согласованный порядок; конкурирующие изменения обрабатываются по правилам проектируемого протокола без потери объектов.
36. Основные пользовательские сценарии проверяются отдельно в Google Chrome и Opera на Windows 11 и в APK на целевом Android-устройстве. В отчёте указываются версии браузеров и WebView, условия и результаты.
37. Windows-приложение устанавливается из загруженного с GitHub EXE-установщика, созданного Inno Setup, только для текущей учётной записи без запроса прав администратора и запускается вручную ярлыком, обслуживает локальный сервер и открывает браузерный интерфейс. Установка для всех пользователей ПК в первую версию не входит. При уведомлении о новой версии пользователь самостоятельно скачивает и запускает установщик обновления в том же режиме текущего пользователя; данные сохраняются, перед миграцией создаётся страховочная копия. Проверка выполняется и из обычной учётной записи без административных прав; средство удаления доступно по согласованным правилам хранения пользовательских данных, которые ещё уточняются отдельно. Первая версия не требует настройки автозапуска ОС; ADR-0017.
38. Независимое перемещение одной карточки в разные колонки сохраняет оба варианта и создаёт конфликт. Выбор колонки доступен на Windows и Android, через интерфейс, HTTP и CLI. После обмена устройства сходятся к выбранной колонке без дублирования карточки, включая повторную доставку изменений.
39. Независимые добавления разных тегов одной карточке автоматически сохраняют оба назначения. Проверяются разный порядок и повторная доставка изменений; существующие назначения не теряются.
40. Удаление самого тега против его независимого назначения карточке создаёт явный конфликт и сохраняет варианты до решения. Оба решения — сохранить тег с назначениями либо подтвердить удаление со снятием назначений — доступны на обеих платформах и через API. Карточки и текст сохраняются; повторный обмен приводит к одинаковому результату без некорректных связей.
41. Перетаскивание карточек между колонками, изменение порядка карточек и колонок работают в браузерном интерфейсе Windows и в APK на Android. Прокрутка и жесты не мешают переносу; явные команды интерфейса, HTTP и CLI выполняют те же операции.
42. Смена папки автоматических копий и возврат к каталогу по умолчанию одинаково доступны на Windows и Android через интерфейс и общий API в пределах выданных прав. Существующие ежедневные и страховочные снимки, включая копии удалённых пространств, копируются и проверяются до переключения; исходные копии удаляются после сохранения нового расположения. Ошибка до переключения сохраняет прежнее расположение и исходные копии; ошибка удаления после переключения сохраняет новое расположение и проверенные копии и явно отображается. Сбои между этапами и перезапуск не приводят к потере исправных копий. Посторонние файлы, состав снимков и лимиты хранения не изменяются самим переносом.
43. Недоступность выбранной папки автоматических копий отображается как ошибка через интерфейс и общий API на обеих платформах; обычная работа с пространствами продолжается. При работающем приложении следующая автоматическая попытка ежедневной копии в выбранную папку выполняется через 5 минут после завершения неудачной, без автоматического переключения; после новой ошибки отсчёт начинается заново. Неуспешная попытка не обновляет последний успешный снимок и не запускает ротацию. После возврата доступа снимки создаются по согласованным правилам частоты и изменений без восполнения пропущенных дней. На управляемом отсчёте проверить отсутствие автоматического повтора при 4:59 и следующую попытку при 5:00 при выполненных условиях частоты/изменений. Новые правки и автоматические повторные события не обходят паузу и не создают параллельных попыток. Проверить возобновление ожидания после перезапуска, повтор после восстановления доступа и соблюдение дневного лимита после успеха; T10/A13/A43 в P07, ADR-0015. До истечения 5 минут после восстановления доступа выполнить «Повторить сейчас» через интерфейс/HTTP/CLI: нужная копия запускается досрочно. При отсутствии изменений, занятом дневном лимите или недостаточных правах новой попытки нет; при уже выполняющейся копии возвращается её состояние. Повторная доставка одного явного запроса и совпадение с автоматическим таймером не дублируют попытку или снимок. Если ручная попытка вновь завершилась ошибкой доступа, следующая автоматическая попытка — через 5 минут от её завершения; прежний таймер не обходит новое ожидание. Ручной успех учитывается как обычный ежедневный снимок, далее действует обычное планирование; Windows/Android, T10/A13/A43, ADR-0015.
44. Перед миграцией базы или восстановлением существующего пространства в выбранной папке создаётся и проверяется новый страховочный снимок текущего состояния. Недоступность папки, ошибка записи или проверки останавливает операцию до изменения исходного состояния этой операцией. Прежний страховочный снимок сохраняется и не подменяет новый; автоматического сохранения в другую папку нет. Причина отказа одинакова для интерфейса и общего API на Windows и Android. Отдельное исключение при восстановлении в новую установку после переустановки без текущего состояния пространства проверяется в сценарии 59 и не отменяет страховочные копии миграции.
45. После установки обновления необходимая миграция автоматически запускается при первом запуске новой версии без отдельной команды или подтверждения. Обязательные проверки и новый проверенный страховочный снимок предшествуют изменению схемы; при невозможности их выполнить миграция не начинается и возвращается причина. Обычные операции новой версии с этой базой доступны после успешного завершения требуемой миграции одинаково через интерфейс и общий API на Windows и Android.
46. Старая версия приложения с более новой схемой базы, которую она не поддерживает для записи, отказывает в открытии и предлагает установить подходящую новую версию. Схема, пользовательские данные и служебные записи сохраняются без изменений; режим чтения такой схемы и автоматический откат не выполняются. Одинаковая причина отказа доступна через интерфейс и общий API на Windows и Android.
47. Разные версии ZeDone на Windows и Android синхронизируются в явно поддержанных и проверенных сочетаниях протокола и формата данных с сохранением данных и согласованных правил конфликтов. Отказ не основывается только на различии номеров версий приложения. Совместимость обмена проверяется отдельно от способности приложения открывать определённую локальную схему базы; поддержанные сочетания и результаты проверок фиксируются в документации. Интерфейс и общий API используют одну проверку совместимости.
48. При несовместимости протокола или формата данных локальная работа продолжается, изменения сохраняются до обмена. После устранения несовместимости и успешной проверки при доступном соединении обмен возобновляется автоматически без отдельной команды. Для пространства с явной паузой после восстановления входящий и исходящий обмен остаётся приостановленным до отдельной команды, в том числе после обновления и перезапуска приложения. Причина остановки и состояние явной паузы различимы через интерфейс и общий API на обеих платформах.

49. На ПК и телефоне без связи независимо создаются одноимённые теги одного пространства, например «Работа» и «работа», и назначаются разным карточкам. После обмена на обоих устройствах автоматически остаётся один тег со всеми назначениями, без ручного конфликта из-за самого создания. Проверяются также имена с пробелами по краям, назначение обоих исходных тегов одной карточке, повторы и перестановки доставки: дубликаты тегов и назначений не появляются. Одноимённые теги других пространств независимы; обычное переименование в занятое имя по-прежнему отклоняется. Другие конфликты обрабатываются по своим согласованным правилам. Поведение одинаково для интерфейса, HTTP и CLI на Windows и Android; ограниченный прототип выбранного Automerge проверяет этот сценарий. Для независимо созданных «Все» и «Всё» после обмена сохраняются два тега с их идентификаторами и назначениями, без слияния и конфликта только из-за этих разных имён. Независимо созданные «Всё» и «ВСЁ» объединяются по общему правилу без потери назначений. Проверить оба случая с повторами, перестановками доставки и перезапуском. Для вариантов «РАБОТА»/«Работа» отображаемое имя должно быть одним из этих исходных написаний, одинаковым на устройствах при одном наборе изменений независимо от порядка и повторов доставки, в том числе после перезапуска. Этот набор отличает сохранение исходного варианта от принудительного нижнего регистра. Проверить последующее переименование через интерфейс и общий API, включая смену только регистра, с сохранением назначений. Повторная доставка уже учтённых изменений объединения не отменяет последующее переименование.

50. На Windows и Android одинаково отображается базовый CommonMark: заголовки, выделение, списки, ссылки, цитаты и блоки кода. Исходный текст сохраняется без удаления маркеров таблиц и текстовых чекбоксов; расширения таблиц и интерактивные чекбоксы не добавляются, такие строки отображаются по базовым правилам. Маркеры не меняют отметку выполнения карточки. Человек и агент читают и изменяют тот же Markdown через общие операции; форматированный просмотр остаётся производным представлением. Пользовательская HTML-разметка отображается буквально вместе с тегами, не интерпретируется и не выполняется; обычное форматирование Markdown продолжает работать, исходный текст сохраняется. Обычные HTTP/HTTPS-ссылки открываются только по нажатию вне ZeDone: в отдельной вкладке браузера на Windows и во внешнем браузере на Android; экран ZeDone не заменяется сайтом. Удалённое изображение до отдельного нажатия не загружается и показывается описанием или заглушкой. До нажатия нет запросов на изображения, включая этапы парсинга и очистки HTML; после нажатия внутри карточки загружается только выбранное изображение. При ошибке сети доступны понятное сообщение и повтор, исходный Markdown сохраняется, работа с карточкой продолжается. Правила одинаковы на Windows и Android.

51. При настроенном Tailscale ПК создаёт приглашение и показывает QR-код; телефон считывает его и запрашивает подключение. На ПК появляется запрос, телефон показывает ожидание. До явного подтверждения на стороне ПК телефон не считается подключённым и не начинает обмен пространствами; код сам по себе не даёт права подтвердить собственный запрос. После подтверждения процесс подключения продолжается. Пространства выбираются явно, способ подключения не открывает остальные пространства. При недоступной камере или отказе от её использования тот же процесс доступен через ручной ввод адреса ПК в Tailscale и одноразового кода. Приглашение, запрос и подтверждение подключения доступны также через общий API/CLI с необходимыми правами без обязательной камеры; прикладные результаты и права совпадают. Незавершённое подключение можно отменить, запрос на ПК — отклонить, подключённое устройство — отвязать по общим правилам. Проверить одноразовость кода; срок действия и технические проверки устройства принимаются по контракту P03. Для обоих способов проверить ожидание, отсутствие подключения и обмена до подтверждения, подтверждение и отказ на ПК и права подтверждающего. QR-сканирование и ручной ввод в Android APK проверяются отдельно от API на Windows/Android. Проверить допустимую первую загрузку модели: без готовой модели/сети доступен ручной ввод, неготовность не выдаётся за неверное приглашение, после готовности можно повторить сканирование; ADR-0022. Генерацию qrcodegen, общее отображение SVG и точное чтение исходных данных выбранным сканером проверить в P01; ADR-0023.

52. В одном пространстве на обоих устройствах существуют разные теги «Работа» и «Личное» с назначениями карточкам. Без связи ПК переименовывает «Работа» в «Важное», телефон — «Личное» в «Важное»; локально новое имя свободно. После обмена показывается конфликт имён: оба тега, их идентификаторы и все назначения сохраняются, теги не сливаются и не переименовываются автоматически. До выбора разных имён спорные теги помечены; у карточки со спорным только именем тега доступны изменения заголовка, текста, статуса выполнения и колонки в пределах пространства. Назначение и снятие обоих спорных тегов приостановлены для всех карточек пространства; существующие назначения сохраняются. После допустимого разрешения имён назначение и снятие снова доступны. Пользователь через интерфейс или общий API явно выбирает разные имена, которые проверяются по общему правилу сравнения без учёта регистра и краевых пробелов с различием «е» и «ё». Занятые имена не завершают разрешение конфликта; после допустимого решения устройства сходятся к одинаковым тегам, именам и назначениям. Проверить сохранение допустимых правок карточки после перезапуска, обмена и разрешения имён; отказ в назначении и снятии спорных тегов через интерфейс и общий API, включая обращение по идентификатору, без изменения назначений; возобновление операций после допустимого разрешения. У карточки без собственных конфликтов остальные теги назначаются и снимаются по обычным правилам; отдельная проверка карточки с собственным конфликтом подтверждает общую блокировку редактирования. Проверить назначения обоих спорных тегов одной карточке, повторную доставку, разный порядок сообщений, перезапуск и сохранность нерешённого конфликта. Независимое создание одноимённых тегов по сценарию 49 по-прежнему объединяется автоматически, обычное переименование в известное занятое имя по сценарию 30 по-прежнему отклоняется. Правила одинаковы для интерфейса, HTTP и CLI на Windows/Android; сценарий входит в ограниченный прототип Automerge в P02 и полную приёмку P06. При отсутствии этих имён у других тегов пара «Все»/«Всё» допустима для разрешения коллизии; пара «Всё»/«ВСЁ» остаётся одним именем и конфликт не разрешает. То же сравнение применяется в сценарии 53.

53. В одном пространстве на обоих устройствах существует тег «Работа» с назначениями карточкам, имя «Важное» свободно. Без связи ПК переименовывает «Работа» в «Важное», телефон создаёт новый тег «Важное» и назначает его карточкам. После обмена показывается явный конфликт имён; существовавший и новый теги, их идентификаторы и все назначения сохраняются. Автоматического объединения, добавления суффиксов или потери назначений нет. Пользователь явно выбирает разные имена с проверкой общей уникальности; недопустимый выбор не завершает конфликт. Для доступных действий применяются правила сценария 52: при спорном только имени тега доступны изменения заголовка/текста/статуса выполнения/колонки карточки, назначение и снятие обоих спорных тегов приостановлены до выбора разных имён, затем возобновляются; собственные конфликты карточки сохраняют блокировку. Проверить повторную доставку, разный порядок сообщений, перезапуск и сохранение нерешённого конфликта, сохранность назначений и допустимых правок карточек после решения, одинаковый итог на устройствах. Назначения нового тега, сохранённые без связи до обнаружения коллизии, не теряются из-за последующего запрета назначения/снятия. Проверить регрессию сценариев 30, 49 и 52. Правила одинаковы для интерфейса, HTTP и CLI на Windows/Android; сценарий входит в прототип Automerge P02 и полную приёмку P06.

54. Создать версии карточки 1, 2 и 3 с различающимися заголовком и описанием. Восстановление первой записывает её заголовок и описание как новую правку и сразу даёт видимую версию 4; версии 1, 2 и 3 остаются доступными без изменения. Восстановление третьей затем создаёт версию 5 с её содержимым и возвращает состояние до первого восстановления, сохраняя версии 1–4. Восстановление не объединяется с соседним непрерывным вводом. Проверить результат через интерфейс, HTTP и CLI на Windows/Android, перезапуск и передачу истории на другое устройство как новой правки без удаления промежуточных версий. Действуют общие права и применимые проверки актуальности и конфликтов. При отказе или ошибке записи текущая карточка и прежняя история сохраняются, новая версия не появляется. Общий API проверяется в P04, паритет в P05, обмен в P06; ADR-0013. При потере ответа на восстановление автоматические и ручной повторы той же команды возвращают её результат без новой версии и без отмены позднейших правок; ADR-0008.

55. На одном работающем устройстве клиент читает колонку с тремя активными карточками. Другой клиент добавляет четвёртую; первая команда отправки колонки в корзину по прежнему составу отклоняется целиком. Колонка, все четыре карточки, их связи и история сохраняются без нового конфликта, версии истории или ложного успеха. Клиент показывает актуальный состав и данные колонки с карточками; после перечитывания и нового явного действия допустимое удаление проходит и остаётся обратимым через корзину. Проверить также удаление/перенос карточки из колонки, перенос/восстановление в неё и замену при прежнем количестве: проверяется набор карточек, а не только число. При неизменном наборе отдельно изменить заголовок/описание, теги, выполнение или порядок одной карточки, название или положение самой колонки: старая команда также отклоняется целиком. Включить пример с дописанным описанием одной из прежних трёх карточек; отказ сохраняет эту правку и все остальные данные. Чтение, техническая фиксация серии истории без изменения проверяемых данных и изменение другой колонки, не затрагивающее это состояние, не вызывают такого отказа. Новое изменение проверяемого состояния после перечитывания снова отклоняет команду; параллельное добавление или изменение данных между проверкой и удалением не обходит условие. Охват интерфейса/HTTP/CLI на Windows/Android: контракт T06/P03, операции P04, паритет A55/P05. Независимые сохранённые изменения на разных устройствах и окончательная очистка корзины сохраняют отдельные правила; ADR-0014. При потере ответа на успешное удаление и последующем восстановлении автоматические и ручной повторы старой команды сохраняют восстановленный объект и прежние группы удаления без нового действия; ещё не выполненная команда проверяет исходное состояние по ADR-0014. ADR-0008/A05.

56. Клиент читает пространство, другой клиент того же ядра меняет данные пространства или содержимое, затем первый отправляет старую команду помещения пространства в корзину. По отдельности проверить добавление/удаление/восстановление колонки или карточки, изменение данных колонки, текста/тегов/выполнения/положения карточки, имени пространства и тегов пространства. Даже при прежнем наборе колонок и карточек команда отклоняется целиком без частичного удаления; все текущие данные, связи и история сохраняются без нового конфликта, версии истории или ложного успеха. Клиент показывает актуальное состояние; после перечитывания и нового явного действия допустимое удаление проходит. Чтение, техническая фиксация серии истории без изменения проверяемых данных и изменение другого пространства сами по себе не вызывают отказа. Проверить обычное восстановление пространства по прежним группам удаления: ранее удалённые объекты остаются в корзине. Контракт T06/P03, операции P04, паритет A56/P05 через интерфейс/HTTP/CLI на Windows/Android. Окончательная очистка и независимые изменения при синхронизации сохраняют отдельные правила; ADR-0014. При потере ответа на успешное удаление и последующем восстановлении автоматические и ручной повторы старой команды сохраняют восстановленный объект и прежние группы удаления без нового действия; ещё не выполненная команда проверяет исходное состояние по ADR-0014. 57. В чистой установке без прежней базы и настроек явно выбрать доступную папку с копиями нескольких пространств за разные даты. Восстановление выбранной копии требует отдельной явной команды и прежних проверок совместимости, целостности и прав. 58. В отчёте фиксировать контрольные данные и историю, открытые вкладки/экраны, набор процессов, метрику и единицы, учёт общей памяти, длительность/частоту замеров и версии ОС/браузера/WebView. Изолированный замер Rust-процесса или Java-кучи не подтверждает совокупный бюджет. Показатели эмулятора отдельно от целевого телефона; численность карточек в нагрузке не вводит продуктового лимита или автоматического удаления данных. Точная методика и контрольные наборы определяются до проверки; достигнутые показатели ещё не измерены. T05/T12/A61, P02/P09; ADR-0019.

62. На прототипе измерить стартовые ориентиры: открытие карточки, её перемещение или изменение отметки выполнения — до 300 мс; первые отображённые результаты поиска — до 1 секунды; первый рабочий экран после запуска — до 3 секунд. На ПК запуск самого браузера измеряется отдельно. Открытие завершается доступностью содержимого, изменяющая команда — подтверждённым сохранением и отображением результата, поиск — показом первых результатов; реакция кнопки сама по себе не считается завершением операции. Зафиксировать устройство, версии, состав и объём данных/истории, состояние запуска и фоновых операций, методику и результаты повторов. Показатели эмулятора отдельно от целевого телефона; ориентиры общие для Windows и Android. Это начальные цели прототипа, а не подтверждённая производительность или окончательные бюджеты выпуска. Дальнейшая работа направлена на уменьшение задержек с сохранением правил данных, памяти и общего API. T02/A62, P01; ADR-0020. При неполном срезе проверки оставшихся действий фиксируются отдельно, A62 не отмечается пройденным по неполному охвату.

63. В Windows-деинсталляторе проверить независимые выборы удаления рабочих данных текущей установки и её автоматических резервных копий. Первоначально оба выключены; без выбора данные сохраняются, выбор только рабочих данных не включает копии. Отказ от выбора или подтверждения не удаляет соответствующие данные. До очистки показывается её состав; при окончательной очистке явно предупреждается о потере возможности восстановления при отсутствии иных копий, затем требуется подтверждение. Окончательная локальная очистка разрешена как явное исключение из обратимости, последняя проверенная копия при выбранном полном охвате не сохраняется принудительно. Ручные экспорты, чужие файлы, данные других установок и устройств не затрагиваются, синхронизируемые команды удаления пространств не отправляются. Обычное обновление программы сохраняет данные и не выполняет очистку деинсталляции. Проверить общий прикладной путь очистки для человека/агента, права и паритет Android отдельно от платформенного удаления файлов программы. Охват управляемых копий/путей, сбои и согласование с работающим процессом ещё проектируются. T11/A63, P08; ADR-0021.

### Целевые устройства и нагрузка

Подтверждены Windows 11 с Google Chrome и Opera и контрольный ПК разработчика: AMD Ryzen 7 7700X, 8 ядер/16 логических процессоров, 64 ГБ установленной ОЗУ. Характеристики сообщены разработчиком; частота 4501 МГц приведена в исходном системном отчёте и не задаёт фиксированной частоты измерений. Целевой телефон — Samsung Galaxy A32 с Android 13 и 4 ГБ ОЗУ. Это контрольные устройства, а не установленная минимальная конфигурация всех поддерживаемых ПК или обещание поддержки всех более старых ОС/браузеров. Масштаб в тысячи карточек остаётся условным ориентиром, не продуктовым ограничением.

Подтверждено 2026-10-27: ОЗУ ZeDone не должна превышать 4 ГБ на ПК и 2 ГБ на Android, включая пиковый расход. На ПК учитываются Rust-сервер и браузерный интерфейс ZeDone, без других сайтов; на Android — всё приложение вместе с Rust и WebView. В границу входят пики синхронизации, создания копий и восстановления, а также обычная работа. Это верхние границы, не целевой обычный расход: инженерная цель — расходовать существенно меньше, особенно на телефоне с 4 ГБ общей ОЗУ. Точные счётчики, учёт общей памяти/процессов браузера и WebView, единицы и перевод в байты, контрольные наборы и частота/длительность измерений определяются до приёмки; численные потолки при этом не переоткрываются. [ADR-0019](decisions/0019-memory-budgets.md).

Подтверждено 2026-10-27: описания карточек часто представляют короткие заметки до 100 строк, иногда — длинный текст более 100 строк. Это ожидаемый профиль использования, не ограничение длины описания и не автоматическое основание обрезать текст. При подготовке конкретных наборов фиксируются также объём UTF-8, длина строк, используемая разметка и визуальные переносы; одно число строк не определяет объём данных.

Исходный инженерный вариант контрольных нагрузок для подготовки прототипа: 5 000 карточек в 10 пространствах с суммарно 50 колонками; дополнительные проверки 1 000 и 10 000 карточек для базовой нагрузки и оценки роста. Описания смешанные: короткие заметки до 100 строк и длинные тексты более 100 строк, с отдельными случаями длинной строки и большого текста. Сравниваются распределение по нескольким пространствам и рост одного большого пространства для проверки гипотезы одного документа Automerge на пространство. Это предложения условий измерения, не согласованные продуктовые пределы. История и корзина включаются отдельно, например набор с 10 версиями карточки и серия дальнейших правок для проверки роста; нерешённые конфликты и загруженные изображения фиксируются в составе нагрузки. Конкретные размеры больших текстов, доли коротких/длинных описаний, история и длительность серий ещё уточняются. Прежнее предложение среднего текста 2 КиБ не принято как профиль и не подменяет сообщённые разработчиком до/более 100 строк. Автоматическое удаление данных или продуктовый лимит числа исторических версий этим не вводятся.

На релизной сборке предлагается измерять:

- Время холодного запуска APK и открытия первого доступного для работы экрана. На ПК запуск локального процесса и загрузка страницы учитываются отдельно от запуска самого браузера.
- Отклик при открытии и редактировании карточки, перемещении и изменении отметки выполнения, включая работу при синхронизации и резервном копировании.
- Время поиска по всем локальным карточкам и время появления первых результатов.
- Память приложения вместе с процессами WebView, пиковую память при обмене и восстановлении, отсутствие устойчивого роста после повторных действий.
- Время первичной передачи пространства и последующего обмена небольшим числом изменений. Ожидание недоступного устройства не включается во время обработки доступного соединения.
- Рост дискового объёма текущих данных, истории, корзины и ротации резервных копий.

Предлагаемые меры: выдавать списки порциями, не загружать все тексты и всю историю для показа доски, не создавать сразу тысячи невидимых элементов интерфейса. Достаточность пагинации и необходимость виртуализации проверяются измерениями. Поиск, обмен и создание копий не должны блокировать редактирование.

Верхние границы ОЗУ приняты: 4 ГБ для ПК и 2 ГБ для Android вместе с интерфейсом и пиками. Для прототипа приняты первые ориентиры задержек: 300 мс на открытие/перемещение/отметку выполнения карточки, 1 секунда на первые результаты поиска и 3 секунды на первый рабочий экран; запуск самого браузера ПК учитывается отдельно. Эти значения служат исходными целями, в дальнейшем задержки должны быть как можно меньше; [ADR-0020](decisions/0020-prototype-latency-targets.md). Итоговые бюджеты выпуска, методика повторов и статистики времени, точная методика памяти и контрольные наборы ещё уточняются. Проверки выполняются на контрольных устройствах, результаты эмулятора отделяются от результатов целевого телефона. До измерений нельзя утверждать, что выбранный стек уже выполняет эти требования. Гипотеза одного документа Automerge на пространство должна пройти проверку роста отдельного пространства и истории в рамках этих границ; её выбор не подтверждает неограниченную производительность.

## 12. Открытые вопросы и передача агенту-планировщику

### Точка остановки мозгового штурма — 2026-10-26

Обсуждение остановлено по просьбе разработчика после согласования восьми решений о миграциях и аварийном восстановлении и десяти решений о синхронизации. Результаты зафиксированы в разделах 1.1 и 1.2. На момент остановки последним решением было сравнение двух ограниченных Rust-прототипов: модели причинных версий отдельных полей на готовых компонентах и Automerge для Rust. При продолжении обсуждения разработчик выбрал Automerge; прежнее сравнение заменено проверкой выбранной библиотеки, см. [ADR-0002](decisions/0002-automerge-sync.md).

Разработчик предпочёл дальнейшую проверку методом проб и ошибок. Следующий этап — ограниченные практические эксперименты с критериями результата. Полный опрос не возобновляется автоматически; оставшиеся темы сохраняются открытыми и уточняются по мере необходимости. Реализация приложения, прототипы синхронизации, сборки и измерения на момент остановки не выполнены. На тот момент основа синхронизации ещё не была выбрана; актуальное решение — Automerge для Rust с обязательной технической проверкой.

Карта блоков на момент остановки:

1. **Миграции и сбои — поведение согласовано, раздел 1.1.** Реализация, формат служебных записей, проверки прерываний и обработка снимков-кандидатов входят в будущий план. См. [организацию SQLite](sqlite-layout.md).
2. **Синхронизация — выбран Automerge для Rust, раздел 1.2 и ADR-0002.** Обязательная проверка выбранной библиотеки заменяет сравнение двух реализаций; модель данных, интеграция и техническая пригодность ещё проверяются. Коллизии имён тегов относятся к блоку 5.
3. **Устройства, права и общий API — частично согласовано.** Для всех изменений существующей карточки проверяется актуальность заголовка, описания, тегов, выполнения, положения и состояния активна/в корзине; устаревшая команда отклоняется с предложением перечитать карточку и подготовить действие заново; правило одинаково для агента и вкладок, введённый текст сохраняется в редакторе; ADR-0007. Отправка колонки или пространства в корзину по устаревшему составу или данным целевого контейнера с содержимым отклоняется целиком, после показа актуального состояния требуется новое явное действие; ADR-0014. Для команд карточки и обычных действий с колонками/пространствами при потере подтверждения согласованы ограниченные автоматические, затем ручной повтор той же команды без повторного действия/версии/группы удаления и отмены позднейших правок или восстановления; ADR-0008. Для подключения телефона к ПК при настроенном Tailscale выбраны QR-код на ПК и запасной ручной ввод адреса и одноразового кода; пространства выбираются явно; ADR-0009. Дополнительное подтверждение запроса на ПК обязательно. В форме выдачи доступа агенту по умолчанию выбрано чтение; изменения разрешаются явно при подтверждаемой выдаче, административные права отдельно. Обычный доступ по умолчанию действует до отзыва; при выдаче можно задать ограниченный срок, после истечения продолжение требует нового явного разрешения; ADR-0010. Открыты протокол подключения, техническая проверка устройства и сведения в запросе подтверждения, сроки и формат приглашения, учётные данные и их отзыв, детали отключения, границы администрирования, признаки версий, дополнительные предусловия конкретных операций и условия команд других объектов, параметры повторов и хранение их результатов. Отдельно определить права на полную копию и аварийное восстановление всей базы и проверку доступа при повреждении базы. Расширение ранее согласованного администрирования устройств и прав не утверждено.
4. **Редактирование и история — частично согласовано.** Смена участника разделяет этапы «человек → агент → человек» без долгой паузы; каждая отдельная прикладная команда изменения заголовка или описания фиксирует свою видимую версию при успешном сохранении, в том числе две команды одного агента подряд; автосохранения непрерывного ввода группируются. Каждая версия хранит заголовок и описание вместе из одного сохранённого состояния. Восстановление создаёт новую правку и видимую версию с выбранными заголовком и описанием, сохраняя всю прежнюю историю. После неожиданной остановки и перезапуска сохранённая серия завершается отдельной версией, дальнейший ввод начинает новую. Существенная пауза — 30 секунд без новых правок; ADR-0013. Открыты частота автосохранения, остальные границы серий, идентификация участника/сессии/команды, техническая фиксация завершения серии после сбоя и обработка ошибок.
5. **Имена, теги и поиск — частично согласовано.** Независимо созданные одноимённые теги объединяются автоматически с сохранением всех назначений и одного из исходных написаний с общим итогом на устройствах; после объединения доступно обычное переименование. Сравнение имён тегов игнорирует регистр/краевые пробелы и различает «е»/«ё»; ADR-0012. Одиночный поисковый запрос совпадает с любой частью слова без учёта регистра; запрос из нескольких слов ищется как один непрерывный фрагмент в указанном порядке. При текстовом поиске «е» и «ё» различаются. Края запроса обрезаются, внутренние пробелы/табуляция/переносы учитываются точно; пустой после обрезки запрос снимает только текстовое условие, возвращая все доступные карточки выбранной области; пунктуация и специальные символы ищутся буквально без поисковых операторов; результаты идут по порядку колонок/карточек доски, при поиске везде сначала пространства со спорными именами в группе «Конфликты названий», затем остальные по именам; найденные карточки со спорным местом карточки/колонки идут в группе «Конфликты» в начале своего пространства; ADR-0011. Для независимого переименования двух существующих тегов в одно имя и переименования существующего против независимого создания нового одноимённого тега согласован явный конфликт с сохранением тегов и назначений и выбором разных имён; ADR-0012. При спорном только имени тега заголовок, текст, статус выполнения и колонка карточки доступны для изменения, спорные теги помечены; их назначение и снятие приостановлены до выбора разных имён. Открыты остальные вопросы Unicode, согласование идентификаторов и алгоритм выбора исходного написания при объединении, остальные коллизии имён, сравнение имён пространств, устойчивый порядок при одинаковых именах и внутри групп, остальные правила совпадения текста, точный набор краевых пробельных символов и размеры полей.
6. **Копии и перенос — частично разобрано.** Ежедневный снимок запускается при первой подходящей возможности при лимите одного успеха за календарный день устройства и после изменений при работающем приложении; ADR-0015. При недоступной выбранной папке повтор ежедневной копии выполняется через 5 минут после неудачной попытки. Доступен явный досрочный повтор «Повторить сейчас» с сохранением условий изменений, дневного лимита и прав через интерфейс/общий API. Остальные согласованные политики сохраняются; открыты технический отсчёт времени и обработка изменения часов/пояса, техническое возобновление ожидания повтора и обработка прочих ошибок копирования, восстановление переноса папки после сбоя, формат архива, перенос на новое устройство, потеря устройства и переустановка APK.
7. **Интерфейс и Markdown — частично согласовано.** Выбраны Reka UI для сложных компонентов, стандартные HTML-элементы для простых кнопок и полей, только необходимые компоненты и собственное оформление ZeDone. Для перетаскивания выбраны SortableJS через VueDraggablePlus. Для Markdown выбран базовый CommonMark без расширений таблиц и текстовых чекбоксов. Пользовательская HTML-разметка показывается как обычный текст. Для HTTP/HTTPS согласовано открытие по нажатию вне ZeDone; удалённые изображения загружаются внутри карточки только по отдельному нажатию. Для просмотра выбраны markdown-it + DOMPurify. Открыты техническая пригодность интеграции компонентов, перетаскивания и Markdown, навигация и критерии доступности клавиатурного и сенсорного управления.
8. **Запуск и распространение — детали не разобраны.** Подтверждённые ручной запуск, браузерный интерфейс, трей и установка сохраняются; открыты средства упаковки, проверка обновлений и детали жизненного цикла.
9. **Производительность и прототипы — требует измерений.** Контрольный набор, бюджеты времени и памяти, критерии пригодности оболочки, инструментов и выбранного Automerge. Стратегия проверки не подтверждает достигнутые показатели.

При необходимости дальнейших вопросов использовать встроенный инструмент, предлагать до четырёх вариантов и отделять предложения от подтверждённых требований. Выбранная основа стека сохраняется; пригодность выбранной Android-оболочки и инструментов, окончательный выбор внутреннего транспорта и алгоритма синхронизации подтверждаются проверками из [оценки стека](stack-candidates.md).

## 13. Соответствие правилам проекта на данном этапе

Дополнительное явное исключение разработчика от 2026-10-27: окончательная локальная очистка рабочих данных и автоматических копий при удалении программы разрешена после предупреждения о возможной потере восстановления и подтверждения состава. Последняя копия не сохраняется принудительно вопреки выбранному охвату. Ручные экспорты и данные других устройств не затрагиваются; остальные правила обратимости сохраняются. [ADR-0021](decisions/0021-uninstall-data-cleanup.md).

Уточнения разделов 1.1 и 1.2 сохраняют согласованные правила обратимости, паритет интерфейса и агентского API, паритет Windows и Android и одно авторитетное локальное состояние. Новая полная копия предназначена для восстановления всей базы; её полномочия и доступ в служебном режиме ещё проектируются и не расширяют права одного пространства или административный доступ молча. Подтверждённые требования и будущие проверки обновлены в документации; проверки реализации ещё не выполнялись.

- Обратимость: подтверждены снятие отметки выполнения, корзина, восстановление с учётом группы удаления и общая история текста карточки без автоматического удаления. Явное исключение разработчика: удалённые теги не попадают в корзину и не имеют отдельного восстановления; повторное создание не возвращает прежние назначения. Полное восстановление пространства возвращает теги и назначения из снимка, даже если их удалили позже. Конфликт удаления тега с его независимым назначением сохраняется. Подтверждены явное разрешение конфликтов удаления карточки или контейнера против правки, синхронизация ручной очистки истории и сохранение независимых новых версий при очистке без связи. Окончательная очистка выполняется только вручную: выбранные объекты либо вся корзина одного пространства. Перед очисткой показывается состав; колонка или пространство очищаются со всеми их вложенными объектами, ещё находящимися в корзине, включая удалённые раньше. Нерешённый конфликт останавливает всю выбранную очистку без частичного удаления; после разрешения очистку запускают заново. Поздняя независимая правка очищенной карточки сохраняется в области «Конфликты» с явным выбором восстановления или подтверждения окончательной очистки. Ротация ежедневных резервных копий не меняет рабочую историю.
- Агентский доступ: подтверждены CLI и HTTP, включая прямое обращение через Tailscale к открытому Android-приложению в пределах выданных прав. Для управления подключёнными устройствами и правами доступа можно отдельно выдать и отозвать административный доступ; обычные права чтения и изменения его не предоставляют. Предложен общий контракт для всех действий. Фактический паритет ещё не проверен.
- Документация: этот документ фиксирует продуктовые и архитектурные договорённости. После согласования поведение пользователя описывается в `docs/user`, агента — в `docs/agent`, разработчика — в `docs/development`; архитектурные решения — в `docs/architecture/decisions`. Неутверждённые предложения не оформляются как принятые ADR.
- Windows и Android: паритет является подтверждённым требованием. Целевые устройства, Google Chrome и Opera на Windows и масштаб в тысячи карточек зафиксированы. Ограничения фоновой работы учитываются; проверки устройства и браузеров ещё впереди.
- Единый источник истины: предложена явная модель локального авторитетного состояния, общего ядра и сходящихся реплик. Нужно согласовать формулировку и модель интеграции выбранного Automerge.
