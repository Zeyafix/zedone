# ADR-0037: постоянная аутентификация и разрешения установки

Дата: 2026-11-05. Техническое решение P03.05.2, проверка —
[EV-055](../../agent/verification/EV-055-persistent-access.md).
Согласованные области ADR-0010/0029 сохраняются; DEC-003 остаётся open.

## Решение

`WriteContext` реализует `AccessTransaction` и `ReplayTransaction`. Оба порта
используют ту же SQLite, соединение и `BEGIN IMMEDIATE`, что данные, история,
сведения обмена и receipts. Аутентификация выполняется после ожидания worker,
до доступа к цели и прежнему результату; другой writer не может изменить права
до завершения операции. Кэш разрешений соединения и локальный обход не вводятся.

Новый субъект — независимый случайный 128-битный ID в hex. Его имя не означает
владение пространствами или администрирование. Субъект сохраняется при смене
прав/ключа и перезапуске; область прежних результатов команды остаётся прежней.
Разные выдачи имеют разных субъектов, чужой receipt не становится доступным.

`AccessKey` содержит случайные 256 бит из системного источника через уже
закреплённый транзитивный `getrandom = 0.4.3`, теперь прямую зависимость storage.
`PendingAccess` готовит субъект и независимый ключ до транзакции. Объекты не
имеют Debug/Serialize/Clone; подготовка сама ничего не разрешает. В SQLite
попадает только SHA-256 с префиксом назначения, не исходный секрет. Это ключ
высокой энтропии, не пароль пользователя; парольный KDF здесь не используется.
Проверяется точная длина предъявленных данных. SQL lookup выполняется по
хешу, а не посимвольным сравнением исходного секрета. Ошибки не содержат ключ,
SQL или путь. Секрет не входит в граф, OpenAPI, запрос/результат команды и логи.

## Начальная выдача и управление

`bootstrap_access` — доверенная однократная подготовка установки после явного
локального подтверждения в будущей точке сборки приложения. Сетевым запросом,
localhost, CLI или произвольной IPC-командой её вызывать нельзя. Ни новая база,
ни миграция автоматически не создают администратора. Bootstrap допускается
только при отсутствии всех субъектов и маркера; оба записываются атомарно.
Исходный администратор получает только управление устройствами/доступами,
без чтения пространств или обслуживания всей базы. Для работы с данными нужны
отдельно выданные права на точные пространства, как у любого другого субъекта.

`issue_access`, `replace_access`, `revoke_access`, `inspect_access` проходят
фиксированное `ManageAccess` через общий core guard до чтения цели. Область —
либо Administration, либо непустая карта точных существующих пространств с
Read/ReadWrite. Неизвестные пространства, пустой набор и повреждённые данные
отклоняются. Начальные значения формы и её подтверждение по ADR-0010 остаются
за UI/API-шагом; инфраструктура получает явно выбранную область.

Смена области/срока и новая выдача после отзыва используют новый ключ при
сохранении субъекта. Все прежние хеши остаются неактивными tombstones:
ни текущий, ни более старый ключ повторно принять нельзя. `issue_access` не
перезаписывает существующего субъекта. Отзыв выключает все его ключи, сохраняет
receipt/субъекта и допускает явную новую выдачу администратором с новым секретом.
Чтение/изменение можно менять в обе стороны. Администрирование можно передать:
сначала явно выдать его другому субъекту, затем отозвать/понизить прежнего.
Последнего активного администратора без срока удалить, ограничить сроком или
понизить нельзя: иначе обратное управление было бы невозможно без обхода прав.
Особого неотзываемого владельца нет; bootstrap не повторяется после передачи.

Срок — необязательная исключительная граница в целых Unix-миллисекундах.
Отрицательное, непредставимое, дробное или уже прошедшее новое значение
отклоняется. `None` означает «До отзыва»; валидность ключа всё равно требует
текущей записи, активного состояния и отсутствия отзыва. Истечение проверяет
core с доверенным Clock, а не время клиента. Политика отката часов/перезапуска
и граница commit длительной операции остаются обязательным P03.05.3.

## Схема и сохранность

Схема v2 состоит из неизменённого `schema/v1.sql` и добавочного
`schema/access-v2.sql`: субъекты, хеши текущих/старых ключей, права пространств,
маркер bootstrap. DDL/FK/STRICT/CHECK дополнены семантическим validator версии:
согласованы область/пространства, активный ключ/отзыв, маркер и сохраняемый
административный путь. Повреждение останавливает startup, не запускает bootstrap.
Реестр вызывает validator как для текущей, так и исторической известной схемы.

Переход v1→v2 создаёт только пустые служебные таблицы. Он проходит P07.08:
новый проверенный полный комплект и снимки пространств, одна транзакция схемы
и свидетельства commit, целевая проверка и публикация до выдачи Storage.
Actor, журналы/история, peers и прежние результаты не переписываются. Новая
установка сразу получает v2, оставаясь без прав до подтверждённого bootstrap.
Бинарный эталон v1 сохраняется. Тестовые схемы 2/3 прежней матрицы — отдельный
синтетический реестр, не продуктовая линейка.

Права и ключи не синхронизируются и не входят в снимок пространства. Его
формат остаётся v1; архивный адаптер журнала тот же. Полная SQLite-копия содержит
локальные права и tombstones. Её откат требует отдельной защиты от оживления
старых полномочий и намерений в P07.09/ADR-0030; восстановление этой работой не
открывается. Ошибки мутации, даже перехваченные callback, запрещают commit
частичных прав или данных. Ответ допускается только после commit транзакции.

При неизвестном исходе сохранять исходный PendingAccess/AccessKey, проверять
субъекта/аутентификацию подготовленным ключом, не генерировать новый при повторе.
Инфраструктурные методы не определяют публичный протокол подтверждения/доставки
секрета и не заменяют командные receipts. Публичные HTTP/CLI/IPC, хранение
секрета клиентом, безопасная доставка и сессии относятся к P03.05.4/P06.

Источники технической проверки: [getrandom fill](https://docs.rs/getrandom/0.4.3/getrandom/fn.fill.html),
[OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
